# 极客数码商城 · 日志规范

> 适用范围：`backend/`（Spring Boot 3.3.5）。前端日志不在本文范围。
> 配套实现：`backend/src/main/resources/logback-spring.xml`、`com.geekmall.common.log.*`、`infra/promtail/promtail-config.yml`
> 配套断言：`StructuredLoggingTest`、`SlowSqlLoggingInterceptorTest`、`RepeatLogThrottlerTest`、`SeckillOrderMessageTest`

---

## 一、为什么要立规范

日志是排障的第一现场，也是最容易被"顺手"写坏的东西。本项目此前的问题不是"没日志"，而是**日志用不起来**：

| 症状 | 根因 |
| --- | --- |
| 排查只能全文搜关键字 | 纯文本日志，没有可检索的字段 |
| 秒杀链路日志断成两截 | MDC 是 ThreadLocal，跨线程池与消息队列不传递 |
| 生产看不到慢 SQL | prod 直接 `NoLoggingImpl`，只有"全开"和"全关"两个极端 |
| 一次故障刷出上万行 | 兜底异常对每个异常都打完整堆栈 |
| 日志里出现手机号 | 没有脱敏约束 |

规范的目的是让日志**可检索、可关联、可承载、不失控**：能按字段过滤，能按 `traceId` 串联，体积不淹没真正有用的信息。

## 二、输出形态：一份日志，两种视图

| 视图 | 去向 | 格式 | 给谁看 |
| --- | --- | --- | --- |
| `CONSOLE` | 标准输出 | 文本 pattern | 人（本地开发、`docker logs`） |
| `JSON_FILE` | `logs/geek-mall.json.log` | 一行一条 JSON | 机器（Promtail → Loki） |

- 滚动策略：单文件 50MB / 保留 15 天 / 总量封顶 2GB
- 日志目录可用环境变量 `LOG_HOME` 覆盖（默认 `logs/`）；环境标识 `APP_ENV`（默认 `dev`）
- **不额外拆「仅 ERROR」文件**：ERROR 行本就在主文件里，Loki 按 `level` 过滤即可；多一个文件会被同一段采集规则重复摄入，付出双份存储却换不到新能力

### 字段字典（Promtail 解析后可直接检索）

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `@timestamp` | 编码器 | `yyyy-MM-dd'T'HH:mm:ss.SSSXXX`，Asia/Shanghai |
| `level` / `logger` / `thread` / `message` | 编码器 | 每条必有 |
| `traceId` | MDC | 链路 ID，跨线程与队列传递，见第五节 |
| `userId` | MDC | 登录用户（数值 id） |
| `orderNo` / `payNo` / `requestId` | MDC | 业务单据，按需写入 |
| `app` / `env` | 静态 | 多环境日志在同一 Loki 中可区分 |

> **缺省即缺省**：MDC 里没有的键在 JSON 中不会出现（不会写空值）。因此"某个字段不存在"本身就是可检索的信号。

## 三、级别语义

| 级别 | 语义 | 典型场景 | 需要人介入 |
| --- | --- | --- | --- |
| `ERROR` | **需要人介入** | 兜底系统异常、落库失败、外部依赖不可用 | ✅ |
| `WARN` | 系统已自行处置，但值得关注 | 限流拒绝、熔断打开、降级回退、慢 SQL、业务失败、重复异常摘要 | ❌（但要能预警） |
| `INFO` | 状态迁移与关键业务结果 | 下单成功、支付回调、任务完成、消费者启停 | ❌ |
| `DEBUG` | 排查细节 | 缓存命中来源、幂等跳过、重试次数 | 仅本地 |

**最容易犯的错**：把异常当作流程控制打 `ERROR`。业务可预期的失败（库存不足、重复领取）应返回业务错误码并打 `WARN`，否则 `ERROR` 失去"需要人介入"的语义，告警也无从下手。

参考实现：`GlobalExceptionHandler` 对 `BizException` / 参数校验 / 限流统一 `WARN` 且不打堆栈，只有兜底分支才 `ERROR`。

## 四、内容规范

### 4.1 用占位符参数，不要手工拼串

```java
// ❌ 拼接后无法结构化提取维度，还容易被人拼接注入
log.warn("[接口限流] 规则 " + rule + " 触发，建议 " + seconds + "s 后重试");

// ✅ 参数化：消息模板稳定，变量由日志框架填充
log.warn("接口限流 rule={} retryAfter={}s", rule, seconds);
```

### 4.2 需要被聚合、过滤的维度，放进 MDC 而不是消息文本

只要一个维度需要"被筛选"（某个用户、某个订单、某条链路），它就该是字段，而不是消息里的字符串。

```java
MDC.put(TraceContext.TRACE_ID, traceId);   // 已在 TraceIdFilter 中自动完成
MDC.put("userId", String.valueOf(userId)); // 登录后写入
MDC.put("orderNo", orderNo);               // 交易入口写入
try {
    ...
} finally {
    // 必须在 finally 中清理：线程池会复用线程，残留上下文会"串"到下一个无关请求
    MDC.remove("orderNo");
}
```

### 4.3 禁止事项

| 禁止 | 原因 |
| --- | --- |
| 在循环 / 批量操作内部逐条打 `INFO` | 1000 条批量 = 1000 行日志，应改为汇总一条 + 计数 |
| 打印完整手机号、地址、证件号、密码、令牌 | 隐私与合规；见第六节 |
| 在 prod 打开全量 SQL 日志 | 噪音淹没一切；用慢 SQL 阈值化通道代替 |
| 用 `ERROR` 记录可预期的业务失败 | 稀释 `ERROR` 的语义，破坏告警基础 |
| 打日志却依赖日志内容做业务判断 | 日志不是数据源 |
| `log.error(e.getMessage())` 丢掉堆栈 | 排查时最需要的是堆栈，且堆栈在 JSON 里已做截断，不必怕长 |

## 五、链路上下文的三个边界

`MDC` 是 `ThreadLocal`，**只覆盖当前线程**。任何一次"换线程"都会断链，必须显式处理：

| 边界 | 机制 | 实现位置 |
| --- | --- | --- |
| HTTP 入口 | 生成/透传 `X-Trace-Id`，写入 MDC 与响应头 | `common/filter/TraceIdFilter` |
| **线程池内** | 提交任务时快照 MDC，执行时恢复，结束后还原 | `common/log/MdcTaskDecorator`（挂在 `AsyncConfig` 的两个线程池上） |
| **消息队列内** | MDC 连进程都跨不过去 → **把 traceId 编进消息体**，消费端恢复 | `SeckillOrderMessage.traceId` + `SeckillOrderConsumer` |

秒杀削峰同时跨越了后两个边界，是三条链路中最容易断的一条：

```java
// 生产端（请求线程）：把当前链路 ID 一起入队
seckillOrderQueue.enqueue(new SeckillOrderMessage(requestId, userId, itemId, addressId,
        TraceContext.currentTraceId()));

// 消费端（消费者线程）：恢复上下文，用完清理
TraceContext.bindTraceId(message.traceId());
try {
    doHandle(...);
} finally {
    TraceContext.clearTraceId();
}
```

> 新增异步路径时的自检：**这个 Runnable / 这条消息，是否还带着 traceId？**

## 六、脱敏

两道防线，各自负责一类：

| 防线 | 机制 | 覆盖 |
| --- | --- | --- |
| 字段级 | `MaskingJsonGeneratorDecorator` 的 `<path>` | `password` / `phone` / `mobile` / `idCard` / `token` 字段整体打码 |
| 值级 | `<value>` 正则（带边界环视） | 自由文本里的手机号 `1[3-9]\d{9}`、身份证 `\d{17}[\dXx]` |

边界环视是必需的：`(?<!\d)1[3-9]\d{9}(?!\d)` 里的前后环视确保 13 位毫秒时间戳内部的 11 位数字不会被误判为手机号。

**已知取舍**：值级脱敏对**所有字段**生效。若把手机号直接当 `userId` 写进 MDC，它同样会被打码——这是隐私优先的有意设计。用户级排查请用数据库 id 或订单号关联。

**脱敏兜不住的部分**：地址、姓名等自由文本没有固定格式，只能靠代码评审纪律——**不要往日志里打完整个人信息**。

## 七、噪音治理

| 手段 | 配置 | 说明 |
| --- | --- | --- |
| 慢 SQL 阈值化 | `mall.logging.slow-sql-threshold-ms: 200` | 平时静默；超阈值打 `WARN`（压成单行、截断 500 字）并计入 `mall_slow_sql_total` |
| 重复异常节流 | `mall.logging.repeat-log-window-seconds: 60`<br>`mall.logging.repeat-log-max-keys: 10000` | 同一「异常类型 + 崩溃点」窗口内只打一次完整堆栈，其余只记一行摘要 + 累计次数 |
| 堆栈截断 | `ShortenedThrowableConverter` | 每个异常最多 20 层、总长 4096 字符，`rootCauseFirst` |
| 采集侧指标 | Promtail `metrics` stage | 直接从日志行产出 `error_log_lines_total` / `warn_log_lines_total`，无需改代码 |

**慢 SQL 刻意不打印绑定参数**：参数里可能有手机号、地址，且会让日志体积失控。需要看具体参数时，用同一条 `traceId` 回到该请求的其它日志与业务上下文。

## 八、检索手册（Grafana / Loki LogQL）

```logql
# 按链路查：拿到用户提供的 X-Trace-Id 后，一条命令串出整条调用链（含秒杀异步段）
{job="geek-mall-server"} | traceId="a1b2c3d4e5f6"

# 只看错误
{job="geek-mall-server", level="ERROR"}

# 定位某个类
{job="geek-mall-server", logger="com.geekmall.modules.trade.service.impl.TradeServiceImpl"}

# 按用户排查
{job="geek-mall-server"} | userId="8"

# 慢 SQL 排行（配合 mall_slow_sql_total 指标看趋势）
{job="geek-mall-server"} |~ "慢 SQL"
```

> `traceId` / `userId` 是 **structured metadata**，不做 label——高基数字段一旦成为 label，Loki 的 stream 数量会随请求量线性膨胀。只有 `level` / `logger` / `env` 这类低基数字段才允许成为 label。

## 九、如何验证（规范靠断言守住，不靠自觉）

| 断言 | 测试类 | 守住什么 |
| --- | --- | --- |
| JSON 可解析、字段齐全 | `StructuredLoggingTest` | 格式改坏立刻红灯 |
| 异常日志是单行 JSON | `StructuredLoggingTest` | 堆栈不会把一条日志拆成多条 |
| 无上下文时不写空字段 | `StructuredLoggingTest` | 空值不污染检索 |
| 手机号被打码、长数字串不被误伤 | `StructuredLoggingTest` | 脱敏既生效又不误伤 |
| 阈值判定 / 单行化 / 截断 / 计数 | `SlowSqlLoggingInterceptorTest` | 慢 SQL 通道可用 |
| 首次放行、重复收敛、窗口过期放行 | `RepeatLogThrottlerTest` | 节流不会把错误彻底吃掉 |
| 消息带 traceId 且兼容老消息 | `SeckillOrderMessageTest` | 链路字段不破坏队列契约 |

- [ ] 需要筛选的维度进 MDC 了吗？在 `finally` 里清理了吗？
- [ ] 换线程 / 进队列的地方，`traceId` 还在吗？
- [ ] 消息里有没有完整的手机号、地址、证件号？

- [ ] 参数用占位符了吗？
