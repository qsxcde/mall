# 库存分桶设计与交互边界

> 代码位置：`backend/src/main/java/com/geekmall/modules/inventory/`
> 迁移脚本：`backend/src/main/resources/db/migration/V11__inventory_bucketing.sql`
> 设计依据：`loadtest/results/跨机压测第二轮-MQ对比.md` 附录 C/D（"把 1 行热点变成 N 行热点"）

---

## 一、定位与核心不变量

库存分桶把「一份商品库存」按业务维度拆成多个**独立的桶行**，让出库扣减可以分散到不同行上并行推进，
而不是所有请求争抢同一行 InnoDB 行锁。它解决的是**并发度**问题，不创造库存、也不负责防超卖。

**三条不变量（应用层强约束）：**

1. **守恒**：`SUM(inv_bucket.stock) == pms_product.stock`，永久成立；
2. **单一维度**：同一商品同一时刻只使用一种分桶维度，避免多维度叠加导致对账歧义；
3. **留痕**：任何桶余量变化都写 `inv_bucket_log`，出库 / 回滚两侧共用 `order_no` 幂等。

---

## 二、分桶粒度

| 层级 | 取值 | 说明 |
| --- | --- | --- |
| **桶粒度** | 一个桶 = `(商品 × 维度值)` | 唯一键 `uk_bucket(product_id, dimension, dimension_value)` |
| **规则粒度（granularity）** | `SKU` / `SKU_BATCH` | `SKU`：商品级拆分；`SKU_BATCH`：商品 + 批次进一步细分 |
| **维度（dimension）** | `WAREHOUSE` 仓库 / `BATCH` 批次 / `EXPIRY` 效期 / `REGION` 地区 | 决定 `dimension_value` 的语义 |
| **扣减粒度** | 一次出库 = 在**若干桶上各做一次 CAS** + 商品总库存一次 CAS | 允许跨桶凑足数量，但不拆单到"每桶各扣一点"以外的语义 |

**桶数量估算**（沿用文档 `桶数 ≈ 峰值 TPS ÷ 单行可承受 TPS` 的思路，但按业务维度取整）：

- 维度值天然给出桶数（例如 5 个仓库 = 5 桶）；
- 桶太多会抬高 `SUM` 对账、展示与回补成本，桶太少则并行度不足；
- **桶数必须与消费者线程数、Hikari 连接池一起配比**，三者取最小值才是有效并行度。

## 三、更新频率

| 操作 | 频率 | 是否改商品总库存 | 说明 |
| --- | --- | --- | --- |
| `allocate` / `autoSplit`（分配、重布局） | **低频**，运营/盘点时 | ❌ 否 | 只把现有库存拆到桶上；`allocate` 为**声明式重布局**：先清零旧桶再写入明细，差额落入「未分配」桶 |
| `transfer` / `merge`（调拨、合并） | **低频**，仓间调拨/合批时 | ❌ 否 | 仅在桶之间搬动，守恒天然保持 |
| `deduct`（出库） | **高频**，每笔成交一次 | ✅ 是 | 桶 CAS 扣减 + 商品总库存 CAS 扣减，同事务 |
| `rollback`（回滚） | 低频，取消/超时 | ✅ 是 | 把数量还回**原来那一桶** |
| `report` / `page` / `logs`（查询） | 高频读 | — | 只读，`report` 实时计算守恒差额 |

**桶余量是实时值**，不做定时批量刷新；`last_sync_time` 记录最近一次变更时刻。
唯一适合定时任务的是**对账巡检**：已实现为 `InventoryBucketReconcileJob`
（`@Scheduled` + `@SchedulerLock`，默认初始延迟 60s、每 10 分钟一次），
扫描「桶合计 ≠ 商品总库存」的商品并告警；正常情况下永远无输出。

## 四、与其他库存模块的交互边界

```
┌──────────────────────── 交易域（trade） ────────────────────────┐
│  TradeServiceImpl：下单 / 取消 / 超时关单                          │
│    ├─ 未分桶商品：走 ProductMapper.deductStock / restoreStock（既有路径，零改动）
│    └─ 已分桶商品：调用 InventoryBucketService.deduct / rollback（新增路径）
└───────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────── 库存分桶域（inventory） ─────────────────┐
│  inv_bucket（桶明细，CAS 扣减的并发单元）                          │
│  inv_bucket_rule（分桶规则）  inv_bucket_log（审计流水）           │
│  inv_bucket_operation（调拨/合并单）                              │
└───────────────────────────────────────────────────────────────┘
                                  │ 同步扣减（同事务）
                                  ▼
┌──────────────────── 商品域（product） ──────────────────────────┐
│  pms_product.stock —— 权威总量；sales —— 销量                    │
└───────────────────────────────────────────────────────────────┘
```

**明确划定的四条边界：**

1. **`pms_product.stock` 仍是权威总量**：分桶不是"又一份库存"，而是它的**维度明细视图**。
   任何桶的增减都必须与它联动，禁止单独改一边。
2. **未分桶商品完全不受影响**：`deduct` 检测到商品没有任何桶时，退化为「仅商品级扣减」，
   与旧链路行为一致；因此分桶可以**按商品灰度**上线。
3. **秒杀库存（`mkt_seckill_item.stock`）不纳入本次分桶**：它是独立活动库存池，
   与商品总库存分开计价。若将来需要，应作为独立维度接入，而不是混进 `inv_bucket`。
4. **调拨 / 合并 / 分配不改商品总库存**：它们只改变"库存放在哪个桶"，
   所以不需要、也不应该调用 `ProductMapper`。

**调用方式（交易域已接入）：**

`TradeServiceImpl` 通过两个私有方法按「商品是否分桶」自动路由，业务代码无感知：

```java
// 下单扣库存：已分桶 -> 桶级 CAS；未分桶 -> pms_product 单行扣减
private void deductProductStock(Long productId, int qty, String title, String orderNo) {
    if (inventoryBucketService.isBucketed(productId)) {
        inventoryBucketService.deduct(dto);   // orderNo 幂等
        return;
    }
    // 旧路径 ...
}

// 取消 / 超时回退：按「该单该商品是否走过桶级出库」决定回补路径
private void restoreStock(String orderNo) {
    if (inventoryBucketService.hasOutbound(orderNo, item.getProductId())) {
        inventoryBucketService.rollbackProduct(orderNo, item.getProductId()); // 还回原桶
        continue;
    }
    // 旧路径：inventory_rollback_log 幂等 + 单行回加
}
```

> 接入点共 3 处：普通下单 `doSubmit`、特殊通道 `createOrderWithFixedPrice`、回退 `restoreStock`。
> `doSubmit` 还会先按商品合并结算项数量，避免同一商品出现多个结算项时误命中幂等。

## 五、并发控制与一致性

| 机制 | 做法 |
| --- | --- |
| **桶扣减** | `UPDATE inv_bucket SET stock = stock - #{qty} WHERE id = ? AND stock >= #{qty} AND deleted = 0`（CAS） |
| **挑桶顺序** | `FIFO`（入桶时间）/ `EXPIRY_FIRST`（效期最近优先，无效期最后）/ `MANUAL`（`priority` 升序） |
| **挑桶时机** | 出库前选出候选桶一次性排序；**桶空了才换下一桶**；桶被锁只会阻塞/重试，不跳行 |
| **CAS 冲突** | 最多重试 `MAX_DEDUCT_ROUNDS = 5` 轮，每轮重新选桶 |
| **跨桶凑数** | 单次出库允许命中多个桶；同一桶多轮命中时**合并记账**，保证 `(biz_type, biz_id, bucket_id)` 唯一 |
| **超卖防护** | 桶 CAS + 商品 CAS 双重；任一步失败整事务回滚 |
| **幂等** | 出库 / 回滚以 `order_no` 为幂等键，先查 `inv_bucket_log` 再执行 |
| **对账** | `report.delta = pms_product.stock − SUM(inv_bucket.stock)`，正常为 0 |

> 与文档结论一致：**分桶不消除锁，只把锁分摊到 N 行**。
> 因此 `deduct` 会同时扣商品总库存（共享行仍然串行），但单热点 SKU 的**有效并行度从 1 提升到 min(桶数, 线程数, 连接池)**。

## 六、假售罄与守恒的处理

- **不会选到空桶**：候选集只取 `stock > 0 AND status = 1` 的桶，不存在"撞空桶再换行"。
- **出库不足即整体回滚**：凑不齐数量直接抛 `OUT_OF_STOCK`，已扣的桶随事务回滚，不会出现半成品。
- **分配自动补「未分配」桶**：显式明细之和不等于商品总库存时，差额落入「未分配」桶，杜绝库存凭空消失。
- **重布局留痕**：`allocate` 清零旧桶时逐桶写 `ADJUST` 流水，历史可追溯。

## 九、上线与灰度建议

1. **优先吃"天然桶"**：多 SKU 场景下每个商品本来就是一行，先确认多 SKU 并行度是否兑现，再考虑单商品人为分桶；
2. **按商品灰度**：先对单热点大库存商品启用分桶，其余商品保持旧链路（`deduct` 已内置降级）；
3. **配比校验**：桶数 ≥ 目标并行度、消费者线程数 ≥ 目标并行度、连接池 ≥ 目标并行度，且 `实例数 × 池 ≤ max_connections`；
4. **对账巡检**：`InventoryBucketReconcileJob` 定时扫描 `delta != 0` 的商品并告警，作为兜底。
