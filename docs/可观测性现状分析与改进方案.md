## 一、结论摘要（TL;DR）

| 维度 | 评级 | 一句话结论 |
| --- | --- | --- |
| 工具链完整度 | ★★★★☆ | Prometheus + Grafana + Loki + Promtail + Actuator 全部编排就绪，只差 Grafana 的数据源与看板 provisioning |
| 日志 | ★★★★☆ | 采集链路通、滚动策略合理，**✅ 已落地结构化 JSON**，可按 level/logger/traceId 字段过滤与聚合（见 `docs/日志规范.md`） |
| 指标 | ★★★☆☆ | 骨架完整，**12 个自定义指标集中在"缓存 + 熔断"**；限流、秒杀队列、业务漏斗等核心链路零指标 |
| 追踪 | ★★★☆☆ | 自研 `traceId` 贯通 HTTP 主链路，并 **✅ 已跨线程池 + 跨 Redis Stream 队列**（消息体携带、消费端恢复），无 span、无跨服务能力 |
| 告警 | ☆☆☆☆☆ | **完全缺失**：无规则文件、无 Alertmanager、无通知渠道 |
| 可视化 | ☆☆☆☆☆ | **完全缺失**：无 dashboard JSON、无 provisioning，需手工建数据源与面板 |
| 故障定位效率 | ★★☆☆☆ | 单点问题（缓存/熔断）可查；**跨模块耗时不可分解**，P99 异常只能靠猜 |

**四个核心判断：**

1. **投入与产出最不成比例的一环是"看板"**。指标已经埋在代码里（`mall_cache_*`、`mall_circuit_*`），Prometheus 已在抓取，但没有任何地方能看见它们——这是**只差最后 1% 的工作量**。
2. **观测能力与业务价值错配**。项目最核心的高并发治理能力是「**全站 118 端点限流**」和「**秒杀削峰队列**」，而这两者**恰好一个指标都没有**；反过来，缓存三防的埋点却非常完整（连 `local`/`redis` 层级都区分了 tag）。
3. **✅ `traceId` 已跨越异步边界**：`MdcTaskDecorator` 挂两个线程池，traceId 随 `SeckillOrderMessage` 入队、消费端恢复。原「异步 / 消费者处断裂」为改造前状态。
4. **缺少"运行版本可考"这一元数据底座**。`docs/高并发处理现状报告.md` 已实测出「运行中的二进制与磁盘产物脱钩、无法证明运行版本==仓库代码」的严重问题，本质是**环境/版本元数据没有进入观测数据**。

## 三、问题诊断

### 3.1 观测盲区（按业务价值排序）

**B1 · 核心治理能力「限流」零指标** —— 最高优先级
- 证据：`common/ratelimit/RateLimitInterceptor.java`、`LocalRateLimiter.java`、`DistributedRateLimiter.java` **均不持有 `MeterRegistry`**，触发限流只有日志
- 项目自己在 `docs/接口限流策略说明.md:290` 承认：「**未接入指标上报**：当前只有日志。可补 Micrometer 计数器（按规则名打点），把 429 数量纳入 Prometheus 面板。」
- 影响：无法回答「限流阈值定得对不对」「是否在误杀正常用户」「多实例下 `LOCAL` 阈值被放大成 N 倍后实际放行量」，而这些恰是限流策略最该被验证的问题（`docs/接口限流策略说明.md:288` 明确记录了该放大效应）

**B2 · 秒杀削峰队列无 lag 指标** —— 最高优先级
- `SeckillOrderConsumer.java` 内的 `AtomicInteger` 只是线程计数，**不是 Micrometer 指标**
- 无队列深度、无 pending 数、无消费滞后（lag）、无消费速率、无死信/回收次数指标
- 影响：削峰系统「把脉冲摊平到什么程度、积压多久能消化完」**完全不可测**；压测时只能靠 `loadtest/results/` 事后统计，线上无法实时判断是否需要扩容消费者

**B3 · 业务漏斗指标全部缺失**
- `docs/后端脚手架搭建方案.md:595-602` 已设计好 5 个业务指标（`mall_order_create_total{status}`、`mall_order_pay_success_rate`、`mall_seckill_deduct_fail_total`、`mall_coupon_claim_total`、`mall_order_timeout_cancel_total`）—— **一个都没落地**
- 影响：技术指标（QPS/P99）不能说明业务是否健康；「下单成功率掉了」「超时取消量骤增」这类信号只能靠翻日志

**B4 · traceId 不跨异步/消费者线程** —— ✅ 已落地（2026-10-07）
- `AsyncConfig` 无 `TaskDecorator`；`SeckillOrderConsumer` 自建线程池
- 影响：**在唯一需要它的地方失效** —— 秒杀链路「请求入队 → 后台落库」被切成两段互不关联的日志，用户报障时无法串联
- **修复**：`MdcTaskDecorator` 挂在两个线程池上；`traceId` 随 `SeckillOrderMessage` 入队、消费端恢复后清理。详见 §9

**B5 · 无慢 SQL 采集** —— ✅ 已落地（2026-10-07）
- `application-prod.yml:43` 直接 `NoLoggingImpl`（因为 MyBatis 全量 SQL 日志本身就是噪音）
- `docs/高并发功能模块全景分析.md:337`、`docs/高并发处理现状报告.md:343` 均已列为已知问题
- 影响：性能退化（索引失效、N+1）**无任何观测入口**，只能等 P99 报警（而现在连报警都没有）
- **修复**：`SlowSqlLoggingInterceptor` 补上「全开 / 全关」之间缺失的中间态——超阈值才打 WARN 并计入 `mall_slow_sql_total`；**刻意不打印绑定参数**（脱敏 + 体积）；需要看参数时用同一 `traceId` 回到该请求的其它日志

**B6 · 无业务级 HealthIndicator**
- `/actuator/health` 只反映 MySQL/Redis/磁盘连通性，**Redis 连通但缓存层已熔断**这种状态对外表现为「健康」

**B7 · 前端与客户端无观测**
- 两个 Vue 应用无错误上报、无性能上报、无 `X-Trace-Id` 透传
- 影响：「用户说点不动」这类问题无法定位到底是前端报错、网络问题还是后端慢

**B8 · 定时任务存活无观测**
- 订单超时关闭依赖轮询扫描（`README 3.3` 已提及），无执行次数/耗时/last-success 指标
- 影响：任务静默死亡（如 ShedLock 锁未释放、线程池被占满）时**没有任何信号**

### 3.2 告警噪音风险

现状是「**零告警**」，但要讨论噪音——因为**一旦把现有指标原样接上告警，会立刻产生噪音**：

| 风险 | 说明 |
| --- | --- |
| 无分级 | `mall_cache_redis_error_total`、`mall_circuit_opened_total`、`mall_resilience_slow_total` 在压测/大促期间必然触发，与「服务不可用」同级别推送会造成告警疲劳 |
| 无抑制关系 | 熔断打开（P0）必然伴随缓存错误与降级激增（P2）—— 若无 inhibition，一次 Redis 抖动会炸出几十条告警 |
| 缺 for 时长 | 压测场景短时尖峰多，无 `for` 窗口会导致告警抖动 |
| 日志侧噪音源 | ~~`GlobalExceptionHandler.java:106-110` 对**每个**非预期异常打完整堆栈~~ → **✅ 已落地**：`RepeatLogThrottler` 按「异常类型 + 崩溃点」节流（窗口 60s 内只打一次完整堆栈），配合 `ShortenedThrowableConverter` 截断；Promtail 也改为 JSON 字段化采集。**剩余风险**：dev 下 `com.geekmall: DEBUG` 未收敛（`docs/高并发功能模块全景分析.md:338`） |
| 告警未绑定动作 | 无 runbook、无看板链接 → 收到告警的人不知道该做什么，最终演变成全员忽略 |

### 3.3 数据孤岛

| 孤岛 | 证据与影响 |
| --- | --- |
| **指标 ↔ 日志只能"时间对齐"**（部分改善） | 指标 tag 只有 `application`（+ 默认 `uri/method/status`），**无 traceId**；**✅ 已落地**：日志侧把 `traceId`/`userId` 提为 structured metadata 并补了 `app`/`env`，**日志内部**已可按链路精确检索。但**指标 → 日志**的下钻仍需 exemplar，未落地 |
| **traceId 未字段化**（已修复） | ~~`promtail-config.yml` 只有 `job`/`application`，查 traceId 只能全文 `|=` 检索~~ → **✅ 已落地**：`json` stage 解析 + `labels`（`level`/`logger`/`env`）+ `structured_metadata`（`traceId`/`userId`），可按字段精确过滤 |
| **Grafana 数据源未 provisioning** | 每人手工接入 → 查询口径、别名、单位各不相同，看板无法共享 |
| **观测数据缺环境/版本维度** | 指标与日志都没有 `env` / `version` / `commit` 标签。`docs/高并发处理现状报告.md:352-354` 实测出「无法证明运行版本 == 仓库代码」——这正是元数据缺失的直接后果 |
| **前端与后端之间无关联键** | 前端不发 `X-Trace-Id`，端到端链路天生断裂 |
| **压测产物与线上观测割裂** | `loadtest/results/` 是静态 markdown/csv，与 Grafana 无关联，压测时的看板快照没有归档机制 |

### 3.4 故障定位效率

现有三个「活体证据」，恰好说明三类效率损失：

| 案例 | 现象 | 暴露的缺陷 |
| --- | --- | --- |
| `README.md:199` 压测大面积失败 | 疑似「已抢光」，实际是**压测账号 JWT 过期导致 401 被计入"业务拒绝"** | **口径不清**：技术失败与业务拒绝混在一个统计口径里，缺乏区分指标 |
| `docs/高并发处理现状报告.md:352-354` | 运行实例持有一个**已从磁盘删除的 jar** 的文件句柄 → 无法回滚、无法证明运行版本 | **元数据缺失**：无 build/version/commit 观测 |
| 缓存击穿验证（`docs/练手项目聚焦范围与框架就绪度报告.md:106,146`） | 8 线程并发冷启动重建「恰好回源 1 次」是**读 `mall_cache_rebuild_total` 指标差值断言的** | **正面案例**：证明指标化验证的价值 —— 但只覆盖了缓存一个域 |

**综合定位效率评估（↑ 标注本次日志改造带来的变化）：**

| 问题类型 | 改造前 | 改造后 | 依据 |
| --- | --- | --- | --- |
| 单域问题（缓存 / 熔断） | 可定位 | 可定位（未变） | 有指标 + 有日志 |
| **单请求全链路（后端内）** | 仅主链路，异步段断链 | **↑ 可定位** | 三条边界贯通，任一 5xx 可按 `traceId` 串出「入参 → 缓存 → DB → 异步落库」 |
| **性能退化（索引失效 / N+1）** | **无任何入口** | **↑ 有入口** | 慢 SQL 阈值化 + `mall_slow_sql_total` |
| 跨模块耗时分解 | **不可定位** | **仍不可定位**（未变） | 无 span，耗时落在 Controller / Service / Redis / MySQL / MinIO 哪一段仍只能推断 |
| 端到端（用户报障） | 不可定位 | **仍不可定位**（未变） | 前端不发 `X-Trace-Id`，用户侧链路起点缺失 |
| 容量（线程池 / 连接池水位） | 部分可定位 | **仍部分可定位**（未变） | HikariCP / Tomcat / JVM 有默认指标，但线程池队列深度仍无指标（`docs/高并发处理现状报告.md:370`） |

## 四、改进方向

### 方向一 · 统一数据采集标准

**目标：让四类数据（日志/指标/追踪/告警）共享同一套元数据与字段口径。**

**1. 元数据三件套贯穿所有观测数据**

| 维度 | 来源 | 注入方式 |
| --- | --- | --- |
| `env`（dev/test/prod） | `spring.profiles.active` | Micrometer 公共 tag + logback pattern |
| `version`（如 `1.0.0`） | `build-info`（`spring-boot-maven-plugin` + `git-commit-id-plugin`） | 同上，暴露到 `/actuator/info` |
| `instance`（主机名/Pod） | `HOSTNAME` | Micrometer 公共 tag |

→ 直接解决「运行版本不可考」问题，并让所有指标/日志可切片。

**2. 日志：结构化 + 字段规范** —— ✅ **已落地（2026-10-07）**

- 引入 `logstash-logback-encoder`，输出 JSON（保留 CONSOLE 为可读文本，FILE 为 JSON）
- **已实现字段**：`@timestamp`、`level`、`logger`、`thread`、`message`、`traceId`、`userId`、`app`、`env`
- **仍待补字段**：`uri`、`method`、`status`、`latencyMs`、`bizCode`、`module`、`orderNo`
  （`spanId` 属 Phase 3 追踪能力；其余建议在后续收敛「关键路径日志埋点」时随代码统一补齐）
- 敏感字段脱敏：字段级 + 值级（手机号、证件号，带边界环视防误伤）；地址/姓名等自由文本仍靠代码评审纪律
- 分级日志规范：`ERROR` = 需人工介入；`WARN` = 降级/熔断/限流/重试；`INFO` = 状态迁移；`DEBUG` = 仅本地
  （已写入 `docs/日志规范.md`，并由断言守住）
- prod 慢 SQL 阈值化（默认 > 200ms 才打），替代全量 SQL 日志

**3. 指标：命名规范 + 五类补齐**

命名规范：`mall_{domain}_{object}_{action}_{unit}`，如 `mall_ratelimit_rejected_total`

| 类别 | 指标（草案） | Tag |
| --- | --- | --- |
| 限流 | `mall_ratelimit_rejected_total`、`mall_ratelimit_passed_total`、`mall_ratelimit_degraded_total`（FAIL_OPEN 放行）、`mall_ratelimit_error_total` | `rule`,`layer`(LOCAL/DISTRIBUTED),`dimension`(IP/USER) |
| 秒杀队列 | `mall_seckill_queue_depth`、`mall_seckill_queue_lag_seconds`、`mall_seckill_consume_total`、`mall_seckill_reclaim_total`、`mall_seckill_accept_total`、`mall_seckill_deduct_fail_total` | `topic`/`stage` |
| 业务漏斗 | `mall_order_create_total`、`mall_order_pay_success_total`、`mall_order_timeout_cancel_total`、`mall_coupon_claim_total`、`mall_review_create_total` | `status`/`result` |
| 下游依赖 | `mall_downstream_call_seconds`(Timer)、`mall_minio_upload_total`、`mall_redis_op_seconds`、**✅ `mall_slow_sql_total`（已落地）** | `dependency`,`result` |
| 容量 | `mall_executor_queue_size`、`mall_executor_active_threads`、`mall_shedlock_last_success_timestamp` | `executor`/`job` |
| 元数据 | `mall_build_info`（Gauge=1，带 version/commit） | `version`,`commit` |

> 基数控制红线：**禁止**把 `userId`、`orderNo`、`traceId` 作为指标 tag（高基数会打爆 Prometheus）——这类上下文用**日志 + exemplar** 承载。

**4. 追踪：先"不断链"，再"上标准"**

- **✅ 已落地**：`TaskDecorator` 复制 MDC 到两个线程池（`MdcTaskDecorator`）；秒杀消费者的 traceId 随消息体入队、消费端恢复（MDC 跨不过队列，这是唯一可行方式）
- **⏳ 未落地**：前端 axios 生成并透传 `X-Trace-Id`（本地保存用于用户报障时提供）
- Phase 3（触发条件：拆服务或引入 MQ）：接入 Micrometer Tracing + OTel，`L2→L3` 平滑演进（与 `docs/后端脚手架搭建方案.md:611-614` 的判断一致：单体阶段过早引入追踪收益低）

### 方向二 · 增强上下文关联能力

| 手段 | 做法 | 收益 |
| --- | --- | --- |
| **日志 label 化** —— ✅ **已落地** | Promtail 加 `pipeline_stages`：`json` 解析 + 抽取 `level`/`logger`/`env` 为 **label**（低基数）；`traceId`/`userId` 走 **structured metadata**（Loki 3.x 支持，`allow_structured_metadata: true` 已开） | 从 `|= "traceId"` 全文检索升级为按字段精确过滤 |
| **userId 进 MDC** —— ⏳ 未落地 | 登录后 `MDC.put("userId", ...)`，Filter 统一清理 | 支持「按用户排查」——客服/用户报障的关键入口。**注意**：手机号形态的值会被值级脱敏打码，`userId` 应使用数值 id |
| **业务单据进上下文** —— ⏳ 未落地 | `orderNo`/`payNo`/`seckillRequestId` 进 MDC 与日志字段 | 交易纠纷可精确回溯 |
| **指标 → 日志下钻** | 用 Micrometer **exemplar**（需切换为可提供 exemplar 的 histogram 配置）把 traceId 带进指标；或 Grafana 面板用变量 + Loki 查询做"跳到日志"链接 | 从「P99 尖刺」一键跳到「那个慢请求的日志」 |
| **frontend → backend 串联** | 前端 axios 拦截器生成 `X-Trace-Id`；错误上报带上它 | 端到端（用户 → 前端 → 后端 → DB）单链路可视 |
| **统一 Grafana provisioning** | `infra/grafana/provisioning/{datasources,dashboards}` + dashboard JSON 入仓 | 消除「每人一套查询」的数据孤岛 |

### 方向三 · 优化告警策略

**三层分级（避免一刀切）：**

| 层 | 关注 | 示例 | 通知方式 |
| --- | --- | --- | --- |
| **L-A 可用性/SLO（P0）** | 用户在受影响 | 5xx 率 > 5%、下单成功率为 0、HikariCP pending > 0、健康检查失败 | 即时通讯 + 电话，5min 内响应 |
| **L-B 容量与资源（P1）** | 即将受影响 | P99 > 2s、JVM 堆 > 85%、秒杀队列 lag > 阈值、熔断打开、慢 SQL 激增 | 即时通讯，工作时段处理 |
| **L-C 业务与治理（P2）** | 指标偏离基线 | 限流拒绝率显著偏离基线、缓存命中率下降、超时取消量骤增 | 日报汇总 + 看板 |

**告警规则草案（Prometheus 表达式 + `for` + 降噪设计）：**

| # | 规则 | 表达式（示意） | for | 级别 | 降噪要点 |
| --- | --- | --- | --- | --- | --- |
| 1 | 5xx 错误率过高 | `sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum(rate(http_server_requests_seconds_count[5m])) > 0.05` | 5m | P0 | 按 `uri` 聚合，避免单端点噪声 |
| 2 | 下单接口 P99 恶化 | `histogram_quantile(0.99, sum(rate(http_server_requests_seconds_bucket{uri=~".*trade/orders.*"}[5m])) by (le)) > 2` | 5m | P1 | 仅对写关键路径 |
| 3 | 下单成功率为 0 | `increase(mall_order_create_total{status="success"}[10m]) == 0` | 10m | P0 | 低峰期用基线而非绝对 0 |
| 4 | 熔断器打开 | `increase(mall_circuit_opened_total[5m]) > 0` | 0m | P1 | 抑制规则：抑制 #5/#6/#8 |
| 5 | 缓存 Redis 错误 | `rate(mall_cache_redis_error_total[5m]) > 1` | 5m | P2 | 被 #4 抑制 |
| 6 | 缓存回源异常激增 | `rate(mall_cache_rebuild_total[5m]) > 基线×3` | 10m | P2 | 用**偏离基线**而非绝对阈值 |
| 7 | 秒杀队列积压 | `mall_seckill_queue_lag_seconds > 30` | 3m | P1 | 仅在活动窗口启用（可用 label 过滤） |
| 8 | 限流拒绝率异常 | `rate(mall_ratelimit_rejected_total[5m]) / rate(http_server_requests_seconds_count[5m]) > 0.3` | 10m | P2 | **必须用比率 + 基线**，绝对条数在大促下必然刷屏 |
| 9 | JVM 堆/GC | `jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.85` | 10m | P1 | 与 Full GC 频次联合判定 |
| 10 | 定时任务死亡率 | `time() - mall_shedlock_last_success_timestamp > 2×周期` | 5m | P1 | 需先补指标 |
| 11 | 连接池等待 | `hikaricp_connections_pending > 0` | 2m | P0 | 直接反映"用户已在等待" |
| 12 | 消费者滞后 | `mall_seckill_consume_total` 速率 → 0 而 `accept_total` 速率 > 0 | 5m | P0 | 消费停摆是高危 |

**降噪机制（比规则本身更重要）：**
1. `group_by: [alertname, uri/rule]` + `group_interval` 聚合，同一根因只推一次
2. **inhibition 抑制链**：P0 触发 → 抑制同域 P2（如熔断 P1 抑制缓存错误 P2）
3. **静默窗口**：压测/发布期间写入 `mute_time_intervals`
4. **基线偏离优先**：能用「同比/环比偏离」的，不用绝对阈值
5. **告警必须绑定动作**：每条规则带 `runbook_url` + 对应 Grafana 面板链接
6. **季度清理**：连续 N 次无人处理的告警 → 删除或重新定阈值（这是防噪音的根本）

### 方向四 · 完善仪表盘设计

**落地方式：Grafana provisioning（数据源 + 看板 JSON 入仓），`docker compose up` 即得成品看板。**

**五层看板结构：**

| 层 | 看板 | 核心内容 |
| --- | --- | --- |
| **L0 业务总览（金指标）** | `GeekMall · Overview` | 请求量、错误率、P50/P95/P99、饱和度（线程池/连接池/CPU）+ **SLO 燃烧率**（当前 vs 预算） |
| **L1 应用运行时** | `GeekMall · JVM & Runtime` | JVM 内存/GC、Tomcat 线程、HikariCP（active/pending/timeout）、Lettuce 连接、日志级别分布 |
| **L2 业务链路** | `GeekMall · Business` | 下单漏斗（创建→支付→完成）、支付成功率、秒杀（受理/入队/消费/lag/成功率）、优惠券领取、超时取消 |

**每个面板的设计纪律：**
- 左上角固定时间范围与 `env` 变量
- 每张图带单位、带对比（上一周期虚线）
- 关键面板挂 `runbook` 链接
- **告警面板必须能在 3 次点击内到达对应日志**（指标 → 日志下钻）

### 阶段总览

## 七、风险与取舍

| 风险 | 说明 | 缓解措施 |
| --- | --- | --- |
| **指标基数膨胀** | 若把 `userId`/`orderNo`/`traceId` 作为 tag，Prometheus 内存与查询成本会失控 | 立**基数红线**：这些上下文只走日志与 exemplar；指标 tag 限于枚举型低基数字段 |
| **观测成本上升** | Loki 写入放大、Prometheus 存储增长 | JSON 日志相比纯文本体积略增，用**日志降噪 + 保留期策略（当前 168h）**对冲；大促期可临时提高采样 |
| **隐私合规** | 日志含手机号、地址、订单信息 | 结构化日志阶段即引入**脱敏 converter**，敏感字段只保留掩码 |
| **过度设计** | 单体阶段上全链路追踪（SkyWalking/ELK）运维负担大于收益 | 沿用 `docs/后端脚手架搭建方案.md:611-614` 的判断：**单体先做 L1+L2**，OTel 以「拆服务 / 引入 MQ」为触发条件 |
| **告警疲劳** | 告警一次接太多，最终全员忽略 | 分层分级 + 抑制 + 基线偏离 + **季度清理**；告警必须绑定 runbook |
| **成本 vs 收益失衡** | 观测建设容易走过场 | 每阶段设**量化出口标准**（MTTD/MTTR/噪音率），不达标不进入下一阶段 |

集成测试全绿是关键证据：它证明**新增的 MyBatis 拦截器 Bean、`GlobalExceptionHandler` 的构造注入、
JSON 日志配置、秒杀消息结构变更**在真实 MySQL 8 / Redis 7 容器下装配正常，
且秒杀削峰链路的正确性未因「消息体加字段」而回归。

### 9.3 改造中值得记录的两个发现

1. **值级脱敏是全字段生效的**：测试里把 `userId` 设成手机号形态的值，结果被一起打码。这不是缺陷——它是隐私优先的必然结果，但意味着**不能用手机号当用户标识做排查**。已固化为断言，防止被"顺手改成不脱敏"。
2. **`logback-spring.xml` 刻意不使用 `<springProperty>`**：代价是环境标识改由 `APP_ENV` 环境变量驱动（默认 `dev`），收益是配置可用 `JoranConfigurator` 离线校验——不必为了验证一段日志格式而拉起 MySQL 与 Redis。这是"规范靠断言守住"的前提。
