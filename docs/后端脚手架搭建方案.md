# 极客数码商城 — Java 后端脚手架搭建方案

> 依据：前端功能点分析（`docs/功能点分析报告.md`）中的 11 个功能模块、A 类 21 项待补逻辑、B 类 8 项待建能力。
> 环境现状：本机已装 **JDK 21.0.12** + **Maven 3.9.16**，工作区**尚无任何后端工程**（无 `pom.xml` / `*.java`）。

---

## 一、技术选型结论

| 维度 | 选型 | 理由 |
| --- | --- | --- |
| 语言/运行时 | **JDK 21**（LTS） | 本机已就绪；虚拟线程对 IO 密集的商品/订单查询友好 |
| 框架 | **Spring Boot 3.3.x** | 与 JDK 21 匹配，Jakarta EE 9+ 命名空间 |
| 构建 | **Maven 3.9** 多模块 | 依赖统一管理，便于按域拆分 |
| Web | spring-boot-starter-web（MVC） | 前端为 REST 调用，无需 WebFlux |
| 鉴权 | **Spring Security 6 + JWT**（备选 Sa-Token） | 对应前端 17 条 `requiresAuth` 路由；Sa-Token 更轻量、中文文档友好 |
| ORM | **MyBatis-Plus 3.5.x** | 分页/逻辑删除/自动填充开箱即用，SQL 可控 |
| 数据库 | **MySQL 8.0** | 交易类数据强一致首选 |
| 缓存 | **Redis 7** | 验证码、Token 黑名单、秒杀库存、商品热点缓存、分布式锁 |
| 对象存储 | **MinIO**（本地）/ 阿里云 OSS（生产） | 头像、评价图、售后凭证上传 |
| 文档 | **Knife4j / springdoc-openapi** | 自动生成接口文档，便于前后端联调 |
| 工具 | Lombok、MapStruct、Hutool、validation | 减少样板代码 |
| 定时/延迟 | Spring `@Scheduled` → **Redis 延迟队列 / RabbitMQ 延迟插件** | 订单超时未支付自动取消 |
| 消息队列 | **可选（非必需）**：RocketMQ / RabbitMQ / Kafka | 仅用于秒杀削峰、订单超时、异步解耦；中小流量可用 Redis 队列替代，见 6.4 |
| 可观测性 | **分级引入**：Actuator + Micrometer + Prometheus/Grafana（必选），Loki，链路追踪可选 | 指标/日志/链路三支柱；最小集几乎零成本，详见 6.9 |
| 消息通知 | 站内消息表 + 可选短信服务商 | 对应消息中心 + 验证码 |

> **两种鉴权路线**：若追求规范与生态用 **Spring Security + JWT**；若追求脚手架轻量、快速出活，推荐 **Sa-Token**（注解式 `@SaCheckLogin`，与前端 `requiresAuth` 语义几乎一一对应）。下文以「Spring Security + JWT」为主干，Sa-Token 作为替代标注。

> **中间件全景**（哪些已定、哪些按需补、哪些明确不需要）见 **6.10**；结论是本项目除 MySQL/Redis/MinIO 外基本无需再引入重型中间件。

## 二、工程结构

### 2.1 推荐路线：先单体分包，后按域拆模块

初期用**单模块 + 清晰包分层**，成本最低；当团队/规模上来后，再按 `common / dao / service / web` 或按业务域拆 Maven 多模块。

```
geek-mall-backend/                     # 聚合父 POM（统一版本、插件、profile）
├── pom.xml
└── geek-mall-server/                  # 阶段一：单模块
    ├── pom.xml
    └── src/main/java/com/geekmall/
        ├── GeekMallApplication.java
        ├── common/                    # 通用基础
        │   ├── result/                # Result<T>、PageResult<T>、ResultCode
        │   ├── exception/             # BizException、GlobalExceptionHandler
        │   ├── enums/                 # OrderStatus、AfterSaleStatus、CouponType…
        │   ├── constant/              # RedisKey、SecurityConstants
        │   └── util/                  # JwtUtil、IdGenerator、MoneyUtil
        ├── config/                    # SecurityConfig、MybatisPlusConfig、RedisConfig、
        │                              # WebMvcConfig(CORS)、Knife4jConfig、AsyncConfig
        ├── security/                  # JwtAuthenticationFilter、LoginUser、UserDetailsServiceImpl
        └── modules/                   # 按业务域分包，每域内部再分层
            ├── auth/                  # 登录/注册/验证码/找回密码
            ├── user/                  # 资料、地址、积分、签到、会员、收藏、足迹
            ├── product/               # 分类、品牌、商品、SKU、搜索
            ├── marketing/             # 秒杀、新品、优惠券
            ├── cart/                  # 购物车
            ├── trade/                 # 结算、订单、支付
            ├── aftersale/             # 售后申请/详情
            ├── review/                # 评价
            ├── message/               # 消息中心
            └── content/               # 关于/帮助/政策 + 文件上传
```

### 2.2 业务域内统一分层（每个 `modules/xxx` 内部）

```
modules/product/
├── controller/ProductController.java      # 只做参数接收/校验/组装响应
├── service/ProductService.java            # 接口
├── service/impl/ProductServiceImpl.java   # 业务编排 + 事务
├── mapper/ProductMapper.java              # MyBatis-Plus Mapper
├── entity/ProductDO.java                  # 数据库实体
├── dto/ProductQueryDTO.java               # 入参
├── vo/ProductCardVO.java                  # 出参（对齐前端字段）
├── converter/ProductConverter.java        # MapStruct DO↔VO
└── enums/…
```

**分层纪律**：Controller 不写业务、Service 不碰 `HttpServletRequest`、VO 与 DO 隔离（禁止实体直接出参）。

### 2.3 资源目录

```
src/main/resources/
├── application.yml                # 公共配置
├── application-dev.yml            # 本地：MySQL/Redis/MinIO
├── application-prod.yml           # 生产：连接池、日志、密钥走环境变量
├── mapper/                        # MyBatis XML（复杂 SQL）
└── db/migration/                  # Flyway 迁移脚本 V1__init.sql、V2__seed.sql
```

### 4.2 核心表 DDL（节选）

```sql
-- 用户
CREATE TABLE sys_user (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  username     VARCHAR(64)  NOT NULL COMMENT '登录账号/手机号',
  password     VARCHAR(100) NOT NULL COMMENT 'BCrypt 密文',
  phone        VARCHAR(20)  NOT NULL,
  nickname     VARCHAR(64),
  avatar       VARCHAR(255),
  status       TINYINT DEFAULT 1 COMMENT '1正常 0禁用',
  level_id     BIGINT DEFAULT 1,
  points       INT DEFAULT 0,
  growth       INT DEFAULT 0,
  deleted      TINYINT DEFAULT 0,
  create_time  DATETIME DEFAULT CURRENT_TIMESTAMP,
  update_time  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_username (username),
  UNIQUE KEY uk_phone (phone)
);

-- 收货地址
CREATE TABLE ums_user_address (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT NOT NULL,
  name        VARCHAR(32) NOT NULL,
  phone       VARCHAR(20) NOT NULL,
  province    VARCHAR(32), city VARCHAR(32), district VARCHAR(32),
  detail      VARCHAR(255) NOT NULL,
  is_default  TINYINT DEFAULT 0,
  deleted     TINYINT DEFAULT 0,
  KEY idx_user (user_id)
);

-- 商品
CREATE TABLE pms_product (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  title         VARCHAR(200) NOT NULL,
  category_id   BIGINT NOT NULL,
  brand_id      BIGINT,
  price         DECIMAL(10,2) NOT NULL,
  old_price     DECIMAL(10,2),
  sales         INT DEFAULT 0,
  rating        DECIMAL(2,1) DEFAULT 5.0,
  cover         VARCHAR(255),
  tags          VARCHAR(255) COMMENT '逗号分隔或 JSON',
  is_hot        TINYINT DEFAULT 0,
  is_new        TINYINT DEFAULT 0,
  status        TINYINT DEFAULT 1 COMMENT '1上架 0下架',
  deleted       TINYINT DEFAULT 0,
  KEY idx_cat (category_id), KEY idx_hot (is_hot)
);

-- SKU（规格：颜色/版本/套餐）
CREATE TABLE pms_product_sku (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  product_id  BIGINT NOT NULL,
  spec_json   VARCHAR(500) COMMENT '{"color":"钛金属","version":"256G"}',
  price       DECIMAL(10,2) NOT NULL,
  stock       INT NOT NULL DEFAULT 0,
  version     INT DEFAULT 0 COMMENT '乐观锁',
  KEY idx_product (product_id)
);

-- 购物车
CREATE TABLE oms_cart_item (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT NOT NULL,
  sku_id      BIGINT NOT NULL,
  qty         INT NOT NULL,
  checked     TINYINT DEFAULT 1,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_sku (user_id, sku_id)
);

-- 订单
CREATE TABLE oms_order (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no      VARCHAR(32) NOT NULL,
  user_id       BIGINT NOT NULL,
  status        TINYINT NOT NULL COMMENT '0待付款 1待发货 2待收货 3待评价 4已完成 5已取消',
  goods_amount  DECIMAL(10,2) NOT NULL,
  shipping_fee  DECIMAL(10,2) DEFAULT 0,
  discount      DECIMAL(10,2) DEFAULT 0,
  pay_amount    DECIMAL(10,2) NOT NULL,
  coupon_id     BIGINT,
  address_snap  VARCHAR(500) COMMENT '下单时地址快照(JSON)',
  pay_method    VARCHAR(20),
  pay_time      DATETIME,
  trade_no      VARCHAR(64),
  create_time   DATETIME DEFAULT CURRENT_TIMESTAMP,
  expire_time   DATETIME COMMENT '超时未支付取消时间',
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_status (user_id, status)
);

CREATE TABLE oms_order_item (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_id    BIGINT NOT NULL,
  product_id  BIGINT NOT NULL,
  sku_id      BIGINT NOT NULL,
  title_snap  VARCHAR(200), price DECIMAL(10,2), qty INT,
  KEY idx_order (order_id)
);

-- 售后
CREATE TABLE oms_aftersale (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT NOT NULL,
  order_no    VARCHAR(32) NOT NULL,
  type        VARCHAR(20) COMMENT 'refund/return/exchange/repair',
  reason      VARCHAR(100),
  content     VARCHAR(500),
  amount      DECIMAL(10,2),
  status      TINYINT DEFAULT 0 COMMENT '0处理中 1已完成 2已取消',
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user (user_id)
);

-- 评价
CREATE TABLE pms_review (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT NOT NULL,
  order_no    VARCHAR(32),
  product_id  BIGINT NOT NULL,
  score_desc  TINYINT, score_logistics TINYINT, score_service TINYINT,
  content     VARCHAR(500),
  anonymous   TINYINT DEFAULT 0,
  reply       VARCHAR(500) COMMENT '商家回复',
  deleted     TINYINT DEFAULT 0,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_product (product_id), KEY idx_user (user_id)
);

-- 优惠券
CREATE TABLE mkt_coupon_template (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  name      VARCHAR(64), type VARCHAR(20), amount DECIMAL(10,2),
  threshold DECIMAL(10,2) COMMENT '使用门槛，对应 cond',
  scope     VARCHAR(50), valid_from DATE, valid_to DATE,
  total     INT, stock INT, per_limit INT DEFAULT 1,
  status    TINYINT DEFAULT 1
);
CREATE TABLE mkt_user_coupon (
  id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id BIGINT, template_id BIGINT,
  status TINYINT DEFAULT 0 COMMENT '0未使用 1已使用 2已过期',
  order_no VARCHAR(32), receive_time DATETIME, use_time DATETIME,
  UNIQUE KEY uk_user_tpl (user_id, template_id)   -- 支撑「重复领取拦截」幂等
);
```

> 说明：`tags`、`spec_json`、`address_snap` 用 JSON/VARCHAR 保留前端展示的灵活性；结构化检索字段（价格、分类、品牌、销量）单独落列并建索引。

## 六、关键技术实现要点

### 6.1 统一响应与全局异常
```java
public record Result<T>(int code, String msg, T data) {
    public static <T> Result<T> ok(T data) { return new Result<>(0, "success", data); }
    public static <T> Result<T> fail(ResultCode rc) { return new Result<>(rc.code(), rc.msg(), null); }
}
```
`@RestControllerAdvice` 统一处理 `BizException`、`MethodArgumentNotValidException`（参数校验）、`AccessDeniedException`（403）、兜底 `Exception`（500 并打日志）。

### 6.2 鉴权链路（对应前端 17 条 `requiresAuth`）
1. `POST /auth/login` 校验密码（BCrypt）→ 签发 JWT（含 `userId`，Redis 存 `login:token:{userId}` 支持单点踢下线）。
2. `JwtAuthenticationFilter` 解析 token → 写入 `SecurityContextHolder`。
3. `SecurityConfig` 白名单：`/auth/**`、`/products/**`、`/home/**`、`/seckill/**`、`/cms/**`；其余 `authenticated()`。
4. 401/403 用统一 `Result` 返回，前端拦截器据此跳登录并带 `redirect`。

### 6.3 订单状态机（B2）
定义 `OrderStatus` 枚举与合法迁移表，所有变更走 `OrderStateMachine.transfer(order, target)` 校验，禁止越权流转；每次迁移写 `oms_order_status_log` 并推送 `sys_message`。

```
0 待付款 → 1 待发货（支付回调）
0 待付款 → 5 已取消（用户取消 / 超时任务）
1 待发货 → 2 待收货（商家发货）
2 待收货 → 3 待评价（确认收货）
3 待评价 → 4 已完成（评价完成）
```

**超时取消**：下单写 `expire_time`，用延迟队列（RabbitMQ 延迟插件）或 Redis ZSet 轮询 + `@Scheduled` 兜底，避免纯定时全表扫描。

### 6.4 秒杀方案：必备件 vs 可选增强（MQ 到底要不要）

> **先给结论：秒杀必须要的是「Redis 原子预扣 + 异步下单 + 一人一单幂等 + 限流」，但「MQ」不是必备件。**
> MQ 解决的是**削峰**与**解耦**，只在瞬时流量远超数据库写入能力时才值得引入；中小流量用 Redis 队列/线程池异步落库即可，不必上 MQ。

**为什么核心不是 MQ？**
秒杀的根本矛盾是「瞬时高并发写入 vs 数据库扛不住」。解决它的第一性动作是：**把"扣库存"从数据库搬到 Redis（Lua 原子操作）**，让绝大多数请求在内存层就被判定与拦截，压根到不了 DB。这一步做完，DB 的写入压力已经从"数十万 QPS"降到"成功下单的那几千单"。此时 MQ 的价值只是把这"几千单的落库"再平滑一下——属于锦上添花，而非救命。

**能力清单与是否必备：**

| 能力 | 是否必备 | 作用 | 实现要点 |
| --- | --- | --- | --- |
| 前端防刷（按钮置灰/验证码/答题） | ✅ 必备 | 拦掉脚本与重复点击 | 秒杀开始才可点，服务端仍须校验 |
| 网关层限流（Nginx/网关 + 单机限流） | ✅ 必备 | 挡住远超承载的流量 | 令牌桶 + 单用户维度限流 |
| **Redis 预热 + Lua 原子扣减** | ✅ **必备（核心）** | 内存层判库存+扣减，根治超卖 | 一个 Lua 脚本内完成：校验库存 → 校验一人一单 → 扣减 |
| 异步下单（请求不直接写库） | ✅ 必备 | 请求快速返回"排队中"，保护 DB | 预扣成功即入队，落库由消费端完成 |
| 一人一单 / 幂等 | ✅ 必备 | 防重复下单、防超卖 | Redis Set 去重 + 订单号唯一索引兜底 |
| 结果反馈（轮询/推送） | ✅ 必备 | 用户得知是否抢到 | 前端轮询 `GET /seckill/result?requestId=` |
| 库存回滚（支付超时/取消） | ✅ 必备 | 归还预扣库存 | 定时任务或延迟消息回补 Redis + DB |
| **MQ 削峰异步落库** | ⚠️ **可选增强** | 把落库压力匀速消化，解耦风控/通知/积分 | RocketMQ/Kafka 按消费能力拉取 |
| 库存分桶 / 多级缓存 / 静态化 | ⚠️ 大规模才需要 | 进一步提升吞吐 | 单 SKU 库存分片、页面 CDN 静态化 |

**按流量规模分级选型：**

| 级别 | 适用场景 | 秒杀实现 | 是否引 MQ |
| --- | --- | --- | --- |
| **L1 小流量** | 演示/中小项目（本仓库场景），数百 QPS 内 | Redis 预扣（或直接 `UPDATE ... WHERE stock>=n`）+ 同步落库 | ❌ 不需要 |
| **L2 中流量** | 单机/少量实例，数千 QPS | Redis Lua 预扣 + 队列异步落库（**Redis List/ZSet 或线程池**）+ 前端轮询结果 | ❌ 可用 Redis 队列替代 |
| **L3 大流量** | 真实电商大促，数万~数十万 QPS | Redis Lua 预扣 + **RocketMQ/Kafka 削峰** + 消费端限速落库 + 风控/通知解耦 | ✅ 建议引入 |
| **L4 超大促** | 头部平台级 | L3 + 网关排队 + 库存分桶 + 多级缓存 + 页面静态化 + 库存预分配 | ✅ 必须 |

**本项目的落地建议（推荐 L2）**：
1. 第一版不引 MQ：`Redis 预热库存 → Lua 原子预扣 → Redis List 入队 → 定时/线程池消费落库 → 前端轮询结果`。复杂度低，已能扛住演示与中小流量且不超卖。
2. **预留可替换抽象**，避免将来改造成本：
```java
public interface SeckillOrderPublisher {   // 秒杀下单消息发布者
    void publish(SeckillOrderMessage msg);
}
// @ConditionalOnProperty(name="mall.mq.enabled", havingValue="false", matchIfMissing=true)
//   → RedisListSeckillOrderPublisher（默认，无 MQ）
// @ConditionalOnProperty(name="mall.mq.enabled", havingValue="true")
//   → RocketMqSeckillOrderPublisher（生产化再启用）
```
3. 这样从 L2 升到 L3 只切一个实现类 + 打开开关，业务代码零改动。

**反例提醒**：不要"为了用 MQ 而用 MQ"——若已用 Redis 完成了原子扣减，却让消费者无脑全速落库，MQ 只是把压力后移，仍可能打爆 DB；消费端必须**限速/批量**。也不要在低并发下用 MQ，只会平白增加运维成本与一致性问题（消息丢失/重复消费/顺序性）。

### 6.5 库存扣减与防超卖（通用商品，非秒杀）
- 普通下单：`UPDATE pms_product_sku SET stock = stock - #{n} WHERE id = #{id} AND stock >= #{n}`，受影响行数为 0 则失败（乐观扣减）。
- 库存不足返回业务错误码，前端提示。

### 6.6 幂等
- 下单：客户端传 `requestId`，Redis `SETNX` 短时锁；或订单号唯一索引兜底。
- 领券：`mkt_user_coupon` 唯一索引 `(user_id, template_id)`。
- 支付回调：`pay_payment_record.trade_no` 唯一 + 状态判断，重复回调直接返回成功。

### 6.7 分页与统一查询
MyBatis-Plus `Page<T>` → `PageResult<T>{ list, total, page, pageSize }`，与前端 `el-pagination` 字段对齐。

### 6.8 其他
- **跨域**：`WebMvcConfig` 配置 `CorsFilter`（开发放行 `http://localhost:5173`）。
- **逻辑删除**：`@TableLogic`，避免物理删除订单/评价。
- **自动填充**：`MetaObjectHandler` 填充 `create_time/update_time`。
- **金额**：一律 `BigDecimal`，禁止 `double`。
- **验证码/限流**：Redis 存储 + 手机号维度滑动窗口限流（防刷）。
- **文件上传**：MinIO 预签名 URL，限制类型/大小。
- **接口文档**：Knife4j `/doc.html`，便于前端联调。

### 6.9 可观测性：要不要用中间件、用哪一档

> **结论：要用，但不必一步到位。** 可观测性分三支柱——**指标（Metrics）、日志（Logging）、链路（Tracing）**。
> 「最小可用集」几乎零成本且任何项目都该有；「全家桶」（ELK + SkyWalking + Alertmanager）只在微服务/大促场景才值得，单体项目上来就上会**运维负担大于收益**。

**按规模分档：**

| 档位 | 适用场景 | 组成 | 成本 |
| --- | --- | --- | --- |
| **L1 最小可用（强烈建议）** | 所有项目，含本项目 | Spring Boot **Actuator** + **结构化日志(JSON)** + **TraceId(MDC)** + 统一异常日志 | 极低（框架自带） |
| **L2 标准（本项目推荐）** | 中小单体/前后端一体 | L1 + **Micrometer + Prometheus + Grafana** + **Loki/Promtail** 日志聚合 | 低（docker-compose 起 3 个容器） |
| **L3 完整** | 微服务、多实例、大促 | L2 + **SkyWalking**（无侵入 agent）或 **OTel + Jaeger** 链路追踪 + **Alertmanager** 告警 + 慢 SQL/连接池监控 | 中高（组件多、需专人维护） |
| **L4 全链路平台** | 头部业务 | L3 + ELK 全量日志 + 链路采样策略 + SLO/错误预算 + 统一观测平台 | 高 |

**三支柱在本项目的落地形态：**

| 支柱 | 选型 | 关键动作 |
| --- | --- | --- |
| 指标 Metrics | Actuator + Micrometer + Prometheus + Grafana | 暴露 `/actuator/prometheus`；看 QPS、RT(P95/P99)、错误率、JVM 堆/GC、HikariCP 连接池、Redis 命中率 |
| 日志 Logging | Logback + JSON encoder + **MDC TraceId** + Loki/Promtail | 每个请求分配 `traceId` 并透传，日志按 JSON 输出，支持按 traceId 聚合检索 |
| 链路 Tracing | **单体可选**；SkyWalking 或 OTel SDK | 单体应用无跨服务调用，收益有限；一旦拆服务/引入 MQ，再上 agent 无侵入接入 |

**必要依赖（L2）：**
```xml

<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-registry-prometheus</artifactId></dependency>
```

**关键配置：**
```yaml

  endpoints.web.exposure.include: health,info,prometheus,metrics
  metrics.tags.application: geek-mall
  endpoint.health.show-details: when_authorized
```

**docker-compose 追加（L2）：**
```yaml

    image: prom/prometheus
    volumes: ["./ops/prometheus.yml:/etc/prometheus/prometheus.yml"]
    ports: ["9090:9090"]
  grafana:

    volumes: ["./logs:/var/log/app", "./ops/promtail.yml:/etc/promtail/config.yml"]
```

**TraceId 贯通（L1 必做，代码极简）：**
```java
public class TraceIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
        String traceId = Optional.ofNullable(req.getHeader("X-Trace-Id"))
                .orElseGet(() -> UUID.randomUUID().toString().replace("-", ""));
        MDC.put("traceId", traceId);
        res.setHeader("X-Trace-Id", traceId);
        try { chain.doFilter(req, res); } finally { MDC.remove("traceId"); }
    }
}
```
> 日志里带上 `traceId` 后，"用户报障 → 定位一条日志 → 串起整条调用链"才成立；这是可观测性里**性价比最高的一步**。

**比 JVM 指标更该看的——业务自定义指标：**
| 指标 | 类型 | 价值 |
| --- | --- | --- |
| `mall_order_create_total{status}` | Counter | 下单成功率，直接反映交易健康度 |
| `mall_order_pay_success_rate` | Gauge | 支付成功率（含回调失败） |
| `mall_seckill_deduct_fail_total` | Counter | 秒杀扣减失败/超卖拦截量 |
| `mall_coupon_claim_total` | Counter | 领券量，活动效果 |
| `mall_order_timeout_cancel_total` | Counter | 超时取消量，异常时骤增 |

**必须配的告警规则（L3，示例）：**
- 5xx 错误率 > 5% 持续 5min
- 下单接口 P99 > 2s
- 支付回调失败/积压
- 订单超时未取消任务未执行（定时任务存活检测）
- JVM 堆使用率 > 85% 或 Full GC 频繁

**为什么不要一上来就全家桶：**
1. **单体无分布式调用**，链路追踪收益低，SkyWalking/ELK 组件多、内存占用大。
2. **过度埋点拖慢迭代**：先保证"出错能查、容量能看"，随规模演进再补。
3. **演进平滑**：L1→L2 只需加 2 个依赖 + 配置；L2→L3 用 SkyWalking **Java Agent 无侵入**接入（`-javaagent`），业务代码零改动。

> 与 6.4 秒杀方案一致的思路：**先解决"必答问题"（能不能查、会不会挂），再上"锦上添花"的重型中间件。**

### 6.10 中间件全景：已定 / 按需补 / 明确不需要

> **结论：除已列组件外，本项目几乎不需要再引入重型中间件。** 很多"标准配置"（网关、注册中心、分布式事务、分库分表）是**微服务 / 超大流量**的产物，单体 + 中小流量引入即为过度设计。

**A. 已确定（见第一节选型表）**

`MySQL 8`（存储）、`Redis 7`（缓存/锁/限流/秒杀库存/轻量队列/Token）、`MinIO`（对象存储）、`[MQ 可选]`、`[Prometheus + Grafana + Loki 可选]`。

**B. 值得补的轻量组件（成本低、收益明确，建议纳入）**

| 组件 | 类型 | 用途 | 说明 |
| --- | --- | --- | --- |
| **ShedLock** | 库（非独立服务） | 多实例定时任务互斥 | 订单超时取消、券过期等任务在**多实例下防重复执行**；存储复用 Redis/MySQL，零新增中间件 |
| **Redisson** | 库（非独立服务） | 分布式锁增强 | 可选：替代手写 `SETNX`，提供可重入锁 + 看门狗续期，秒杀/幂等更稳 |
| **Nginx** | 中间件 | 反向代理 + 静态资源 + 接入层限流 | 部署必备（非业务中间件），前端 `dist` 与 `/api` 同源转发 |
| **Flyway / HikariCP / Knife4j** | 库 | 库版本管理 / 连接池 / 接口文档 | 已在方案中，无需额外部署 |

**C. 按需后置（给出触发条件，到点再引）**

| 需求 | 触发条件 | 届时选型 | 现状方案（先用） |
| --- | --- | --- | --- |
| 商品全文搜索 | 商品量 > 数万，或需分词/相关度/高亮 | **Elasticsearch** | MySQL 索引 + `LIKE`（前端高亮已自实现） |
| 分布式任务调度 | 调度任务 > 20 个 或 需跨服务编排/可观测 | **XXL-Job** | `@Scheduled` + ShedLock |
| 限流熔断大盘 | 大促 / 服务数量上升 | **Sentinel** | Redis 限流 + Nginx 接入限流 |
| 配置 / 注册中心 | 拆分为微服务、多实例动态扩缩容 | **Nacos** | `application-*.yml` + 环境变量 |
| 分布式事务 | 跨服务 / 跨库写入 | **Seata** | 单库 `@Transactional` 本地事务 |
| 分库分表 | 单表行数到千万级 | **ShardingSphere** | 单库单表 + 索引 |
| 数据同步 | 需自动刷新 ES 索引 / 缓存 | **Canal / Debezium** | 应用层双写 + 缓存失效 |

**D. 明确不需要（避免过度设计）**

| 中间件 | 为什么不需要 |
| --- | --- |
| API 网关（Spring Cloud Gateway） | 单体直接暴露 REST，Nginx 七层转发已足够；网关是微服务产物 |
| 注册中心（Eureka/Nacos/Consul） | 无服务间发现与负载均衡需求 |
| 分布式事务（Seata） | 单库单数据源，本地事务即强一致 |
| 分库分表（ShardingSphere） | 数据量级远未达到，且徒增复杂度 |
| 推荐系统（Flink/ClickHouse/特征平台） | "猜你喜欢 / 看了又看"用**销量+品类规则**即可，无需推荐中间件 |
| 分布式 ID 服务（Leaf/TinyID） | **雪花算法工具类**足够生成订单号，无需独立服务 |
| Memcached 等第二套缓存 | Redis 已覆盖，重复引入只增运维面 |
| 消息队列 | 见 6.4：秒杀非必需，中小流量用 Redis 队列替代 |

**E. 判断准则（引入前问三句）**

1. **现在的方案真的扛不住了吗？**（有没有实测数据/压测支撑）
2. **新增的运维、一致性、学习成本，是否小于收益？**
3. **能否先用已有组件顶住？**——本项目里 **Redis 就是"万能替补"**：缓存、验证码、分布式锁、限流、秒杀库存、轻量队列、Token 黑名单全由它承担，**是性价比最高的中间件**。

> 一句话：**中间件按"痛点触发"引入，而不是按"别人都有"引入。**

| 6 | 实现 `product` + `marketing` 查询域（首页/分类/搜索/详情/秒杀/券列表） | 浏览链路通 |
| 7 | 实现 `cart` + `trade` + `pay`（下单/支付回调/订单列表/状态机/超时取消） | 交易主链路闭环 |
| 8 | 实现 `user`（资料/地址/积分/签到/收藏/足迹）+ 上传 | 账户链路通 |
| 9 | 实现 `aftersale` / `review` / `message` / `cms` | 全量覆盖前端页面 |
| 10 | Docker Compose 起 mysql/redis/minio；联调前端 | 端到端可跑 |
| 11 | （建议同时做）接入可观测性最小集：Actuator + TraceId 过滤器 + 结构化日志；需要时再起 Prometheus/Grafana/Loki | 线上问题可定位 |

## 九、与前端联调改造点

前端当前直接读 `src/data/shop.js`（同步函数）。接入后端需要：

1. **新增 `src/api/` 层**：基于 `axios` 封装 `request.js`（`baseURL=/api/v1`、请求拦截加 `Authorization: Bearer`、响应拦截统一解包 `Result` 与 401 跳登录）。
2. **逐个改写 Pinia store / 页面**：把 `shop.js` 的静态导入替换为 API 调用，按本文第五节接口表逐条对接。
3. **开发期代理**：`vite.config.js` 增加 `server.proxy['/api'] → http://localhost:8080`，避免 CORS。
4. **改造顺序**对齐前端优先级：P0 交易闭环（A3/A4/A5/A6/A9 + 订单状态机）→ P1 账户与营销 → P2 筛选与个人中心 → P3 增强能力。

## 十、实施优先级建议

| 优先级 | 后端范围 | 对应前端缺口 |
| --- | --- | --- |
| **P0** | auth(JWT) + product 查询 + cart + trade 下单 + pay 回调 + 订单状态机 + review | A3/A4/A5/A6/A9、B2、B3 |
| **P1** | user(资料/地址/积分/签到) + marketing(秒杀/领券) + aftersale | A11/A12/A16、B4、B5 |
| **P2** | 服务筛选落地 + 优惠码校验 + 收藏/足迹/消息 + 上传 | A1/A2/A10/A13/A14/A15 |
| **P3** | 三方登录 + 在线客服/工单 + 消息推送 + CMS 后台 | B6/B7/B8 |

> **横切项（贯穿各期）**：可观测性建议在 **P0 阶段就落地 L1 最小集**（Actuator + TraceId + 结构化日志，成本极低），随 P1/P2 流量上升再补 **L2**（Prometheus/Grafana/Loki），**L3** 链路追踪待拆微服务或引入 MQ 时再上（详见 6.9）。
