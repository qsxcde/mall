### P0-3 方法级权限注解全程为空 —— **已修复** ✅

**现象**：`@EnableMethodSecurity` 已开启，但全项目 **`@PreAuthorize` / `@Secured` / `hasRole` 使用数为 0**（唯一命中是 `GlobalExceptionHandler` 的注释）。越权防护完全依赖「白名单 + `authenticated()` + 服务内手写归属校验」（`SecurityUtils.getUserId()` / `MerchantSecurityUtils.getShopId()`）。

**实测确认的后果**（修复前）：

| 请求 | 修复前 |
| --- | --- |
| 匿名 → 商家接口 | `401` 未登录 |
| **买家令牌 → 商家接口** | **`401` 未登录** ← 已认证却被判成"未登录"，语义错误 |
| 商家令牌 → 商家接口 | `200` |

不是"能读到数据"的漏洞（9 个商家 service 都调了 `getShopId()`），但**防护是隐式的**（依赖每个新接口都记得加校验），且**语义错**（应 403 无权限）。

**修复**（两处，纵深防御）：

1. `SecurityConfig` 加路径规则：`/api/v1/merchant/**` → `hasAuthority(ROLE_MERCHANT)`（白名单里的 `/merchant/auth/**` 在其之前，登录不受影响）；
2. 8 个商家业务 Controller 加类级 `@PreAuthorize("hasRole('MERCHANT')")`（`MerchantAuthController` 除外，其端点在白名单内）。

**验证**：修复后买家令牌 → **403**；商家令牌 → 200；匿名 → 401；商家登录 / 买家接口 / 公开接口全部不受影响。
回归：`mvn test` **569 项全绿**（其中 `MerchantApiIntegrationTest` 的 `buyerTokenShouldNotAccessMerchantApi`
原本断言 401，属"固化了错误语义"，已一并改为断言 403）。

> **保留的已知边界**：反方向（商家令牌 → 买家接口）仍返回 401，由买家域 service 的 principal 类型校验兜底；
> 未对买家域加路径规则，因为这些路径里有既允许买家也允许匿名的接口（如公开读、`/api/v1/files` 上传），
> 贸然加 `hasRole('USER')` 会误伤。这条不对称需在面试叙事里主动说明。

**成本**：低（实际约 0.5 天）。

### 四.1 格式化为什么用 ratchet 而不是全量重排

实测：后端 **371 / 374** 个 Java 文件不符合 palantir 格式，前端两个工程共 **39** 个文件不符合 Prettier。
一次性 `apply`/`--write` 会产生几乎覆盖全库的 diff、冲掉 `git blame`，还要重审每一处手写注释的排版。

因此两边都用 **ratchet（只约束「相对基线有改动」的文件）**：CI 立刻能绿，旧文件不动，
此后被改动过的文件自动收敛到统一风格 —— 这是遗留代码库引入格式化的标准做法。

- 后端：Spotless 的 `<ratchetFrom>origin/main</ratchetFrom>`；
- 前端：Prettier 没有内置 ratchet，用 `scripts/check-frontend-style.sh` 按 `git diff` 算改动文件再 `--check`。

### 四.2 落地时踩到并修掉的三个真问题

1. **vite 6 有已知告警** → 升级 `vite ^6.0.5 → ^7.1.11`（实际解析 7.3.7）、
   `@vitejs/plugin-vue ^5.2.1 → ^6.0.9`；两个前端重新构建通过。
2. **Prettier 3 + `semi: false` 会把 Vue 指令里的多语句内联表达式拆坏**：
   `@click="a = false; b()"` 被格式化成多行且去掉分号，而 Vue 指令的表达式位置**不允许语句序列**，
   直接编译失败（`Error parsing JavaScript expression: Unexpected token`）。
   共 2 处（`OrderListView`、`FinanceSettleView`），已抽成具名函数 `shipFromDrawer` / `closeFromDrawer` / `withdrawAll`，
   并全库扫描确认无同类残留。**这是本次最有价值的发现**：它只有在"格式化 + 构建"同时跑时才会暴露。
3. **ESLint 9 改了 `no-unused-vars.caughtErrors` 默认值**（`none` → `all`），
   项目里 60+ 处「刻意忽略异常」的 `catch (e)` 被全量报出。已显式设为 `none` 并注明理由
   （真正未使用的变量仍然会被报 —— 正是它顺带揪出了 12 处真死代码：未使用的导入/变量，以及一个删掉后连带暴露的死函数）。

## 五、不建议现在做的（避免浪费时间）

- ❌ **堆功能**：CMS 后台、Admin 控制台、追评/富文本、消息模板化——校招不考核功能数量。
- ❌ **为技术栈而技术栈**：分库分表、K8s/Helm、Seata、Nacos——讲不深反而暴露「只是用过」。
- ⚠️ **Elasticsearch / SKU 多规格**：属**功能扩展**而非面试深度，是文档自认的「硬骨头」。除非你打算把「搜索优化」作为主打话题，否则优先级低于 P0/P1。
- ⚠️ **换掉手写熔断/自研限流去用 Sentinel/Resilience4j**：没必要。**手写实现反而是加分项**——前提是你能讲清设计取舍（见 §六）。

### 特别推荐：把「预测错了并找到原因」讲出来

`loadtest/results/秒杀分桶×MQ对比-2026-10-08.md` 记录了一次完整的闭环：

> 按 `有效并行度 = min(线程 64, 连接池 50, 桶数 10) = 10` 预测应有 ~10× 吞吐；
> **实测只有 1.74×（同步）/ 2.10×（MQ）**；
> 归因：**同一个 DB 事务里还扣了一行未分桶的 `pms_product`**，该单行成为新瓶颈；
> 并给出「要接近 10× 必须同时打破商品行」的结论与验证路径。

**主动讲自己预测错了、并用实测定位到原因，是校招里罕见的高级信号**——它证明你会做实验、看得懂数据、而不是只会背结论。这段务必写进简历描述并准备口述。
