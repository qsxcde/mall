# 极客数码商城 — 接口限流策略说明

> 文档日期：2026-10-07
> 适用范围：`backend/` 全部 **117 个 HTTP 端点**（28 个 Controller）
> 单一事实来源：`com.geekmall.common.ratelimit.RateLimitPolicies`
> 配套测试：`RateLimitPoliciesTest`、`RateLimitCoverageIntegrationTest`、`RateLimitIntegrationTest`、`LocalRateLimiterTest`、`DistributedRateLimiterTest`、`RateLimitInterceptorTest`

---

## 一、设计总览

### 1.1 三个关键决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 规则放在哪 | **集中式策略表**（按「方法 + 路径模式」匹配），不再用方法级注解 | 注解散落在 117 个方法上无法审阅、无法证明无遗漏；集中在 `RateLimitPolicies` 后，一份文件即可完整核对，且断言式的覆盖度测试可以自动化证明「没有端点漏配」 |
| 计数放在哪 | **默认进程内，仅 7 个接口走 Redis** | 早前把拦截器统一挂 Redis INCR，压测实测把普通下单 P99 抬高 **12.1 倍** —— 限流器自己成了瓶颈。只有「限流是唯一防线」的接口才值得付这次网络往返 |
| 突发怎么处理 | **滑动窗口**替代固定窗口 | 固定窗口在边界瞬时放行量最多可达阈值 2 倍，正是要削掉的形态；滑动窗口用「上一窗口计数 × 剩余权重 + 当前窗口计数」估算，代价只是每窗口多存一个计数器 |

### 1.2 分层依据（为什么大多数接口不需要 Redis）

| 接口性质 | 层级 | 判断依据 |
| --- | --- | --- |
| 登录 / 验证码 / 注册 / 改密 / 商家登录 / 上传 | `DISTRIBUTED` + `FAIL_CLOSED` | 漏了会有**真实代价**（撞库、短信费用、刷号），且必须多实例下全局准确 |
| 下单 / 领券 / 积分兑换 | `LOCAL` | 防重由 **`requestId` 幂等键 + 唯一索引**兜底，限流只需挡手抖与脚本；在这里加 Redis 只是白付成本 |
| 高频读接口（商品 / 首页 / 分类） | `LOCAL` | 请求量最大、单次最便宜，最不该被限流器拖慢 |
| 其余业务接口 | `LOCAL` | 同上 |

## 二、限流元模型

### 2.1 维度（`RateLimitDimension`）

| 维度 | 含义 | 回退规则 |
| --- | --- | --- |
| `SUBJECT` | 按**登录主体**分组：买家取 `userId`，商家取 `merchantUserId` | 都取不到时回退 IP |
| `IP` | 按客户端 IP（优先取 `X-Forwarded-For` 首个地址） | — |
| `GLOBAL` | 全站共享一个计数 | — |

> 业务接口一律用 `SUBJECT`：限的是「这个人的操作频率」，而不是「这个出口 IP 的频率」，否则同一公司网关后的所有用户会互相影响。

### 2.2 层级（`RateLimitTier`）

| 层级 | 成本 | 一致性 | 适用 |
| --- | --- | --- | --- |
| `LOCAL` | 纯内存，零网络往返 | 单实例内准确；多实例时总阈值 = 单实例阈值 × 实例数 | 高频读、以及已有业务幂等的写 |
| `DISTRIBUTED` | 每次请求一次 Redis 往返 | 跨实例全局准确 | 防撞库 / 防短信轰炸 / 防爆破 |

`DISTRIBUTED` 的计数用一段 Lua 脚本完成 **`INCR` + 首次 `EXPIRE`**：

```lua
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return count
```

> 为什么必须用 Lua：朴素的「先 INCR 再 EXPIRE」两步之间若进程退出或网络抖动，key 会**永久没有过期时间**，计数器只增不减 —— 表现为「某天之后这个接口对某个 IP 永久 429」，是线上极难排查的一类事故。

### 2.3 滑动窗口算法

```
估算值 = 上一窗口计数 × 权重 + 当前窗口计数
权重   = 1 − 当前窗口已过去的时间比例
允许条件：估算值 + 1 ≤ 阈值
```

窗口内额度用尽即拒绝；跨窗口后额度按权重**渐进恢复**，而不是瞬间满额。

### 2.4 降级（`RateLimitFallback`）

仅 `DISTRIBUTED` 会触发（即 Redis 不可用），且必须逐条显式声明：

| 策略 | 行为 | 适用 | 当前使用 |
| --- | --- | --- | --- |
| `FAIL_OPEN` | 放行 | 限流只是锦上添花，不该把正常业务一起拖死 | 全部 `LOCAL` 规则 |
| `FAIL_CLOSED` | 拒绝 | 限流是唯一防线，宁可短暂不可用 | 7 个 `DISTRIBUTED` 规则 |

> 无论哪种降级都会打 `error` 日志：限流器失效本身就是需要立刻介入的故障。任意非受检异常都不会向外抛——限流组件绝不能把业务请求打成 500。

### 2.5 并发度控制

频率限制管「单位时间多少次」，挡不住「同一时刻有 N 个慢请求在跑」。对高成本接口额外限制**单实例最大在途数**：

| 规则 | 并发上限 | 原因 |
| --- | --- | --- |
| `file-upload` | 5 | IO + 对象存储，单次开销最大 |
| `trade-submit` | 10 | 长事务持有库存行锁，堆积会拖垮连接池 |

槽位在请求结束后释放；异步请求走 `afterConcurrentHandlingStarted`，两条路径都带幂等标记，避免重复释放把计数压成负数（那等于永久放宽并发上限）。

## 五、边界情况处理

| # | 边界 | 处理 | 验证 |
| --- | --- | --- | --- |
| 1 | **异步二次分发**（秒杀 `DeferredResult` 会以 `ASYNC` 类型再走一次过滤链与 DispatcherServlet） | 只对最初的 `REQUEST` 分发计数，否则一次抢购被算两次、阈值凭空减半 | `RateLimitInterceptorTest#asyncDispatchIsNotCounted`、`RateLimitIntegrationTest#asyncEndpointCountsOncePerRequest` |
| 2 | **跨域预检 `OPTIONS`** | 不计数（浏览器自动发起，与用户行为无关，计数会误伤正常页面） | `RateLimitInterceptorTest#optionsIsNotCounted` |
| 3 | **运维 / 文档 / 静态资源** | 豁免：`/actuator/**`、`/swagger-ui*`、`/v3/api-docs`(+`.yaml`、`/**`)、`/doc.html`、`/webjars/**`、`/uploads/**`、`/favicon.ico`、`/error`。否则健康检查被高频抓取会被误判故障 | `RateLimitPoliciesTest#shouldBeExempt`、`RateLimitIntegrationTest#exemptPathsAreNeverLimited` |
| 4 | **非控制器处理器**（静态资源走 `ResourceHttpRequestHandler`） | 放行，不消耗后端计算资源 | `RateLimitInterceptorTest#nonHandlerMethodIsNotCounted` |
| 5 | **未登录访问受保护端点** | 由 Spring Security 更外层的过滤器链先行拒绝（401），**不进入限流器**。见下方「已知边界」 | `RateLimitIntegrationTest#unauthenticatedRequestsAreRejectedBeforeRateLimiting` |
| 6 | **匿名访问白名单端点** | 正常计数，`SUBJECT` 维度自动回退 IP（登录、验证码、商品、首页、CMS、秒杀浏览、支付回调都属于这一类，也正是匿名刷量需要被约束的地方） | `RateLimitInterceptorTest#subjectFallsBackToIp` |
| 7 | **窗口边界突刺** | 滑动窗口按权重带入上一窗口计数，边界不再出现 2 倍瞬时放行 | `LocalRateLimiterTest#smoothsBurstAtWindowBoundary` |
| 8 | **限流组件自身故障** | 按策略降级：防刷类 `FAIL_CLOSED`，其余 `FAIL_OPEN`；异常绝不外抛 | `DistributedRateLimiterTest#failOpenAllowsWhenRedisDown`、`#failClosedRejectsWhenRedisDown` |
| 9 | **计数 key 永不过期** | Lua 内原子完成 `INCR` + 首次 `EXPIRE`，TTL 比窗口多 1 秒宽限 | `DistributedRateLimiterTest#usesAtomicLuaScript`、`RateLimitIntegrationTest#distributedTierStoresCounterInRedisWithTtl` |
| 10 | **并发槽位泄漏**（会导致接口被永久拒绝） | 同步走 `afterCompletion`、异步走 `afterConcurrentHandlingStarted`，带幂等标记防重复释放 | `RateLimitInterceptorTest#releasesOnCompletionExactlyOnce`、`RateLimitIntegrationTest#concurrencySlotsAreReleasedAfterEachRequest` |
| 11 | **业务失败的请求** | 一样计数（防的是请求量，不是成功业务量，否则撞库可以无限尝试） | `RateLimitIntegrationTest#invalidRequestsAreAlsoCounted` |
| 12 | **内存膨胀**（大量伪造 IP 产生海量 key） | 本地窗口用 Caffeine 限制容量（默认 20 万）并按访问过期回收；并发计数归零即移除 key | `LocalRateLimiterTest#removesKeyWhenIdle` |
| 13 | **代理后取不到真实 IP** | IP 维度优先取 `X-Forwarded-For` 首个地址，其次 `X-Real-IP`，最后 `remoteAddr` | `RateLimitInterceptorTest#ipDimensionUsesForwardedHeader` |
| 14 | **同一路径的读写规则** | 允许共存（方法集合不相交即不算重复），由测试校验「方法 + 路径模式」不重复 | `RateLimitPoliciesTest#methodPatternPairsAreUnique` |

## 六、响应契约

### 6.1 放行

```http
HTTP/1.1 200 OK
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 57
```

客户端可据此自适应退避（例如余量低于 10% 时降低轮询频率）。

### 6.2 限流

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 7
Content-Type: application/json

{"code": 429, "msg": "系统繁忙，请稍后再试", "data": null}
```

`Retry-After` 取自 Redis 中计数 key 的剩余 TTL（本地滑动窗口则取当前窗口剩余秒数），客户端应据此等待而非立即重试。

| `mall.rate-limit.enabled` | `true` | 总开关。测试 profile 为 `false`：功能用例验证的是业务流程，而限流会在「同一 IP 连续登录几十次」这类场景下把测试打断；限流自身的行为由专门的用例在开启状态下验证 |
| `mall.rate-limit.local-max-keys` | `200000` | 本地窗口容量上限 |

### 7.2 如何调整阈值

只改 `RateLimitPolicies` 一处即可，不需要动任何 Controller。改完跑：

```bash
mvn test -Dtest='RateLimitPoliciesTest,RateLimitCoverageIntegrationTest,RateLimitIntegrationTest'
```

### 7.3 日志

被限流时打 `WARN`，包含规则名、维度、阈值与层级：

```
[限流] 规则=auth-login, 维度=ip:203.0.113.9, 阈值=10/60s, 层级=DISTRIBUTED
```

并发触顶另有一条：

```
[限流] 规则=file-upload 并发已达上限 5，拒绝请求
```

Redis 降级打 `ERROR`（限流器失效本身是需要立刻介入的故障）：

```
分布式限流不可用，按 FAIL_CLOSED 降级：key=..., cause=...
```

## 八、已知边界与后续

1. **未通过鉴权的请求不由本模块限流**（见边界 5）。受保护端点上的「无令牌洪水」会被鉴权层廉价拒绝，但确实不被限流计数约束。若要覆盖这一层，正确做法是在网关 / LB 做全局限流，或把限流前移到安全链之前（代价是 `SUBJECT` 维度退化为 `IP`，因为此时还没有登录态）。当前选择是「精确、低开销、覆盖真正需要约束的白名单匿名流量」，并把该边界用测试固化下来。
2. **`LOCAL` 层级在多实例下阈值会放大**（总阈值 = 单实例阈值 × 实例数）。这是刻意的性能取舍；若某个 `LOCAL` 规则将来需要全局精确，把它改成 `DISTRIBUTED` 即可（一行改动）。
3. **滑动窗口是近似算法**：权重法在极端边界下仍有小幅误差，换来的是无需 ZSET 的低成本。若将来需要严格精确，可换成 Redis 令牌桶（Lua 实现）。
4. **未接入指标上报**：当前只有日志。可补 Micrometer 计数器（按规则名打点），把 429 数量纳入 Prometheus 面板。
5. **`default` 兜底规则只是安全网**：任何落到兜底规则的端点都会被覆盖度测试判为「未分类」并让构建失败，因此它不会成为「悄悄绕过分类」的后门。
