### 2.2 取舍理由

- **为什么砍"集成类"功能**：支付渠道、快递轨迹、IM、Admin 后台的核心工作量在"对接外部系统与资质"，练到的是流程而非技术难点；且支付一旦真实化会引入资损与合规负担。
- **为什么保留商家端**：`frontendMerchant` + `merchant` 模块已建好，它本身是"并发压力源"的绝佳素材（批量发货、看板聚合、批量改价打穿 C 端缓存），建议保留但冻结，用作高并发练习的对照面。
  - 状态补充：商家端 9 个页面**已全部从本地 mock 切换为真实接口**（`src/api/*` 无 `resolveMock` 调用，仅 `utils/mock.js` 保留为无引用的参考实现），因此它作为"对照面"是可真实驱动的，不再是纯演示壳。

**测试基础设施的三个关键决策（避免踩坑）**

1. **不使用 H2**：迁移脚本与商家域聚合查询大量使用 MySQL 专有语法（`JSON_EXTRACT` / `JSON_VALID`、`DATE_SUB(CURDATE(), INTERVAL …)`、`INSERT IGNORE`、`ON DUPLICATE KEY UPDATE`），H2 兼容模式跑不通——用 H2 等于测了个假环境，因此集成测试走真实 MySQL 容器。
2. **容器为进程级单例**（不用 `@Testcontainers` 注解，改为静态块启动 + 退出时 shutdown hook 释放）：否则每个测试类都会重启一次 MySQL，冷启动十几秒会让测试慢到没人愿意跑。
3. **`testcontainers.version` 提升到 1.21.4**：Spring Boot 3.3.5 默认的 1.19.8 携带的 docker-java 使用过旧的 Docker API（1.32），被较新的 Docker Desktop / Engine 拒绝（`Status 400`），集成测试会在容器启动阶段**整体失败**且难以定位；1.21.4 会做 API 版本协商。

**测试驱动的缺陷修复（1 处业务代码）**

- `FileValidator.buildObjectName(biz, null)` 抛 `NullPointerException`：`EXT_BY_TYPE` 是不可变 Map，不接受 null key。已加归一化，未知 / 空 MIME 兜底 `.png`（该路径此前被 `validate()` 先拦下才未暴露，属真实隐患）。

**同时纠正的两处"我以为"（实现才是对的，测试按真实契约固化）**

- 取消订单是**幂等设计**：重复取消返回成功而非报错；库存由 `inventory_rollback_log` 唯一索引保证"最多回退一次"。测试断言的是"库存只回退一次"，而不是"第二次必须报错"。
- JWT 时间戳精度为**秒**：同一秒内为同一用户签发的令牌字节相同，因此"连续两次登录"构造不出失效令牌（这是错误测法）。单点会话改为直接替换 Redis 会话值来验证。

### 3.6 缓存治理（穿透 / 击穿 / 雪崩）—— ✅ 已补齐

改造前 `CacheConfig` 的三个缺口：`disableCachingNullValues()`（穿透无防护）、`@Cacheable` 无 `sync`（且即便加了也只是单 JVM 的 `ReentrantLock`，多实例照样各自回源）、`entryTtl` 固定值（同批 key 同一秒集中失效）。

> 实现收敛在 `common/cache/`，业务代码只改两处：`ProductServiceImpl`（详情拆两层）、`MerchantProductServiceImpl`（上架维护布隆）。TTL / 抖动 / 击穿锁 / L1 白名单外置于 `mall.cache.*`，熔断参数外置于 `mall.resilience.*`，调整缓存行为不需要动代码。

| 问题 | 手段 | 关键实现 |
| --- | --- | --- |
| **穿透** | 布隆过滤器 + 空值缓存（两道） | `RedisBloomFilter`（Redis Bitmap，MD5 双哈希派生 k 个位）：判定"一定不存在"直接 404，**不查库也不写缓存**；被约 1% 假阳性放行的请求再由空值缓存挡住，只查库一次 |
| **击穿** | 跨实例互斥重建 | `ResilientRedisCache` 覆写 `get(key, Callable)`：Redis `SET NX PX` 锁 + 双重检查，未抢到锁的线程轮询等待；释放用 Lua 比对 token，避免误删他人锁 |
| **雪崩** | TTL 抖动 + 本地 L1 + 熔断 | `JitterTtlFunctionFactory` 每次写入叠加 ±20% 随机浮动（打散集中失效）；Caffeine L1 承接瞬时流量；通用 `CircuitBreaker` 在 Redis 故障时直接跳过，不再让请求等满 timeout（见 §3.7） |

**五个刻意的设计决策（都是容易踩的坑）**

1. **布隆过滤器未就绪时必须放行，而不是拒绝**：Redis 被清空或服务首次启动时位图是空的，"空位图"意味着"所有商品都不存在"——照常校验会造成**全站 404**。因此用独立就绪标记，`mightContain` 在未就绪时返回 `true` 降级放行。同理 `ProductBloomFilterWarmer` 只在未就绪时预热，避免多实例启动互相清空位图。
2. **空值缓存要求被缓存的方法返回 `null`，而不是抛异常**：`@Cacheable` 方法一旦抛异常就不会写缓存，无效 ID 仍会次次打库。因此把 `detail()` 拆成两层：外层负责布隆前置 + 抛 404，内层 `cachedDetail()` 查不到时返回 `null`。
3. **本地 L1 只给"能容忍数秒陈旧"的聚合数据**：白名单默认仅 `homeFloors` / `categoryTree`；商品详情含价格，商家改价后必须尽快生效，刻意不进 L1。代价是 `clear()` 只能清本实例的 L1，其他实例最多陈旧一个 L1 TTL（3s）——这正是把白名单收窄的原因。
4. **未抢到锁的线程在超时后放行回源，而不是无限等待**：锁的语义是"尽量减少并发回源"，不是"宁可让用户超时也不许回源"。可用性优先。
5. **缓存层也要熔断**：Lettuce 在 Redis 不可用时，每个请求都要等满 3s timeout 才失败；若不熔断，数据库会被"排队 3s 后同时涌入"的流量打穿。熔断后请求直接走 L1 / 数据库，把影响限制在"失去缓存加速"这一层。该熔断器与业务级共用同一个 `CircuitBreaker` 实现（参数见 `mall.resilience.resources.cache`，见 §3.7）。

**写库路径必须同步维护布隆过滤器**：`MerchantProductServiceImpl` 在商品上架时 `add` 其 ID。漏掉这一步的后果很隐蔽——**新品会被自己的防穿透机制判为"不存在"**。另外布隆只能加不能删，下架商品仍会通过校验，由空值缓存兜住（标准权衡）。

**验证方式**：不靠"看代码觉得对"，而靠可重复的断言（见 §3.5「缓存三防」链路）——"冷 key 并发重建只发生 1 次"是读 `mall_cache_rebuild_total` 指标差值断言的；Redis 故障降级路径由 `ResilientRedisCacheTest` 用 Mockito 让读/写抛 `RedisConnectionFailureException` 覆盖。

### 3.7 业务级熔断降级 —— ✅ 已补齐

§3.6 的熔断保护的是「Redis ↔ 数据库」，本节保护的是「应用 ↔ 外部依赖」。两者回答的问题不同：

> **缓存层熔断回答「缓存挂了怎么办」；业务级熔断回答「某个非核心下游挂了，怎么不让它把无关业务一起拖垮」。**

**为什么必须是业务级**：`MinioConfig` 原先用裸的 `MinioClient.builder()`，**一个超时都没配**。于是 MinIO 网络抖动时，上传请求会长期挂住 Tomcat 线程（`max: 120`）——120 个卡住的上传请求就足以让**与文件毫无关系的**商品详情、下单、支付一起排队。这是一条完整的故障扩散路径，而缓存层熔断挡不住它（文件上传根本不走缓存）。

**四项落地内容**

| 项 | 内容 |
| --- | --- |
| ① 超时（前提） | `MinioConfig` 显式装配 OkHttp：connect 3s / write 30s / read 30s / **call 60s**。最后一项最关键：`writeTimeout` 只在「写数据长时间无进展」时触发，「连接已建立但服务端不返回」不触发它。**没有超时的熔断是伪熔断** —— 熔断器必须等调用返回才能计数，而「慢」只有配了超时才会变成「失败」 |
| ② 熔断器 | `common/resilience/CircuitBreaker`：滑动窗口（10 桶环形数组）失败率 + 慢调用率 + 最小样本数 + 半开探测。状态转换是惰性的（不启后台线程），半开探测带超时回收（避免探测卡死导致熔断永久停在半开态） |
| ③ 执行器 | `ResilienceGuard`：把「调用下游 → 记录成败 → 熔断判定 → 降级回退」收敛到一处，业务代码只声明「资源名 + 主逻辑 +（可选）降级逻辑」，并支持并发信号量先于熔断生效 |
| ④ 降级目标 | `LocalDiskFileStore`（从 `LocalFileServiceImpl` 抽出，**始终注册**）。`LocalFileServiceImpl` 只在 `storage.type=local` 时才存在，用 MinIO 的环境里根本没有它、也就无从降级 —— 这是抽取它的真正原因。本地写入的安全规则同时保持只有一份，避免降级路径比主路径放松校验 |

**四个刻意的设计决策**

1. **判定用失败率 + 慢调用率，而不是连续失败计数**。连续计数在两个真实场景下会失效：低峰期「连续 2 个偶发异常」就能熔断依赖（故引入 `minimumCalls`）；下游「不报错但很慢」时连续失败计数恒为 0，**熔断永不触发而线程池早已被占满**（故引入 `slowCallRateThreshold`）。
2. **并发上限先于熔断生效**。熔断是**事后**的：要等失败累计到阈值才打开，这期间线程已经被占住。所以对慢依赖先用信号量（`minio-upload` 限 20 并发）把请求挡在门外，熔断器只作兜底。
3. **降级按业务语义区分，而不是按依赖**。同一个 MinIO：头像 / 评价图属展示型附件 → 降级到本地磁盘；**售后凭证不降级** → 明确报错让用户重试（凭证是纠纷举证的依据，静默写进多实例部署下不共享的本地目录等于丢数据）。降级结果在响应里带 `degraded: true` 标记；未降级时为 null，配合 `non_null` 策略**正常响应结构完全不变**。
4. **调用边界写进约定**：交给 `ResilienceGuard` 的必须是依赖调用本身，参数校验要放在外面 —— 否则用户传错一个参数会被计成「依赖失败」，甚至把非法文件降级写进本地磁盘。

**顺带消除了一处重复实现**：缓存层原本有独立的 `CacheCircuitBreaker`（连续失败计数）。既然要新建通用熔断器，就删掉它并让缓存层改用 `CircuitBreaker` —— **同一个依赖两套熔断状态**会让行为不可预测，这也是最终没有引入 Resilience4j 的原因（功能重叠且会让状态表分裂）。缓存层与业务层因此共用同一个 `ResilienceGuard` 注册表。

**验证方式**：`CircuitBreakerTest`（14 例：失败率 / **慢调用率单独触发** / 样本不足不熔断 / 半开限流·恢复·重开·探测超时回收）、`ResilienceGuardTest`（8 例：熔断打开转降级 / 无降级路径抛 `CircuitOpenException` / **并发信号量先于熔断** / 总开关透传 / 同资源共用一个熔断器）、`MinioFileServiceImplTest`（3 例：**头像降级到本地并标记** / **售后凭证拒绝降级** / 非法文件在熔断保护外被拒且不碰下游）。

> 留白：降级文件落在单个实例的本地磁盘上，其他节点访问不到。已在 `degraded` 标记与 WARN 日志中写明「需人工核对是否补传」，真正的解法是接共享降级存储（NFS / 第二个对象桶）。本项目选择「可用性优先 + 明确标记」并把这个取舍显式记录下来。

## 七、结论

1. **方向对**：以"主链路 + 商品展示 + 登录 + 高并发"为焦点，砍掉全部集成类功能，是练手项目的最优取舍。
2. **框架已就绪**：工程基础设施、通用能力层、配置层、安全鉴权层均已完备；四个聚焦方向都有可运行的骨架与接口。
3. **测试空白已补齐**：507 个用例把"不超卖、不重复回退、不重复建单、双端不越权、缓存重建只发生一次、凭证不降级"从压测观察固化为自动化断言，后续加固有了回归网。
4. **限流空白已补齐**：117 个端点全部纳入显式规则，分层执行（本地为主）、含并发度与故障降级，并由覆盖度测试防止新增接口漏配。
5. **缓存三防已补齐**：布隆过滤器 + 空值缓存挡住穿透、跨实例互斥锁让热点 key 重建只发生一次、TTL 抖动 + 本地 L1 + 熔断让"缓存故障"不再升级为"数据库故障"；业务代码仅改两处，参数全部外置于 `mall.cache.*`。
6. **熔断降级已补齐**：业务级熔断把「某个非核心下游变慢」与「无关业务」隔离开 —— 改造前 MinIO 连超时都没配，一次网络抖动就能让上传请求占满 Tomcat 线程，把下单和商品详情一起拖垮；现在四层超时 + 跨实例熔断（含慢调用判定）+ 按业务语义降级，且缓存层与业务层共用同一套熔断状态机（顺手消除了一份重复实现）。
7. **下一步不是搭框架，而是做深度**：仅剩异步化与搜索进阶（**MQ 削峰是当前最大空白**）——这比再铺 20 个页面更有价值。
