# 秒杀削峰压测对比报告

> 日期：2026-10-07
> 目的：用同一份代码、同一套压测脚本，只切换 `mall.seckill.async.enabled`，量化「MQ 削峰」的真实收益与代价
> 结论一句话：**用户侧延迟下降 77%~83%，但落库吞吐没有提升（甚至略降）—— 这正是「削峰摊平脉冲、不提升吞吐」的实测证据**

---

## 一、测试方法（为什么这样测）

### 1.1 唯一的变量是异步开关

| 项 | A 组（基线） | B 组（削峰） |
| --- | --- | --- |
| 代码 | 同一份 `target/classes` | 同左 |
| 实例 | 8081（独立实例，**不动开发用的 8080**） | 8081（重启切换参数） |
| 启动参数 | `--mall.seckill.async.enabled=false` | `--mall.seckill.async.enabled=true` |
| 压测脚本 | `loadtest/k6/seckill.js` | **同一个脚本** |
| 压测参数 | `VUS=200 ITERATIONS=100 ITEM_ID=1` | 同左 |
| 活动库存 | 200 | 200 |
| 限流 | 关闭 | 关闭 |
| 数据库/Redis | 同一套容器（MySQL 8.0 + Redis 7） | 同左 |

**两组完全对称，唯一差异就是那一行开关。**

### 1.2 两个刻意的测试决策

**① 关闭限流（`--mall.rate-limit.enabled=false`）**

`seckill-grab` 规则是「每用户 5 次/秒」。而压测构造成 200 VU × 100 轮，同一个 VU 会在一秒内连发数十次 —— 限流会淹没整条链路，测到的是限流器而不是业务链路。两组同时关闭，保证可比。

**② 不沿用历史基线数据**

`loadtest/results/k6-seckill-burst.summary.json`（P50 821ms / 165.69 单每秒）是**限流策略重构前**测的。当时的注释写着「限流：秒杀抢购 8000 次/秒（全局）」，而现在是「每用户 5 次/秒」—— 两者不可直接比较。因此本报告重新测了 A 组基线。

### 1.3 一个必须先解决的坑：压测账号的 token 已过期

首次跑 A 组时 20000 个请求**全部失败**，且应用日志里**没有任何秒杀业务日志** —— 说明请求根本没进业务层。

排查发现 `loadtest/data/users.csv` 里的 JWT 是 10-05 生成的，而 token 有效期只有 2 小时（`exp - iat = 7200s`），此时已过期 30 小时；401 被脚本的兜底分支计入了 `order_rejected`，看起来像「被抢光」，很容易误判。

顺带发现 `prepare_data.py` 硬编码了 `BASE_URL = "http://localhost:8080"`，而批量登录 1000 个账号会撞上登录接口的 IP 维度限流（`FAIL_CLOSED` 直接 429）。已改为可用环境变量覆盖：

```python
BASE_URL = os.environ.get("BASE_URL", "http://localhost:8080")
```

## 二、结果对比

### 2.1 用户侧延迟（核心收益）

| 指标 | A 组（同步） | B 组（削峰） | 变化 |
| --- | --- | --- | --- |
| P50 | 776.7 ms | **177.0 ms** | **↓ 77.2%** |
| P90 | 1670 ms | **284.0 ms** | **↓ 83.0%** |
| P99 | 1880 ms | **320.4 ms** | **↓ 83.0%** |
| max | 1930 ms | **370.4 ms** | **↓ 80.8%** |

> ⚠️ **两组统计的是不同阶段**，这是理解削峰的关键：
> - A 组的 `order_latency` = 预扣 + **DB 落库完成**（用户拿到订单号）
> - B 组的 `order_latency` = 预扣 + **入队受理**（用户拿到「排队中」的请求号，订单稍后由消费者建出）

也就是说：**用户「点击后得到响应」的时间被压掉了八成**，而落库工作并没有消失，只是移到了后台。

### 2.2 正确性与最终交付（两组必须一致）

| 校验项 | A 组 | B 组 | 判定 |
| --- | --- | --- | --- |
| 工具侧成功受理 | 200 | 200 | 一致 |
| **数据库订单增量** | **200** | **200** | ✅ 均 == 库存 |
| `mkt_seckill_item.stock` 终态 | 0 | 0 | ✅ 不超卖 |
| Redis 预扣库存终态 | 0 | 0 | ✅ 一致 |
| `sold / total` | 200 / 200 | 200 / 200 | ✅ 完全卖出 |
| 一人一单（去重用户数） | **200 单 / 200 用户** | **200 单 / 200 用户** | ✅ 均无用户重复成单 |
| 队列 pending | — | **0** | ✅ 消息全部消费确认 |

两组的订单可以用 `oms_order.request_id` 精确区分 —— 同步模式传入 `null`，异步模式传入队列消息里的 UUID。所以「异步落库的订单是否真的带上了幂等键」也可以直接查证：

```
SELECT order_no, request_id FROM oms_order WHERE request_id IS NOT NULL LIMIT 2;
GM202610071932190000022297    8b1c4e6cc8b34ad2bc2f030ff8614848
```

> 复核时需排除压测前的两条冒烟订单（`GM202610071930440000019802`、`GM202610071932000000017557`）：它们与 VU 1 用的是同一账号，不排除会得出「有用户重复下单」的错误结论 —— 这正是本次复核中真实踩到的坑。

### 2.3 落库吞吐（关键的反直觉结论）

| 指标 | A 组（同步） | B 组（削峰） |
| --- | --- | --- |
| 落库方式 | 200 个请求经 `seckillExecutor` 并发落库 | 4 个消费线程从队列拉取落库 |
| 200 单实际耗时 | 约 **5.0 s** | 约 **6.69 s** |
| **落库吞吐** | **≈ 40 单/秒** | **≈ 29.9 单/秒** |
| 队列是否积压 | — | 压测期间短暂积压，压测后 ~7s 内排空 |

**吞吐没有提升，反而略降。** 原因不是削峰做错了，而是：

1. 单热点 SKU 的瓶颈是**数据库行锁串行**（`pms_product.stock >= qty` 条件扣减 + 唯一索引），与「请求从哪来」无关；
2. B 组默认只用 4 个消费线程，而 A 组有 `seckillExecutor` 的 64 个核心线程在并发提交 —— **并行度不同**，这也说明消费线程数是可调项；
3. 把消费者线程数调大能提升，但**上限由 DB 决定**：调到远超 DB 承载，只是把雪崩点从 Tomcat 平移到数据库。

---

## 三、三个结论

**① 削峰确实生效，且幅度可观**：用户侧 P99 从 1880ms 降到 320ms（↓83%）。收益来自「把耗时最长的 DB 落库从请求线程移走」。

**② 削峰不提升吞吐**：落库吞吐 40 单/秒 → 29.9 单/秒。要真正提吞吐，得靠**批量落库**（一个事务建 N 单）或**库存分桶**（把热点行锁拆成 N 个独立行锁）—— 这是两件不同的事，不能混为一谈。

**③ 正确性没有因为异步而受损**：两组都恰好建出 200 单、库存归零、一人一单、队列 pending 归零。异步引入的重复投递风险由「结果终态 + `uk_user_request` 唯一索引」双重兜住（已有集成测试覆盖崩溃重投场景）。

---

## 四、必须说清的代价

**用户拿到订单号的时间反而变长了。** 本报告的 P99 ↓83% 是「受理耗时」，而端到端（点击 → 拿到订单号）需要额外等待：

```
抢购受理（~177ms）  →  排队等待消费者落库（取决于队列积压）  →  轮询到 SUCCESS
```

压测数据显示，200 单在队列里最多积压约 6.7 秒才排空。也就是说**最坏情况下用户要等几秒并轮询若干次**才能看到订单号。

这是「可用性 / 吞吐」与「即时确定性」之间的取舍，只能靠**告知用户**来缓解：

- 接口返回的是「排队中」而不是失败，前端必须展示排队状态而不是转圈；
- 需要配套结果查询接口 `GET /api/v1/seckill/result/{requestId}`（已实现，并已按归属校验防越权）；
- 削峰更适合「**瞬时脉冲远超系统能力**」的场景（秒杀正是如此）；若队列持续积压不降，说明消费能力不足，此时削峰只会把用户等待从「同步超时」变成「排队无期」。

---

## 五、本次压测的局限（避免过度解读）

1. **单机环境**：压测机与两个 JVM（8080 开发实例 + 8081 压测实例）同机，存在 CPU 争抢；A 组与 B 组受到的干扰不完全相同，绝对数值会有噪声。
2. **限流关闭**：为隔离变量而关闭，因此本报告**不能**用来评估开限流后的端到端表现。
3. **消费者线程数固定为默认的 4**：未做「消费者线程数 × 落库吞吐」的扫描，因此「29.9 单/秒」只是该配置下的实测值，不代表异步方案的吞吐上限。
4. **未测多实例**：单实例下验证。多实例（多个消费者进程共享消费者组）才是削峰真正发力的场景，也是下一步值得补的验证。
5. **未测长稳**：压测仅数秒级脉冲，未验证长时间持续下的队列滞后与内存增长（`XADD` 已带近似 `MAXLEN` 裁剪，但未经长时间观察）。

## 六、复现方式

```bash
# 1. 起一个独立实例（不动开发用的 8080），限流关闭以隔离变量
cd backend
mvn -o dependency:build-classpath -Dmdep.outputFile=/tmp/cp.txt -q
nohup java -cp "target/classes:$(cat /tmp/cp.txt)" com.geekmall.GeekMallApplication \
  --server.port=8081 --mall.rate-limit.enabled=false --mall.seckill.async.enabled=false \
  > /tmp/app-sync.log 2>&1 &

# 2. 刷新压测账号 token（有效期仅 2 小时，过期会导致整轮压测全是 401）
BASE_URL=http://localhost:8081 python3 loadtest/scripts/prepare_data.py 1000
python3 loadtest/scripts/gen_k6_users.py loadtest/data/users.csv loadtest/k6/data/users.js 1000

# 3. 重置秒杀库存与一人一单标记
docker exec geek-mall-mysql mysql -uroot -proot -N geek_mall \
  -e "UPDATE mkt_seckill_item SET stock=200,total=200,sold=0,not_start=0 WHERE id=1;"
docker exec geek-mall-redis redis-cli SET mall:seckill:stock:1 200
docker exec geek-mall-redis redis-cli DEL mall:seckill:bought:1

# 4. 压测（记录压测前后 oms_order 行数，增量即建单数）
BASE_URL=http://localhost:8081 ITEM_ID=1 VUS=200 ITERATIONS=100 \
  k6 run --summary-export=loadtest/results/k6-seckill-sync.summary.json \
  --summary-trend-stats="avg,min,med,max,p(50),p(90),p(99)" loadtest/k6/seckill.js

# 5. 切换为削峰模式后重复 2~4（把 async.enabled 改为 true）
```

原始结果：`loadtest/results/k6-seckill-sync.summary.json`、`loadtest/results/k6-seckill-async.summary.json`
