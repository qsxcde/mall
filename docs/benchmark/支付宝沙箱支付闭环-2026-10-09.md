# 支付宝沙箱支付闭环（P1-2）

> 对应 `docs/planning/校招面试视角的项目完善建议.md` 的 **P1-2：支付 mock → 沙箱闭环**。
> 把支付从「点一下『我已支付』」做成 **验签 → 回调幂等 → 金额与订单状态校验 → 关单转退款** 的完整闭环，
> 并补上 **主动查单补偿**。

## 一、结论速览

| 项 | 结果 |
| --- | --- |
| 渠道 | 支付宝沙箱**当面付**（`alipay.trade.precreate` 返回 `qr_code`） |
| 签名 | **手写 RSA2**（纯 JDK：`Signature("SHA256withRSA")` + `Base64`），**零新增 Maven 依赖** |
| HTTP | JDK 原生 `java.net.http.HttpClient`（不引 okhttp） |
| 渠道切换 | `mall.payment.channel=local \| alipay`；**默认 local**，零配置可启动 |
| 本地验证 | `PaymentSandboxIntegrationTest` **10/10**（走完整验签链路） |
| 真联调 | 需你的沙箱密钥 + 公网隧道（步骤见 §五） |

## 二、设计要点

### 2.1 渠道抽象

`PaymentChannelClient` 收敛五个动作：`prepay` / `query` / `close` / `refund` / `verifyNotify`。

- `LocalSandboxChannel`（默认，`matchIfMissing=true`）：进程内自生成 RSA 密钥对，**用与支付宝相同的 RSA2 算法自签自发**。
  因此本地跑的不是"假流程"，而是真实的「验签 → 幂等 → 校验 → 退款」链路，只是不产生网络与资金。
- `AlipaySandboxChannel`（`mall.payment.channel=alipay`）：JDK HttpClient 调网关，包在
  `ResilienceGuard.execute("alipay", ...)` 下（网关慢/挂时尽快熔断）。

### 2.2 回调四件事

| 环节 | 实现 |
| --- | --- |
| **验签** | `AlipaySigner.verify`：剔除 `sign`/`sign_type`/空值 → 字典序 → `k=v&` → `SHA256withRSA`。**验签之外还校验 `app_id`（配了 `seller-id` 再校验 `seller_id`）** —— 签名只证明报文没被改，不证明这笔钱打给了你 |
| **幂等** | `pay_payment_record` 的 `update ... where status != 1` 是**唯一落账判定**；回调与主动查单都收敛到 `applySuccess`，并发下只有一个能成功 |
| **校验** | 金额必须与支付单一致（`BigDecimal.compareTo`，容忍 `159.0` / `159.00`） |
| **驱动订单 / 退款** | `TradeService.applyPayment` 返回 `APPLIED` 或 `ORDER_CLOSED`；后者转 `PaymentRefundService` 退款 |

**应答体必须是裸文本 `success` / `failure`**（支付宝的约定），返回 `Result` JSON 会被判失败并无限重试；
因此回调方法 **永不向外抛异常**，异常一律 catch 后返回 `failure`。

### 2.3 关单转退款（三个触发点）

1. 回调到达时订单已被关闭（超时/取消的竞态）
2. 用户取消一笔**已支付**订单
3. 商家关闭一笔**已支付**订单

退款幂等两层闸门：`pay_payment_record.refund_status` 的 `0→1` CAS（唯一闸门）+ `pay_refund_record.refund_no` 唯一索引；
`refund_no` 同时作为支付宝 `out_request_no`，交给渠道做二次幂等。

### 2.4 主动查单补偿

`PayQueryCompensationJob`（`@Scheduled` + `@SchedulerLock`，多实例只跑一个）扫「待支付且创建满 1 分钟」的支付单，
调 `alipay.trade.query` 兜底对账 —— **渠道通知会丢**（网络抖动/重启/重试耗尽），这是唯一能把"用户已付款但系统仍是待支付"捞回来的手段。

## 四、本地验证结果（`PaymentSandboxIntegrationTest` 10/10）

| 用例 | 断言 |
| --- | --- |
| 创建支付单 | 返回可渲染的二维码；渠道 = `local` |
| 同订单重复创建 | 复用同一张支付单（防"多张可付订单，用户付两笔"） |
| 验签通过的通知 | 订单 → 待发货；`channel_trade_no` 落库 |
| **签名被篡改** | 应答 `failure`；订单与支付单均不变 |
| **金额被篡改**（签名有效） | 应答 `failure`；订单仍待付款 |
| `WAIT_BUYER_PAY` 中间态 | 不改状态，但应答 `success`（否则渠道无限重推） |
| `TRADE_CLOSED` | 支付单置为已关闭 |
| 未知 `out_trade_no` | 应答 `success`（避免渠道无意义重试） |
| **订单先取消、通知后到** | 自动退款：`refund_status=2`、退款单落库；重复通知只产生一张退款单 |
| 已支付订单被用户取消 / 被商家关闭 | 均触发退款 |
| 补偿任务跑两遍 | 只落账一次（第二次返回 0） |

## 五、真沙箱联调步骤（需你提供密钥 + 隧道）

1. 把密钥写进 `infra/.env`（已 gitignore）：
   ```
   MALL_PAYMENT_CHANNEL=alipay
   MALL_ALIPAY_APP_ID=<沙箱 appId>
   MALL_ALIPAY_PRIVATE_KEY=<应用私钥，PKCS#8 或 PKCS#1，可带 PEM 头尾>
   MALL_ALIPAY_PUBLIC_KEY=<支付宝公钥，注意不是应用公钥>
   MALL_ALIPAY_SELLER_ID=<可选，收款方 PID>
   MALL_ALIPAY_NOTIFY_URL=https://<你的隧道域名>/api/v1/pay/callback
   ```
   `application-dev.yml` 已配置 `spring.config.import: optional:file:../infra/.env[.properties]`，
   因此从 `backend/` 目录 `java -jar` 启动时会自动读取，**无需手动 export**。
2. 启动后端 → 前端下单 → 进入支付页 → 调 `/api/v1/pay/create` 应返回真实 `qr_code`（形如 `https://qr.alipay.com/...`）。
3. 用**沙箱版支付宝 App** 扫码付款。
4. 观察：
   - 隧道是否收到 `POST /api/v1/pay/callback`（表单）；
   - 后端日志是否出现 `[支付回调]` 且无"验签失败"；
   - 订单是否从待付款变为待发货；
   - `pay_payment_record.channel_trade_no` 是否落库。
5. 若回调没到，前端点「我已完成支付」或等补偿任务（默认 60s 一轮）→ 走主动查单落账。

## 六、过程中修掉的真问题（比"功能可用"更值钱）

1. **退款是同步模型，不是异步回调**：`alipay.trade.refund` 的结果在 HTTP 响应里，支付宝**不支持退款专属 notify_url**。
   最初的设计按"退款回调"做是错的。
2. **`trade_status` 没有"支付失败"这个通知态**：只有 `WAIT_BUYER_PAY` / `TRADE_SUCCESS` / `TRADE_FINISHED` / `TRADE_CLOSED`。
   "非成功即置失败"会误伤 `WAIT_BUYER_PAY` 中间态，并让渠道无限重推。
3. **`closeExpiredOrders` 会因并发支付整批回滚**：原实现在一个事务里循环关闭，某笔订单被并发支付导致状态机抛异常时，
   会**把整批（含其它已关闭订单的库存回补）一起回滚**。已改为逐单独立事务 + try/catch。
4. **`markPaid` 遇到已关闭订单抛异常** → 支付域事务回滚 → 退款永不触发。已改为 `applyPayment` 返回 `ORDER_CLOSED` 信号。
5. **用户取消已支付订单没有退款兜底**：商家关闭有、用户取消没有，两处都补上了。
6. **网络调用必须在事务外**：`create`（预下单）/ 退款（渠道调用）都刻意不加 `@Transactional`，
   否则会在事务里发起 HTTP、长时间持有数据库行锁。
7. **PKCS#1 私钥兼容**：纯 JDK 只能解析 PKCS#8，支付宝密钥工具导出的"非 Java 格式"是 PKCS#1，
   已实现自动包装成 PKCS#8（含单测）。

## 七、已知取舍

- **不做响应验签**：支付宝响应签的是响应节点**原始 JSON 子串**，Jackson 反序列化再序列化会破坏字节一致性。
  若要做，需保留原始响应子串再验。
- **只做全额退款**：因此 `refund_no` 可以确定化为 `"RF" + tradeNo`（一单一退）。部分退款需要每次退款一个独立 `out_request_no`。
- **`payMethod` 与 `channel` 未完全解耦**：`mall.payment.channel` 是全局单 bean，而 `pay_method` 有 4 种取值；
  非 `alipay` 的支付方式也走同一渠道。当前是演示取舍，已在 `payment/package-info.java` 记录。
