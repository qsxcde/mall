# 支付宝沙箱支付闭环（P1-2）

> 对应 `docs/planning/校招面试视角的项目完善建议.md` 的 **P1-2：支付 mock → 沙箱闭环**。
> 把支付从「点一下『我已支付』」做成 **验签 → 回调幂等 → 金额与订单状态校验 → 关单转退款** 的完整闭环，
> 并补上 **主动查单补偿**。

## 二、设计要点

### 2.1 渠道抽象

`PaymentChannelClient` 收敛五个动作：`prepay` / `query` / `close` / `refund` / `verifyNotify`。

- `LocalSandboxChannel`（默认，`matchIfMissing=true`）：进程内自生成 RSA 密钥对，**用与支付宝相同的 RSA2 算法自签自发**。
  因此本地跑的不是"假流程"，而是真实的「验签 → 幂等 → 校验 → 退款」链路，只是不产生网络与资金。
- `AlipaySandboxChannel`（`mall.payment.channel=alipay`）：JDK HttpClient 调网关，包在
  `ResilienceGuard.execute("alipay", ...)` 下（网关慢/挂时尽快熔断）。

### 2.2 回调四件事

| 环节 | 实现 |
| --- | --- |
| **验签** | `AlipaySigner.verify`：剔除 `sign`/`sign_type`/空值 → 字典序 → `k=v&` → `SHA256withRSA`。**验签之外还校验 `app_id`（配了 `seller-id` 再校验 `seller_id`）** —— 签名只证明报文没被改，不证明这笔钱打给了你 |
| **幂等** | `pay_payment_record` 的 `update ... where status != 1` 是**唯一落账判定**；回调与主动查单都收敛到 `applySuccess`，并发下只有一个能成功 |
| **校验** | 金额必须与支付单一致（`BigDecimal.compareTo`，容忍 `159.0` / `159.00`） |
| **驱动订单 / 退款** | `TradeService.applyPayment` 返回 `APPLIED` 或 `ORDER_CLOSED`；后者转 `PaymentRefundService` 退款 |

**应答体必须是裸文本 `success` / `failure`**（支付宝的约定），返回 `Result` JSON 会被判失败并无限重试；
因此回调方法 **永不向外抛异常**，异常一律 catch 后返回 `failure`。

### 2.3 关单转退款（三个触发点）

1. 回调到达时订单已被关闭（超时/取消的竞态）
2. 用户取消一笔**已支付**订单
3. 商家关闭一笔**已支付**订单

退款幂等两层闸门：`pay_payment_record.refund_status` 的 `0→1` CAS（唯一闸门）+ `pay_refund_record.refund_no` 唯一索引；
`refund_no` 同时作为支付宝 `out_request_no`，交给渠道做二次幂等。

### 2.4 主动查单（无回调通道时的主链路）

渠道通知会丢（网络抖动 / 服务重启 / 重试耗尽），因此主动查单不是"补充"而是**兜底与主链路的统一实现**。
它有三个入口，全部收敛到同一个 `queryAndApply`：

1. **查状态时顺带查**：前端每 3s 轮询 `/pay/{tradeNo}/status` → 触发一次节流后的查单（延迟 < 5s）。
   没有内网穿透时，这就是主链路。
2. **「我已完成支付」按钮**：立即主动查单一次。
3. **`PayQueryCompensationJob`**：`@Scheduled` + `@SchedulerLock`（多实例只跑一个），
   默认 15s 一轮，扫「待支付且创建满 60s」的单。用户不在页面上时由它收敛。

三条入口共用 `status != 1` 的 CAS 落账判定，因此与回调并发也是安全的（只落账一次）。

| 用例 | 断言 |
| --- | --- |

| `WAIT_BUYER_PAY` 中间态 | 不改状态，但应答 `success`（否则渠道无限重推） |

| **回调与查单并发** | 两条入口同时到达只落账一次，不产生退款 |

## 五、真沙箱联调

支付宝有**两条**拿到支付结果的通道，二者幂等共存（共用同一个 `status != 1` 落账判定）：

| 通道 | 方向 | 需要公网？ |
| --- | --- | --- |
| 异步通知 `notify_url` | 支付宝 → 你 | ✅ 必须（才需要隧道） |
| **主动查单** `alipay.trade.query` | 你 → 支付宝 | ❌ 出站请求即可 |

因此**不搭内网穿透也能完整跑通**，此时主动查单是主链路。触发它的三个入口：

1. 前端每 3s 轮询 `/pay/{tradeNo}/status` → **顺带触发一次节流后的主动查单**（延迟通常 < 5s，见 `mall.payment.status-query.*`）
2. 前端点「我已完成支付」→ 立即主动查单一次
3. `PayQueryCompensationJob` 定时兜底（默认 15s 一轮）

> 注意：主动查单在「查状态」里做了两层保护 —— ① 只查待支付单；② 同一支付单
> `throttle-seconds`(5s) 内最多查一次（Redis `SET NX`）。否则一个用户开多个页面就能把网关打爆并误触发熔断。
>
> **刻意没有「创建满 N 秒」的前置过滤**：`create_time` 由数据库的 `CURRENT_TIMESTAMP` 生成并截断到秒，
> 而比较基准是 JVM 的 `now` —— 两者只要有毫秒级漂移（NTP 同步误差、容器时钟偏移），
> 刚写入的行就会「比现在还新」，让查单被**静默跳过**。真正需要的保护是节流，不是时间窗（见 §六.8）。
>
> 另：**不要用 `return_url`（支付后浏览器同步跳转）作为对账依据** —— 它只证明"用户浏览器到过这个地址"，
> 用户直接关浏览器就没有了，且可伪造。资金状态必须以服务端主动查单为准。

### 5.1 有公网隧道（回调为主，查单兜底）

1. `infra/.env`：
   ```
   MALL_PAYMENT_CHANNEL=alipay
   MALL_ALIPAY_APP_ID=<沙箱 appId>
   MALL_ALIPAY_PRIVATE_KEY=<应用私钥，PKCS#8 或 PKCS#1，可带 PEM 头尾>
   MALL_ALIPAY_PUBLIC_KEY=<支付宝公钥，注意不是应用公钥>
   MALL_ALIPAY_SELLER_ID=<可选，收款方 PID>
   MALL_ALIPAY_NOTIFY_URL=https://<隧道域名>/api/v1/pay/callback
   ```
2. 启动后端：推荐 `bash scripts/run-backend.sh`（显式加载 `infra/.env` 并回显生效的支付渠道）→ 下单 → 进入支付页，
   `/api/v1/pay/create` 应返回真实 `qr_code`（形如 `https://qr.alipay.com/...`）。
3. 沙箱版支付宝 App 扫码付款。
4. 观察：隧道是否收到 `POST /api/v1/pay/callback`（表单）；日志是否出现 `[支付回调]` 且无"验签失败"；
   订单是否转为待发货；`pay_payment_record.channel_trade_no` 是否落库。

### 5.2 无公网隧道（查单为主）

1. `infra/.env` 同 5.1，但 **`MALL_ALIPAY_NOTIFY_URL` 留空** —— 实现只在它非空时才向支付宝注册回调地址，
   因此不会产生支付宝侧的无意义重试。
2. 同样扫码付款。
3. 付款后：前端页面会在数秒内自动跳到「支付成功」（轮询驱动主动查单）；
   若用户不在页面上，补偿任务会在 15s 内收敛。
4. 想验证「回调丢失也能兜住」：付款后**不要**等前端轮询，直接查库或调 `compensatePending`，效果相同。

> 纯粹走查单时，`支付宝公钥` 只在验签（回调）时用到。启动校验目前仍要求它存在 ——
> 这是刻意的：将来补上隧道后就能直接启用回调，不用再改配置并重启。

## 六、过程中修掉的真问题（比"功能可用"更值钱）

1. **退款是同步模型，不是异步回调**：`alipay.trade.refund` 的结果在 HTTP 响应里，支付宝**不支持退款专属 notify_url**。
   最初的设计按"退款回调"做是错的。
2. **`trade_status` 没有"支付失败"这个通知态**：只有 `WAIT_BUYER_PAY` / `TRADE_SUCCESS` / `TRADE_FINISHED` / `TRADE_CLOSED`。
   "非成功即置失败"会误伤 `WAIT_BUYER_PAY` 中间态，并让渠道无限重推。
3. **`closeExpiredOrders` 会因并发支付整批回滚**：原实现在一个事务里循环关闭，某笔订单被并发支付导致状态机抛异常时，
   会**把整批（含其它已关闭订单的库存回补）一起回滚**。已改为逐单独立事务 + try/catch。
4. **`markPaid` 遇到已关闭订单抛异常** → 支付域事务回滚 → 退款永不触发。已改为 `applyPayment` 返回 `ORDER_CLOSED` 信号。
5. **用户取消已支付订单没有退款兜底**：商家关闭有、用户取消没有，两处都补上了。
6. **网络调用必须在事务外**：`create`（预下单）/ 退款（渠道调用）都刻意不加 `@Transactional`，
   否则会在事务里发起 HTTP、长时间持有数据库行锁。
7. **PKCS#1 私钥兼容**：纯 JDK 只能解析 PKCS#8，支付宝密钥工具导出的"非 Java 格式"是 PKCS#1，
   已实现自动包装成 PKCS#8（含单测）。
8. **「应用时钟 vs 数据库时钟」的静默跳过**（本轮最隐蔽的一个）：
   `create_time` 由数据库的 `CURRENT_TIMESTAMP` 生成并截断到秒，而「创建满 N 秒」的比较基准是 JVM 的 `now`。
   两者只要有毫秒级漂移（NTP 同步误差、容器时钟偏移都会造成），**刚写入的行就会「比现在还新」**，
   于是 `create_time < now - 0s` 不成立 —— 主动查单与补偿扫描双双**静默跳过**这笔单，表现为「偶发不落账」。
   - 修法一：查单路径**去掉时间窗前置过滤**，只靠 Redis 节流（真正需要的保护）；
   - 修法二：补偿窗口的「创建满 N 秒」判据从 `<` 改成 `<=`（「满 N 秒」本就该含等号），
     并让测试以生产同款窗口（60s）+ 回拨创建时间来构造场景，而不是把窗口调成 0 贴在时钟边界上。
   - 教训：**凡是「由数据库生成的时间戳」与「应用生成的当前时间」做比较，都要留出容差或统一时钟源。**

9. **`sign_type` 必须参与签名（本轮唯一导致真联调失败的错误，且与网上流传的文档相反）**：
   大量文章（以及我最初的实现）写「除去 `sign`、`sign_type` 两个参数」。但真联调时网关直接回了
   `isv.invalid-signature`，并**把它的待验签串原样打印出来**：

   ```
   ...&method=alipay.trade.precreate&sign_type=RSA2&timestamp=2026-10-09 13:53:12&version=1.0
   ```

   与我们签的串**只差 `sign_type=RSA2&` 这一段** —— 剔除它必然验签失败。
   改成「只剔除 `sign`、保留 `sign_type`」后，立刻返回了真实 `qr_code`。
   教训：**协议细节以服务器实际回显为准，不要凭记忆**；而且这类错误的信息就藏在错误码里。

10. **熔断器不应统计业务返回码**：主动查单遇到 `ACQ.TRADE_NOT_EXIST`（交易还没创建/尚未支付，
    是**完全正常的业务态**）时，最初它经由 `callGateway` 抛出、被 `ResilienceGuard` 记为一次下游失败 ——
    持续下去会把熔断器打开。已把「取 code 判成败」这一步**移出熔断保护范围**：
    熔断只统计连不上/超时/HTTP 非 200/响应不可解析这类基础设施故障。

11. **密钥配好了但渠道开关没切**（本次联调的乌龙）：`mall.payment.channel` 默认 `local`，
    填好密钥却忘了改这个开关时，程序会安静地继续走本地模拟渠道。
    已加 `PaymentConfigValidator`：启动时若检测到「密钥齐备但渠道仍是 local」就打 WARN。


## 七、已知取舍

- **不做响应验签**：支付宝响应签的是响应节点**原始 JSON 子串**，Jackson 反序列化再序列化会破坏字节一致性。
  若要做，需保留原始响应子串再验。
- **只做全额退款**：因此 `refund_no` 可以确定化为 `"RF" + tradeNo`（一单一退）。部分退款需要每次退款一个独立 `out_request_no`。
- **`payMethod` 与 `channel` 未完全解耦**：`mall.payment.channel` 是全局单 bean，而 `pay_method` 有 4 种取值；
  非 `alipay` 的支付方式也走同一渠道。当前是演示取舍，已在 `payment/package-info.java` 记录。

### 启动方式（本次结论）

用 `scripts/run-backend.sh`，它把 `infra/.env` 显式 `source` 成真实环境变量，
并回显生效的支付渠道 —— 「密钥填了但渠道开关还是 local」是本轮真实踩过的坑（见 §六.11）。

> `application-dev.yml` 里仍保留了 `spring.config.import: optional:file:../infra/.env[.properties]`，
> 但从**其它工作目录**启动时相对路径会失效且被 `optional:` 静默跳过；用脚本启动可规避这一不确定性。
