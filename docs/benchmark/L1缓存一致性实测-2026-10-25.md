# L1 本地缓存一致性实测（本机 · 2026-10-25）

> 补上 `多实例部署验证-2026-10-08.md` 与 `Redis Stream 消费组多实例验证-2026-10-25.md` 留下的最后一块空白：
> **本地 Caffeine L1 在多实例下到底会造成多长的「读到旧值」窗口**。
> 验证方式：3 实例真实 Docker 部署 + 5 组对照实测，全部由 `loadtest/scripts/verify_cache_l1.py` 产出。

---

## 〇、先说结论

**白名单收窄足够，不需要加跨实例失效广播。**

实测的陈旧窗口**严格等于「写时刻本地 L1 的剩余 TTL」**，上界就是 `mall.cache.local.ttl`（默认 3s），
而且随这个旋钮线性缩放（3s → 窗口 2.9s；1s → 窗口 0.97s）。价格敏感的 `productDetail` 不在白名单里，
改价后**全局 5~17ms 内可见**。因此当前「L1 只放能容忍数秒陈旧的聚合类数据」的边界是成立的、可证的。

代价是明确的：**改价后其它实例最长约 3 秒还看得到旧的首页/分类**。这在聚合页场景可接受，
但它必须写在文档里，不能只留在代码注释里。

---

## 一、测量口径（先定义，再测量）

- **t0**：改价请求（经实例 A）HTTP 响应返回的时刻 = 事务已提交
- **t1**：实例 B 首次读到新价的时刻，轮询粒度 50ms
- **W = t1 − t0**：陈旧窗口；另记 **W_start = t1 − 请求发起时刻** 作参考
- **上界命题**：`W ≤ 写时刻的剩余 L1 TTL ≤ mall.cache.local.ttl`
  —— 成立的前提是 L1 用 `expireAfterWrite`（读不续期），所以持续读不会把旧值「续命」
- 每轮之间等 `ttl + 0.5s` 让 L1 彻底过期，否则上一轮的填充时刻会污染本轮的「最坏情形」前提

触发方式：商家端 `POST /api/v1/merchant/product/batch-price`（`mode=amount`，每轮 +1 元），
在 `homeFloors` 的 `hotProducts[].price` 与 `/api/v1/products/{id}` 的 `price` 上观测变化。

## 三、结果：5 组用例

| 用例 | 覆盖 | 结果 |
| --- | --- | --- |
| **L1-1** 最坏情形窗口 | B 刚填满 L1 就立刻改价，10 轮 | ✅ 10/10，W ∈ [2.81, 2.99]s |
| **L1-2** 对照组（无 L1） | `productDetail` 同协议，10 轮 | ✅ 10/10，W ∈ [0.005, 0.017]s |
| **L1-3** 随机间隔分布 | warm 读与写之间随机 gap，20 轮 | ✅ 20/20，W+gap ∈ [2.86, 2.98]s |
| **L1-4** 写时高并发读 + 再缓存污染 | 3 实例 × 2 线程压测下改价，10 轮 | ✅ 10/10 收敛，缓存值 == DB 值 |
| **L1-5** TTL 缩放反证 | `mall.cache.local.ttl=1s` 重跑 L1-1 | ✅ W ≈ 0.97s，随旋钮缩放 |

### L1-1 最坏情形（ttl=3s）

```
轮次      gap     写耗时       W  W_start
1      0.00   0.039   2.910    2.948
2      0.00   0.013   2.957    2.971
3      0.00   0.049   2.815    2.863
...
10     0.00   0.028   2.991    3.018
W: n=10 min=2.81s P50=2.92s P95=2.99s max=2.99s
```

**读指标差值断言**（不靠观察猜）：B 侧 `mall_cache_hits_total{cache="homeFloors",level="local"}`
从 93 涨到 565（**+472**）—— 陈旧窗口期间读到的旧值**确实由 L1 提供**，不是别的路径。

### L1-2 对照组：价格敏感数据不进 L1（productDetail）

```
W: n=10 min=0.00s P50=0.01s P95=0.02s max=0.02s
B 侧 productDetail 本地命中 0 → 0（+0）  ✅ 未走 L1（与白名单一致）
```

改价后其它实例 **5~17ms** 就看到新价 —— 正好是一个轮询粒度，等价于「立即」。
这是白名单收窄**有效**的直接证据：`CacheProperties.Local#names` 把价格/库存敏感的
`productDetail`、`productRecommend` 挡在 L1 外，`@CacheEvict` 清的是共享 Redis，于是全局即时生效。

### L1-3 陈旧窗口 = 剩余 L1 TTL

随机化 warm 读与写之间的间隔，看 `W + gap` 是否恒定：

| gap | W | W+gap | | gap | W | W+gap |
| --- | --- | --- | --- | --- | --- | --- |
| 0.22 | 2.717 | 2.94 | | 2.16 | 0.731 | 2.89 |
| 0.43 | 2.501 | 2.93 | | 2.34 | 0.603 | 2.94 |
| 1.09 | 1.839 | 2.93 | | 2.64 | 0.320 | 2.96 |
| 1.27 | 1.640 | 2.91 | | 2.73 | 0.128 | 2.86 |
| 1.75 | 1.198 | 2.95 | | 2.95 | 0.008 | 2.96 |

20 轮 `W + gap ∈ [2.86, 2.98]s`，标准差极小 —— **陈旧窗口不是随机的，就是「L1 还剩多久过期」**。
gap 越长窗口越短，正好落在 `ttl − gap` 上。

### L1-4 长尾：再缓存污染检查

这条是唯一可能把窗口从 3s 放大到 **30 分钟** 的路径：若 `@CacheEvict` 跑在事务提交**之前**，
并发读可能在中间窗口重建出**提交前的旧值**并写回 Redis，还带上 5min(`homeFloors`) /
30min(`categoryTree`) 的新 TTL。

10 轮，每轮 3 实例 × 2 线程持续打读（写后继续压 5s），结果：

```
第 1 轮 新价=31.15 三实例=[8081:31.15, 8082:31.15, 8083:31.15] Redis缓存=31.15 DB=31.15  ✅
...
第 10 轮 新价=40.15 三实例=[8081:40.15, 8082:40.15, 8083:40.15] Redis缓存=40.15 DB=40.15  ✅
读压力：{8081: {ok: 5658, 429: 456}, 8082: {ok: 5660, 429: 466}, 8083: {ok: 5661, 429: 463}}
```

**10/10 轮三实例全部收敛、Redis 缓存值 == DB 值**，在约 1.7 万次并发读的压力下未观测到污染。
（429 是 `home-read` 本地限流额度分摊到每实例约 66/s 的正常拒绝，不影响结论。）

### L1-5 反证：窗口随 TTL 旋钮缩放

| `mall.cache.local.ttl` | W（3 轮） | 判定 |
| --- | --- | --- |
| 3s（默认） | 2.95 / 2.96 / 3.00 s | ✅ ≈ 3s |
| **1s** | 0.95 / 0.97 / 0.99 s | ✅ ≈ 1s |
| 3s（改回） | 2.95 / 2.96 / 3.00 s | ✅ 回到 ≈ 3s |

窗口跟着旋钮线性走 —— 证明上界**由 `mall.cache.local.ttl` 决定**，想收窄窗口就收窄 TTL，无需改代码。

## 四、结论：要不要加跨实例失效广播？

**不加。** 理由是三条同时成立：

1. **窗口有硬上界**，且等于一个显式配置项（`mall.cache.local.ttl`），不是隐式行为；
2. **价格敏感数据不在 L1 里**（L1-2 实测 5~17ms 全局可见），商家改价这类「必须尽快生效」的写已经不受 L1 影响；
3. **L1 里只剩聚合类数据**（首页楼层、分类树），本来就是「能容忍数秒陈旧」的，白名单注释里写明了这个取舍。

加广播（复用 `LoginSessionBroadcaster` 的 Redis Pub/Sub 模式）能把窗口压到毫秒级，
但代价是每次写都要多一次跨实例通信 + 一套失效协议的正确性维护，**对这两类数据换不到实际收益**。

**建议保留现状**，并把「改价后其它实例最长 3s 看到旧首页」这条已知取舍写进文档（本报告与 README 已写）。

## 五、仍未钉死的一个风险（留白）

`CacheConfig` **没有**用 `TransactionAwareCacheManagerProxy`，因此 `@CacheEvict` 相对**事务提交**的先后
取决于 Spring 的 advisor 顺序 —— 而 cache 与 tx 的 order 都是 `Ordered.LOWEST_PRECEDENCE`，**没有显式固定**：

- evict **晚于** commit（安全）：窗口上界就是 L1 TTL，本次实测的所有读数都与这一形态吻合；
- evict **早于** commit（危险）：并发读可能把提交前的旧值重新缓存并带长 TTL（见 L1-4）。

L1-4 在约 1.7 万次并发读 / 10 次写下未观测到污染，与「安全形态」一致，但**这毕竟是概率覆盖**——
真正的窗口只有亚毫秒级。若要彻底钉死，一个低成本改法是把缓存管理器包一层
`TransactionAwareCacheManagerProxy`，让失效明确推迟到提交之后。

**本次不改**（属于行为变更，不该混在实测里顺手做）。留作独立加固项，若后续要做，建议单独提交并补一条集成测试。

## 六、测试设计上踩到的坑

1. **陈旧窗口不能靠「看日志」测**，只能靠「写一个可识别的值 + 轮询读到新值的时刻」。
   本次用「价格 +1」当版本号：不引入额外字段，DB 里就是真值，收尾一条 SQL 复原。
2. **收尾读会被本地限流误伤**。`home-read` 是 LOCAL 层、额度按 instance-count 分摊到约 66/s/实例，
   压测线程正好把它打满，于是「检查三实例是否收敛」的那几次读会拿到 429 → 被误判成 `None` → 看起来像不收敛。
   改法：检查阶段暂停压测线程并等限流窗口（1s）排空。
   **第一版脚本就是这样误报了 3 轮「未收敛」，而那 3 轮的 Redis 缓存值其实都等于 DB 值。**
3. **Redis 缓存值不能直接 `json.loads` 后取字段**：缓存用 `GenericJacksonJsonRedisSerializer` +
   `DefaultTyping.NON_FINAL`，非 final 类型会被写成 `["java.util.ArrayList", [...]]` /
   `["java.math.BigDecimal", "30.15"]`，迭代前必须先剥类型壳。
4. **SQL 直改价格不会触发 `@CacheEvict`**，收尾复原后必须顺手清掉缓存 key，否则下一轮 warm 读拿到的是上一轮的陈旧价。

## 七、复现方式

```bash
# 1) 起 3 实例（默认 L1 TTL=3s）
docker compose -f infra/docker-compose.yml -f infra/docker-compose.multi.yml up -d

# 2) 跑全部用例（L1-1 ~ L1-4，约 6 分钟）
python3 loadtest/scripts/verify_cache_l1.py

# 3) L1-5 反证：TTL 改成 1s 后只跑 L1-1
MALL_CACHE_LOCAL_TTL=1s docker compose -f infra/docker-compose.yml \
  -f infra/docker-compose.multi.yml up -d
python3 loadtest/scripts/verify_cache_l1.py --only l1-1 --rounds 3 --ttl 1
```

单用例：`--only l1-1|l1-2|l1-3|l1-4`；轮数：`--rounds N`；不复原价格：`--skip-restore`。

## 八、局限

- 单机、本机回环网络，3 实例同宿主机 —— 跨主机网络抖动未覆盖
- 陈旧窗口的测量分辨率是轮询粒度 50ms
- `categoryTree`（L1 白名单另一项）**没有独立内容变更接口**，本次通过 `homeFloors` 覆盖了同一套 L1 机制；
  两者共享 `mall.cache.local.ttl`，但 `categoryTree` 的 Redis TTL 是 30min，若发生「旧值被重新缓存」，
  后果比 `homeFloors`（5min）更久 —— 这也是 L1-4 要单独看 Redis 缓存值的原因
- L1-4 对「evict 早于 commit」是**概率覆盖**（约 1.7 万次读 / 10 次写），不是确定性证明，见第五节
