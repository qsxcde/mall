# 商品搜索容量边界实测（LIKE 全表扫描）

> 实测日期：2026-10-17
> 环境：单机，MySQL 8.0（容器，:3307）、后端 Spring Boot（本机 :8080）、k6 未参与（单次串行测量）
> 目的：为「是否需要引入 Elasticsearch」给出**量化依据**，而不是凭感觉判断。

---

## 一、结论摘要

| 数据量 | 表体积 | 无匹配关键词 | 低频词（2 条命中） | 高频词（13 万条命中） |
| --- | --- | --- | --- | --- |
| 20 万 | ~100 MB | **135 ms** | 355 ms | 129 ms |
| 50 万 | ~246 MB | **447 ms** | 2,891 ms | 887 ms |
| 100 万 | **479 MB** | **1,062 ms** | **5,560 ms** | 914 ms |

> 测量口径：单次串行请求，每组 5 次取均值；测量前执行 `ANALYZE TABLE` 更新统计信息。
> 延迟为**后端接口端到端**（含 HTTP、参数解析、SQL、序列化），与纯 SQL 层耗时交叉验证一致。

**核心结论：**

1. **MySQL `LIKE '%kw%'` 在 100 万行时最坏情况 5.5 秒**，已完全不可接受（一般搜索 SLA 要求 P99 < 500ms）。
2. **增长不是线性的**：20 万→100 万（5 倍数据），最坏情况 355ms→5560ms（**15.7 倍**），因为数据量超出 buffer pool 后开始大量磁盘 IO。
3. **低频词比高频词慢得多**（5,560ms vs 914ms）——这是最容易误判的陷阱，见第二节。
4. **并发下进一步恶化且无扩展性**：3 并发 8.8s、6 并发 11.1s，延迟随并发线性上涨，见第二节之二。

## 二、关键发现：LIMIT 提前终止陷阱

### 现象

在 100 万行下，同样的 SQL：

| 关键词 | 命中数 | 耗时 |
| --- | --- | --- |
| 华为 | 138,384 | **914 ms** |
| iPhone | 2 | **5,560 ms** |

命中多的反而快 6 倍。

### 根因

后端查询带 `ORDER BY sales DESC LIMIT 8`：

```sql
SELECT * FROM pms_product
WHERE status=1 AND deleted=0
  AND (title LIKE '%iPhone%' OR brand_name LIKE '%iPhone%' OR category_name LIKE '%iPhone%')
ORDER BY sales DESC LIMIT 8
```

MySQL 选择 `idx_sales` 做反向索引扫描：

- **高频词**：沿 `idx_sales` 从高销量往下扫，很快凑满 8 条 → 提前终止 → 914ms
- **低频词**：沿索引扫完 100 万行也凑不满 8 条 → **必须全表扫完** → 5560ms

`EXPLAIN` 显示两者的执行计划**完全一致**（`key: idx_sales`, `rows: 16`, `Backward index scan`），这正是它容易被忽略的原因——**执行计划看起来没问题，但实际扫描量差了几个数量级**。

### 影响

这意味着：

- ❌ **不能只用高频词做压测**，会严重低估真实成本
- ✅ **压测必须包含「无匹配」和「低频词」场景**，它们才是最坏情况
- ⚠️ 真实用户搜索大量是长尾低频词，所以**线上体验会比高频词测试结果差得多**

## 二之二、并发下的恶化：比单次延迟更致命

单次 5.5 秒已经不可接受，但**并发下的表现更差**。同样是低频词 `iPhone`（100 万行）：

| 并发数 | 实测耗时 |
| --- | --- |
| 1 | 5.56 s |
| 3 | **8.79 s** |
| 6 | **11.08 s** |

### 关键观察

1. **所有并发请求耗时几乎完全相同**（8.793 / 8.793 / 8.793）——说明它们**没有真正并行**，而是在排队争抢同一份 CPU 与磁盘 IO。
2. **延迟随并发线性恶化**，而不是保持稳定。健康系统的典型表现是「吞吐上升、单请求延迟基本不变」；这里是「吞吐不变、延迟线性上涨」。
3. 这意味着：**该接口没有任何水平扩展能力**。即使加到 6 个并发用户，每个用户都要等 11 秒。

### 为什么这决定性地否定了 MySQL 方案

若一个搜索接口在 6 并发下就要 11 秒：

- 单实例 Tomcat 120 线程，理论上几十个并发用户就会把线程池占满
- 由于是全表扫描，**占满的是 CPU 和 buffer pool**，会连带拖慢同实例的其它接口（详情、下单）
- 这不是「搜索慢一点」的问题，而是**搜索会拖垮整个单体应用**

Elasticsearch 在同样 100 万数据下，倒排索引命中是 O(1) 级别的词项查找，并发扩容几乎线性——这正是它存在的根本理由。

## 三、索引使用情况

### 现有索引

```sql
KEY idx_status (status)
KEY idx_status_hot_sales (status, is_hot, sales)
KEY idx_category (category_key, parent_key)
KEY idx_price (price)
KEY idx_sales (sales)
KEY idx_hot_new (is_hot, is_new)
```

**没有任何一个能支持 `LIKE '%kw%'`**——前置通配符使 B+ 树索引完全失效。

### EXPLAIN 实证

```
type: index, key: idx_sales, rows: 16, filtered: 1.49%
Extra: Using where; Backward index scan
```

`Using where` 表示：索引只用于满足排序（`ORDER BY sales`），**过滤条件全部在回表后逐行判断**。

## 四、如果要做优化，成本/收益排序

| 方案 | 100 万行预期 | 成本 | 适用性 |
| --- | --- | --- | --- |
| 现状：`LIKE '%kw%'` | 1,062 ~ 5,560 ms | — | ❌ 不可接受 |
| **MySQL 全文索引**（`FULLTEXT` + `ngram`） | 预计 50~200 ms | 1 天（含分词调优） | ✅ 中等规模够用 |
| **Elasticsearch** | 20~50 ms | 3~5 天（含双写一致性、降级、对账） | ✅ 大规模首选 |
| 前置 `LIKE 'kw%'`（仅前缀匹配） | 5~20 ms | 半天 | ⚠️ 只能搜开头，体验差 |

### Elasticsearch 的真实成本（不只是装一个容器）

必须配套：

1. **数据同步**：应用双写（易不一致）或 Canal/Debezium 订阅 binlog（项目当前无 CDC）
2. **降级路径**：ES 不可用时回落 MySQL（可复用现有 `ResilienceGuard`）
3. **对账任务**：定时比对 ES 文档数 vs MySQL 行数
4. **索引重建**：mapping 变更时的 reindex 流程

> 这四项的工作量约为「接入 ES」本身的 3 倍，且都是面试高频追问点。

## 五、建议

### 立即结论

- **100 万行是明确的临界点**：最坏 5.5s 不可接受，此时必须引入搜索引擎。
- **10 万行以内**（62ms/135ms）MySQL `LIKE` 完全够用，**引入 ES 是过度设计**。
- **20~50 万行**（135~447ms）处于灰区，建议先用 MySQL 全文索引过渡。

### 如果要继续推进

1. 先用 `FULLTEXT` + ngram 做一版，测同一组关键词的对比数据
2. 拿到「MySQL 全文索引 vs ES」的实测差异，再决定是否上 ES
3. 压测脚本必须覆盖：高频词 / 低频词 / 无匹配 / 多关键词 AND

## 六、复现方式

```bash
# 生成指定规模数据（自动刷新布隆过滤器）
python3 loadtest/scripts/gen_mock_products.py --count 1000000

# 更新统计信息（否则 EXPLAIN 的行数估计不准）
docker exec geek-mall-mysql mysql -uroot -proot geek_mall -e "ANALYZE TABLE pms_product;"

# 测量（注意 URL 编码中文）
K=$(python3 -c "import urllib.parse;print(urllib.parse.quote('iPhone'))")
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{time_total}s\n" \
    "http://localhost:8080/api/v1/products/search?keyword=$K&page=1&pageSize=8"
done
```

> ⚠️ 测量前建议重启后端或至少预热 JIT，首轮通常偏慢。
