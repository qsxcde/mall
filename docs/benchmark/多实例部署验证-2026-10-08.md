> 目的：把「多实例部署能力」从**设计宣称**变成**可复现的实测证据**。
> 起因：`planning/校招面试视角的项目完善建议.md` 把「多实例从未实测」列为 P0-1

## 一、环境与方法

| 项 | 取值 |
| --- | --- |
| 编排 | `infra/docker-compose.multi.yml`（overlay，叠加在 `infra/docker-compose.yml` 上） |
| 实例 | `app1/app2/app3`，宿主端口 **8081/8082/8083**，同挂 compose 网络 `geek-mall-net` |
| 关键配置 | `-Dmall.cluster.instance-count=3`、`MYSQL_POOL_SIZE=50`、`mall.rate-limit.enabled=true`、prod profile |
| 中间件 | MySQL 8.0（`max_connections=300`）、Redis 7，容器 `geek-mall-mysql` / `geek-mall-redis` |
| 启动 | 3 实例 **10s 内全部 health=UP**；启动日志均打印容量自检 |

启动日志（三个实例一致，证明 `instance-count` 已生效）：

```
c.g.c.c.ClusterCapacityReporter - [容量] 连接池评估通过：3 实例 × 50 连接/实例 = 150 ≤ max_connections 300
```

> 说明：这条日志印证了 `docs/benchmark/库存分桶实现分析.md` §2.4 的「**实例数 × 池 ≤ max_connections**」铁律
> 在代码里有自检实现（`common/cluster/ClusterCapacityReporter`）。用 prod 默认的 `MYSQL_POOL_SIZE=100`
> 时 3×100 会正好顶格 300，再加实例就超 —— 因此压测/多实例环境必须显式下调。

## 二、四项验证结果

| # | 验证项 | 方法 | 结果 |
| --- | --- | --- | --- |
| **V1** | 限流全局量 | 请求均匀打到 3 实例，统计放行/429 | ✅ 通过（见下两行） |
| V1a | 分布式限流不被实例数放大 | `auth-login`（DISTRIBUTED 10 次/60s，IP 维度）打 60 发 | **放行 10 / 429 × 50** —— 全局恰好 10，未变成 30 |
| V1b | 本地限流按实例数分摊 | `cart-items`（LOCAL 60 次/10s，USER 维度）打 180 发 | **放行 60 / 429 × 120** —— 60 = 每实例 20 × 3（若不分摊会是 180） |
| **V2** | 号段发号跨实例唯一 | 3 实例轮流向 300 个用户发秒杀请求建单 | ✅ 300 单、**300 个不同订单号**、0 次 `uk_order_no` 冲突 |
| **V3** | 缓存击穿互斥 | 清 `mall:cache:productDetail::1` 后，30 并发轮流打 3 实例 | ✅ 全局**回源重建 = 1**（其余命中），锁等待 18 次 |
| **V4** | ShedLock 定时任务单点 | 制造 5 笔过期待付款订单，观察哪个实例执行关闭 | ✅ 仅 `app3` 执行（`app1/app2` 各 0 次），5 笔订单全部关闭 |

### V1 详解：`instance-count` 是怎么起作用的

`RateLimitPolicy.effectiveLimit(instanceCount)`（`common/ratelimit/RateLimitPolicy.java`）：

```java
public int effectiveLimit(int instanceCount) {
    // DISTRIBUTED 层已是全局计数，不切分；LOCAL 层计数在进程内，按实例数分摊
    return tier == RateLimitTier.DISTRIBUTED ? limit : shard(limit, instanceCount);
}
/** 向上取整分摊，且至少保留 1（避免小额度被取整成 0，等于禁用接口） */
private static int shard(int configured, int instanceCount) {
    return instanceCount <= 1 ? configured
            : Math.max(1, (int) Math.ceil((double) configured / instanceCount));
}
```

- **LOCAL 层**（多数接口）：计数在进程内，N 个实例若不分摊总量会放大成 `配置值 × N`。声明 `instance-count=3` 后，
  `cart-items` 的 60 次/10s 被切成每实例 20 次 → 实测全局 60，**与单实例一致**。
- **DISTRIBUTED 层**（7 个防刷接口，走 Redis 全局计数）：本身不受实例数影响，`auth-login` 实测全局 10。

### V2 详解：Redis `INCRBY` 号段

`OrderNoGenerator` 一次 `INCRBY key 1000` 领取一段连续号，返回值是该段上界；N 个实例拿到的是
**互不重叠的区间**，区间内 `AtomicLong` 无锁自增，**每 1000 单才出网一次**。

- 首次压测（实例刚启动）：号段计数器 `18000 → 21000`，**恰好 +3000 = 3 实例各领 1 段**；
- 紧接着重复压测：计数器**不变**——本地号段还有余号，未触发新的 `INCRBY`（这正是号段缓存的设计，不是缺陷）；
- 两次都满足：300 单 300 个唯一订单号，`oms_order` 无 `uk_order_no` 冲突。

### V3 详解：跨实例互斥重建

`ResilientRedisCache.get(key, loader)` 在 L1 与 Redis 都未命中后走 `rebuildWithLock`：
`SET NX` 抢锁 → 抢到者双重检查后回源并写缓存 → 未抢到者轮询等待复用。

清掉 `productDetail` 的 Redis key 后 30 个请求同时打到 3 个实例，结果：

```
8081: 重建 +1   锁等待 +n    命中 +x
8082: 重建 +0   锁等待 +n    命中 +y
8083: 重建 +0   锁等待 +n    命中 +z
全局回源重建增量 = 1  ✅
```

若没有跨实例互斥，3 个实例会在同一瞬间各自回源一次（重建 = 3）。

### V4 详解：ShedLock 单点

两个定时任务（`OrderTimeoutJob`、`InventoryBucketReconcileJob`）均带 `@SchedulerLock`（Redis provider）。
验证手法：把 5 笔 `status=0`（待付款）订单的 `expire_time` 改为 1 小时前，等下一轮扫描。

```
t≈4s  出现锁: job-lock:default:orderTimeoutJob
各实例执行次数：app1=0  app2=0  app3=1
订单状态：status=5（已取消）由 11 → 16（+5 笔）
```

**锁存在 + 只有一个实例执行 + 订单恰好关闭一次**，三者共同证明定时任务在多实例下是单点执行的。

## 三、验证过程中发现的三个边界（比"通过"更有价值）

1. **击穿互斥只覆盖 `productDetail` 一个缓存**。
   `ResilientRedisCache` 的互斥路径只在 `Cache#get(key, Callable)` 被调用时才生效，即 `@Cacheable(sync = true)`。
   全项目只有 `ProductServiceImpl.productDetail` 标了 `sync = true`；
   `homeFloors`、`categoryTree`、`productRecommend` 都是普通 `@Cacheable`（走 `get` + `put`），
   **不享受跨实例互斥**——热点 key 失效时 N 个实例会各自回源一次。
   → 若要声称"缓存三防护击穿"，需要把这几处也改成 `sync = true`。

2. **缓存 key 里含空格**：`mall:cache:homeFloors::SimpleKey []`（Spring `SimpleKey` 的 `toString`）。
   运维/清理脚本若用 `redis-cli --scan | xargs redis-cli del`，**会因空白切分而删不掉**，必须整体作为一个参数传。

3. **本地 L1 不在失效广播范围内**：`ResilientRedisCache.clear()` 只能清掉本实例 L1，
   其他实例最长继续服务 `mall.cache.local.ttl`（默认 3s）。这是刻意的取舍（L1 白名单只放"能容忍数秒陈旧"的聚合数据），
   但要知道其边界。

## 四、复现方式

```bash
# 1) 中间件
docker compose -f infra/docker-compose.yml up -d

# 2) 构建后端镜像（Dockerfile 只 COPY 现成 jar）
cd backend && mvn -DskipTests package
docker build -t geek-mall-server:1.0.0 .

# 3) 起 3 实例（overlay）
docker compose -f infra/docker-compose.yml -f infra/docker-compose.multi.yml up -d app1 app2 app3

# 4) 验证 V1 / V2 / V3（V4 需要制造过期订单，见 §二）
python3 loadtest/scripts/verify_multi_instance.py

# 5) 停止
docker compose -f infra/docker-compose.yml -f infra/docker-compose.multi.yml down
```

> V2 需要先准备秒杀场景（库存/商品/Redis），否则会全部返回"已抢光"。

## 五、结论

- **限流**：`instance-count` 声明后，本地限流全局总量回到配置值（实测 60 = 20×3），分布式限流本就全局（实测 10）。
- **发号**：Redis 号段使 3 实例拿到的区间互不重叠，300 单零冲突。
- **缓存**：`sync=true` 的缓存实现了真正的跨实例互斥（重建 = 1）。
- **定时任务**：ShedLock 保证同一时刻只有一个实例执行。
- **附带收益**：发现"击穿互斥只覆盖 1/4 个缓存"这一真实边界 —— 这类"通过之后还能指出边界"的结论，
  比"全部通过"本身更能经受面试追问。
