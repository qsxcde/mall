> 目的：把「多实例部署能力」从**设计宣称**变成**可复现的实测证据**。
> 起因：`planning/校招面试视角的项目完善建议.md` 把「多实例从未实测」列为 P0-1

## 二、四项验证结果

| # | 验证项 | 方法 | 结果 |
| --- | --- | --- | --- |
| **V1** | 限流全局量 | 请求均匀打到 3 实例，统计放行/429 | ✅ 通过（见下两行） |
| V1a | 分布式限流不被实例数放大 | `auth-login`（DISTRIBUTED 10 次/60s，IP 维度）打 60 发 | **放行 10 / 429 × 50** —— 全局恰好 10，未变成 30 |
| V1b | 本地限流按实例数分摊 | `cart-items`（LOCAL 60 次/10s，USER 维度）打 180 发 | **放行 60 / 429 × 120** —— 60 = 每实例 20 × 3（若不分摊会是 180） |
| **V2** | 号段发号跨实例唯一 | 3 实例轮流向 300 个用户发秒杀请求建单 | ✅ 300 单、**300 个不同订单号**、0 次 `uk_order_no` 冲突 |
| **V3** | 缓存击穿互斥（4 个缓存） | 逐个清 key 后，30 并发轮流打 3 实例 | ✅ 四个缓存**回源重建均 = 1**、**等待超时 0 次** |
| **V4** | ShedLock 定时任务单点 | 制造 5 笔过期待付款订单，观察哪个实例执行关闭 | ✅ 仅 `app3` 执行（`app1/app2` 各 0 次），5 笔订单全部关闭 |

### V1 详解：`instance-count` 是怎么起作用的

`RateLimitPolicy.effectiveLimit(instanceCount)`（`common/ratelimit/RateLimitPolicy.java`）：

```java
public int effectiveLimit(int instanceCount) {
    // DISTRIBUTED 层已是全局计数，不切分；LOCAL 层计数在进程内，按实例数分摊
    return tier == RateLimitTier.DISTRIBUTED ? limit : shard(limit, instanceCount);
}
/** 向上取整分摊，且至少保留 1（避免小额度被取整成 0，等于禁用接口） */
private static int shard(int configured, int instanceCount) {
    return instanceCount <= 1 ? configured
            : Math.max(1, (int) Math.ceil((double) configured / instanceCount));
}
```

- **LOCAL 层**（多数接口）：计数在进程内，N 个实例若不分摊总量会放大成 `配置值 × N`。声明 `instance-count=3` 后，
  `cart-items` 的 60 次/10s 被切成每实例 20 次 → 实测全局 60，**与单实例一致**。
- **DISTRIBUTED 层**（7 个防刷接口，走 Redis 全局计数）：本身不受实例数影响，`auth-login` 实测全局 10。

### V2 详解：Redis `INCRBY` 号段

`OrderNoGenerator` 一次 `INCRBY key 1000` 领取一段连续号，返回值是该段上界；N 个实例拿到的是
**互不重叠的区间**，区间内 `AtomicLong` 无锁自增，**每 1000 单才出网一次**。

- 首次压测（实例刚启动）：号段计数器 `18000 → 21000`，**恰好 +3000 = 3 实例各领 1 段**；
- 紧接着重复压测：计数器**不变**——本地号段还有余号，未触发新的 `INCRBY`（这正是号段缓存的设计，不是缺陷）；
- 两次都满足：300 单 300 个唯一订单号，`oms_order` 无 `uk_order_no` 冲突。

### V3 详解：跨实例互斥重建

`ResilientRedisCache.get(key, loader)` 在 L1 与 Redis 都未命中后走 `rebuildWithLock`：
`SET NX` 抢锁 → 抢到者双重检查后回源并写缓存 → 未抢到者轮询等待复用（最多 `waitTimeout` 800ms）。

四个缓存各清一次 key，再让 30 个请求同时打到 3 个实例：

| 缓存 | 是否有本地 L1 | 回源重建增量 | 锁等待 | 等待超时 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `categoryTree` | 是（需等 3s 过期） | **1** | 1 | **0** | ✅ |
| `homeFloors` | 是（需等 3s 过期） | **1** | 29 | **0** | ✅ |
| `productDetail` | 否 | **1** | 1 | **0** | ✅ |
| `productRecommend` | 否 | **1** | 19 | **0** | ✅ |

- 若没有跨实例互斥，3 个实例会在同一瞬间各自回源一次（重建 = 3）；
- `mall_cache_lock_timeout_total` **没有任何样本**，说明 29 个等待者全部在 800ms 内拿到了
  重建后的值 —— **既没有重复回源，也没有「等锁等超时再回源」的兜底**；
- 锁等待数为 1/19 的差异来自请求时序：后到的请求直接命中已填充的缓存，不进锁路径。

> 注：`sync = true` 是这条路径的开关。首轮验证时全项目只有 `productDetail` 标了它，
> 其余三个缓存是普通 `@Cacheable`（走 `get` + `put`，只有进程内锁）—— 见 §三.1，**现已补齐**。

### V4 详解：ShedLock 单点

两个定时任务（`OrderTimeoutJob`、`InventoryBucketReconcileJob`）均带 `@SchedulerLock`（Redis provider）。
验证手法：把 5 笔 `status=0`（待付款）订单的 `expire_time` 改为 1 小时前，等下一轮扫描。

```
t≈4s  出现锁: job-lock:default:orderTimeoutJob
各实例执行次数：app1=0  app2=0  app3=1
订单状态：status=5（已取消）由 11 → 16（+5 笔）
```

**锁存在 + 只有一个实例执行 + 订单恰好关闭一次**，三者共同证明定时任务在多实例下是单点执行的。

## 三、验证过程中发现的问题（2 已修复 / 2 待处理）

### 三.1 击穿互斥原本只覆盖 1/4 个缓存 —— **已修复** ✅

**发现**：`ResilientRedisCache` 的互斥路径只在 `Cache#get(key, Callable)` 被调用时才生效，即
`@Cacheable(sync = true)`。首轮验证时全项目只有 `ProductServiceImpl.cachedDetail`（`PRODUCT_DETAIL`）标了它；
`categoryTree`、`homeFloors`、`productRecommend` 都是普通 `@Cacheable`（走 `get` + `put`，只有进程内锁），
**多实例下热点 key 失效时 N 个实例会各自回源一次** —— 实测这三个缓存的 `rebuild` 计数确实为 0，
即互斥路径根本没被走到。

**修复**：给三者补上 `sync = true`（`ProductServiceImpl.categoryTree/homeFloors/recommend`）。
三者都不返回 null、也没有使用 `unless`/`condition`，因此与 `sync = true` 无冲突。
修复后四个缓存的实测结果见 §二 V3 表（重建均 = 1、超时 0）。

### 三.2 `homeFloors()` 对 `categoryTree()` 是自调用，导致分类缓存从未生效 —— **已修复** ✅

**发现**：`ProductServiceImpl.homeFloors()` 里 `vo.setCategories(categoryTree())` 属于**同类内自调用**，
不经过 Spring 缓存代理，因此**拿不到 `CATEGORY_TREE` 缓存** —— 每当 `HOME_FLOORS` 失效（5 分钟一次）
都会直接查库取分类树。同类中 `detail()` 已用 `selfProvider.getObject().cachedDetail(id)` 规避，`homeFloors` 没有。

**修复**：改为 `selfProvider.getObject().categoryTree()`（一行）。

**验证**（单实例，观察 `mall_cache_*{cache="categoryTree"}`）：

| 检查 | 操作 | 预期 | 实测 |
| --- | --- | --- | --- |
| A | 清空全部缓存 + 等 L1(3s) 过期 → 调一次 `/api/v1/home/floors` | `categoryTree` 回源重建 **+1**（修复前恒为 0，即根本不走缓存） | 0 → 1 ✅ |
| B | 先预热 `categoryTree`，再**只清** `homeFloors` → 调 `/api/v1/home/floors` | `categoryTree` 重建 **+0**、命中 **+1**（复用而非再查库） | 重建 1→1、命中 1→2 ✅ |

回归：`CacheGovernanceIntegrationTest` + `RateLimitIntegrationTest` + `AuthApiIntegrationTest`
+ `RateLimitPoliciesTest` + `ResilientRedisCacheTest` 共 **127 项全绿**。

### 三.3 ⚠️ 运维脚本清理缓存 key 会因空格失效 —— **待处理**

缓存 key 形如 `mall:cache:homeFloors::SimpleKey []`（Spring `SimpleKey` 的 `toString` **含空格**）。
用 `redis-cli --scan --pattern 'mall:cache*' | xargs redis-cli del` 时，`xargs` 按空白切分，
会把一个 key 拆成两个参数 → **删不掉且不报错**（实测返回删除 0 个）。
必须逐行精确删除（`redis-cli --scan ... | while read k; do redis-cli del "$k"; done`，
或整体作为单个参数传入）。

### 三.4 边界：本地 L1 不在跨实例失效范围内

`ResilientRedisCache.clear()` 只能清掉本实例 L1，其他实例最长继续服务 `mall.cache.local.ttl`（默认 3s）。
这是刻意的取舍（L1 白名单只放「能容忍数秒陈旧」的聚合数据），但要知道其边界 ——
所以 §二 V3 里对两个 L1 缓存必须**先等 4s** 再压，否则读到 L1 就测不到互斥。

## 四、复现方式

```bash
# 1) 中间件
docker compose -f infra/docker-compose.yml up -d

# 2) 构建后端镜像（Dockerfile 只 COPY 现成 jar）
cd backend && mvn -DskipTests package
docker build -t geek-mall-server:1.0.0 .

# 3) 起 3 实例（overlay）
docker compose -f infra/docker-compose.yml -f infra/docker-compose.multi.yml up -d app1 app2 app3

# 4) 验证 V1 / V2 / V3（V4 需要制造过期订单，见 §二）
python3 loadtest/scripts/verify_multi_instance.py

# 5) 停止
docker compose -f infra/docker-compose.yml -f infra/docker-compose.multi.yml down
```

> V2 需要先准备秒杀场景（库存/商品/Redis），否则会全部返回"已抢光"。

## 五、结论

- **限流**：`instance-count` 声明后，本地限流全局总量回到配置值（实测 60 = 20×3），分布式限流本就全局（实测 10）。
- **发号**：Redis 号段使 3 实例拿到的区间互不重叠，300 单零冲突。
- **缓存**：4 个缓存全部实现跨实例互斥重建（重建 = 1、等待超时 0）—— 首轮验证只覆盖 1 个，
  补齐 `sync = true` 后达标（见 §三.1）。
- **定时任务**：ShedLock 保证同一时刻只有一个实例执行。
- **附带收益**：验证过程中发现两处真实问题 —— ①「击穿互斥只覆盖 1/4 个缓存」（已修）；
  ②`homeFloors` 对 `categoryTree` 自调用导致该缓存从未生效（已修，见 §三.2）。
  这类"通过之后继续指出并修掉问题"的结论，比"全部通过"本身更能经受面试追问。
