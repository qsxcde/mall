## 〇、一句话结论（先给答案）

| 问题 | 结论 |
| --- | --- |
| 是否需要在**另一台机器**上重做压测？ | **需要**，但只针对"要出可引用容量结论"的那几项；方向性结论（削峰是否生效）现有单机数据已足够 |

## 三、核心问题：MQ / 非MQ 是否需要在另一台机器分别压测？

### 3.1 先把两件事拆开，否则会答错

| 子问题 | 内容 |
| --- | --- |
| **(a) 压测机与被测服务分离** | B 机发压、A 机服务，消除"压测工具与被测系统抢同一批 CPU" |
| **(b) 两组各自在对称环境下独立压一遍** | 同一 jar、同一批账号、同一库存、同一限流开关、同一脚本，**唯一变量是削峰开关** |

**结论：(a) 需要，(b) 需要，但 (a)(b) 都只解决"噪声与对称性"，不解决"口径可比性"。**

### 3.2 结论分层

- **若目的只是回答"削峰是否生效"（方向性）** → 现有单机结论**已经足够**，不需要换机。
  证据强度足够：P99 降幅 83%、正确性终态两组完全一致（均 200 单、库存 0、一人一单、pending 0）。
- **若目的是回答"要不要上 MQ、异步到底能带来多少容量、代价多大"（决策性）** → **必须换机 + 必须先统一口径**。
  因为要下"异步**不提升吞吐**"这种**接近性结论**（40 vs 29.9，差值仅 25%），
  而同机噪声的量级本身就与 25% 相当，**结论有被噪声反转的风险**。

### 3.3 为什么必须换机 —— 四条具体理由

**理由 1｜要测的是"接近 1 的差异"，同机噪声同量级。**
现有对比里，唯一想推翻"异步提升吞吐"这个直觉的证据，是 40 → 29.9 单/秒（↓25%）。
但同机压测中，"压测机 + 后端 JVM + MySQL + Redis"共享 8 核，被测系统的实际可用 CPU 是个未知数。
用带 ±30% 级别噪声的环境去证一个 25% 的差异，**统计上不成立**。换机后客户端不再抢 CPU，
服务端可用算力可标定，这 25% 才能被判定为"真实"还是"噪声"。

**理由 2｜两种模式的 CPU/资源曲线不同，同机偏差是"结构性不对称"，不是均匀加噪。**
- 非MQ：DB 写发生在**请求线程**（`seckillExecutor` core 64 / max 128 密集消耗 CPU），Redis 只用预扣。
- MQ：请求线程只做"预扣 + 入队"（CPU 占用低），DB 写移到 4 个消费线程，但**新增了 Redis Stream 的
  `XADD` / `XREADGROUP` / `XACK` / pending 扫描 `reclaimStale` 负载**，而 Redis 同样是容器、
  同样与压测机抢同一批核。

也就是说两组跟压测机争抢的方式**不一样**。同机环境下无法断言"扣掉噪声后两组的真实差距还是 83%"。

**理由 3｜MQ 的价值本体是"横向扩展"，单机测不出来。**
`docs/concurrency/秒杀异步化分析.md` 已明确：MQ 的核心价值是"按 `itemId` 分区 → 同一 SKU 顺序消费 → 行锁争抢变排队"，
以及"加分区 + 加消费者线性扩展"。这两点都要求**消费者进程 ≠ 压测机 ≠ 数据库**的多机拓扑。
单机上加消费者线程只会与压测机争 CPU，测到的是争抢而不是扩展性。

**理由 4｜网络 RTT 是异步链路的额外变量，loopback 下测不到。**
异步模式的用户路径是"入队 → **多次轮询** 结果"，**往返次数远多于同步模式**，
因此对客户端↔服务端 RTT 更敏感。同机走 loopback 的 RTT≈0，跨机才有真实 RTT，
这会影响"端到端时延"这个异步最该被质疑的指标。

### 3.4 换机也修不了的 3 个缺陷（必须**先**修，否则换机后仍不可比）

> 这是本次梳理最重要的部分：**换机是必要条件，不是充分条件。**

| # | 缺陷 | 现状 | 为什么换机修不了 | 必须先做的事 |
| --- | --- | --- | --- | --- |
| **D1** | **并行度不对等**（不公平对比） | 非MQ：`seckillExecutor` **64 核线程**并发落库；MQ：**仅 4 个消费线程** | 这是**配置差异**，与机器无关 | 先做 **P0-2 消费线程数扫描**，把两组放在**同等有效并行度**上比 |
| **D2** | **统计口径不同**（苹果比橘子） | 非MQ 的 `order_latency` = 预扣 + **落库完成**；MQ 的 = 预扣 + **入队受理** | 口径是**度量定义**问题 | 改为 **统一端到端口径**：点击 → 轮询到 SUCCESS 的总时长（P0-3） |
| **D3** | **单热点 SKU 掩盖收益** | 200 件库存集中 1 个 SKU，瓶颈是 InnoDB **行锁串行**，与请求来自哪台机器无关 | 瓶颈是**物理约束** | 增加**多 SKU / 不同库存量级 / 分桶**维度（P2-4、P2-5） |

> 结论：**"换机 + 不修 D1/D2/D3" 的产出价值很低**；"修 D1/D2/D3 + 换机" 才能得到可上决策的结论。

## 四、两种场景（MQ / 非MQ）的测试目标

| 目标 | 非MQ（同步落库） | MQ（削峰异步落库） |
| --- | --- | --- |
| G1 客户端受理时延 | 基线 | 量化收益（口径：受理） |
| G2 **端到端**时延 | 基线（受理即终态） | **核心**：受理 + 排队 + 轮询到 SUCCESS |
| G3 稳态落库吞吐 | 基线（64 线程并发） | 消费线程数扫描，找**上限**与**拐点** |
| G4 脉冲吸收能力 | 峰值直接冲击 DB | 队列摊平；积压峰值 / 排空时长 |
| G5 资源画像 | 请求线程 CPU / 行锁等待 | +Redis Stream 负载 / 消费线程 / 队列内存 |
| G6 一致性 | 不超卖 / 一人一单 / 不重复建单 | 同左 **+ 重复投递 / 死信 / 回滚后库存守恒** |
| G7 故障形态 | 请求超时 / 5xx | 排队无期 / 结果查不到 / MQ 不可用降级 |
| G8 横向扩展性 | 受 DB 行锁上限约束 | 多实例多消费者是否**线性**提升 |

## 五、预期指标（先定验收线，再测）

> 以下为**基于现有单机数据的推演区间**，用于设定验收线；实测以换机后的正式轮次为准。

| 指标 | 非MQ 预期（跨机） | MQ 预期（跨机） | 判读标准 |
| --- | --- | --- | --- |
| P99 受理时延 | 比同机下降（噪声剔除） | 仍显著低于非MQ | 同步组有 64 线程写库，**更受 CPU 争抢影响**，故同机的 83% 降幅**可能被放大**，跨机后**降幅预期收窄** |
| 端到端 P99（单热点 SKU，库存 200） | ≈ 受理时延（无排队） | 受理 ~180 ms + 排队，**预期 3~7 s** | 200 单 ÷（30~40 单/秒）≈ 5~7 s，与单机实测 ~6.69 s 吻合 |
| 端到端 P99（多 SKU，463 单/秒量级） | ≈ 受理时延 | 排队接近**无感**（200 单 ÷ 463 ≈ 0.43 s） | 这是 MQ 真正的收益场景 |
| 稳态落库吞吐 | 40~60 单/秒（单热点 SKU） | **消费线程 ≥32 时应收敛到同一 DB 上限** | 若对等并行度下仍显著低于同步 → 说明 Redis Stream 开销真实存在，需记录 |
| 队列积压峰值 | — | ≤ 库存数（队列天然有界） | 队列长度应 ≈ 预扣成功数，**不应被无效请求灌爆** |
| 排空时长 | — | 持续过载时必须**有界**；若持续不降 = 消费能力不足 | `max-stream-length=100000` 裁剪生效 |
| 死信 / 重投率 | — | 稳态应 **0**；`max-deliveries=3` 超限转死信 | 死信 > 0 必须归因 |
| 系统错误率 | **0**（5xx + 连接异常） | **0** | 业务"已抢光""排队中"不计入 |
| 一致性（两组必须一致） | 订单数 == 库存；库存归零；一人一单 | 同左 **+ pending 归零 + 库存守恒** | 任何一项不一致即判定失败 |

## 六、两种场景的对比关注点（对比矩阵）

> 这一节是"两组对比时到底看什么"，避免只比一个 P99 就下结论。

| # | 关注点 | 非MQ 侧要看的 | MQ 侧要看的 | 对比结论的意义 |
| --- | --- | --- | --- | --- |
| 1 | **受理时延**（P50/P90/P99） | 基线 | 收益幅度 | 收益来自"把 DB 落库移出请求线程" |
| 2 | **端到端时延** | == 受理时延 | 受理 + 排队 + 轮询 | **唯一能代表用户体感的指标**，必须两组同口径 |
| 3 | **吞吐（同等并行度）** | 64 线程 | 扫描后的最优线程数 | 判断"削峰是否真的提吞吐"，还是只搬移了瓶颈 |
| 4 | **瓶颈归属** | 请求线程 / 行锁 | Redis Stream 吞吐 / 消费线程 / **仍受 DB 行锁上限** | 验证"瓶颈迁移"而非"瓶颈消除" |
| 5 | **资源占用** | Tomcat 线程饱和度、线程池队列 | Redis QPS/内存、消费线程、Stream 长度 | MQ 新增成本：Redis 压力与运维面 |
| 6 | **脉冲吸收** | 峰值直接压 DB，QPS 掉、延迟飙升 | 队列摊平，受理恒定、落库匀速 | 削峰的本质收益 |
| 7 | **失效模式** | 同步超时 / 503 | **排队无期** / 结果过期查不到 / MQ 不可用 | 后者危害更隐蔽，需降级开关覆盖 |
| 8 | **一致性风险面** | 事务内，强一致 | 重复投递、死信、回滚后库存守恒、结果与订单的时序 | MQ 多出的风险点必须逐项验证 |
| 9 | **横向扩展性** | 受 DB 行锁线性上限 | 加消费者/分区是否线性 | MQ 的核心价值，必须多机验证 |
| 10 | **运维复杂度/成本** | 无新增中间件 | 队列监控、积压告警、死信处理 | 决策必须计入 |

| 项 | 说明 |
| --- | --- |
| 压测账号 token 有效期仅 **2 小时** | 换机前后必须先重跑 `prepare_data.py` + `gen_k6_users.py`，否则整轮 401 被误计为"已抢光" |
| 限流必须关闭（`mall.rate-limit.enabled=false`） | 否则测到的是限流器；两组必须一致 |
| 两机时钟需 NTP 同步 | 否则端到端时延与超时判定失真 |
| 网络带宽需确认 | B 机需保持"干净"，避免带宽成为新瓶颈（文档已提示用 `nettop` 观测） |
| `loadtest/k6/data/users.js` 被 `.gitignore` 排除 | 必须手动拷贝，缺文件直接报模块不存在 |
| 结论纪律 | 明确区分"方向性结论（现有单机足够）"与"容量结论（必须换机 + 对齐口径）"，不得混用 |

## 九、总结

1. **已完成测试覆盖面已经不错**：正确性 8/8、秒杀/读/下单/混合四类压力、MQ 单机对比、555 个测试用例。
2. **需要补充的测试项**集中在三块：**削峰决策类压测（P0）**、**规模与盲区（多实例/B端/长稳）**、**优化验证（P2）**。
3. **MQ / 非MQ 需要在另一台机器分别压测** —— **需要**，理由是要测的吞吐差异只有 ~25%、
   两种模式资源曲线不对称、MQ 的扩展性单机测不出、异步链路对 RTT 更敏感。
4. **但换机是必要条件而非充分条件**：必须**先修 D1（并行度对等）、D2（端到端统一口径）、D3（多 SKU）**，
   否则换机只是换一种噪声，结论依旧不可引用。
5. **推荐顺序**：对齐口径/配置 → 换机正式对比 → 多实例 + 长稳 → 商家端与 prod 参数。

### P0-5：结果查询接口（轮询读放大）怎么压

```bash
# A 机 —— 前提：先跑过一轮削峰模式秒杀压测（否则 Redis 里没有结果可轮询）

# ① live：真实链路，一次抢购 + 按 200ms 间隔轮询到终态，得出「每单放大多少倍」
#    B 机：
VUS=100 ITERATIONS=1 k6 run -e BASE_URL=http://<A_IP>:8080 \
  --summary-export=results/seckill-result-live.json loadtest/k6/seckill-result.js
#    报告里看 poll_requests / grab_ok = 读放大倍数；result_latency = 单次轮询延迟
#    ⚠️ sync_mode_detected > 0 说明后端没开削峰，此时没有中间态，压不出轮询路径

# ② replay：纯读压测，标定接口承载上限（必须先采集 requestId）
#    A 机：
python3 loadtest/scripts/collect_seckill_results.py            # → k6/data/seckill-results.js
#    把该文件拷到 B 机后（与 users.js 同样属于 gitignore 产物）：
RATE=500 DURATION=60s k6 run -e BASE_URL=http://<A_IP>:8080 \
  --summary-export=results/seckill-result-read.json loadtest/k6/seckill-result-read.js
```

判读要点：

| 现象 | 含义 |
| --- | --- |
| `result_server_error > 0` | 查询接口出 5xx —— 已设为 threshold，k6 会直接判失败 |
| `result_not_found` 占比高 | 结果 key 已过期（TTL 默认 30m），重新采集即可，**不是接口问题** |
| `result_rate_limited` 出现 | 打到限流保护线（保护生效），需要区分「接口上限」与「限流阈值」 |
| `poll_requests` / `grab_ok` 偏高 | 前端轮询策略过于激进，读放大代价大 —— 可用它反推合理的轮询间隔 |
