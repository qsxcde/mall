# 商品搜索三方案对比实测：LIKE / FULLTEXT / Elasticsearch

> 实测日期：2026-10-17 ~ 2026-10-18
> 环境：单机 macOS，MySQL 8.0（容器 :3307）、Redis 7（容器）、Elasticsearch 8.15.3（容器，-Xms512m -Xmx512m）、
> 后端 Spring Boot 3.3.5 / JDK 21（本机 :8080）
> 数据量：`pms_product` 共 1,000,038 行，其中在售 800,374 行
> 测量工具：[`loadtest/scripts/bench_search.py`](../../loadtest/scripts/bench_search.py)（同一脚本、同一口径测量三种引擎）

---

## 一、结论先行

| 场景 | 最优方案 | 最差方案 | 差距 |
| --- | --- | --- | --- |
| **低频词 / 无匹配**（最坏情况） | **ES 9.9 ms** | LIKE 5,240 ms | **529 倍** |
| **高频词**（1.4 万条命中） | **ES 23.6 ms** | FULLTEXT 6,888 ms | **292 倍** |
| **并发 6** | **ES 16.2 ms** | LIKE 10,325 ms | **637 倍** |

**三句话总结：**

1. **FULLTEXT 不是「更好的 LIKE」，而是「另一种舍取」** —— 低频词快 900 倍，高频词反而慢 6.6 倍。它适合"大多数搜索都有结果"的场景，不适合热门词检索。
2. **ES 在全部 5 个关键词、全部 3 个并发档位上都优于另外两者**，且最慢也只有 23.6 ms。
3. **LIKE 的唯一优势是零组件成本**，但代价是 5 秒级的最坏情况延迟，已经越过可用性红线。

**推荐：数据量 ≤ 10 万用 LIKE；10 万 ~ 50 万可用 FULLTEXT（需接受热门词变慢）；> 50 万上 ES。**

## 三、逐方案分析

### 3.1 LIKE（基线，`mall.search.engine=mysql-like`）

```sql
WHERE status=1 AND deleted=0
  AND (title LIKE '%kw%' OR brand_name LIKE '%kw%' OR category_name LIKE '%kw%')
ORDER BY sales DESC LIMIT 8
```

**性能特征：所有查询都在 1 秒以上，与命中数无关。**

原因：前置通配符 `%kw%` 让 B+ 树索引完全失效，必须全表（或全索引）扫描后逐行判断。

#### 陷阱：LIMIT 提前终止会掩盖真实成本

`ORDER BY sales DESC LIMIT 8` 让 MySQL 沿 `idx_sales` 反向扫描：

- **高频词**（华为 13.8 万命中）：扫几千行就凑满 8 条 → 提前终止 → **1.0 s**
- **低频词**（iPhone 2 条命中）：扫完 100 万行也凑不满 → **5.2 s**

`EXPLAIN` 显示两者执行计划**完全相同**（`key: idx_sales`, `Backward index scan`）。
这就是为什么"压测时用热门词"会得出"1 秒还行"的错误结论。

#### 并发表现

3 并发 7.2 s、6 并发 10.3 s，且**所有并发请求耗时几乎一致**（如 6 并发全部为 10,324 ms）。
这说明它们共享同一份 CPU / buffer pool 在排队，**没有任何横向扩展能力**。
更严重的是：全表扫描会吃满 buffer pool，**连带拖慢同实例的详情、下单等同库接口**。

### 3.2 FULLTEXT（`mall.search.engine=mysql-fulltext`）

```sql
ALTER TABLE pms_product
  ADD FULLTEXT INDEX ft_search (title, brand_name, category_name) WITH PARSER ngram;

WHERE MATCH(title, brand_name, category_name) AGAINST('"华为"' IN BOOLEAN MODE)
```

#### 索引构建成本

| 项 | 数值 |
| --- | --- |
| 构建耗时（100 万行） | **50 秒** |
| 索引体积 | 约 180 MB（原表 479 MB） |

#### 必须用短语模式，否则语义不等价

`ngram_token_size=2`，中文被切成**双字 token**：

- `IN BOOLEAN MODE` 普通模式：`折叠屏` → `折叠` OR `叠屏`，命中集**大于** `LIKE '%折叠屏%'`
- `IN BOOLEAN MODE` **短语模式**（关键词加双引号）：要求 token 连续 → **与 LIKE 等价**

实测验证（三种口径命中数完全一致）：

| 关键词 | BOOLEAN | 短语 | LIKE |
| --- | ---: | ---: | ---: |
| 华为 | 138,384 | 138,384 | 138,384 |
| 折叠屏 | 106,364 | 106,364 | 106,364 |
| MateBook | 20,284 | 20,284 | 20,284 |

#### 性能是「两极分化」的，不是全面提升

| 查询类型 | FULLTEXT vs LIKE | 原因 |
| --- | --- | --- |
| 低频词 / 无匹配 | **快 900 ~ 370 倍**（5.2 s → 5.8 ms） | 倒排索引直接返回空集或极小集合，无需扫描 |
| 高频词（13.8 万命中） | **慢 6.6 倍**（1.0 s → 6.9 s） | 要把 13.8 万个 doc id 全部取出、回表、再排序取前 8 |

**这是本次实测最有价值的发现**：如果说"FULLTEXT 更快"，那是不准确的。
准确说法是：**FULLTEXT 优化了「结果少」的场景，牺牲了「结果多」的场景。**

> 为什么高频词变慢：`ORDER BY sales LIMIT 8` 在 LIKE 下能借 `idx_sales` 提前终止，
> 而 FULLTEXT 必须先拿到**全部**命中 doc id 才能排序 —— 失去了提前终止的能力。

#### 适用判断

- ✅ 适合：站内搜索以**长尾词**为主（大多数搜索只命中少量商品）
- ❌ 不适合：有大量热门词查询（如大促时的品牌词、品类词）
- ⚠️ 风险：性能可预测性差，快慢取决于查询词的命中规模，**很难做容量规划**

### 3.3 Elasticsearch（`mall.search.engine=elasticsearch`）

#### 部署与索引

```yaml
# docker run 参数
discovery.type=single-node
xpack.security.enabled=false      # 本地开发；生产必须开启
ES_JAVA_OPTS=-Xms512m -Xmx512m
```

mapping 关键决策：

| 字段 | 类型 | 理由 |
| --- | --- | --- |
| `title` | `text`（standard） | 全文检索，标题权重 3.0 |
| `brandName` / `categoryKey` / `parentKey` | `keyword` | 精确过滤 + 聚合 |
| `price` | `scaled_float` ×100 | 电商金额标准做法，比 double 省空间 |
| `status` / `isHot` / `isNew` | `byte` | 枚举值，极省空间 |
| **`cost`（成本价）** | **不入索引** | 商家端敏感字段，进索引就有泄露给买家的风险 |
| `stock` | **不入索引** | 变化极快，进索引会造成高频更新 |

#### 全量导入

| 项 | 数值 |
| --- | --- |
| 导入条数 | **800,374**（在售商品） |
| 耗时 | **42 秒** |
| 吞吐 | 约 **19,000 条/秒** |
| 失败数 | 0 |
| 数量校验 | ES 800,374 == MySQL 800,374 ✅ |

导入方式：`id > cursor ORDER BY id LIMIT 2000` 游标分页 + `_bulk` 批写。
不用 `LIMIT offset` —— 后者在百万行下深分页会越翻越慢。

#### 性能

| 类型 | 关键词 | 命中 | ES | vs LIKE |
| --- | --- | ---: | ---: | --- |
| 高频 | 华为 | 138,384 | **23.6 ms** | 快 44 倍 |
| 高频 | Redmi | 31,735 | **12.6 ms** | 快 89 倍 |
| 极低频 | iPhone | 2 | **9.9 ms** | 快 529 倍 |
| 中频 | ThinkPad | 20,059 | **14.2 ms** | 快 72 倍 |
| 无匹配 | zzz不存在zzz | 0 | **5.9 ms** | 快 176 倍 |

**关键特性：延迟与命中数弱相关。** 从 2 条命中到 13.8 万条命中，延迟只在 9.9 ~ 23.6 ms 之间波动。
这意味着**容量可预测** —— 这是 LIKE 和 FULLTEXT 都不具备的。

## 四、三个必须讲清楚的工程细节

### 4.1 ES 只负责「找 id」，内容一律回 MySQL

```
ES 查 → 得到有序 id 列表 → selectOnShelfByIds(ids) 批量回表 → ProductConverter 组装 VO
```

**为什么不能直接返回 ES 的 `_source`：**

1. **一致性**：ES 有 `refresh_interval`（本配置 5s）。商家刚改价/下架，ES 里还是旧值。
   直接展示会出现"搜到了但点进去已下架"。
2. **安全**：`_source` 里若包含 `cost`（成本价），会把商家端敏感字段泄露给买家。
3. **契约**：回表复用现有 `ProductConverter`，前端字段零变化。

代价是多一次主键批量查询（`IN (8 个 id)`，亚毫秒级）。

### 4.2 排序语义必须与 LIKE 对齐（踩过的坑）

**问题**：初版实现里，只要有关键词就把 `_score` 放在排序首位。结果 `sort=price_asc` 返回：

```
7499 → 12999 → 1499     ❌ 完全不按价格升序
```

**原因**：`_score` 是主排序键，价格排序退化成了几乎无效的次级条件。

**修正**：`_score` 只在**用户没有显式指定排序**时才作为主排序键；
一旦指定 `price_asc` / `sales` / `rating` 等，就严格按该字段排。

**验证**（与 MySQL 直接查询逐条对齐）：

```
ES      : [(3135802, 19.0), (3138762, 19.0), (3143870, 19.0)]
MySQL   : [(3135802, 19.00), (3138762, 19.00), (3143870, 19.00)]   ✅ 完全一致
```

> **这类语义漂移是搜索引擎接入最常见的 bug** —— 性能没问题、也没报错，但结果悄悄变了。
> 因此每种引擎都必须做**同条件结果对拍**，而不只是测延迟。

### 4.3 降级路径（已实测）

```java
try {
    return doSearch(...);                     // ES
} catch (Exception ex) {
    if (degradeToMysql) {
        log.warn("[搜索降级] ES 查询失败，回落到 mysql-like：{}", ex.getMessage());
        return mysqlFallback.search(query);   // LIKE
    }
    throw new IllegalStateException("搜索服务不可用", ex);
}
```

**实测**：`docker stop geek-mall-es` 后请求搜索接口：

```
http_code=200 time=7.47s  code=0 total=2      ✅ 服务不中断
日志: [搜索降级] ES 查询失败，回落到 mysql-like：Connection refused
```

**取舍**：ES 挂掉后搜索延迟从 9.9 ms 退化到 7.5 s（低频词），但**功能可用**。
如果业务要求"宁可不可用也不要慢"，把 `mall.search.es.degrade-to-mysql` 设为 `false` 即可。

## 六、决策建议

### 按数据量选择

| 数据量 | 推荐 | 理由 |
| --- | --- | --- |
| **≤ 10 万** | **LIKE** | 实测 10 万行时最坏 135 ms，完全够用。引入任何额外方案都是过度设计 |
| **10 万 ~ 50 万** | **FULLTEXT**（若搜索以长尾词为主） | 零额外组件，低频词亚毫秒；但需接受热门词变慢 |
| **> 50 万** | **Elasticsearch** | 延迟稳定在 25 ms 内，且与命中数弱相关，容量可预测 |

### 本项目（100 万行）的结论

**推荐 ES**，理由三条：

1. 最坏情况 23.6 ms，相比 LIKE 的 5.2 s 提升 **220 倍**，已越过"可用"门槛
2. **延迟可预测** —— 容量规划才有意义（FULLTEXT 的 3ms~6.9s 波动无法规划）
3. 并发下真并行（3→6 并发耗时几乎不变），是唯一能横向扩展的方案

**但代价必须说清楚**：

- 新增 1 个中间件 + 索引管理 + 数据同步链路
- **数据同步是最大的工作量**（本报告只做了全量导入，生产必须做增量同步）
- 当前实现**没有增量同步**，这是上生产前的必需项

### 如果暂时不接 ES

用 FULLTEXT 作为过渡，但必须：

1. 监控高频词的 P99（6.9 s 会触发用户投诉）
2. 对热门词做**结果缓存**（Redis，TTL 30~60 s）—— 高频词的命中集稳定，缓存收益极高
3. 明确接受"性能不可预测"这个特性

## 八、局限说明

1. **单机环境**：MySQL、ES、后端、压测脚本共享同一台机器，绝对数值会受 CPU 争抢影响；
   但三种方案的**相对差异**（几十到几百倍）远超噪声，结论方向可靠。
2. **数据为合成数据**：商品标题由脚本生成，词汇分布比真实商品库更均匀；
   真实场景中长尾词占比更高，**会进一步放大 ES 的优势**。
3. **未测增量同步**：本报告只覆盖全量导入，生产环境的写入链路（outbox / CDC）未实现也未测。
4. **ES 单节点、无副本**：生产需至少 1 副本，性能与容量结论需按副本数调整。
5. **未测深分页**：ES 默认 `max_result_window=10000`，`page × pageSize > 10000` 会报错，
   当前未做限制（这是一个已知缺口）。
