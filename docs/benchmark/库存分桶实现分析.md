## 1. 分桶策略：把"1 行热点"变成"N 行热点"

### 1.1 本质定义（D.1、D.12）

> **分桶 = 把 1 行库存预拆成 N 行，每单仍然只扣其中 1 行。**

| 方案 | 行数 | 每单写入 | 并行度 | 主要代价 |
| --- | --- | --- | --- | --- |
| A. 现状（单行库存） | 1 行（固定） | `UPDATE` 同一行 | **1** | 无 |
| **B. 库存分桶** | **N 行（预先固定）** | `UPDATE` 其中 1 行 | **≤ N** | 假售罄、调剂、对账 |
| C. append-only 流水 | 每单新增 1 行（持续增长） | `INSERT` 新行（不争锁） | 无行锁争用 | **写入总量变大**、需汇总与清理 |

关键澄清：**"写入量变大"是 C 方案的特征，不是分桶**（分桶总行数固定为 N，写入次数不变）。分桶变的是**并发度**，不是工作量。

### 1.2 核心机理解释（D.9）：没有"跳转"，只有"一开始就被分到不同行"

"队列"不是真实实体，而是 **InnoDB 挂在那"一行"上的锁等待者列表**。所以：

| 比喻 | 技术实体 |
| --- | --- |
| 收银台 | 库存表里的**一行**（一个 id） |
| 排队的队伍 | 挂在这行上的 InnoDB 锁等待者列表 |
| 找收银台 | `UPDATE ... WHERE id = ?` 的主键定位（O(1)，微秒级） |
| "分 N 个收银台" | 把 1 行拆成 N 行（N 个不同 id） |
| "被分到不同队" | 路由 `id = base + hash(userId) % N`，**在 SQL 发出前就算好** |

**分配发生在扣减之前，不是被锁之后** —— 所以不存在"跳到另一个队列"这个动作。

### 1.3 本系统的落点：把"选桶"放进已有的 Redis Lua 预扣（D.6）

现有 `GRAB_SCRIPT` 只操作 1 个库存 key；分桶只需扩展成 **N 个桶 key + 返回选中的桶号**：

```lua
-- KEYS[1..N] = 各桶库存；KEYS[N+1] = 一人一单集合
-- ARGV[1]=userId, ARGV[2]=TTL, ARGV[3]=随机起点（由应用传入，保证脚本确定性）
local n = #KEYS - 1
local bought = KEYS[n + 1]
if redis.call('SISMEMBER', bought, ARGV[1]) == 1 then return {-3, 0} end
local start = tonumber(ARGV[3]) % n + 1
for i = 0, n - 1 do
  local idx = (start + i - 1) % n + 1
  local v = tonumber(redis.call('GET', KEYS[idx]) or '0')
  if v > 0 then
    redis.call('DECR', KEYS[idx])
    redis.call('SADD', bought, ARGV[1]); redis.call('EXPIRE', bought, ARGV[2])
    return {1, idx}          -- 返回「选中的那一行」
  end
end
return {-2, 0}               -- 所有桶都空 = 真的售罄
```

**关键收益：选桶在 Redis 的"一次原子调用"内完成**（Lua 内 O(N) 内存循环，不产生 N 次 DB 往返），所以既不会撞空桶、也不需要"试着扣、失败再换一行"的重试。

### 1.4 两层分工（D.8）

| 层 | 职责 | 会不会撞锁 |
| --- | --- | --- |
| Redis Lua 预扣 | **选桶** + 扣桶余量 | ❌ 不会。Lua 原子单线程串行，按"余量>0"挑桶，**一次选中** |
| DB 落库 | 对选中行做 CAS 兜底与记账 | ⚠️ 会，但队列长度 = **同桶人数**，而非全场人数 |

## 2. 桶数量与分片规则

### 2.1 桶数由公式反推，不是拍脑袋（E.3、E.5）

```
桶数 ≈ 预期峰值 TPS ÷ 单行可承受 TPS
```

- 现实案例（iPhone 首发，单 SKU 备货 10 万台、峰值约 5 万 TPS、要求 3 秒出结果）：
  `桶数 = 50,000 ÷ 500 = 100`，每桶 `100,000 ÷ 100 = 1,000` 台，路由 `bucket = userId % 100`。
- 桶太少没效果；**太多则 `SUM` 对账 / 展示 / 回补成本线性上升**。

### 2.2 本项目的可验证数字（D.4）

单行库存实测落库 **38 单/s**（单事务均摊 26ms）：

| 方案 | 理论上界 |
| --- | --- |
| 多 SKU（12 行） | ≈ 12 × 38 ≈ **456 单/s** |
| 分桶 10 行 | ≈ 10 × 38 ≈ **380 单/s** |

### 2.3 分片规则与最佳 schema（D.18）

```sql
CREATE TABLE mkt_seckill_bucket (
  item_id   BIGINT NOT NULL,   -- 哪个秒杀商品
  bucket_no INT    NOT NULL,   -- 第几个桶
  stock     INT    NOT NULL,
  PRIMARY KEY (item_id, bucket_no)
);
```

**`(item_id, bucket_no)` 二维结构：每个 SKU 可配不同桶数**，桶数为 1 时即退化为原写法。

| SKU 类型 | 桶数 |
| --- | --- |
| 爆款（10 万台） | **100 桶** |
| 中等（5,000 件） | 10 桶 |
| 长尾（200 件） | **1 桶**（= 不分桶） |

统一选桶 SQL：`WHERE item_id=? AND bucket_no=?`。

### 2.4 桶数的硬约束：必须与连接池、消费者数一起配（D.17）

```
有效并行度 = min( 消费者/线程数 , Hikari 连接数 , 可并行的桶数/热点行数 )
吞吐       = 并行度 ÷ 单事务耗时（再被 redo/fsync/CPU 截断 → 平台化）
且须满足：实例数 × 池大小 ≤ MySQL max_connections
```

**瓶颈转移阶梯（谁最小，瓶颈就是谁）**：

| 场景 | min(线程64, 池50, 行数) | 瓶颈归属 |
| --- | --- | --- |
| 单 SKU | min(64, 50, **1**) = 1 | **热点行数** ❌ |
| 12 SKU | min(64, 50, **12**) = 12 | 仍是热点行数 |
| 50 桶 | min(64, **50**, 50) = 50 | **连接池** ← 瓶颈转移 |
| 64 桶 + 池 128 | min(**64**, 128, 64) = 64 | **消费者线程** ← 再转移 |
| 200 桶 + 池 256 + 线程 256 | min(256, 256, 200) = 200 | 才可能撞**底座** |

⚠️ 本项目 dev 环境 Hikari 池仅 **50** → **100 桶会被连接池卡在 50**。**桶数不是越多越好**。

## 3. 库存扣减与回滚在分桶间的分配逻辑

### 3.1 扣减：即时计算 + 单行扣减 + 记录 bucketNo

**路由是"请求到达时即时计算"，不是"提前统一规划"（D.10）**：零协调、无中心节点，SQL 里带的是固定值 `WHERE id = base + (userId % N)`。

DB 侧随后只扣那一行（D.6）：

```sql
UPDATE mkt_seckill_bucket SET stock = stock - 1 WHERE item_id = ? AND bucket_no = ? AND stock > 0
```

### 3.2 回滚 / 回补：必须记下"扣的是哪一桶"

| 路由方式 | 能否重算 | 回补（取消/超时/预扣回滚） |
| --- | --- | --- |
| A. `userId % N` | ✅ 可重算 | 不必记录，回补时重算即可 |
| B. 随机起点探测 | ❌ **不可复现** | **必须记录 `bucketId`**（落库 / 进消息） |

文档采用 B（随机起点+顺序探测），因此：

1. **异步路径 `bucketNo` 必须进消息体**：`SeckillOrderMessage` 现为 `requestId/userId/itemId/addressId/traceId`，**需增加 `bucketNo`**，否则消费者不知道扣哪桶（同步路径无此问题）。
2. **回补必须还回原桶**：现状 `increment(SECKILL_STOCK + itemId)` 只回补全局计数；分桶后须 `increment(bucketKey(itemId, bucketNo))`。

### 3.3 三条守恒红线（D.6 / D.12）

1. **守恒**：一次订单 = 一次成功的单行扣减；`SUM(各桶) == 全局余量`，扣减总量 == 订单数；
2. **一人一单不能分桶**：判重集合必须是**每个活动一个全局 key**（不按桶拆），否则用户可借不同桶重复抢；
3. **必须记录 bucketId**：预扣回补、订单取消回退，都要把 +1 还给原来那一行。

### 3.4 "桶空了"怎么办（D.13 / D.14）

| 阶段 | 会不会选到空桶 | 处理 |
| --- | --- | --- |
| ① 预扣（Redis Lua 选桶） | ❌ 不会 —— 按"余量>0"挑桶 | 选不到 = 所有桶空 = **真售罄** |
| ② 落库（DB CAS） | ⚠️ 会（预扣与记账短暂不一致） | 按架构而定 |

- **本系统形态（Redis 预扣 + DB 兜底）**：落库发现桶空 = "预扣/记账不一致"异常 → **不换桶**（换桶会导致"预扣扣了桶 A、DB 扣了桶 B"，两个桶余量都不对，回补也找不回原桶）→ 回补预扣 + 业务失败 + 打监控指标。
- **架构 1（DB 直打，无预扣）**才会有界换桶重试 3~5 次，或用"小桶+中心池"两级调剂。
- **绝对不能做**：直接返回"已抢光"（假售罄）、无限重试（重试风暴）、1 单拆多桶各扣（破坏守恒+死锁）、"重新排队"（DB 行锁排队是内核行为，无法主动排队）。
- **方向**：排队应发生在前面的层 —— `限流 → Redis 预扣 → MQ 削峰 → DB 行锁`，**DB 层排队是最贵的排队**。

### 3.5 最大坑：假售罄（D.10.1 实测模拟）

200 单 / 10 桶 × 20 件：

| 路由方式 | 各桶收到的请求数 | 实际成交 | 假售罄 | 剩余库存 |
| --- | --- | --- | --- | --- |
| A. 固定路由 `userId % 10` | `[16,21,27,13,21,22,19,15,23,23]` | **183/200** ❌ | **17 单** | **17 件卖不掉** |
| B. 随机起点 + 顺序探测 | — | **200/200** ✅ | **0** | **0（恰好归零）** |

原因：哈希分布天然波动（13~27），桶容量固定 20 → ≥21 单的桶拒人、13 单的桶剩货。**这就是推荐"动态探测"的原因：不是按用户属性硬分，而是"看着余量挑"，挑到的一定有货。**

## 4. 并发控制机制（锁与 CAS）

### 4.1 物理基础：InnoDB 行级锁（D.11 本机实测）

| 场景（10 个并发事务，各持锁 200ms） | 总耗时 | 结论 |
| --- | --- | --- |
| 各改**不同行**（id=1..10） | **0.34 s** | ≈ 1 × 200ms → **并行** |
| 各改**同一行**（id=1） | **2.14 s** | ≈ 10 × 200ms → **串行** |
| 并行加速比 | **6.4×** | 接近满并行 |

### 4.2 分桶与锁的关系：不消除锁，只分摊锁（D.8）

> 分桶只做一件事：**把"命中同一行"的概率从 100% 降到 1/N。**

| | 排队形态 | 吞吐 |
| --- | --- | --- |
| 不分桶 | 200 人挤 **1 条队列** | 1 ÷ 单事务耗时 |
| 分 10 桶 | 平均 20 人 × **10 条队列** | **10** ÷ 单事务耗时 |

每一行内部**仍然串行**。实测对应：更新不同行 **0.08s**（无锁冲突）／更新同一行 **1.10s 超时**（锁等待）。

### 4.3 关键澄清："行被锁了不跳行"（D.8）

| 触发条件 | 行为 |
| --- | --- |
| 该桶**余量 = 0**（空桶） | ✅ 换下一行重试（这才是"跳转"） |
| 该桶**余量 > 0，但该行正被锁** | ❌ **阻塞排队等待**（`innodb_lock_wait_timeout` 默认 50s），**不跳行** |

**选桶依据的是"桶里有没有货"（业务状态），不是"这行有没有被锁"（并发状态）。** 锁状态瞬时且不可预知（查询时未锁，`UPDATE` 时可能已被锁），**锁只能撞上再等，无法事先避开**。

**为何不用"撞锁就跳行"（try-and-rotate）**：需把锁等待超时调到极短（如 100ms）→ 超时导致整个事务中断（1205）需重开 → 会出现"明明有货却报失败"→ 重试/退避逻辑自研，复杂度收益不如直接在 Redis 选桶。

### 4.4 CAS 兜底（D.14）

- 防超卖靠 **CAS**（`WHERE stock > 0`），**分桶只影响并发度，不负责防超卖**。
- **桶空不是 SQL 错误**：`UPDATE ... WHERE stock>0` 匹配不到行只返回 `affected rows = 0`（**正常返回**），事务仍干净。**回滚是代码的设计选择，不是 DB 的强制行为**。

### 4.5 四个关键约束（D.11）

| # | 约束 | 说明 |
| --- | --- | --- |
| ① | **`WHERE` 必须走索引** | 主键等值 → 只锁一行（满并行）；无索引/范围查询 → 退化近似表锁或间隙锁互相阻塞 |
| ② | **受全局共享资源截断** | redo log 刷盘（group commit）、buffer pool latch、undo/binlog、磁盘 IOPS、CPU → 收益递减并**平台化** |
| ③ | **顺序不一致会死锁** | 本项目下单路径"按 productId 升序加锁 + 退避重试"（`MAX_RETRY_ON_LOCK`）正为此 |
| ④ | **隔离级别加额外锁** | RR 下范围扫描加间隙锁；唯一索引等值命中时只加行锁（**分桶 SQL 的最理想形态**） |

## 5. 数据一致性保障

### 5.1 澄清："选桶"不保证一致性（D.15）

| | 选桶解决的事 | 一致性由谁保证 |
| --- | --- | --- |
| 内容 | **对账口径对齐**（Redis 桶 i ↔ DB 桶 i 是同一逻辑桶） | **最终一致**：预扣/记账语义 + 回补 + 幂等 + 按桶对账 |
| 反例 | — | Redis 扣了桶 3、落库失败回滚、回补又没成功 → Redis 桶 3 比 DB 少 1。**该不一致与"怎么选桶"无关** |

➡️ 选桶被固化的真正价值：**让逐桶对账成为可能**（否则 Redis 扣桶 3、DB 扣桶 7，账都对不上）。

### 5.2 双防线 + 最终一致

| 机制 | 作用 |
| --- | --- |
| Redis 预扣 | 第一道防线：挡掉 99% 请求，不打穿 DB |
| DB CAS（`WHERE stock > 0`） | 最后一道防线：**即使 Redis 计数错了也不超卖** |
| 回补 + 幂等表 | 收敛中间失败（`requestId` / `uk_user_request` / 回退幂等表） |
| 按桶对账 | 发现并修复数值漂移 |

**对账口径**：`DB桶余量_i − Redis桶余量_i ≈ 该桶"已预扣未落库"的在途单数`

| 差额 | 含义 |
| --- | --- |
| ≈ 在途单数 | ✅ 正常（预扣与记账有时间差） |
| 长期偏大 | ⚠️ 落库堆积 / 回补未执行 |
| 为负 | ❌ 异常（回补过多或超发风险），必须告警 |

### 5.3 完整链路（D.15）

```
① 预热（setIfAbsent，按桶）      DB 桶 i 库存 ──→ Redis bucket:{i}
② 抢购：Lua 原子「挑有货的桶 + DECR」→ 返回 {1, bucketNo}
③ 传递 bucketNo：同步 → 方法参数；异步 → ★ 必须放进队列消息体 ★
④ DB 落库（最终记账）：UPDATE ... WHERE item_id=? AND bucket_no=? AND stock > 0
⑤ 失败收敛：回补（+1 还回原桶）+ 幂等（requestId / uk_user_request / 回退幂等表）
⑥ 对账：按桶比 DB 与 Redis 差额
```

### 5.4 现存隐患：回补幂等（F.8.4#3）

现状 `releaseReservation` 是**无条件 `INCREMENT` 回补**；队列重投 / 用户重试会让它执行两次 → **凭空造库存**。交易域已有 `inventory_rollback_log` 唯一索引的幂等范式可直接借鉴。**这是与做不做分桶无关的正确性隐患。**

## 6. 与 MQ 在压测对比中的性能表现差异

> 场景限定（很重要）：**单热点 SKU**（库存 200 集中在 item1）、**单实例**、脉冲深度仅 200 单、消费线程 64、限流关闭、200VU×100。
> 唯一变量：`mall.seckill.async.enabled`。

### 6.1 三轮实测数据

| 指标 | 同步落库 | 削峰·旧上限32 | 削峰·修复后256 |
| --- | --- | --- | --- |
| 受理 P50 | 2426 ms | 54.8 ms | 674.6 ms |
| 受理 P90 / P99 | 4118 / 4660 ms | 519.9 / 533.6 ms | **688.1 / 689.5 ms** |
| 排队 P50 | 0 | 2810 ms | 2890 ms |
| 端到端 P50 | 2426 ms | 3000 ms | **3574 ms** |
| 成功落库 | 200 | 200 | **200** |
| **系统错误** | 0 | **104** ❌ | **0** ✅ |
| 排队峰值 / 排空 | — | 187 / 5.4 s | 185 / 5.3 s |
| 轮询请求数 | 0 | 2591 | **2839** |
| 总 QPS | 3156 | 3234 | **3153** |
| 熔断拒绝计数 | 0 | 104 | 0 |

队列排空曲线：`pending` 峰值 **185**，`lag=0`、无重投，**5.3 s 匀速排空 ≈ 38 单/s**（`XLEN` 因不随 ACK 下降，排空判据看 `pending`/`lag`）。

### 6.2 MQ 得到的 / 没得到的

**得到（受理侧，两轮复现，稳健）**
- 受理尾部时延大幅下降：P90 4118 → 520/688 ms；P99 4660 → 534/690 ms（**↓6~9 倍**）；
- 脉冲被可视化摊平：pending 峰值 185、5.3s 匀速排空，同步模式下这份压力直接压在请求线程上；
- 中间态可见（产品能力）：可轮询到 `QUEUED → SUCCESS/FAILED`。

**没得到（落库侧）**
- **端到端变差**：P50 2426 → 3000/3574 ms；P99 4660 → 5500/6040 ms（**+18%~30%**）；
- **吞吐无提升**：QPS 3156/3234/3153（噪声内）；落库速率 43 → **37.7 单/s（反降 12%）**；
- 稳定性无改善（同步本就 0 失败），且新增故障面（旧配置 104 次系统错误）。

### 6.3 根因：单热点 SKU 让并行度恒为 1

> **吞吐 = 有效并行度 ÷ 单事务耗时。** MQ 既没提高并行度、也没降低单事务耗时，**只改变"排队的位置"**。

- 200 单全部落在**同一对行**上（`mkt_seckill_item.id=1` 与 `pms_product.id=1`）→ 争用同一把 X 锁 → **并行度恒为 1**；
- 并行度对比：同步 `seckillExecutor` core **64** ↔ 削峰 `consumer-threads` **64**，**完全相同** → 吞吐必然相近；
- 单事务均摊耗时：同步 23ms/单 ↔ 削峰 26~29ms/单（多出的正是 `XADD → XREADGROUP → XACK` 队列开销）。

**MQ 是"搬运工"（把排队从 A 挪到 B），不是"生产力"（提高单位时间完成量）。**

### 6.4 分桶在对比中的定位（关键结论）

MQ 对比最终把落库侧的收益**押注在"下游可并行"上**，而分桶正是实现它的手段：

| 维度 | 谁解决 | 文档定位 |
| --- | --- | --- |
| 受理体验、脉冲摊平、系统保护 | **MQ** | 已实测收益（↓6~9 倍） |
| **DB 落库并行度 1 → N** | **分桶 / 多 SKU** | 未实测，**预测能真正提吞吐** |
| 防止雪崩 | MQ（把等待移出请求线程） | 需持续过载才能证明 |

> **MQ 提供"容器"，分桶提供"资源"，二者缺一不可 —— 光有 MQ 不会提升吞吐（已实测）。**

**四种组合的有效并行度推算（D.17）**：

| 组合 | 有效并行度 | 预期落库吞吐 |
| --- | --- | --- |
| 单行 + 同步 | 1 | **43 单/s**（实测） |
| **单行 + MQ** | min(64, 50, **1**) = **1** | **37.7 单/s**（实测） |
| **12 SKU + MQ** | min(64, 50, **12**) = **12** | **~456 单/s**（待验证） |
| 100 桶 + MQ | min(64, **50**, 100) = **50**（连接池先到顶） | 受连接池与 fsync 约束 |

**现实印证（E.4）**：大厂大促单品 = `Redis 按 stock:{skuId}:{分段} 存多段库存 + Lua 原子扣减，DB 异步落单`，即 **"分桶 + 削峰的组合"** —— 正是本项目"分桶"与"MQ"两条路的合体。

### 6.5 收益量级排序（D.19）

| 层 | 拦下多少 |
| --- | --- |
| 限流 | 无效流量（防刷/重放） |
| **Redis 预扣** | **20,000 → 200（挡掉 99%）** ✅ 收益最大 |
| MQ 削峰 | 脉冲摊平，受理 P90/P99 ↓6~9 倍 |
| 分桶 / 多 SKU | 落库并发度 1 → N（12 SKU 预计 12 倍） |
| DB CAS | 保证不超卖 |

## 7. 关键设计取舍

### 7.1 最大取舍：先做多 SKU，而不是分桶（D.3 / D.18）

| | 多 SKU | 库存分桶 |
| --- | --- | --- |
| 桶从哪来 | **天然存在**（不同商品 = 不同行） | 需要人为拆行 |
| 路由 | 由用户选商品决定 | 需要路由算法 |
| 一人一单 | 天然按商品隔离 | 需保证判重集合不分桶 |
| 回补 | 回补对应商品行，天然正确 | 必须记录 `bucketId` |
| 改造量 | **0** | 表 + Lua + 回补记录 + 校验脚本 |
| 假售罄风险 | 无 | 有 |

> **多 SKU 是"白捡的并行度"；分桶是"单点爆款不得已才付的复杂度"。**

**判据（D.18）**：`单个 SKU 排空时间 = 该 SKU 库存 ÷ 单行吞吐`，若最大那个 SKU 能在可接受时长内卖完 → 不需要分桶。

| 场景 | 最大单 SKU 库存 | 生产环境排空（~500/s） | 需要分桶吗 |
| --- | --- | --- | --- |
| 12 个 SKU，各 200 件 | 200 | 0.4 s | ❌ 不需要 |
| 1 个爆款 10 万台 + 长尾 | 100,000 | 200 s | ✅ 必须分桶 |

⚠️ **环境差异极大**（本项目实测仅 38 单/s）：同一 5,000 件库存在本项目环境需 **132 s** → 必须分桶；在快环境则不必。**绝对容量数字不可外推。**

### 7.2 选桶层次取舍：Redis 预扣层 vs DB 层（D.14）

| | 做法 A（推荐，本系统形态） | 做法 B（DB 层挑桶） |
| --- | --- | --- |
| 挑桶位置 | Redis Lua 挑"有货的桶" | 应用层 `id = base + hash % N` |
| 撞空桶 | 预扣阶段**不会撞** | 需换桶重试（有界 3~5 次） |
| 失败代价 | 挡在最便宜的一层 | 20 万请求 = 20 万次 attempt 打到最贵的 DB 层 |

> 若坚持在 DB 层挑桶，必须抽成**独立短事务且放在主事务之前**（`REQUIRES_NEW`），且回滚后**不能直接换桶**（事务已 `rollback-only`，须新开事务，否则 `UnexpectedRollbackException`）；换桶也必须**整笔业务事务重做**（一次下单含 5 个写操作）。

### 7.3 固定路由 vs 动态探测

| 策略 | 优点 | 缺点 |
| --- | --- | --- |
| A. 固定路由 `userId % N` | 确定、重试可复现、幂等友好 | 负载不均；某桶先空时命中它的用户会**假售罄** |
| B. 轮询 / 随机 | 消耗最均匀 | 可能撞空桶，需要换行重试 |
| **C. 随机起点 + 顺序探测**（本系统采纳） | 均匀 + 命中率高 | 逻辑略复杂；**不可复现 → 必须记录 `bucketId`** |

### 7.4 其他关键取舍

- **分桶不消除锁，只分摊锁**；收益有上限（全局资源共享 → 平台化）。
- **分桶不防超卖**（防超卖靠 CAS），只影响并发度。
- **"重新排队"方向错误**：DB 层排队最贵，正确做法是把 99% 请求挡在 DB 之前（本系统已做到）。
- **代价清单**：记账粒度变复杂（`SUM(stock)`）、**假售罄**、回补需记录 `bucketId`、一人一单集合不能分桶、校验断言要改（`verify_results.py` 的"库存扣减到 0""sold == total"都要跟着改）。
- **配比铁律**：想让并行度达到 P，必须同时满足 ① 消费者线程 ≥ P　② 连接池 ≥ P　③ 桶数 ≥ P　④ 实例数 × 池 ≤ `max_connections`。**三项里只有前两项能靠改配置解决，桶数只能改数据模型或场景。**

## 8. 结论速览

| 问题 | 答案 |
| --- | --- |
| 分桶策略 | 把 1 行热点拆成 N 行，每单只扣 1 行；路由在扣减前即时算好，无"跳转" |
| 桶数量 / 分片规则 | `桶数 ≈ 峰值TPS ÷ 单行TPS`；`(item_id, bucket_no)` schema，各 SKU 可配不同桶数；**受连接池截断，非越多越好** |
| 扣减 / 回滚分配 | Lua 一次原子选桶（返回 `{1, idx}`）→ DB 只扣该桶；**回补必须记 `bucketId` 还回原桶**；异步需把 `bucketNo` 放进消息体 |
| 并发控制 | InnoDB 行级锁（不同行并行、同行串行）+ CAS 兜底；**锁被分摊而非消除**；空桶才换行，被锁只能等 |
| 一致性 | 选桶保证"对账口径对齐"而非一致性；真正靠 **双防线 + 最终一致 + 逐桶对账**；回补幂等是现存隐患 |
| 与 MQ 的差异 | MQ 提升**受理侧**（P99 ↓6~9 倍、脉冲有界），**不提落库吞吐**（并行度仍为 1）；**分桶才是把并行度 1→N、真正提吞吐的那一层**，二者是"容器 vs 资源"的互补关系 |
