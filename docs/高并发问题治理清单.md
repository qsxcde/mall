### 1.3 容量粗估（供参考，非压测结论）

假设下单事务耗时 **50ms**：

- 全局下单吞吐上限 ≈ `50 连接 ÷ 0.05s ≈ **1000 QPS**`
- 同一热点 SKU 的行锁在整个事务期间独占 → 单爆款商品吞吐 ≈ `1 ÷ 0.05s ≈ **20 QPS**`
- 50 条连接占满后，其余 ≈150 个 Tomcat 线程**不是快速失败，而是挂起 30 秒**，随后线程池耗尽 → **全站雪崩**

> 结论：**几十 QPS 平稳；热点单品或瞬时峰值会立刻触及瓶颈，且没有兜底。**

## 三、P0 级问题详解

### P0-1 连接池与线程池配比失衡

**证据**

```1:7:backend/src/main/resources/application.yml
server:
  port: 8080
  shutdown: graceful
  tomcat:
    threads:
      max: 200
      min-spare: 20
```

```7:11:backend/src/main/resources/application-prod.yml
    hikari:
      pool-name: GeekMallHikariCP
      minimum-idle: 10
      maximum-pool-size: 50
      connection-timeout: 30000
```

**影响**
200 个并发请求抢 50 条连接，超出部分在 `getConnection()` 上**阻塞等待 30 秒**而非快速失败。
结果是：连接池耗尽 → 线程全阻塞 → Tomcat 线程池耗尽 → accept 队列满 → **全站不可用**。
同时 MySQL 默认 `innodb_lock_wait_timeout=50s > connection-timeout=30s`，行锁等待同样会长时间挂住连接。

**修复方案**
1. 按「数据库能承受的并发写」反推 Tomcat 线程数，建议 Tomcat `threads.max` 降到 **100~120**，与连接池形成合理比例；
2. `connection-timeout` 降到 **3000ms**（快速失败，配合前端重试/排队页）；
3. Hikari `maximum-pool-size` 提到 **80~100**，并补齐 prod 缺失的 `idle-timeout: 600000` / `max-lifetime: 1800000`；
4. MySQL 侧设置 `innodb_lock_wait_timeout = 5`，让锁冲突快速报错而不是拖死连接；
5. Controller/Service 层加 `spring.jpa` 无关，改为在 `@Transactional` 上显式加 `timeout`，见 P2-8。

**验收标准**
- 压测注入 2 倍峰值流量时，接口表现为**快速失败（≤3s 返回 503/繁忙）**，而非整体挂起；
- Actuator `/actuator/metrics/hikaricp.connections.pending` 峰值 ≤ 10，且不持续增长。

### P0-2 下单事务过长，库存行锁持有时间 = 整个事务

**证据**

```222:242:backend/src/main/java/com/geekmall/modules/trade/service/impl/TradeServiceImpl.java
        // 扣库存：带 stock >= qty 条件，受影响行数为 0 即库存不足，整体回滚
        for (OrderItemDraft draft : drafts) {
            int rows = productMapper.deductStock(draft.product().getId(), draft.qty());
            if (rows == 0) {
                throw new BizException(ResultCode.OUT_OF_STOCK,
                        "商品「" + draft.product().getTitle() + "」库存不足");
            }
        }

        String orderNo = persistOrder(userId, address, drafts, shippingFee, discount,
                dto.getCouponId(), dto.getPayMethod(), dto.getRemark());

        if (coupon != null) {
            couponService.markUsed(userId, coupon.getId(), orderNo);
        }

        // 下单成功，从购物车移除已结算商品
        items.forEach(item -> cartService.remove(userId, item.getId()));
```

扣库存发生在事务**中段**，其后还有：插入订单主表、循环插入明细、插入状态日志、核销优惠券、循环删购物车。
这些 SQL 全部在持有 `pms_product` 行锁的前提下串行执行。

SQL 条数统计（N = 结算 SKU 数）：

| 步骤 | 条数 |
|---|---|
| 查购物车 + 查地址 | 2 |
| 循环查商品（N+1） | N |
| 优惠券校验 | 2 |
| 循环扣库存 | N |
| 插订单主表 + 插状态日志 | 2 |
| 循环插明细（未批处理） | N |
| 核销优惠券 | 1 |
| 循环删购物车（每轮 select+delete） | 2N |
| **合计** | **≈ 6N + 7**（买 10 件 ≈ 67 条） |

**影响**
行锁持有时间 ≈ 67 条 SQL 总耗时。热点商品的所有下单被迫串行，吞吐被压到十位数 QPS。

**修复方案**
1. **调整语句顺序**：把「扣库存」挪到事务最末尾（紧邻提交前），让长耗时操作（查商品、插订单、删购物车）先完成；
2. **循环插入改批量**：`orderItemMapper` 用 MyBatis-Plus `saveBatch`，让 `rewriteBatchedStatements=true` 真正生效（见 P2-4）；
3. **购物车删除移出主事务**：下单成功后通过 `@TransactionalEventListener(AFTER_COMMIT)` 异步清理，失败不影响订单；
4. **商品查询批处理**：用 `selectBatchIds` 替代循环 `selectById`（N+1）；
5. 中期可引入 **Redis 预扣 + 异步落库**（下单进 MQ，由消费者串行扣减 DB 库存），彻底把行锁移出请求线程。

**验收标准**
- 单事务 SQL 数从 6N+7 降至 ≈ 2N+6；
- 下单 RT（P95）下降 ≥ 40%；
- 热点 SKU 下单吞吐提升 ≥ 3 倍。

### P0-3 无序加锁导致死锁，且无重试机制

**证据**：同上 `TradeServiceImpl.java:222-228`，`drafts` 的顺序来自购物车返回顺序，不同用户不同。

**影响**
用户 A 的购物车顺序是 (SKU1, SKU2)，用户 B 是 (SKU2, SKU1)。并发下单时 A 持 SKU1 等 SKU2、B 持 SKU2 等 SKU1 → **InnoDB 死锁**。
MySQL 会回滚其中一个事务，但因为**代码没有重试机制**，用户直接看到「下单失败」。

**修复方案**
```java
// 按 productId 升序排序，保证所有事务加锁顺序一致
List<OrderItemDraft> sorted = drafts.stream()
        .sorted(Comparator.comparing(d -> d.product().getId()))
        .toList();
for (OrderItemDraft draft : sorted) {
    ...deductStock...
}
```
并补充死锁重试：捕获 `DeadlockLoserDataAccessException` / SQLState `40001`，退避重试 2~3 次。

**验收标准**
- 多线程并发下单同一批 SKU（乱序），压测 5 分钟 **0 死锁**；
- MySQL `SHOW ENGINE INNODB STATUS` 中无 Lock wait timeout 记录。

### P0-4 库存可被重复回退（账面错误）

**证据**

```24:26:backend/src/main/java/com/geekmall/modules/product/mapper/ProductMapper.java
    @Update("UPDATE pms_product SET stock = stock + #{qty}, sales = GREATEST(sales - #{qty}, 0) "
            + "WHERE id = #{productId}")
    int restoreStock(@Param("productId") Long productId, @Param("qty") int qty);
```

`WHERE` 只有主键，**没有任何 CAS 条件**（无 version、无状态判断、无幂等表）。

配合非原子的状态流转：

```66:70:backend/src/main/java/com/geekmall/modules/trade/service/OrderStateMachine.java
        Order update = new Order();
        update.setId(order.getId());
        update.setStatus(target.getCode());
        applyTimestamp(update, target, remark);
        orderMapper.updateById(update);
```

**影响**
用户重复点「取消」或「取消」与超时任务并发时：两个事务都读到 `PENDING_PAY` → 都通过 `canTransferTo` → **都执行 `restoreStock`** → 同一订单库存退回两次→ 超卖 + 销售额为负修正。
这是**唯一会造成资金/实物账面错误**的缺陷，且数据库无唯一索引可以兜底。

**修复方案**
1. 状态机 `transfer` 改为带 CAS 的条件更新：
   ```java
   // OrderMapper 新增
   @Update("UPDATE oms_order SET status = #{target} ... WHERE id = #{id} AND status = #{expected}")
   int updateStatusWithCas(@Param("id") Long id, @Param("expected") Integer expected, ...);
   // 返回 0 → 说明已被其他线程流转，直接返回（幂等）
   ```
2. 新增库存回退幂等表 `inventory_rollback_log(order_no, product_id)`，加 **唯一索引** `(order_no, product_id)`；回退前先插入该表，插入失败则跳过回退；
3. 或退一步：`restoreStock` 加幂等标记 `WHERE id = ? AND ... `配合订单状态 CAS（方案 1 落地后即可自然幂等）。

**验收标准**
- 并发 100 线程同时取消同一订单 → 库存**只回退 1 次**，`sales` 不出现负值修正；
- 状态机 `transfer` 返回 0 行时正确走「已被其他操作处理」分支。

1. **接口级限流**：接入 Sentinel 或 Bucket4j，对 `/api/v1/trade/submit`、`/api/v1/seckill/*`、`/api/v1/sms/*` 做 QPS / 并发数限制；

- 对下单接口以 10 倍容量压测：**超出的请求被快速拒绝（429/503）**，其余请求 RT 无明显劣化；
- 秒杀接口满载时，普通浏览/下单接口仍正常响应。

## 四、P1 级问题详解

### P1-1 完全没有业务缓存

**证据**：全仓库 `@Cacheable` / `@CacheEvict` / `@EnableCaching` **0 命中**。

```106:122:backend/src/main/java/com/geekmall/modules/product/service/impl/ProductServiceImpl.java
    public HomeFloorVO homeFloors() {
        HomeFloorVO vo = new HomeFloorVO();
        vo.setCategories(categoryTree());
        vo.setHotProducts(productMapper.selectList(new LambdaQueryWrapper<Product>()
                        .eq(Product::getStatus, ON_SHELF)
                        .orderByDesc(Product::getSales)
                        .last("limit 8"))
                .stream().map(ProductConverter::toCard).toList());
        vo.setNewProducts(productMapper.selectList(new LambdaQueryWrapper<Product>()
                        .eq(Product::getStatus, ON_SHELF)
                        .eq(Product::getIsNew, 1)
                        .orderByDesc(Product::getId)
                        .last("limit 8"))
                .stream().map(ProductConverter::toCard).toList());
        return vo;
    }
```

**影响**：首页（最高频接口）每次都要 3 次查询；商品详情、推荐位、订单列表同理，全部直穿 MySQL。

**修复方案**
1. 首页楼层、分类树、商品详情、推荐位接入 Redis 缓存；
2. 防击穿：缓存 miss 时用 `SETNX` 互斥重建（单飞），避免热点 key 失效瞬间打爆 DB；
3. 防雪崩：TTL 叠加随机抖动（如 `5min + random(0, 60s)`）；
4. 防穿透：不存在的商品 id 缓存空值（短 TTL，5~60s）；
5. 更新策略：商品上下架 / 改价 / 库存变动时 `@CacheEvict`（或与库存热点区分对待——库存字段不入缓存）。

**验收标准**
- 首页压测 QPS 提升 ≥ 5 倍，MySQL CPU 无显著上升；
- 缓存全部失效后重建期间，DB QPS 无尖刺。

### P1-2 每请求同步访问 Redis + prod 未启用连接池

### P1-4 下单幂等键不可靠

**证据**

```168:174:backend/src/main/java/com/geekmall/modules/trade/service/impl/TradeServiceImpl.java
            redisTemplate.opsForValue().set(idempotentKey, IDEMPOTENT_PENDING, IDEMPOTENT_LOCK_TTL);
        }

        try {
            String orderNo = doSubmit(userId, dto);
            if (idempotentKey != null) {
                redisTemplate.opsForValue().set(idempotentKey, orderNo, IDEMPOTENT_RESULT_TTL);
```

三个缺陷：
1. 第 168 行用 **`set` 而不是 `setIfAbsent`** → 并发的同 `requestId` 请求会互相覆盖占位，**起不到去重作用**；
2. 结果在 **DB 事务提交之后**才写入 Redis → 提交成功但写 Redis 前崩溃，会留下 5 分钟 `PENDING` 占位；占位过期后重入会**生成第二张订单**；
3. `requestId` 为空时（前端未传）**整段幂等逻辑被跳过**。

**修复方案**
1. 占位改为 `setIfAbsent(key, PENDING, 10s)`（Redisson 的 `tryLock` 亦可），抢不到则直接返回「处理中」；
2. 把「写幂等结果」移入事务提交后的回调：`TransactionSynchronizationManager.registerSynchronization(...).afterCommit(...)`；
3. 兜底：在订单表用 `(user_id, request_id)` **唯一索引**做最终防线（request_id 允许为空时不参与）；
4. 前端强制生成 `requestId`（UUID），后端对空值直接拒绝或降级为「同用户 3 秒内重复同购物车指纹」判重。

**验收标准**
- 同一 `requestId` 并发 100 次提交 → **只生成 1 张订单**，其余返回同一订单号；
- 进程在 commit 后被 kill，重启后重试不会重复建单。

### P2-6 秒杀链路的三个隐患

**证据**

```98:136:backend/src/main/java/com/geekmall/modules/marketing/service/impl/SeckillServiceImpl.java
    @Transactional(rollbackFor = Exception.class)
    public String grab(Long userId, Long itemId, Long addressId) {
```

问题：
1. **补偿非原子**：`catch` 里回补 Redis，若进程在 DB 回滚与 Redis 回补之间崩溃，活动库存被**永久占用**；

3. 把 Redis 预扣移到**事务之外**（先扣 Redis → 再进 DB 事务），缩短行锁持有；
4. 更彻底：秒杀异步化——抢购成功后写 MQ，由消费者串行落库。

## 八、附录：当前做对的地方（改造时请勿破坏）

1. **库存原子扣减**（`ProductMapper.java:19-21`）：`UPDATE ... SET stock = stock - N WHERE id = ? AND stock >= N`，依赖 InnoDB 行锁，**不会超卖**，是全项目最关键的正确实现。
