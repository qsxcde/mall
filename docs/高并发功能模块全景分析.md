## 一、结论摘要

### 1.1 一句话结论

**C 端三条核心链路的高并发问题已被系统性治理并有实测背书；真正的风险已经转移到两个盲区：
① 商家端 34 个接口（无缓存、无中间表、全表扫描 + 单事务大批量写，且从未压测）；
② C 端其余 14 类写接口（限流覆盖率 2/117，且多为从未验证的并发正确性）。**

### 1.2 风险等级分布

| 等级 | 数量 | 典型模块 |
|---|---|---|
| 🔴 **极高** | 5 | B 端经营看板聚合、B 端发货中心、B 端批量改价（打穿 C 端缓存）、B 端批量发货事务、限流覆盖率 2/117 |
| 🟠 **高** | 6 | 秒杀限流占用 Tomcat 线程、单热点 SKU 行锁、缓存击穿、登录 bcrypt、领券/兑换热点行锁、B 端顶栏搜索无防抖 |
| 🟡 **中** | 8 | 购物车并发 add、短信验证码刷取、签到集中写、未读数实时 COUNT、深分页、订单号多实例、日志放大、定时关单积压 |
| 🟢 **低** | 5 | 收藏/足迹、评价、售后、支付回调、取消订单（均有唯一索引或 CAS 兜底） |

### 1.3 与既有结论的对照（已达成 vs 仍欠缺）

## 二、已治理的高并发核心链路（复核）

这三条链路有完整压测背书，此处只做复核并列出**剩余风险**。

### 2.1 秒杀抢购 🔴→🟠 高风险（已大幅缓解）

| 维度 | 内容 |
|---|---|
| **业务场景** | 限量商品定时开抢，N 万用户在同一秒点击「马上抢」，库存远小于请求量（500 抢 50 件） |
| **并发压力来源** | ① **瞬时惊群**：开抢瞬间请求量从 0 跳到峰值；② **热点集中**：全部流量打在同一个 `itemId` 上；③ **Redis 原子操作高频**：每个请求 1 次 Lua 脚本执行；④ 成功后**同步落库**建单 |
| **当前实现** | Redis Lua 原子预扣（`SeckillServiceImpl.java:54-69`，GET→判重→DECR→SADD→EXPIRE 一步完成）+ `@RateLimit` 全局 8000/s（`SeckillController.java:70`）+ `seckillExecutor` 独立舱壁（core64/max128/queue2000/`AbortPolicy`）+ `DeferredResult` 释放 Tomcat 线程（`SeckillController.java:78-99`）+ DB 二次 CAS 扣减兜底 |
| **实测** | 持续 3594 QPS / P99 403.9ms；1000 并发齐发 165.7 TPS / P99 1127ms；**0 个 5xx**（等级 A） |
| **剩余瓶颈** | **① 限流拦截器在 Tomcat 工作线程上执行 Redis INCR**（`RateLimitInterceptor.java:59`）——1000 并发瞬时占满 120 个 Tomcat 线程，实测把普通下单 P99 从 15.2ms 抬到 183.8ms（**12.1 倍**）。这是**唯一未被隔离**的能力缺口。<br>**② 排队换稳定性是有意取舍**：1000 请求只有 128 个立即执行，P50 819ms 属设计预期，非缺陷。<br>**③ 限流阈值 8000/s 远高于线程池容量 2064**，实际瓶颈是线程池，阈值形同虚设。<br>**④ 秒杀商品元数据 3s 本地缓存**（`SeckillServiceImpl.java:89-92`）与 Redis 库存是双源，靠 DB 兜底保证不超卖 |
| **风险等级** | 🟠 **高**（正确性已解决，隔离性未解决） |

### 2.2 普通下单 🟠 中高风险

| 维度 | 内容 |
|---|---|
| **业务场景** | 大促期间用户集中提交订单，涉及库存扣减、优惠券核销、购物车清理、订单落库 |
| **并发压力来源** | ① **同一热点 SKU 的行锁争抢**；② **跨 SKU 死锁**；③ 幂等键 Redis 高并发读写；④ 每单触发 1 条异步站内消息（`@Async`） |
| **当前实现** | 幂等 `setIfAbsent` + `afterCommit` 回写 + `uk_user_request` 兜底（`TradeServiceImpl.java:200-208, 534-552`）；按 `productId` 升序加锁 + 死锁退避重试 3 次（`:292-293, 228-257`）；事务瘦身（`selectBatchIds` 消 N+1、明细批量 INSERT、扣库存移到事务末尾）；`@RateLimit` 200/s 按用户（`TradeController.java:39`） |
| **实测** | 12 个非热点 SKU **463.5 TPS**；单一热点 SKU **165.7 TPS**；三轮压测死锁零复现（等级 A） |
| **剩余瓶颈** | **① 单热点 SKU 行锁串行是物理上限**（463.5 → 165.7 TPS），只能靠 MQ 异步化或库存分桶突破。<br>**② 订单号 `AtomicLong` 秒内自增 + 4 位实例随机位**（`TradeServiceImpl.java:60,89`）——单实例已修复撞号，**多实例未验证**（8.1）。<br>**③ 幂等键释放用 `delete` 而非 Lua 比对删除**（`:216`），理论上可能误删他人占位（边界场景）。<br>**④ 购物车异步清理竞态**已从 9/10000 降至 0，但理论窗口未完全关闭 |
| **风险等级** | 🟠 **中高**（正确性达标，吞吐受物理约束） |

### 2.3 商品读链路（首页/详情/分类/推荐） 🟡 中低风险

| 维度 | 内容 |
|---|---|
| **业务场景** | 首页、分类页、商品详情页，是大促期间**流量最大的入口**（占比通常 80%+） |
| **并发压力来源** | ① 海量用户同时浏览，**读多写少**；② 首页一次挂载扇出 **4 个请求**、商详 **3 个**（`HomeView.vue:59`、`ProductView.vue:67`）；③ 缓存同时失效瞬间的**回源风暴** |
| **当前实现** | Spring Cache 分级 TTL（`CacheConfig.java:48-51`：`homeFloors` 5m / `categoryTree` 30m / `productDetail` 3m / `productRecommend` 5m）+ 令牌 30s Caffeine 本地缓存（`JwtAuthenticationFilter.java:57-60`） |
| **实测** | 9092 QPS / P99 73.8ms / 成功率 100%（等级 A） |
| **剩余瓶颈** | **① `@Cacheable` 未开 `sync=true`** → 热点 key（尤其 `homeFloors`）TTL 到期瞬间大量并发同时回源 MySQL，**缓存击穿**风险明确存在但从未压测。<br>**② `disableCachingNullValues()`**（`CacheConfig.java:44`）→ 不存在的商品 ID **无空值缓存**，可被构造请求穿透打 DB。<br>**③ 无 TTL 抖动** → 同类 key 同时创建则同时失效，有**雪崩**形态。<br>**④ `productDetail` TTL 仅 3 分钟**，热点商品周期性击穿。 |
| **风险等级** | 🟡 **中低**（稳态达标，失效瞬间是盲区） |

## 三、C 端未压测的写接口（首次评估，全部等级 C）

> 全仓 **117 个端点，仅 2 个加了 `@RateLimit`**（`SeckillController.java:70`、`TradeController.java:39`）。
> 以下接口均无接口级限流，且**从未做过并发正确性验证**。

### 3.1 领券 / 积分兑换 🟠 高风险

| 维度 | 内容 |
|---|---|
| **业务场景** | 大促前「整点抢券」、积分商城限量兑换 —— 与秒杀同构的**限量抢**场景 |
| **并发压力来源** | ① 定时开抢的瞬时惊群；② 所有请求争抢**同一张券模板/同一积分商品的行锁**；③ 无缓存，每次领券都要读模板表 |
| **当前实现** | 领券：`templateMapper.deductStock()` CAS 扣库存 + `uk_user_template` 唯一索引兜底重复领取（`CouponServiceImpl.java:92-105`）；兑换：`pointsGoodsMapper.deductStock()` CAS + 条件扣积分（`PointsServiceImpl.java:53-59`） |
| **并发正确性** | ✅ **基本安全**——CAS 防超发、唯一索引防重复领，模式与秒杀一致，是正确实现 |
| **性能瓶颈** | **① 无缓存**：`claim()` 每次都要 `selectById` 模板 + `selectCount` 已领数量，全部直穿 DB。<br>**② 热点行锁**：限量大额券等同于秒杀热点 SKU，推测吞吐上限与「单热点 SKU 165 TPS」同量级——但**完全没压测过**。<br>**③ `refreshPercent()` 每次领取都回写模板表**（`CouponServiceImpl.java:106`），放大同一行的写冲突。<br>**④ 无限流**：可被脚本批量刷券。<br>**⑤ 无 `@CacheEvict`**：券模板变更不会失效 C 端券列表（该列表本身也无缓存） |
| **风险等级** | 🟠 **高**（正确性 OK，**吞吐未知 + 无限流**） |
| **建议** | 复用秒杀模式：Lua 原子预扣 + 独立限流；`refreshPercent` 改为异步/定时批量刷新 |

### 3.2 登录 / 短信验证码 🟠 高风险

| 维度 | 内容 |
|---|---|
| **业务场景** | 大促开场前用户集中登录；验证码可被脚本刷取 |
| **并发压力来源** | ① **bcrypt 是 CPU 密集型**（`AuthServiceImpl.java:57` `passwordEncoder.matches`），单次校验约 50-100ms CPU；② **每次登录写 Redis 令牌**（`:134-135`）；③ 验证码接口无 IP 维度限流 |
| **当前实现** | 验证码 60s 冷却用 `setIfAbsent`（`SmsCodeService.java:41`）✅；令牌存 Redis 支持踢下线 |
| **性能瓶颈** | **① bcrypt 无成本因子配置暴露，且无限流** —— 100 QPS 的暴力破解即可持续占用 8 核中的数核（推算：100 × 80ms ÷ 1000ms ≈ **8 核**），**单接口即可打满 CPU**。这是**全项目最容易造成 CPU 型雪崩**的点。<br>**② 无失败次数锁定/验证码前置** → 撞库无成本。<br>**③ 验证码仅按手机号冷却 60s**，**无 IP/全局维度限流** → 换手机号即可无限刷，接真实短信通道后是**直接资损**。<br>**④ 登录写 Redis 是同步阻塞**在 Tomcat 线程上。<br>**⑤ `findUserByAccount` 用 `OR` 查询**（`:140-142`），`username`/`phone` 需各自有索引否则易走错执行计划 |
| **风险等级** | 🟠 **高**（CPU 型拒绝服务 + 资损双风险） |
| **建议** | 优先补 IP 维度限流（含 `/auth/sms-code`、`/auth/login`、`/auth/register`）+ 失败 N 次锁定；bcrypt cost 显式化并考虑降级为更低成本算法 |

### 3.3 购物车 🟡 中风险

| 维度 | 内容 |
|---|---|
| **业务场景** | 大促前用户批量加购；下单前频繁改数量/勾选 |
| **并发压力来源** | ① 高频读写同一用户的购物车行；② `addBatch` 循环调用 `add()`（`CartServiceImpl.java:77-81`），N 个商品 = N 轮 select+insert/update；③ **与下单后的异步清理竞争** |
| **当前实现** | `add()` 为 check-then-insert/update（`CartServiceImpl.java:54-72`），同规格累加合并复用同一行 |
| **性能瓶颈** | **① `add()` 无唯一索引保护** —— `findExist` + `insert` 之间存在竞态窗口，并发加入同一商品会产生**重复行**（不像收藏那样有 `DuplicateKeyException` 兜底）。<br>**② `addBatch` 无批量化**：循环单条操作，`rewriteBatchedStatements` 无效。<br>**③ 清理竞态**：下单成功后 `@Async` 按 id 删除购物车（`CartCleanupListener.java:26-27`），与用户同时 `add()` 合并复用同一行 id 竞争，历史上有 9/10000 的失败率，现靠"数量乐观守卫"缓解但**理论窗口未关闭**。<br>**④ 无限流** |
| **风险等级** | 🟡 **中**（脏数据 + 竞态，不影响资金） |
| **建议** | 加 `uk_user_product_spec` 唯一索引；改「条件更新 + 影响行数判断 + 回退插入」 |

### 3.4 签到 / 收藏 / 足迹 🟡 中低风险

| 模块 | 场景与压力 | 现状 | 风险 |
|---|---|---|---|
| **签到** `UserServiceImpl.java:164-170` | 每日零点前后集中签到；同一用户所有请求打同一行 | `selectCount` 预检 + `uk_user_date` 唯一索引兜底 ✅ | 🟡 中——**零点集中写**，`selectCount + insert` 有竞态窗口，靠唯一索引兜底但**未捕获 `DuplicateKeyException`**（相比收藏少了这层），并发签到会抛 500 而非友好提示 |
| **收藏 toggle** `CollectionServiceImpl.java:57-73` | 商品详情页高频点击；每次点击 1 次写 | check-then-insert + `DuplicateKeyException` 兜底 ✅ | 🟢 低——已正确处理 |

### 3.5 站内消息 / 未读数 🟡 中风险

| 维度 | 内容 |
|---|---|
| **业务场景** | 每笔订单状态变更都触发 1 条站内消息（`OrderStatusMessageListener.java:32-33`），大促期间消息写入量与订单量同量级 |
| **并发压力来源** | ① **写放大**：1 单 = 1 条消息 INSERT + 提交后异步任务；② 未读数被前端高频查询 |

| **风险等级** | 🟡 **中** |

## 四、商家端（B 端）—— 🔴 最高风险盲区

> 既有文档 8.1 明确承认：「本轮新增商家端接口 34 个（含跨表聚合统计）**未纳入任何压测**，性能未知」。
> 本节为首次全量评估。**结论：该模块没有任何缓存、没有聚合中间表、没有异步化，且批量写全部包在单个事务里逐行执行。**

### 4.1 B 端拖垮 C 端的直接通道 🔴 极高风险

**`MerchantProductServiceImpl` 的三个写操作都带 `@CacheEvict(allEntries = true)`，一次操作清空 C 端全部 4 个缓存：**

```java
// MerchantProductServiceImpl.java:92-93 / 141-142 / 160-161
@CacheEvict(value = {"homeFloors","categoryTree","productDetail","productRecommend"}, allEntries = true)
```

| 维度 | 内容 |
|---|---|
| **业务场景** | 商家批量改价 / 批量上下架，大促前集中操作 |

### 4.4 批量发货 / 关单：单事务 N 次写 🔴 极高风险

```java

    List<Order> orders = selectOwned(shopId, dto.getIds());  // L108

        if (current != PENDING_SHIP) throw ...;               // L112 ⚠️ 一笔不合法 → 整批回滚

    }

```

| 维度 | 内容 |
|---|---|
| **业务场景** | 大促后商家批量发货，一次勾选 50~200 单 |
| **并发压力来源** | ① 批量操作本身；② 多个商家/多个客服并发发货；③ 每单提交后还要往 `messageExecutor` 塞 1 条异步消息任务 |
| **性能瓶颈** | **① 锁范围 = 批次大小**：100 单批量发货 = 100 行 `oms_order` 排他锁持有到事务提交。<br>**② 死锁**：`selectOwned`（`:270-272`）用 `IN (order_no)` 返回**无序**，两个并发批次 id 集合有交集且更新顺序相反 → **直接死锁**（C 端已用「按 productId 排序加锁」修复，B 端**没有对应修复**）。<br>**③ 失败成本极高**：`:112` 遇第一笔非法状态即抛异常，前面已做的 N 条 UPDATE/INSERT **全部回滚白写**。<br>**④ 无幂等**：`close`（`:139-141`）直接调状态机，重复点击后果依赖 CAS |
| **同类** | `MerchantShipmentServiceImpl.deliver` `:140-160`（每迭代最多 3 次写）、`print` `:116-137`、`MerchantAftersaleServiceImpl.resolve` `:96-153`（`:146-151` 任意一笔 rows==0 即整批回滚）、`MerchantProductServiceImpl` 批量改价/上下架 `:143-156/:162-190` |
| **风险等级** | 🔴 **极高** |
| **建议** | ① 循环前按主键**排序加锁**（复用 C 端已验证的模式）；② 改**分批提交**或单笔独立事务 + 逐笔结果返回；③ 非法状态改为**跳过并汇总**，而非整批回滚；④ 批量发货异步化 |

### 4.5 B 端关键词搜索：LIKE '%kw%' + 相关子查询 🟠 高风险

| 位置 | SQL 形态 |
|---|---|

### 🔴 最显著的请求放大点：B 端顶栏全局搜索无防抖

