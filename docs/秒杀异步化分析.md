# 秒杀异步化:为什么需要,以及如何实现

> 基于本项目(`geekmall` 单体后端)的实际代码与压测报告分析。
> 结论先行:**项目当前做的是「线程异步」,不是「业务异步」;两者解决的不是同一个问题。**

---

## 一、先破题:三种"异步"不是一回事

"异步"这个词在秒杀语境下至少有三层含义,混用会导致方案走偏:

| 层级 | 机制 | 效果 | 请求-响应关系 |
|---|---|---|---|
| ① **线程异步** | Servlet Async / `DeferredResult` + 业务线程池 | 释放 Tomcat 容器线程 | **仍然同步等待结果** |
| ② **业务异步** | MQ / Redis Stream 削峰 | 请求立即返回"排队中",后台慢慢处理 | **解耦,结果延迟可见** |
| ③ **IO 异步** | NIO / 响应式 / CompletableFuture | 不阻塞线程等待 IO | 依实现而定 |

### 项目现状:停在 ①

```78:98:backend/src/main/java/com/geekmall/modules/marketing/controller/SeckillController.java
DeferredResult<Result<String>> deferred = new DeferredResult<>(GRAB_TIMEOUT_MS);
try {
    seckillExecutor.execute(() -> {
        try {
            deferred.setResult(Result.ok(seckillService.grab(userId, itemId, addressId)));
        } catch (BizException e) {
            // 库存不足 / 重复抢购等属于预期内的失败，返回业务码而非 5xx
            deferred.setResult(Result.fail(e.getCode(), e.getMessage()));
        } catch (Exception e) {
            log.error("秒杀处理异常：userId={}, itemId={}", userId, itemId, e);
            deferred.setResult(Result.fail(ResultCode.SYSTEM_ERROR.getCode(),
                    ResultCode.SYSTEM_ERROR.getMsg()));
        }
    });
} catch (RejectedExecutionException e) {
    // 舱壁已满：快速失败，绝不排队到拖垮系统
    log.warn("[秒杀舱壁] 线程池已满，快速拒绝：userId={}, itemId={}", userId, itemId);
    deferred.setResult(Result.fail(ResultCode.TOO_MANY_REQUESTS.getCode(),
            "当前抢购人数过多，请稍后再试"));
}
return deferred;
```

`DeferredResult` 确实把 Tomcat 工作线程让出来了(NIO 连接器持有连接即可),这是**真实的收益**。但请注意:

- 用户这条 HTTP 请求**仍然挂在那里等** `grab()` 返回,`GRAB_TIMEOUT_MS = 10_000L` 意味着最长等 10 秒;
- `grab()` 内部依然**同步落库**(`grabInTx` 的 DB 事务在同一个执行链上);
- 业务线程池只是"换了个地方阻塞",**没有把请求与结果解耦**。

所以它是**"半异步"——解耦了线程,没解耦请求-结果**。真正的秒杀异步化是 ②。

## 二、为什么需要异步:六个理由,逐个对应本项目的实测数据

### 1. 秒杀是**脉冲**,而数据库能力是**恒定**的

报告显示洪峰集中在**第 12~14 秒**(约 2 秒的突发)。而 Hikari 连接池是 `50(dev)/100(prod)` 条,**这是一个恒定值**。

> 用恒定能力去承接脉冲,只有两种结局:要么按峰值配置资源(99% 时间浪费),要么在峰值处崩掉。异步队列是第三种:**把脉冲摊平**。

### 2. 砍掉用户等待链路上的每一段耗时

当前一次秒杀请求的耗时构成:

```
限流(RateLimitInterceptor)
  └─ Redis INCR 往返              ~0.5~1 ms   ← 在 Tomcat 线程上,瓶颈 2
业务处理(seckillExecutor + grab)
  ├─ loadItem(3s 本地缓存)          ~0 ms
  ├─ Redis Lua 预扣往返             ~0.5~1 ms
  └─ grabInTx:DB 事务(扣库存+建单)  数 ms~数十 ms  ← 行锁争抢时更久
```

异步化后,用户侧只需要**前两段**(限流 + 预扣 + 入队),第三段移出请求链路。用户延迟从"数十毫秒起步"降到"入队耗时"。

### 3. 把"并发写争抢"变成"队列排队"——这是最根本的收益

报告瓶颈 3 的数据:

| 分布 | 建单 TPS |
|---|---|
| 12 个非热点 SKU | **463.5** |
| 单一热点 SKU | **165.7** |

热点 SKU 慢,不是因为代码写得差,而是因为**所有事务在串行争抢同一个商品行的排他锁**——这是 InnoDB 的物理约束。

> 异步化的关键价值:**MQ 按 `itemId` 做分区键,让同一 SKU 的订单天然落到同一分区顺序消费**。
> 于是"锁争抢"变成了"排队",DB 从"被并发压垮"变成"平稳消费"。**串行没有消失,但串行变得不再伤害用户。**

### 4. 让"请求接纳能力"与"处理能力"解耦

| 能力 | 现在的方式 | 异步后 |
|---|---|---|
| 接入 | Tomcat 120 线程 / 限流 8000 QPS | 同左,但只做"预扣 + 入队" |
| 处理 | 与接入**同一个池**,互相拖累 | MQ 消费端独立配置,按 DB 能力定速 |

现在这两个数字被**强行绑定**(Tomcat 慢 = DB 慢),异步化后可以独立调优。

### 5. 消除"排队延迟"对用户的可见影响

瓶颈 1 的实测:1000 并发下 **P50 819ms / P99 1127ms**。这段延迟被报告定性为"有意的取舍"(换取不打满线程)。

但可以用**更好的方式**达成同一目的:
- 现在:用户等 819ms,页面转圈,不知道能不能抢到;
- 异步后:用户 5ms 内看到"排队中,第 1234 位",**同样拿不到结果,但体验和心理预期完全不同**。

### 6. 为"超卖兜底 + 补偿"留出空间

异步化天然要求一套**最终一致性机制**(结果查询、超时回补、幂等)。这套机制建起来后,顺带解决了当前 `releaseReservation` 那种"失败后同步回补"的脆弱路径。

## 三、如何实现:四级方案,按代价递增

### 方案 A|L1-L2:仅 Redis 预扣(项目当前)

```
请求 → 限流 → Redis Lua 预扣 → 同步落库(DB 事务) → 返回订单号
```

**优点**:无新增组件,`pom.xml` 干净。
**缺点**:落库仍在请求链路;热点 SKU 行锁争抢;DB 能力直接决定用户等待时间。

项目注释明确承认这是主动取舍:

```36:41:backend/src/main/java/com/geekmall/modules/marketing/service/impl/SeckillServiceImpl.java
 * <p>按方案 6.4 的 L2 档实现：<b>不引入 MQ</b>，用 Redis Lua 原子预扣把绝大多数请求拦在内存层，
 * 只有预扣成功的少量请求才落库并建单。</p>
```

报告 8.2 也把它列为已知缺口:

> **无 MQ 削峰** —— `pom.xml` 无 Kafka / RabbitMQ / RocketMQ;秒杀与下单均**同步落库**

**评价**:作为"不引入新中间件"的档位,这是**性价比极高的正确选择**——Lua 预扣把 99% 的请求挡在内存层,DB 只承接"真正抢到的人"。但它不解决"抢到者之间的争抢"。

---

### 方案 B|引入 MQ:真正的业务异步(推荐目标)

#### 时序

```
客户端        网关/Nginx        应用(Tomcat)          Redis         MQ          消费者        DB
  │              │                  │                   │            │            │           │
  ├─抢购请求────▶│                  │                   │            │            │           │
  │              ├─limit_req 粗筛──▶│                   │            │            │           │
  │              │  (超量429,不进JVM)│                   │            │            │           │
  │              │                  ├─Lua 预扣─────────▶│            │            │           │
  │              │                  │  (判库存+一人一单)  │            │            │           │
  │              │                  ├─预扣成功,发消息─────────────────▶│            │           │
  │◀─202 排队中───┴──────────────────┤  (key=itemId 分区) │            │            │           │
  │  + 排队凭证                       │                   │            ├─顺序消费───▶│ 扣库存    │
  │              │                  │                   │            │  (幂等)     │ 建订单    │
  ├─轮询结果─────▶│─────────────────▶│                   │            │            │           │
  │◀─订单号/失败──────────────────────┤                   │            │            │           │
```

#### 关键设计点(每一条都是坑)

| # | 设计点 | 说明 |
|---|---|---|
| 1 | **分区键 = `itemId`** | 同一 SKU 落同一分区 → 顺序消费 → 行锁争抢变排队。**这是方案的核心价值所在** |
| 2 | **消息必须带 `requestId`** | 消费端幂等键;重复投递时直接跳过(参照项目已有的 `uk_user_request` 思路) |
| 3 | **预扣成功 ↔ 消息发出 必须原子** | 最大难点,详见下一节 |
| 4 | **秒杀仍需保留 Redis 预扣** | 异步不能替代预扣:预扣负责"即时判断谁抢到了",MQ 负责"慢慢落库"。**两者是接力,不是替代** |
| 5 | **结果查询接口** | 新增 `GET /api/v1/seckill/result/{requestId}`,客户端轮询或以 SSE/WebSocket 推送 |
| 6 | **超时未支付回补** | 复用现有 `closeExpiredOrders` 逻辑,但要**同时回补 Redis 和 DB** 库存 |
| 7 | **MQ 不可用的降级** | MQ 挂了是新增故障点,需要降级开关(直接同步落库 or 快速拒绝) |

#### 为什么"预扣 + MQ"是接力而非替代

很多人会想"有了 MQ 还要 Redis 预扣干嘛"。答案是:

- **MQ 不判重**:1000 个请求同时入队,消费者逐个处理时才判断"已抢光"——那 1000 个请求都经历了一次排队 + 一次 DB 查询;
- **Redis 预扣极快且原子**:`GRAB_SCRIPT` 一个 Lua 脚本内完成"判库存 → 判一人一单 → 扣减",**0.5ms 内给出确定答案**;

> 正确分工:**Redis 决定"谁有资格",MQ 决定"何时落库"**。前端只接受预扣成功的请求入队,队列长度天然有界(= 库存数),不会被无效请求灌爆。

---

### 方案 C|Redis Stream:轻量异步(若坚持不引入 MQ)

用 Redis Stream 替代 MQ,复用现有 Redis:

```
XADD seckill:stream * itemId=1 userId=8 requestId=xxx
消费者组 XREADGROUP → XACK
```

- **优点**:零新增中间件,复用项目已有的 Redis 依赖;
- **优点**:Stream 有**消费者组 + ACK + pending 列表**,比 List(`BRPOP`)可靠得多;
- **缺点**:可靠性、堆积监控、死信处理都要**自己实现**,运维能力不如成熟 MQ;
- **适用**:项目当前"单体 + 单实例 + 不引入 MQ"的定位下,这是**最贴合现状的折中**。

> ⚠️ 不要用 `LPUSH/BRPOP`:消息弹出即消失,进程崩溃就丢单,没有 ACK 语义。

---

### 方案 D|库存分桶:绕开而非消除串行

报告对瓶颈 3 的定性:

> "串行本身是物理上限,只能靠 MQ 异步化或**库存分桶**突破。"

思路:把一个 SKU 的 100 件库存拆成 `bucket_0..bucket_9`(各 10 件),请求按 `userId % 10` 路由到不同桶独立扣减 → **10 个独立行锁,不再争抢同一行**。

- **优点**:不改架构,纯 DB 层优化,可与方案 B 叠加;
- **缺点**:桶间余量不均(桶 A 抢光时桶 B 还有,造成"明明有货却提示抢光");需要兜底二次分配逻辑;
- **定位**:`方案 A` 的增强,不是 `方案 B` 的替代。

## 四、最大的技术难点:预扣与落库的原子性

异步化不可避免会遇到这个问题:

```
① Redis Lua 预扣成功  ─┐
                        ├─ 这两步之间进程崩溃 → 库存被扣,消息没发出 → 用户永远等不到订单
② 发送 MQ 消息        ─┘
```

三种解法,可靠性递增:

| 解法 | 机制 | 代价 |
|---|---|---|
| **本地消息表** | 与业务同库同事务写一条"待发送"记录,定时任务扫描补发 | 需新表 + 定时任务,最终一致 |
| **事务消息** | RocketMQ 支持半消息 + 回查 | 强绑定 RocketMQ |
| **Redis Stream + pending** | 消费者崩溃后,pending 列表可 `XCLAIM` 重投 | 需自己处理超时重投 |

**推荐**:项目已有 ShedLock + 定时任务基础设施,「本地消息表」与现有技术栈契合度最高,不引入新中间件也能做到可靠。

另外,**失败回补路径要重新设计**。当前实现是同步回补:

```197:205:backend/src/main/java/com/geekmall/modules/marketing/service/impl/SeckillServiceImpl.java
    private void releaseReservation(Long itemId, Long userId) {
        try {
            redisTemplate.opsForSet().remove(RedisKeys.SECKILL_BOUGHT + itemId, String.valueOf(userId));
            redisTemplate.opsForValue().increment(RedisKeys.SECKILL_STOCK + itemId);
            log.warn("秒杀预扣已回补：itemId={}, userId={}", itemId, userId);
        } catch (Exception ex) {
            log.error("秒杀预扣补偿失败，需人工核对 Redis 库存：itemId={}, userId={}", itemId, userId, ex);
        }
    }
```

异步化后,"落库失败"发生在**消费者线程**,距离"预扣"已经隔了一次消息投递。回补必须:
1. 由**消费者**触发,而不是请求线程;
2. 回补动作本身也要**幂等**(避免重复消费导致多次 `INCREMENT` 把库存刷高)。

> 注意现有代码的 `log.error("...需人工核对 Redis 库存...")` —— 异步化后这类"需人工介入"的路径会变多,必须收敛成自动补偿 + 对账。

## 五、异步化之后,瓶颈会迁移到哪里

| 阶段 | 主要瓶颈 | 依据 |
|---|---|---|
| **现在** | ① 限流占 Tomcat 线程(瓶颈 2)<br>② 单热点 SKU 行锁(瓶颈 3) | P99 12 倍放大;单 SKU 165.7 TPS |
| **异步化后** | ① **Redis 吞吐**(预扣是全链路唯一的同步热点)<br>② **MQ 吞吐与堆积**<br>③ 消费者的处理速率 | 需重新压测 |

这不是"解决问题",而是"把问题挪到可控的位置":
- Redis 单机可扛数万~十万 OPS,不够可上集群/Proxy;
- MQ 可通过加分区 + 加消费者线性扩展;
- DB 变成**平稳消费**,不再被脉冲直接冲击。

> ⚠️ 但注意:**并行消费者的数量必须以 DB 写能力为上限**。如果消费者数远超 DB 承载,只是把雪崩点从 Tomcat 挪到了 DB。

## 六、落地建议(结合项目现状的推荐路径)

### 阶段 1:补齐前置条件(必须先做)

异步化的收益全部依赖"流量已经被收敛",否则只是把洪峰灌进队列。

| 事项 | 理由 |
|---|---|
| **Nginx `limit_req` 接入层限流** | 解瓶颈 2;否则超量请求仍占 Tomcat 线程 |
| **`grab()` 全链路幂等键** | 客户端重试是异步模式的常态,没有幂等就无法安全重试 |
| **结果查询接口** | 异步化的必备配套,否则用户拿不到结果 |

### 阶段 2:最小可行异步

- 用 **Redis Stream**(而非 MQ),避免引入新中间件,契合"单体"定位;
- 入队字段:`requestId / userId / itemId / addressId`,分区键 `itemId`;
- 保留现有 Lua 预扣作为"资格判定",**入队前完成**;
- 消费端:幂等校验 → `grabInTx` 落库 → `XACK`。

### 阶段 3:演进

- 流量增长后,把 Redis Stream 换成 RocketMQ/Kafka(接口抽象后替换成本低);
- 叠加**库存分桶**,进一步压榨热点 SKU 吞吐;
- 用 SSE / WebSocket 替代轮询,降低查询接口压力。

### 不建议的做法

| 做法 | 问题 |
|---|---|
| `@Async` 直接包一层就号称"异步化" | 只换了线程,DB 争抢和数据一致性完全没变 |
| 用无界队列削峰 | 队列无限堆积 → OOM(项目已在 `AsyncConfig` 里明确规避过这个坑) |
| 去掉 Redis 预扣,全部交给 MQ | 队列被无效请求灌爆,消费者做无用功 |
| 消费者数量按峰值配置 | 把雪崩点从 Tomcat 平移到 DB |

---

## 附录:一句话总结

> **秒杀异步化的本质,是把"用户请求的处理"从"用户等待的链路"中剥离出来。**
> 它不提升系统总吞吐(DB 还是那么快),但它让**脉冲不再直接冲击恒定能力的资源**,并把"行锁争抢"转化为"队列排队"。
>
> 对本项目而言:Redis Lua 预扣已经解决了"99% 的请求不该到 DB",**异步化要解决的是剩下那 1% 之间的互相争抢**。二者是接力关系,不是替代关系。
