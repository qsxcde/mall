| 维度 | 结论 | 等级 |
|---|---|---|
| 单机承载能力 | 8 核单实例下：读链路 **9092 QPS**、秒杀 **3594 QPS**、普通下单 **463.5 TPS** | A |

## 二、架构设计与技术选型

### 2.1 总体架构

单体分层应用，**无 MQ、无注册中心、无 API 网关**。并发压力全部由应用层 + Redis + MySQL 承接。

```
客户端 →【Tomcat 120 线程】→【限流拦截器(LOCAL 滑动窗口 / 少数 DISTRIBUTED Redis)】→ Controller
   →【业务线程池：messageExecutor / seckillExecutor】→ Service
   →【Spring Cache(Redis) / Caffeine(本地)】→【MyBatis-Plus】→【Hikari】→ MySQL
                                    ↘【Lua 原子脚本】→ Redis
```

### 2.3 并发控制三大支柱

项目**未使用** Redisson、悲观锁（`SELECT ... FOR UPDATE`）、乐观锁（`@Version` / version 列）。
并发正确性依赖以下三条，属**无锁化设计**：

1. **Redis Lua 原子前置**（热点拦截）
   `GET stock → 判空 → SISMEMBER bought → DECR stock → SADD bought → EXPIRE 24h`
   三步在同一脚本内原子完成 —— `modules/marketing/service/impl/SeckillServiceImpl.java:54-69`。
   效果：占绝大多数的「已抢光」请求被完全挡在 DB 之外。

2. **DB 条件更新 CAS**（临界资源保护）

   | 场景 | 语句 | 位置 |
   |---|---|---|
   | 扣库存 | `UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?` | `ProductMapper.java:19-21` |
   | 秒杀二次扣减 | `... WHERE id = ? AND stock > 0` | `SeckillItemMapper.java:19-21` |
   | 订单状态流转 | `UPDATE ... SET status = ? WHERE id = ? AND status = <读到的值>` | `OrderStateMachine.java:75-87` |
   | 支付回调 | `... SET status = 1 WHERE id = ? AND status <> 1` | `PaymentServiceImpl.java:121-127` |

3. **唯一索引兜底**（最终一致性防线）
   `uk_user_request`（幂等下单）、`uk_order_product`（库存回退幂等）、
   `uk_order_doing`（售后单）、`uk_user_order_product`（重复评价）
   —— `db/migration/V8__concurrency_hardening.sql`。

### 2.4 削峰与隔离手段

| 手段 | 实现 | 位置 |
|---|---|---|
| 限流 | 自研集中式规则（43 条）+ 双层（LOCAL 滑动窗口 / DISTRIBUTED Redis Lua）+ 并发槽位，超限 **HTTP 429** | `common/ratelimit/RateLimitInterceptor.java`、`LocalRateLimiter.java`、`DistributedRateLimiter.java` |
| 线程池舱壁 | 秒杀独立池 + `DeferredResult`，满则 `AbortPolicy` 立即拒绝 | `AsyncConfig.java:45-59`、`SeckillController.java:72-99` |
| 异步化 | 下单后事件（清购物车、站内消息）`AFTER_COMMIT` + `@Async` | `CartCleanupListener.java:26-28`、`OrderStatusMessageListener.java:32-34` |
| 削峰队列 | Redis Stream（消费者组 + ACK + pending 回收 + DLQ/`max-deliveries`），`mall.seckill.async.enabled` 默认 false | `modules/marketing/queue/RedisStreamSeckillOrderQueue.java`、`SeckillOrderConsumer.java` |
| 定时任务互斥 | ShedLock + Redis（多实例安全） | `config/ShedLockConfig.java:20-23` |
| 缓存 | L1 Caffeine 白名单 + `ResilientRedisCache`（分布式互斥重建 + 空值缓存 + TTL 抖动 ±20% + 缓存熔断）+ 布隆过滤器 | `common/cache/*` |
| 幂等 | `setIfAbsent` 占位 + `afterCommit` 回写 + 唯一索引兜底 | `TradeServiceImpl.java:200-208, 534-552` |

## 五、瓶颈分析（均已定位到具体组件）

### 瓶颈 1｜秒杀舱壁排队 —— 有意的延迟取舍（非缺陷）

- **现象**：1000 并发齐发时 P50 **819 ms**、P99 **1127 ms**。
- **归因**：`seckillExecutor`（core 64 / max 128 / queue 2000）下，1000 个请求只有 128 个立即执行。
  按「1000 ÷ 128 × 单请求 ≈ 80 ms」估算排队延迟 **600~800 ms**，与实测吻合。
- **反证**：压测后 `hikaricp.connections.pending = 0`、`active = 0` → **不是数据库瓶颈**；
  k6 的「总耗时 − TTFB」均值仅 **1.1~2.1 ms** → **不是压测机噪声**（该结论修正了 JMeter 轮的错误推断）。
- **定性**：这段延迟换来「秒杀不打满 120 个 Tomcat 线程、不雪崩」，属设计预期。

### 瓶颈 2｜限流拦截器占用 Tomcat 线程 —— **真正的短板**

- **现象**：秒杀洪峰期间（第 12~14 秒），普通下单 **P99 15.2 ms → 183.8 ms（12.1 倍）**，
  且服务端 TTFB P99 同步为 **183.7 ms**（延迟确在服务端）；洪峰过后 1 秒内恢复至 12.5 ms。
- **根因**：`RateLimitInterceptor` 在 **Tomcat 工作线程**上对每个秒杀请求执行一次 Redis `INCR` 往返
  （`RateLimitInterceptor.java:59`）。1000 并发瞬时占满 120 个 Tomcat 线程，普通下单只能排队。
- **定性**：唯一**未被隔离**的能力缺口 → 验收项判定 ⚠️ 部分达成。

### 瓶颈 3｜单热点 SKU 的行锁串行 —— 物理上限

| 分布 | 建单 TPS | 说明 |
|---|---|---|
| 12 个非热点 SKU | **463.5** | 每 SKU 约 16 并发事务 |
| 单一热点 SKU | **165.7** | 所有事务串行争抢同一商品行排他锁 |

已用「按 `productId` 升序加锁 + 死锁退避重试（3 次）」消除**死锁**（`TradeServiceImpl.java:292-293, 228-257`），
但**串行本身**是物理上限，只能靠 MQ 异步化或库存分桶突破。

### 瓶颈 4｜偏长事务（代码审查发现，未压测）

| 位置 | 问题 |
|---|---|
| `TradeServiceImpl.closeExpiredOrders`（`:452-470`） | 单事务内**循环**处理最多 **500** 笔订单，每笔含状态流转 + 库存回退 + 券释放 → 单事务可能数百条 SQL |
| `TradeServiceImpl.restoreStock`（`:633-646`） | 每个订单明细**循环**执行 `INSERT IGNORE` + `UPDATE` |
| `MerchantOrderServiceImpl.ship/close`（`:105-145`） | 事务内循环调用状态机 + 更新 |

### 6.3 压测过程中额外发现并修复的 4 个缺陷（价值最高）

| # | 缺陷 | 现象 | 根因 | 修复与验证 |
|---|---|---|---|---|
| 1 | **订单号撞号** | 随机 `Duplicate entry ... uk_order_no`，下单 **500** | `时间戳 + 6 位随机`，620 单/秒时按生日问题**每秒撞号概率约 17%**，实测 16 秒撞 4 次 | 改 `时间戳 + 秒内原子自增 + 4 位实例随机位`；复测 10000 单 **0 撞号** |
| 2 | **幂等兜底缺 return** | 唯一索引拦住重复建单，但异常冒泡成 **500 / code 9999** | `submitWithRetry` 未捕获 `DuplicateKeyException` | 改为捕获后按 `(userId, requestId)` 查回并**幂等返回订单号**；`server_error = 0` |
| 3 | **幂等键生命周期长于业务数据** | 重置脚本只删订单不删 Redis 键 → 返回**数据库里不存在的悬空订单号** | 数据治理未同步失效幂等键 | `reset_env.sh` 补 `del mall:order:idempotent:*` |
| 4 | **购物车异步清理竞态** | 偶发「购物车为空」下单失败（首轮 **9 / 10000**） | `add()` 同规格**累加合并复用同一行 id**，与异步按 id 删除竞态 | 清理改**数量乐观守卫**（数量被改动则保留）；复测 **0 次** |

> 缺陷 4 的守护把竞态窗口大幅收窄但**未在理论上完全关闭**，见第八节。

### 附录 B 指标口径

- **QPS** = 总请求数 ÷ 压测时长；**TPS** = 成功建单数 ÷ 压测时长。
- **服务端 TTFB** = k6 `http_req_waiting`，用于剥离客户端开销；
  「总耗时 − TTFB」即客户端开销（实测均值 0.1~2.1 ms）。
- 秒杀场景的"失败"绝大多数为业务预期（已抢光/限购，HTTP 200 + 业务码），
  仅在报告中按"是否建单成功"统计；**真正的故障口径是 5xx 与连接异常，本次为 0**。
- 单次压测时长约 5~30s，属**突发型**测量；稳态 QPS 取每秒分桶中位，峰值取单秒最大。
