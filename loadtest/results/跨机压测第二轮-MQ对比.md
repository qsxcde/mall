## 七、结论判定：加入 MQ 获得了收益吗

> 场景限定（很重要）：**单热点 SKU**（库存 200 集中在 1 个商品）、**单实例**、脉冲深度仅 200 单、消费线程 64。

### 7.1 确实得到的

| 收益 | 数据 | 稳健性 |
| --- | --- | --- |
| **受理尾部时延大幅下降** | P90 4118 → 520 / 688 ms；P99 4660 → 534 / 690 ms（两轮 MQ 一致，约 **6~9 倍**） | 稳健（两轮复现） |
| **脉冲被可视化摊平** | pending 峰值 185 条，**5.3 s 匀速排空（≈38 单/s）**；同步模式下这份压力直接压在请求线程上 | 稳健 |
| 受理中位数下降 | P50 2426 → 54.8 / **674.6** ms | ⚠️ **不稳健**（两轮差 12 倍，疑似冷 JVM） |

### 7.2 没有得到的

| 目标 | 结果 |
| --- | --- |
| **端到端（用户真实体感）** | **变差**：P50 2426 → 3000 / 3574 ms；P99 4660 → 5500 / 6040 ms（**+18% ~ +30%**） |
| **吞吐** | **没有提升**：总 QPS 3156 → 3234 → 3153（噪声内）；落库速率 43 单/s（同步推算）→ **37.7 单/s**（队列实测），**反降约 12%** |
| **系统稳定性** | 没有改善（同步模式本就 0 失败，无雪崩可防）；反而**新增故障面**：旧配置下 104 次系统错误，修完才归零 |

### 7.3 代价清单（同步模式完全不存在）

1. 一致性风险面：至少一次投递、重复消费、死信、结果与订单时序（QUEUED 与已建单并存、结果 30m 过期）；
2. 读放大：**2839 次轮询（14.2 次/单）**，服务端查询接口新增 13.4 s CPU 时间；
3. 运维面：Redis Stream 常驻消息、消费者组 64 个消费者、pending/lag/死信需监控；
4. 契约变更：前端必须从「下单即完成」改为轮询。

### 7.4 判定

- 以**端到端 + 吞吐**为标准 → **本轮未取得收益，端到端略有倒退**；
- 以**受理体验 + 过载保护**为标准 → 取得了收益，但本轮过载强度（200 单脉冲）**不足以证明防护价值**（同步模式在最深脉冲下也是 0 失败）；
- 因此更准确的表述是：**本轮数据既不能证明 MQ 有价值，也不能否掉它** —— 它恰好落在 MQ 最不该发挥作用的场景：**单 SKU 行锁串行（瓶颈与"谁在写"无关）+ 浅脉冲 + 单实例**。

### 7.5 还需要什么才能下"上不上 MQ"的结论

| 缺的场景 | 为什么关键 | 对应测试项 |
| --- | --- | --- |
| **多 SKU** | 打断 InnoDB 行锁串行，DB 才能并行写；这才是削峰能提吞吐的前提 | D3 / P2-5 |
| **持续过载 ≥10 min** | 只有持续过载才能暴露"同步模式排队无期/超时"与"队列积压是否有界"的差别 | P0-4 |
| **多实例 / 多消费者** | MQ 的核心价值（横向扩展）单机测不出 | P1-1 |

**判定规则（建议固化）**：
1. 若多 SKU 下 MQ 的**端到端与落库速率仍不优于同步** → 瓶颈始终在 DB，MQ 只增加复杂度，**保留开关但不作默认路径**；
2. 若多 SKU 下 MQ **显著优于**同步 → 值得作为默认路径，并补齐 DLQ、多实例扩展、消费者线程调优；
3. 若业务目标是"大促不雪崩"而非"更快" → 验收指标应改为**过载下的系统错误率/超时率**，而不是 P50。

## 八、多实例 + 负载均衡：能补上 MQ 的收益吗（判定与实验设计）

> 结论先行：**不完全成立**。「单实例下 MQ 收益不明显」的**主因不是单实例，而是单热点 SKU 让 DB 行锁串行** —— 多实例改变不了同一个 InnoDB 行上的串行。

### 8.1 两件事是正交的，别混为一谈

| 手段 | 解决什么 |
| --- | --- |
| **MQ 削峰** | 上游到达速率 与 下游处理速率 的**解耦**（把脉冲摊平、把等待从请求线程移到队列） |
| **多实例 + Nginx** | 应用层处理能力的**水平复制**（Tomcat 线程 / CPU / 连接） |

**瓶颈不在应用层时，多实例不产生吞吐收益。**

### 8.2 瓶颈位置决定收益（决策矩阵）

| 瓶颈在哪 | MQ 削峰 | 多实例 + 负载均衡 |
| --- | --- | --- |
| 应用层 CPU / 线程（读链路、无状态接口） | 不适用 | ✅ **近似线性**（直到 Redis/网络成为瓶颈） |
| **DB 单行锁（单热点 SKU）** | ❌ 不解决 | ❌ **不解决，甚至更差**：N 个实例的消费者一起抢同一行锁，等待加剧 |
| DB 多行可并行（多 SKU / 分桶） | ✅ 排队换吞吐上限 | ✅ 可与削峰叠加 |
| 峰值脉冲导致雪崩 | ✅ 摊平 + 保护（受理体验） | ✅ 分摊受理压力 |

### 8.3 控制变量：顺序不能跳

现在连「单实例下削峰到底有没有用」都还没测清（缺多 SKU）。若直接跳到多实例，测出的差异**无法归因**（是多实例的功劳，还是多 SKU 的功劳？）。

## 九、修正判定：「多 SKU 就有收益」是必要而非充分条件

第八节 8.2 说「DB 多行可并行时 MQ 有收益」，这句话需要两处限定，否则会高估多 SKU 的作用。

### 9.1 修正一：多 SKU 对**同步模式同样有利**，差值未必扩大

多 SKU 打散的是 **InnoDB 行锁**这个瓶颈，而它与「用不用队列」无关：
- 同步模式：64 个舱壁线程 × 12 个 SKU → 12 路并行写；
- 削峰模式：64 个消费者 × 12 个 SKU → 同样 12 路并行写。

**两边一起变快，差距不一定变大。** 谁更快取决于三件事：① 有效并行度是否对齐（同步侧 64 舱壁线程 vs 异步侧 `consumer-threads`，即文档里的 **D1**）；② DB 总写能力余量；③ 单事务耗时。

### 9.2 修正二：削峰**不创造 DB 能力**，同等并行度下两边收敛到同一上限

削峰的本质是「把请求线程与落库解耦」，不是「让 DB 变快」。因此：
- 落库吞吐：同等并行度下，同步与削峰**收敛到同一个 DB 上限**；
- 端到端：也未必改善（最后一个用户的等待 ≈ 总工作量 ÷ 并行度，两边近似相等）；
- **削峰稳定能拿到的只有「受理时延解耦」**（已实测：尾部 P90/P99 ↓6~9 倍），以及下面 9.3 的隔离收益。

### 9.3 MQ 收益最可能出现的地方（按「预期收益 × 可验证性」排序）

| 优先级 | 场景 | 收益类型 | 我们已有的条件 |
| --- | --- | --- | --- |
| 🔴 **1** | **秒杀洪峰 × 普通业务同轮** | **隔离**：秒杀不拖垮其它接口 | 脚本 `order-vs-seckill.js` + 窗口分析 `order_timeline.py`；**历史基线：同步模式下普通下单 P99 被抬高 12 倍（15.2 → 183.8 ms）** |
| 🟠 2 | 多 SKU + 并行度对齐扫描 | 吞吐 | D3 场景脚本 + `CONSUMER_THREADS` 已可配（P0-2） |
| 🟠 3 | 持续过载 ≥10 min | 有界积压 / 不雪崩 | `queue_metrics.py --watch`（P0-4） |
| 🟡 4 | 多实例 + 多消费者 | 横向扩展线性度 | 多实例前置已备（见 8.4） |

**为什么把「混合场景」排在多 SKU 之前**：秒杀请求在同步模式下会**占满 Tomcat 线程去等 DB**（`max-threads=120`），这不是"秒杀自己慢"，而是"整站被拖慢"。削峰让抢购在毫秒级释放线程，正是治这个病。**这个收益量级大（12 倍）、机理清晰、且有现成脚本与历史基线**，比多 SKU 那点吞吐差异更容易判定。

## 十、汇总：MQ 带来了哪些提升（一页版）

> 一句话：**MQ 提升的是「受理侧」（入口体验 + 系统保护），不提升「落库侧」（DB 吞吐）。** 单热点 SKU 场景下已实测确认；落库侧的价值取决于三个尚未开测的场景。

### A. 已实测确认的提升（受理侧）

| # | 提升项 | 数据（同步 → 削峰） | 稳健性 |
| --- | --- | --- | --- |
| A1 | **受理尾部时延** | P90 4118 → **520 / 688 ms**；P99 4660 → **534 / 690 ms**（↓ **6~9 倍**） | ✅ 两轮复现，稳健 |
| A2 | 受理中位时延 | P50 2426 → 54.8 / **674.6** ms | ⚠️ 不稳健（两轮差 12 倍，疑似冷 JVM） |
| A3 | **脉冲被有界摊平** | pending 峰值 **185**（≈库存量级，未被无效请求灌爆），**5.3 s 匀速排空 ≈38 单/s**，`lag=0`、无重投 | ✅ 稳健 |
| A4 | **中间态可见**（产品能力，非性能） | 抢购立刻拿到回执，可轮询到 `QUEUED → SUCCESS/FAILED`，用户不会无限转圈 | ✅ 设计即有 |

### B. 确认**没有**提升（落库侧）

| # | 维度 | 数据 | 结论 |
| --- | --- | --- | --- |
| B1 | **端到端（用户真实体感）** | P50 2426 → 3000 / **3574** ms；P99 4660 → 5500 / **6040** ms | ❌ **变差 +18%~30%** |
| B2 | **总吞吐** | QPS 3156 / 3234 / 3153 | ❌ 噪声内，无提升 |
| B3 | **落库速率** | 43 单/s（同步推算）→ **37.7 单/s**（队列实测） | ❌ **反降约 12%** |
| B4 | 稳定性 | 同步模式本就 0 失败 | ❌ 本档位下无可改善空间 |

**根因**：库存集中在 1 个 SKU → 瓶颈是 InnoDB **单行锁串行**，与「谁在写、怎么写」无关。削峰只是把等待从请求线程挪到队列，总时长仍由 "订单数 ÷ DB 落库速率" 决定，再叠加受理开销与轮询间隔 → 必然略慢。

### C. 机理上应有、但本轮**未测出**的提升（按预期收益排序）

| 优先级 | 待验证的提升 | 机理 | 现有基线 |
| --- | --- | --- | --- |
| 🔴 1 | **隔离性：秒杀不拖垮其他业务** | 同步模式下抢购会占满 120 个 Tomcat 线程去等 DB；削峰让线程在毫秒级释放，其他接口不被挤占 | 历史数据：同步下单机测试中普通下单 P99 被洪峰抬高 **12 倍**（15.2 → 183.8 ms） |
| 🟠 2 | 多 SKU 下的吞吐 | 行锁分散后，落库并行度才不受请求线程数限制 | ⚠️ 需先做并行度对齐（D1），且多 SKU 对同步模式同样有利 |
| 🟠 3 | 持续过载下的"不雪崩" | 同步：线程池耗尽 → 超时/拒绝；队列：转为**有界积压** | 需 ≥10 min 恒定过载 |
| 🟡 4 | 多实例横向扩展 | 消费者组天然支持多消费者，按 itemId 分区可线性提落库并行度 | 前置条件已备（见 8.4） |

### D. 代价（同步模式完全不存在，必须计入决策）

一致性风险面（至少一次投递 / 重复消费 / 死信 / 结果 30m 过期）、读放大（**2839 次轮询，14.2 次/单**）、运维面（Stream 常驻消息 + 64 个消费者 + pending/lag/死信监控）、契约变更（前端必须改轮询）、**新增故障点**（旧配置下 104 次系统错误，靠调大并发上限才归零）。

## 附录 A：引入 MQ 理论上是为什么（原理 → 兑现条件 → 本项目实测对照）

### A.1 本质只有一句话

**引入 MQ 买的是「解耦」**：把**用户的等待**与**系统的处理**分开，把**上游的到达速率**与**下游的处理能力**分开。
所有具体收益都是从这一条派生出来的。

### A.2 七类理论收益

| # | 理论收益 | 机理 | 兑现的**前提条件** |
| --- | --- | --- | --- |
| 1 | **削峰填谷**（受理快、下游不被打死） | 队列当蓄水池，把脉冲摊平成下游能承受的匀速 | 上游速率 **远大于** 下游速率，且下游处理能力**稳定** |
| 2 | **故障隔离 / 防雪崩** | 把「等待」从稀缺的请求线程里移走，下游慢不再占满上游线程池 | 同步路径**确实会**因线程耗尽级联失败 |
| 3 | **吞吐天花板抬升** | 多消费者 / 分区并行消费，加实例加分区即加吞吐 | **下游可并行**（多 SKU / 分片）+ 并行度对齐 |
| 4 | **可靠投递 / 最终一致** | 持久化 + ACK + 重投，消费者崩溃不丢事 | 必须实现**幂等消费**（去重） |
| 5 | **生产者消费者解耦** | 上游不需要知道下游是谁、有几个、在哪 | 接口抽象（可换实现） |
| 6 | **主链路不被旁路拖累** | 下单后把发短信/推送/积分/数仓等**旁路重活**异步化 | 旁路确实是重活，且**不在主链路关键路径上** |
| 7 | **背压与有界缓冲** | 有界队列 + 满则快速失败，而不是无限堆积 | 队列长度上限 + 拒绝策略 + 死信机制 |

### A.3 兑现条件矩阵（对照本项目实测）

| 理论收益 | 本项目状态 | 证据 |
| --- | --- | --- |
| 1 削峰填谷 | ✅ **已兑现** | 受理 P90/P99 ↓6~9 倍；pending 峰值 185、5.3s 有界排空 |
| 2 故障隔离 | ⬜ 未验证 | 本档位同步模式**也是 0 失败**，无雪崩可防；需混合场景/持续过载 |
| 3 吞吐抬升 | ❌ **当前不成立** | 单热点 SKU → 行锁串行，落库速率反降 12%（43 → 37.7 单/s） |
| 4 可靠投递 | ✅ 已实现，未压测 | `requestId` + `uk_user_request` 幂等、`max-deliveries` 死信 |
| 5 解耦 | ✅ 已实现 | `SeckillOrderQueue` 接口注释明确「换 RocketMQ/Kafka 只换实现类」 |
| 6 旁路解耦 | ❌ **本项目不涉及** | 落库本身就在主链路上，不是旁路 |
| 7 背压 | ✅ 已实现 | `max-stream-length=100000`、死信、队列满快速失败 |

### A.4 三条常见误区（MQ 做不到的事）

1. **不能让下游更快** —— 下游是瓶颈时，队列只能把排队搬到别处，**不创造处理能力**；
2. **不必然降低端到端** —— 若瓶颈在下游，端到端 ≈ 总工作量 ÷ 并行度，与用不用队列无关（本项目实测端到端反而 +18%~30%）；
3. **不必然提升吞吐** —— 只有在「上游被线程池卡住」或「下游可并行」时，吞吐才会上升；否则只是把雪崩点从 Tomcat 平移到 DB。

### A.5 面试口径（一段话可直接讲）

> 引入 MQ 的本质是**解耦**：把用户等待与系统处理解耦、把上游速率与下游能力解耦。它买到四样东西——**受理更快、系统更稳、下游可并行时能扩吞吐、消息不丢可重试**。
> 但它**不创造下游能力**：我们实测在单热点 SKU（InnoDB 行锁串行）下，削峰让受理 P99 降了 6~9 倍、队列积压有界（185 条 5.3 秒排空），但**端到端反而慢了 18%~30%、落库速率反降 12%** —— 因为瓶颈在 DB，与"谁在写"无关。
> 所以我不会说"上了 MQ 就更快"，而会说：**削峰买的是入口体验和系统保护，值不值取决于业务目标是"更快"还是"别崩"**。

## 附录 B：为什么本系统「没提升吞吐」（机理拆解）

### B.0 一句话

**吞吐 = 有效并行度 ÷ 单事务耗时。** MQ 既没提高并行度、也没降低单事务耗时，**只改变了"排队的位置"**；还额外支付了队列开销，所以吞吐不动甚至略降。

### B.1 四条原因，逐条有实测证据

#### 原因 1：MQ 只作用于 1% 的请求，剩下 99% 根本不走队列

- 200VU×100 = **20000 个抢购请求，成功仅 200 个（1%）**，其余 19800 个是"已抢光"的**快速拒绝**；
- 快速拒绝的路径 = Redis Lua 预扣失败 → 抛业务异常 → 返回，**同步与削峰两种模式完全相同，MQ 完全不参与**；
- 所以"整体 QPS"几乎不可能变化 —— 实测 **3156 / 3234 / 3153**（噪声内）。
- 📌 结论：**只优化 1% 的请求路径，不可能改变整体吞吐。**

#### 原因 2：瓶颈是 DB 单行锁，并行度被压成 1

- 秒杀落库的关键语句是 `UPDATE mkt_seckill_item SET stock=stock-1, sold=sold+1 WHERE id=? AND stock>0`（CAS 扣活动库存）；
- 200 单集中在**同一行**（item1 → product 1）→ 这行上的更新**串行排队**，对该行而言并行度恒为 **1**；
- 谁在写都一样：**换执行者不改变串行事实**。

#### 原因 3：并行度根本没变（这是 D1，也是最直观的原因）

| | 有效并行写度数 |
| --- | --- |
| 同步落库 | `seckillExecutor` core **64** 线程并发写 |
| 削峰异步 | `consumer-threads` = **64** 个消费者并发写 |

**并行度 64 ↔ 64，完全相同** → 吞吐必然相近。实测落库速率 **43 单/s ↔ 37.7 单/s**（差距 = 队列自身开销，见原因 4）。

> 要提升吞吐，必须让**并行度提升**（消费者数 > 同步侧并发，即 P0-2 扫描）或让**下游可并行**（多 SKU / 分桶）。

#### 原因 4：单事务耗时没降，反而多付了队列开销

| 模式 | 单事务均摊耗时（200 单 / 排空时长） |
| --- | --- |
| 同步 | 200 / 4.66s ≈ **23 ms/单** |
| 削峰 | 200 / 5.3~5.7s ≈ **26~29 ms/单** |

**两种模式下"单事务耗时"几乎相同 → 证明瓶颈完全在 DB 侧，与执行者无关**；削峰多出的部分正是队列链路开销：`XADD` → `XREADGROUP` → 结果写入 → `XACK`，以及 pending 扫描（`reclaimStale`）。

### B.2 被环境放大的因素（绝对数字不可外推）

单事务均摊 23~29ms，远高于正常 Linux + 本地 SSD 的 **1~3ms**（一次提交 = 一次 fsync）。强烈提示 **Docker Desktop on Windows 的虚拟磁盘 fsync 开销**在拖慢每次事务提交（本机跨网测到的 Redis 往返 5.87ms、ping 6.5ms 也印证该环境 I/O 偏高）。

- 这不改变"MQ 不提升吞吐"的结论（两种模式同样受影响）；
- 但它决定**绝对容量数字不能外推**：换到 Linux + 本地 SSD，同样代码的落库上限可能高一个数量级。
- A 机可验证：`SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'`（=1 则表示每事务一次 fsync）+ `redis-cli --latency`。

### B.3 反证：什么情况下本系统的吞吐**会**提升

| 条件 | 本系统现状 |
| --- | --- |
| 下游可并行（多 SKU / 库存分桶） | ❌ 单 SKU，一行串行 |
| 上游被卡住（线程池耗尽 → 拒绝/超时） | ❌ 0 失败、无拒绝，没有"被释放"的空间 |
| 并行度提升（消费者数 > 同步侧并发） | ❌ 都是 64，D1 未对齐 |
| 单事务耗时下降（批量落库 / 降 fsync / 减 SQL） | ❌ 未做，且 MQ 反而 +3~6ms |

**四条一条都不满足，所以吞吐不可能提升。**

### B.4 结论

"MQ 不提升吞吐"**不是实现缺陷，而是结构性结果**：
> MQ 是**搬运工**（把排队从 A 挪到 B），不是**生产力**（提高单位时间完成量）。
> 要提吞吐，必须动**下游**（多 SKU / 分桶 / 批量落库 / 降 fsync）或**并行度**（消费者数对齐并超过同步侧）；只加一个队列，改变不了任何一项。

## 附录 C：「下游可并行」具体指什么

### C.1 先定义「下游」

本系统秒杀链路的**下游 = DB 落库这条写路径**（`SeckillServiceImpl.grabInTx` → `TradeServiceImpl.createOrderWithFixedPrice`），**不是 Redis**。
Redis 预扣虽然单线程，但每单只有 1 次 Lua，实测不是瓶颈（`reject_latency` P50 仅 13.6ms，且 99% 的请求止步于此）。

### C.2 「可并行」的精确含义

InnoDB 是**行级锁**：**不同行可并行，同一行必须串行**。
所以「下游可并行」= **事务之间不去争用同一个 DB 行（或同一个共享资源）**。

- **单 SKU（本系统现状）**：200 单全部落在**同一对行**上 → 争用同一把 X 锁 → **并行度恒为 1**；
- **多 SKU**：12 个 SKU → 12 对行 → 并行度上限 = `min(12, 消费者数, DB 总能力)`。

### C.3 本系统写路径的逐个语句：并行 / 串行点

| # | 语句 | 并行性 | 说明 |
| --- | --- | --- | --- |
| 1 | `UPDATE mkt_seckill_item SET stock=stock-1, sold=sold+1 WHERE id=? AND stock>0` | **🔴 串行（单 SKU）** | **本系统的瓶颈行**；12 SKU → 分散到 12 行 |
| 2 | `UPDATE pms_product SET stock=stock-qty, sales=sales+qty WHERE id=? AND stock>=qty` | **🔴 串行（单 SKU）** | 与 #1 同一商品，同样只有 1 行；12 SKU → 12 行 |
| 3 | 幂等前置检查 `SELECT ... WHERE request_id=?` | 🟢 并行 | 快照读 + 二级索引，无锁 |
| 4 | `INSERT oms_order`（唯一索引 `uk_order_no` / `uk_user_request`） | 🟢 并行 | 号段发号使键各不相同；唯一索引 B-tree 插入互不冲突 |
| 5 | `INSERT oms_order_item` / `INSERT oms_order_status_log` | 🟢 并行 | 主键不同 |
| 6 | `COMMIT`（redo log flush / undo） | ⚠️ **共享资源** | 全局共享：并发提交靠 **group commit** 合并，但磁盘 IOPS/延迟是硬上限 |
| 7 | 事务外：Redis 写结果 + `XACK` | 🟢 并行 | 每单 1~2 条命令，实测非瓶颈 |

**结论：本系统的串行点集中在 #1、#2 两个热点行，其余都可并行。**

### C.4 让「下游可并行」的具体手段（针对本系统，按性价比）

| 优先级 | 手段 | 做法 | 代价 |
| --- | --- | --- | --- |
| 🔴 1 | **多 SKU**（已有，D3） | 热点行从 2 个 → 24 个，并行度上限 ≤12 | 无（场景配置即可） |
| 🔴 2 | **库存分桶**（P2-5） | 同一 SKU 拆成 N 个库存桶行（按 userId 哈希取桶扣减）→ **单 SKU 也能并行** | 桶间余量不均会产生「假售罄」，需桶间调剂 |
| 🟠 3 | **批量落库**（P2-4） | 单事务建 N 单 → 减少 fsync 与锁获取/释放次数 | 属于「降低单事务耗时」，与提并行度互补 |
| 🟠 4 | **库存扣减改 append-only 流水** | `UPDATE` 改为 `INSERT 库存流水`（无行锁争用），汇总任务归集 | 引入最终一致与对账 |
| 🟡 5 | **分库分表 / 按 SKU 分片** | 热点行落到不同库，跨库无锁争用 | 跨库事务与运维复杂度 |
| ✅ 6 | 缩短锁持有时间 | 非必要操作移出事务（本项目 Redis 结果写入已在事务外，已做） | — |

### C.5 必须澄清的误区

**「加线程 / 加消费者」不算让下游可并行** —— 那只是提高**应用层**并行度。
当下游被同一行锁串行时，加线程只会加长锁等待队列（并加剧上下文切换与死锁概率），**吞吐不升反降**（实测 43 → 37.7 单/s）。这正是 D1 的教训。

### C.6 可验证的预测（给多 SKU 实验定预期）

| 情形 | 预期落库速率 |
| --- | --- |
| 并行度 12 且 #6 不成为瓶颈 | 理论上界 ≈ **12 × 38 ≈ 456 单/s** |
| #6（redo/fsync、磁盘延迟）成为瓶颈 | **提前平台化**（不到 12 倍）——本环境单事务均摊 26ms 偏高，需实测确认 |

因此多 SKU 实验必须**同时**采集：落库速率、`innodb_flush_log_at_trx_commit`、以及 `SHOW ENGINE INNODB STATUS` 的行锁等待——否则无法判断是「并行度没放开」还是「底座先到顶」。

## 附录 D：库存分桶到底是什么（澄清一个常见误解）

### D.1 澄清：分桶**不是**「一次写多行」

**分桶 = 把 1 行库存预拆成 N 行，每单仍然只扣其中 1 行。**

| 方案 | 行数 | 每单写入 | 并行度 | 主要代价 |
| --- | --- | --- | --- | --- |
| **A. 现状**（单行库存） | 1 行（固定） | `UPDATE` 同一行 | **1** | 无 |
| **B. 库存分桶** | **N 行（预先固定）** | `UPDATE` 其中 1 行 | **≤ N** | 假售罄、调剂、对账 |
| **C. append-only 流水** | 每单**新增 1 行**（持续增长） | `INSERT` 新行（不争锁） | 无行锁争用 | **写入总量变大**、需汇总与清理 |

「写入量变大」是 **C 方案**的特征，**不是分桶**（分桶总行数固定为 N）。

### D.2 分桶必须回答的四个问题

1. **路由**：`userId hash % N`（稳定但消耗不均）／随机（均匀但可能命中空桶）／随机 + 空桶重试（常用）；
2. **扣减**：仍是单行 CAS，不超卖 —— `UPDATE mkt_seckill_bucket SET stock = stock - 1 WHERE id = ? AND stock > 0`，返回 0 即该桶空；
3. **假售罄（最大坑）**：总量还有、但路由到的桶空了 → 直接返回「已抢光」就是假售罄。解法：空桶重试其它桶 / 余量池调剂 / 小桶 + 定时合桶；
4. **回滚与对账**：补偿必须知道「扣的是哪一桶」（记录 `bucketId`）；库存展示变 `SUM(stock)`；`verify_results.py` 的「库存扣减到 0」「sold == total」等断言都要跟着改。

### D.3 为什么建议**先做多 SKU，而不是分桶**

| | 多 SKU | 库存分桶 |
| --- | --- | --- |
| 并行度来源 | **天然**（12 个商品 = 12 行） | 需新建 N 行 + 路由 + 调剂 |
| 改动量 | 0（`prepare_seckill_scenario.py --profile multi12` 已就绪） | 新表/新列 + 空桶重试 + 回滚记录 + 校验改造 |
| 假售罄风险 | 无 | 有 |
| 适用场景 | 大促有多个爆款 | **单个 SKU 库存极大**（如 1 万台压 1 个商品） |

**多 SKU 是「白捡的并行度」；分桶是「单点爆款不得已才付的复杂度」。**

### D.4 对应的可验证数字（基于本系统实测）

单行库存实测落库 **38 单/s**（单事务均摊 26ms）。若 #6（redo/fsync）不成为瓶颈：

| 方案 | 理论上界 |
| --- | --- |
| 多 SKU（12 行） | ≈ 12 × 38 ≈ **456 单/s** |
| 分桶 10 行 | ≈ 10 × 38 ≈ **380 单/s** |
| append-only 流水 | 无行锁争用，但受 redo/磁盘写入总量约束 |

### D.5 「一行」到底指什么（本机 MySQL 实测记录）

「一行」= **数据库表里的一条记录**。本系统秒杀落库触碰的行分两类：

**① 全场「共用」的库存计数行（瓶颈就在这里）**

`mkt_seckill_item`（秒杀活动商品表，每行 = 一场秒杀里的一个商品）：

| id | session_id | product_id | seckill_price | stock | total | sold |
| --- | --- | --- | --- | --- | --- | --- |
| **1** | 3 | 1 | 8999.00 | 0 | 200 | 200 | ← **单 SKU 时全场共用这一行** |
| 2 | 3 | 6 | 1999.00 | 0 | 50 | 50 |
| 3 | 3 | 12 | 1499.00 | 47 | 200 | 153 |
| 4 | 4 | 2 | 6499.00 | 20 | 80 | 60 |

`pms_product`（商品表，每行 = 一个商品）：

| id | title | stock | sales | version |
| --- | --- | --- | --- | --- |
| **1** | iPhone 15 Pro Max 256G | 100000 | 0 | 0 | ← 同样只有一行 |
| 6 | 红米 K70 | 100000 | 0 | 0 |
| 12 | AirPods Pro 2 | 998332 | 1668 | 0 |

抢到一次 = `UPDATE mkt_seckill_item SET stock=stock-1, sold=sold+1 WHERE id=1` → 改的是**同一行的两个字段**（`stock`/`sold`）；随后 `UPDATE pms_product ... WHERE id=1` 也是**同一行**。

> 关键区分：**库存是「每单改旧行」（UPDATE 已有行的字段），订单是「每单写新行」（INSERT 新记录）。**

**② 每单「新增」的行（天然并行，不是瓶颈）**

| 表 | 本机行数 | 说明 |
| --- | --- | --- |
| `oms_order`（订单主表） | 266 | 每下一单 +1 行 |
| `oms_order_item`（订单明细） | 266 | 每下一单 +1 行 |
| `oms_order_status_log`（状态流水） | 542 | 每单 +1~2 行 |
| `inventory_rollback_log`（回退幂等） | 457 | 每次回退 +1 行 |

这些行**主键各不相同**，INSERT 之间不争同一把锁 → 从来不是瓶颈。

**③ 行锁实测（本机，决定性证据）**

| 操作 | 结果 | 耗时 |
| --- | --- | --- |
| 会话 A 开启事务并锁住 `mkt_seckill_item.id=1`（持锁 6s） | — | — |
| 会话 B 更新**同一行 id=1** | `ERROR 1205 Lock wait timeout exceeded` | **1.10 s**（等锁超时被拒） |
| 会话 B 更新**不同行 id=3** | 成功，无报错 | **0.08 s** |

**结论：同一行必须排队、不同行可并行 —— 这就是「单 SKU 并行度 = 1」的物理原因**，也是分桶/多 SKU 能提升吞吐的原理所在。

### D.6 分桶时「选哪一行」：是随便挑，还是固定的？

**两者都不是"每一行都减 1"，本质是：先选中一行，然后只在那一行上扣 1。**

| 说法 | 对不对 |
| --- | --- |
| ❌ 每单把所有桶都减 1 | 错。那是把 1 单放大成 N 次写，写入量反而变大，且破坏「总量 = 订单数」语义 |
| ❌ 闭眼随机挑一行，撞空再说 | 半对。能工作，但会产生「撞空桶 → 换行重试」的额外往返，且空桶多时出现**假售罄** |
| ✅ **先按规则选中一行，只扣那一行；空则换行** | 正确 |

**三种选行策略：**

| 策略 | 选行方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 固定路由 | `userId % N` | 确定、重试可复现、幂等友好 | 负载不均；某桶先空时命中它的用户会**假售罄** |
| B. 轮询 / 随机 | 每次随机或轮流取一行 | 消耗最均匀 | 可能撞空桶，需要换行重试 |
| C. **随机起点 + 顺序探测**（工程常用） | 从随机位置起，顺序找第一个有货的行 | 均匀 + 命中率高 | 逻辑略复杂 |

### 本系统的落点：把「选桶」放进已有的 Redis Lua 预扣

现有预扣脚本只操作**1 个**库存 key（`SeckillServiceImpl.GRAB_SCRIPT`，`KEYS[1]` = 库存、`KEYS[2]` = 一人一单集合）。
分桶只需把它扩展成 **N 个桶 key + 返回选中的桶号**：

```lua
-- KEYS[1..N] = 各桶库存；KEYS[N+1] = 一人一单集合
-- ARGV[1]=userId, ARGV[2]=TTL, ARGV[3]=随机起点（由应用传入，保证脚本确定性）
local n = #KEYS - 1
local bought = KEYS[n + 1]
if redis.call('SISMEMBER', bought, ARGV[1]) == 1 then return {-3, 0} end
local start = tonumber(ARGV[3]) % n + 1
for i = 0, n - 1 do
  local idx = (start + i - 1) % n + 1
  local v = tonumber(redis.call('GET', KEYS[idx]) or '0')
  if v > 0 then
    redis.call('DECR', KEYS[idx])
    redis.call('SADD', bought, ARGV[1]); redis.call('EXPIRE', bought, ARGV[2])
    return {1, idx}          -- 返回「选中的那一行」
  end
end
return {-2, 0}               -- 所有桶都空 = 真的售罄
```

**关键收益：选桶在 Redis 的**一次原子调用**内完成（Lua 内 O(N) 内存循环，不产生 N 次 DB 往返）**，
所以既不会撞空桶、也不需要「试着扣、失败再换一行」的重试。

DB 侧随后只扣那一行：

```sql
UPDATE mkt_seckill_bucket SET stock = stock - 1 WHERE item_id = ? AND bucket_no = ? AND stock > 0
```

### 分桶必须守住的三条约束

1. **守恒**：一次订单 = 一次成功的单行扣减；`SUM(各桶) == 全局余量`，扣减总量 == 订单数；
2. **一人一单不能分桶**：判重的集合必须是**每个活动一个全局 key**（不按桶拆），否则用户可借不同桶重复抢；
3. **必须记录 bucketId**：预扣回补（`releaseReservation`）、订单取消回退，都要把 +1 还给**原来那一行**，否则总量对不上。

### 与「多 SKU」的关系

| | 多 SKU | 库存分桶 |
| --- | --- | --- |
| 桶从哪来 | **天然存在**（不同商品 = 不同行） | 需要人为拆行 |
| 路由 | 由用户选商品决定 | 需要路由算法 |
| 一人一单 | 天然按商品隔离 | 需保证判重集合不分桶 |
| 回补 | 回补对应商品行，天然正确 | 必须记录 bucketId |
| 改造量 | **0** | 表 + Lua + 回补记录 + 校验脚本 |

**结论：多 SKU 是「桶天然存在」的特例，零改造；分桶是为「单个 SKU 库存极大」专门造桶，必须额外付路由、判重、回补三份复杂度。**

### D.7 分桶 vs 不分桶：都要「找那一行」，区别到底在哪

**区别不在「要不要找那一行」，而在「找到的是不是所有人都要找的同一行」。**

| 维度 | 不分桶 | 分桶（N=10） |
| --- | --- | --- |
| 库存表行数 | **1 行**（stock=200） | **10 行**（每行 stock=20） |
| 每单的 WHERE | `WHERE id = 1`（全场恒定） | `WHERE id = 1 + router(userId)`（散到 10 个值） |
| 找行的成本 | 一次主键查找（微秒级） | 一次主键查找 + 一次取模（微秒级） |
| 同一时刻可并行的事务数 | **1** | **≤ 10** |
| 后面的人等什么 | 等**同一条记录**的锁 | 等**自己命中那条记录**的锁 |
| 队列形态 | 200 人 1 条队列 | 平均 20 人 × 10 条队列 |
| 吞吐上限 | 1 ÷ 单事务耗时 | **N** ÷ 单事务耗时 |

**用 D.5 的实测把两件事拆开：**

| 操作 | 耗时 | 说明 |
| --- | --- | --- |
| 更新**不同行 id=3** | **0.08 s** | 这 0.08s = 「找行 + 执行扣减」的真实成本 |
| 更新**同一行 id=1**（被他事务锁着） | **1.10 s** 后被拒 | 多出来的 1s **全是等锁**，与「找行」无关 |

➡️ **「找那一行」本身很快（0.08s），瓶颈 100% 在「那行被别人锁着」。**
分桶不降低「找行」成本，它降低的是**「有多少人和你抢同一行」**。

**类比**：不分桶 = 只有 1 个收银台，200 人排一条队（找到收银台不费时，但必须排队）；分桶 = 10 个收银台，200 人分 10 队（找收银台同样容易，但能同时结 10 个）。

**数量感受**（200 单、单行实测 38 单/s）：

| | 排空耗时 |
| --- | --- |
| 不分桶（1 行） | 200 ÷ 38 ≈ **5.3 s**（实测 5.3s） |
| 分 10 桶（10 行） | 每行 20 单 ÷ 38 ≈ **0.53 s** |

**总库存仍是 200，一单仍只扣 1 行，写入量不变** —— 变的只是分散到 10 条队列上。

**代价（区别的另一半）**：记账粒度变复杂（`SUM(stock)`）、**假售罄**、回补需记录 `bucketId`、一人一单集合不能分桶、校验断言要改。
而**多 SKU 是零成本特例**（桶天然存在、路由由选品决定、判重按商品天然隔离、回补天然正确）。

### D.8 澄清：分桶后「这一行被锁了」会跳到另一行吗？

**不会。触发「跳行重试」的是「桶空了」，不是「行被锁了」。**

| 触发条件 | 行为 |
| --- | --- |
| 该桶**余量 = 0**（空桶） | ✅ 换下一行重试（这才是「跳转」） |
| 该桶**余量 > 0，但该行正被锁** | ❌ **阻塞排队等待**（InnoDB `innodb_lock_wait_timeout` 默认 50s），**不跳行** |

**选桶依据的是「桶里有没有货」（业务状态），不是「这行有没有被锁」（并发状态）。**
且「先看锁再决定」在原理上不可行：查询时未被锁，`UPDATE` 时可能已被别人锁上（竞态），锁状态是瞬时且不可预知的 —— **锁只能撞上再等，无法事先避开**。

**那分桶为什么还快？因为排队没消失，只是被拆散：**

| | 排队形态 | 吞吐 |
| --- | --- | --- |
| 不分桶 | 200 人挤 **1 条队列** | 1 ÷ 单事务耗时 |
| 分 10 桶 | 平均 20 人 × **10 条队列**（并行推进） | **10** ÷ 单事务耗时 |

每一行内部**仍然串行** —— 分桶不消除锁，只是把锁**分摊**到 N 行上。

**本系统两层分工：**

| 层 | 职责 | 会不会撞锁 |
| --- | --- | --- |
| Redis Lua 预扣 | **选桶** + 扣桶余量 | ❌ 不会。Lua 原子单线程串行执行，按「余量 > 0」挑桶，**一次选中**，无需「撞了再跳」 |
| DB 落库 | 对选中行做 CAS 兜底与记账 | ⚠️ 会，但队列长度 = **同桶人数**，而非全场人数 |

**「撞锁就跳行」（try-and-rotate）为何不用**：需把锁等待超时调到极短（如 100ms）→ 超时导致**整个事务中断**（1205）需重开 → 会出现「明明有货却报失败」（原本排 100ms 队就能成功）→ 重试/退避逻辑自研，复杂度收益不如直接在 Redis 选桶。

**实测对应：** 更新不同行 **0.08s**（无锁冲突，即分桶后多数请求的情形）／更新同一行 **1.10s 超时**（锁等待，即分桶后少数同桶请求的情形）。
➡️ **分桶只做一件事：把「命中同一行」的概率从 100% 降到 1/N。**

## 附录 E：库存分桶的现实案例（iPhone 新品首发）

### E.1 场景

| 项 | 值 |
| --- | --- |
| SKU 数 | **1 个**（单个商品、单个库存行） |
| 备货 | **100,000 台** |
| 开抢瞬时 | 100 万人点击，有效并发请求约 **20 万** |
| 业务要求 | **秒级售罄**（用户端 1~3 秒内必须有结果） |

### E.2 不分桶：所有人抢同一行

```sql
UPDATE mkt_seckill_item SET stock = stock - 1, sold = sold + 1 WHERE id = 1001;  -- 全场唯一
UPDATE pms_product     SET stock = stock - 1, sales = sales + 1 WHERE id = 88;   -- 全场唯一
```

单行锁把并行度压成 **1**：

| 环境 | 单行吞吐 | 10 万单耗时 |
| --- | --- | --- |
| **本项目实测环境**（Docker Desktop/Windows，单事务均摊 26ms） | **38 单/s** | ≈ **44 分钟** |
| 生产环境（NVMe，单事务 1~2ms） | 500~1000 单/s | **100~200 秒** |

**一个要求 3 秒出结果的秒杀，库存要卖 3 分钟以上 → 全体超时。**
这就是「单热点 SKU 加机器、加线程都没用」的现实后果。

### E.3 分桶：拆成 100 个桶

```
桶数 ≈ 预期峰值 TPS ÷ 单行可承受 TPS = 50,000 ÷ 500 = 100 个桶
每桶库存 = 100,000 ÷ 100 = 1,000 台
路由     : bucket = userId % 100
扣减     : UPDATE ... WHERE id = 1001 + (userId % 100)
```

| | 不分桶 | 分 100 桶 |
| --- | --- | --- |
| 库存行数 | 1 | 100 |
| 同一时刻并行事务数 | **1** | **≤100** |
| 总吞吐 | 500/s | **50,000/s** |
| 10 万单耗时 | 100~200 s | **≈ 2 s** ✅ |

**总库存仍是 10 万台、一单仍只扣 1 行、写入量不变** —— 只是把 1 条队列变成 100 条。

### E.4 现实中的三个变体（同一思想的不同形态）

| 场景 | 「桶」是什么 |
| --- | --- |
| **12306 抢票** | 同一趟车同一席别的票额拆成**多个票额池**（按区间 / 按预分额度）出票，不同旅客命中不同池 |
| **演唱会 / 大麦开票** | 一个场次几万张票**分批次、分区域放票**，每批次是一份独立库存 |
| **大厂大促单品**（天猫/拼多多爆款） | Redis 按 `stock:{skuId}:{分段}` 存多段库存 + Lua 原子扣减，DB 只做异步落单 —— **分桶 + 削峰的组合**（正是本项目「分桶」与「MQ」两条路的合体） |

### E.5 现实中的两个配套机制

1. **假售罄处理**（分桶的真实痛点）：某桶空了但总量还有 → 常用**「小桶 + 中心池」两级结构**（先扣小桶，桶空则向中心池申请调剂），或定时回收空桶余量重分配；
2. **桶数靠公式反推**，不是拍脑袋：`桶数 ≈ 峰值 TPS ÷ 单行可承受 TPS`。桶太少没效果、太多则 `SUM` 对账/展示/回补成本高。

### E.6 回到本项目

- `multi12` 场景（12 个商品）**就是天然的 12 个桶**，零改造成本 → 先用它验证「并行度是否兑现」；
- 若场景是「1 个 iPhone 备货 10 万台」，就必须**人为拆 100 个桶**，并额外实现：路由、**判重集合不分桶**、回补记录 `bucketId` 三件事。

### D.9 对齐「队列」这个比喻：没有「跳转」，只有「一开始就被分到不同的行」

**「队列」不是真实实体，而是 InnoDB 挂在那「一行」上的锁等待者列表 —— 它是行的附属物，不存在「跳到另一个队列」的动作。**

| 比喻 | 技术实体 |
| --- | --- |
| 收银台 | 库存表里的**一行**（一个 id） |
| 排队的队伍 | 挂在这行上的 **InnoDB 锁等待者列表** |
| 找收银台 | `UPDATE ... WHERE id = ?` 的**主键定位**（O(1)，微秒级） |
| 「分 N 个收银台」 | 把 1 行拆成 N 行（N 个不同 id） |
| 「被分到不同队」 | **路由** `id = base + hash(userId) % N`，**在 SQL 发出前就算好** |

**为什么不需要「跳」：分配发生在扣减之前，不是被锁之后。**

```sql
-- id 在路由阶段就确定了，SQL 里带的是固定值
UPDATE mkt_seckill_item SET stock = stock - 1 WHERE id = 1001 + (userId % 10);
```

| 环节 | 不打桶 | 分 10 桶 | 有区别吗 |
| --- | --- | --- | --- |
| **定位那一行**（主键查找） | 0.08s 量级 | 0.08s 量级 | ❌ **完全相同** |
| **该行后面站着几个人** | **199 人** | **平均 19 人** | ✅ **差 10 倍** |
| 最后一个用户的等待 | ≈ 199 × 26ms ≈ **5.2 s**（实测 5.3s 排空） | ≈ 19 × 26ms ≈ **0.5 s** | — |

➡️ **分桶不改变「找行」，也不存在「跳转」；它改变的是「这一行后面站着几个人」。**
（注：InnoDB 锁等待非严格 FIFO，但「等的人越多、平均等待越久」成立。）

⚠️ 易混点：前面的「跳行重试」只在**桶空（没货）**时发生，与锁无关。

### D.10 「分配」到底发生在什么时候：请求到达时即时计算

**不是「系统提前给 N 单规划好目标行」，而是「每个请求到达时，用自身属性即时算出来」。**

| | 不是 | 而是 |
| --- | --- | --- |
| 时机 | 预先知道总量再统一规划 | 每个请求到达时**独立计算** |
| 协调 | 需中心节点分配 | **零协调**（哈希均匀则结果大致均匀） |
| 上层视角 | — | 算完后 SQL 里带的是**固定值**：`WHERE id = 1001 + (userId % 10)` |

### D.10.1 两种路由方式的实测模拟（200 单 / 10 桶 × 20 件）

**方式 A：固定路由 `bucket = userId % 10`**

各桶收到的请求数：`[16, 21, 27, 13, 21, 22, 19, 15, 23, 23]`（容量各 20）

| 指标 | 数值 |
| --- | --- |
| 实际成交 | **183 / 200** ❌ |
| **假售罄**（桶满但别桶有货） | **17 单** |
| 剩余库存 | **17 件卖不掉** |

原因：**哈希分布天然波动（13~27）**，而桶容量固定 20 → ≥21 单的桶拒人、13 单的桶剩货。

**方式 B：随机起点 + 顺序探测「有货的桶」**

| 指标 | 数值 |
| --- | --- |
| 实际成交 | **200 / 200** ✅ |
| 假售罄 | **0** |
| 剩余库存 | **0**（恰好归零） |

➡️ 这是 D.6 推荐方式 B 的原因：**不是按用户属性硬分，而是「看着余量挑」**，挑到的一定有货。

### D.10.2 分配结果要不要记下来

| 路由方式 | 能否重算 | 回补（取消/超时/预扣回滚） |
| --- | --- | --- |
| A. `userId % N` | ✅ 可重算 | 不必记录，回补时重算即可 |
| B. 随机起点探测 | ❌ **不可复现** | **必须记录 `bucketId`**（落库 / 进消息），否则 +1 还不回原来那一行 |

**一句话：分配是扣减前的一次即时计算；固定路由靠 `hash(userId)`，动态路由靠「挑有货的桶」——只有后者不会假售罄，但必须把选中的桶号记下来。**

### D.11 数据库支持多行并行修改吗？（本机实测）

**支持。InnoDB 是行级锁，不同行可以真正并行修改。**

| 场景（10 个并发事务，每个持锁 200ms） | 总耗时 | 结论 |
| --- | --- | --- |
| 各改**不同行**（id=1..10） | **0.34 s** | ≈ 1 × 200ms → **并行** |
| 各改**同一行**（id=1） | **2.14 s** | ≈ 10 × 200ms → **串行** |
| 并行加速比 | **6.4×** | 含 `docker exec` 启动开销，纯并行段 ≈0.2s，接近满并行 |

（实验用临时表，全程 `ROLLBACK`，业务数据未改动）

**但有 4 个关键约束：**

| # | 约束 | 说明 |
| --- | --- | --- |
| ① | **`WHERE` 必须走索引** | 主键等值 `WHERE id = 5` → 只锁一行（满并行）；无索引/`LIKE '%x%'` → 锁住扫描过的所有行，**退化成近似表锁**；范围查询 → 间隙锁互相阻塞 |
| ② | **并行度受全局共享资源截断** | redo log 写入与刷盘（靠 group commit 合并）、buffer pool latch、undo/binlog、磁盘 IOPS、CPU 核数 → 收益递减并出现平台期 |
| ③ | **顺序不一致会死锁** | A 锁 row1→row2、B 锁 row2→row1 即循环等待。**本项目下单路径「按 productId 升序加锁 + 退避重试」正是为此** |
| ④ | **隔离级别加额外锁** | RR 下范围扫描加间隙锁；唯一索引等值且命中时只加行锁（分桶 SQL 的最理想形态） |

**回到本系统：**

| 事实 | 结论 |
| --- | --- |
| 秒杀扣减 SQL 均为 `WHERE id = ?`（主键等值） | **并行前提已满足** ✅ |
| 但所有人都去改同一个 id | 并行度被人为压成 **1** |

➡️ **数据库一直「支持」并行修改多行，是业务把它压成了改同一行。**
分桶 / 多 SKU 做的是**让「并行的对象」变多**（1 行 → N 行），而不是让数据库「学会」并行。

### D.12 本节小结（一句话版本 + 理解检验）

**精确表述：**
> 分桶 = **把「1 行热点」变成「N 行热点」**，让本来必须排成一队的事务**分散到多条队列并行推进**。
> **写入次数不变、总工作量不变，变的是「并发度」**；代价是路由、判重（不能分桶）、回补（记录 `bucketId`）、对账（`SUM`）四份复杂度，且收益有上限（受全局资源约束）。

**常见说法检验：**

| 说法 | 判定 | 原因 |
| --- | --- | --- |
| 把写入请求「从 1 行拓展到多行」 | ✅（措辞微调） | 是**表的库存行数**从 1 行 → N 行；**每个请求仍只写 1 行** |
| 然后「同时写入」 | ✅ | 不同行**真正并行**（实测：不同行 0.34s / 同一行 2.14s） |
| 「减少等待时间」 | ✅ | 减少的是**排队等锁**时间（队列 199 人 → 19 人）；单次 UPDATE 耗时（0.08s）不变 |
| 「增加了写入量」 | ❌ | **写入次数完全不变**，变的是被争用的行 |
| 「让每个请求更快」 | ⚠️ | 不是更快，是**不用排长队** |
| 「能无限提升吞吐」 | ❌ | 受 redo 刷盘 / 磁盘 IOPS 等全局资源截断，会**平台化** |
| 「能防超卖」 | ❌ | 防超卖靠 CAS（`WHERE stock > 0`）；分桶只影响并发度 |

**全景流程（把 D.5~D.11 串起来）：**

```
请求到达
  ↓ ① 路由（D.10）：即时算出目标行 id = base + hash(userId) % N
  ↓    或由 Redis Lua 挑「有货的桶」（D.6）
  ↓ ② 只扣那一行（D.1/D.7）：UPDATE ... WHERE id = ? AND stock > 0
  ↓    不同行 → 并行（0.34s）；同一行 → 排队（2.14s）（D.11 实测）
  ↓ ③ 桶空了 → 换一行重试（D.8）；行被锁 → 只能等，不能跳
  ↓ ④ 记录 bucketId → 取消/回补才能 +1 还回原来那一行（D.10.2）
  ↓ ⑤ 库存展示/校验 = SUM(各桶)（D.7 的代价）
```

### D.13 某个桶空了怎么办？「重新排队」是错误方向

**先分清阶段：**

| 阶段 | 会不会选到空桶 | 处理 |
| --- | --- | --- |
| ① 预扣（Redis Lua 选桶） | ❌ 不会 —— 脚本按「余量 > 0」挑桶，自动跳过空桶 | 选不到 = 所有桶空 = **真售罄** |
| ② 落库（DB CAS 扣减） | ⚠️ 会（预扣与记账短暂不一致） | 按架构而定，见下 |

**两种分桶架构，处理方式完全不同：**

| | 架构 1：DB 直打（无 Redis 预扣） | 架构 2：Redis 预扣 + DB 兜底（**本系统形态**） |
| --- | --- | --- |
| 桶在哪选 | 应用层 `id = base + hash % N` | **Redis Lua 里挑一次** |
| 撞到空桶 | ✅ **换桶重试**（有界，最多 3~5 次） | 预扣阶段**不会撞空桶** |
| 落库发现桶空 | 同上 | ❌ **不换桶**：属「预扣与记账不一致」异常 → 回补预扣 + 返回业务失败 + **打监控指标** |

> ⚠️ **架构 2 中「换桶重试」本身就是错的**：桶在预扣时已定，落库换桶会导致「预扣扣了桶 A、DB 扣了桶 B」，两个桶余量都不对，回补也找不回原桶。

**架构 1 撞空桶的三种策略：**

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 🔴 **有界换桶重试**（默认） | 换另一桶再 CAS，最多 3~5 次 | 简单、边界清晰 | 多几次 DB 往返；极端偏斜仍可能失败 |
| 🔴 **小桶 + 中心池**（两级） | 小桶空了从中心池借一批搬入再扣 | **几乎消除假售罄** | 需额外表 + 搬运逻辑，要防并发超借 |
| 🟠 后台合桶/调剂 | 定时回收空桶余量重分配 | 请求侧零改动 | 秒级延迟，秒杀窗内来不及 |
| ⚪ 桶数给足 | 按 `峰值 TPS ÷ 单行 TPS` 估，宁多勿少 | 直接降低偏斜概率 | 管理成本线性上升 |

**四个绝对不能做：**

| ❌ | 后果 |
| --- | --- |
| 直接返回「已抢光」 | **假售罄**（D.10 模拟：200 单丢 17 单，17 件卖不掉） |
| 无限重试 | 请求放大 → **重试风暴**，可能打穿 DB |
| 1 单拆到多桶各扣一点 | 破坏**总量守恒**，跨行事务反而制造死锁 |
| 想着「重新排队」 | DB 行锁排队是**内核行为，无法主动排队**；只能「换桶」或「失败」 |

**「重新排队」方向错了 —— 排队应发生在前面的层：**

```
限流(@RateLimit)  →  Redis Lua 原子预扣  →  MQ 削峰  →  DB 行锁
  挡无效请求          挡掉 99%（20000→200）   摊平脉冲     只剩极少数
```

**DB 层排队是最贵的排队**（占连接、事务、undo，还要等锁超时 50s）。正确做法是把 99% 的请求挡在 DB 之前 —— 本系统已经做到。因此「桶空了」的正确处理位置是**预扣层（挑有货的桶）**，而非「到 DB 层排队等」。

**本系统落地建议：**
1. 扩展 `GRAB_SCRIPT`（D.6）返回 `{1, bucketIdx}`，**一次选对，不撞空桶**；
2. 落库用 `bucketIdx` 扣那一行；DB 返回 0 时**不回换桶**，按业务失败 + 回补 + 打不一致指标；
3. 复用已有先例：下单路径的「死锁退避重试最多 3 次」（`MAX_RETRY_ON_LOCK`）；
4. 桶数给足 + 后台调剂兜底，把假售罄概率压到接近 0。

### D.14 「DB 层发现桶空 → 回滚 → 换桶」这个理解要修正三点

**✅ 对的部分**：在本系统现有写法下，桶空**确实会回滚** —— 但那是「业务代码主动抛异常」造成的：

```java
if (seckillItemMapper.deductStock(itemId) == 0) {
    throw new BizException(ResultCode.OUT_OF_STOCK, "手慢了，本场已抢光");
}
```
配合 `@Transactional(rollbackFor = Exception.class)` → 整体回滚。

**❌ 要修正的三点：**

| # | 修正 |
| --- | --- |
| ① | **桶空不是 SQL 错误**：`UPDATE ... WHERE stock > 0` 匹配不到行时只返回 `affected rows = 0`（**正常返回**），事务仍干净、可继续执行甚至正常 commit。**回滚是你的设计选择，不是 DB 的强制行为** |
| ② | **回滚后不能「直接换桶」**：事务已被标记 `rollback-only`，必须**新开事务**重试，否则抛 `UnexpectedRollbackException` |
| ③ | **换桶重试不能只重做扣库存那一步**：一次下单事务含 5 个写操作（扣活动库存 / 扣商品库存 / insert 订单 / 明细 / 状态流水），换桶必须是**整笔业务事务重做** |

**❌ 直觉写法「DB 扣减失败 → 回滚 → 换桶」的致命问题**：每个失败尝试都要打到 DB，20 万请求 = 20 万次 attempt（最终只成功 200 次）—— 把「挑桶」放在 DB 前面，等于把压力全压在最贵的一层。

**✅ 做法 A（推荐，本系统形态）：挑桶放在 Redis 预扣层**

```
Redis Lua：挑「有货的桶」+ 预扣   →  带 bucketNo 传下去
DB：只扣那一桶（几乎不可能为 0）
若 DB 真的返回 0（预扣/记账不一致）→ 回补预扣 + 业务失败 + 打不一致指标（不换桶）
```
DB 层永远不会遇到「桶空」，也就不需要「回滚换桶」。

**✅ 做法 B（若坚持在 DB 层挑）：抽成独立短事务，且放在主事务之前**

```java
long bucketNo = bucketService.acquireBucket(itemId);   // REQUIRES_NEW，循环换桶 ≤3~5 次
orderService.create(userId, addressId, bucketNo, ...); // 再开主事务建单，桶已确定
```
「桶空换桶」只重试**那一小步**（廉价、可重入），不会重做整个建单流程。
**本系统已有先例**：下单路径的死锁退避重试最多 3 次（`MAX_RETRY_ON_LOCK`）。

**一句话：桶空在 DB 是 `affected rows = 0`（不是报错），是否回滚由代码决定；而「换桶」绝不能放在 DB 事务里 —— 要么在 Redis 预扣层挑对桶，要么抽成「独立短事务 + 主事务之前」的小步骤。**

### D.15 预热 → 选桶 → 传 bucketNo → DB 落库：这条链路与「一致性」的正确理解

**✅ 对的两点：**

| 理解 | 评价 |
| --- | --- |
| 预热时把（每桶）库存传到 Redis | ✅ 分桶后按桶逐个灌 `mall:seckill:stock:{itemId}:bucket:{i}`，仍用 `setIfAbsent`（防滚动发布复位已扣桶） |
| Redis 把「要扣哪个桶」传给落库事务 | ✅ Lua 返回 `{1, bucketNo}` → 一路带到 DB，DB 只扣那一桶 |

**⚠️ 要修正：「选桶」不保证一致性，它保证的是「两边扣同一个桶」。**

| | 选桶解决的事 | 一致性由谁保证 |
| --- | --- | --- |
| 内容 | **对账口径对齐**（Redis 桶 i ↔ DB 桶 i 是同一逻辑桶） | **最终一致**：预扣/记账语义 + 回补 + 幂等 + 按桶对账 |
| 反例 | — | Redis 扣了桶 3、落库事务失败回滚、**回补又没成功** → Redis 桶 3 比 DB 少 1。**该不一致与「怎么选桶」无关** |

➡️ 「选桶被固化」的真正价值：**让逐桶对账成为可能**（否则 Redis 扣桶 3、DB 扣桶 7，账都对不上）。

**对账口径：**

```
DB桶余量_i − Redis桶余量_i ≈ 该桶「已预扣未落库」的在途单数
```

| 差额 | 含义 |
| --- | --- |
| ≈ 在途单数 | ✅ 正常（预扣与记账有时间差） |
| 长期偏大 | ⚠️ 落库堆积 / 回补未执行 |
| 为负 | ❌ 异常（回补过多或超发风险），必须告警 |

**完整链路：**

```
① 预热（setIfAbsent，按桶）      DB 桶 i 库存 ──→ Redis bucket:{i}
② 抢购：Lua 原子「挑有货的桶 + DECR」→ 返回 {1, bucketNo}
③ 传递 bucketNo：同步 → 方法参数；异步 → ★ 必须放进队列消息体 ★
④ DB 落库（最终记账）：UPDATE ... WHERE item_id=? AND bucket_no=? AND stock > 0
⑤ 失败收敛：回补（+1 还回原桶）+ 幂等（requestId / uk_user_request / 回退幂等表）
⑥ 对账：按桶比 DB 与 Redis 差额
```

**三个最容易漏的点：**

| # | 点 | 说明 |
| --- | --- | --- |
| ① | **异步路径 `bucketNo` 必须进消息体** | `SeckillOrderMessage` 现为 `requestId/userId/itemId/addressId/traceId`，**需增加 `bucketNo`**，否则消费者不知道扣哪桶（同步路径无此问题） |
| ② | **回补必须还回原桶** | 现状 `increment(SECKILL_STOCK + itemId)` 只回补全局计数；分桶后须 `increment(bucketKey(itemId, bucketNo))` → 这就是「分配结果必须记下来」的代码落点 |
| ③ | **别把选桶当一致性机制** | Redis 扣了 DB 未扣（在途）、DB 扣了 Redis 未回补（延迟）都是**正常中间态** |

**一致性来自「双防线 + 最终一致」，不是「Redis 与 DB 强一致」：**

| 机制 | 作用 |
| --- | --- |
| Redis 预扣 | 第一道防线：挡掉 99% 请求，不打穿 DB |
| DB CAS（`WHERE stock > 0`） | 最后一道防线：**即使 Redis 计数错了也不超卖** |
| 回补 + 幂等表 | 收敛中间失败 |
| 按桶对账 | 发现并修复数值漂移 |

### D.16 「同步要一条条等，异步发完不等结果就能发下一条」——这在 MySQL 上做不到

**先分清「同步/异步」的三层含义：**

| 层 | 同步 | 异步 |
| --- | --- | --- |
| ① 业务层 | 抢购请求当场等落库完成 | 只入队，消费者异步落库（**MQ，前面讨论的**） |
| ② 驱动/协议层 | 发一条 SQL，**等服务器回包** | 发完不等结果就发下一条（**本次讨论的**） |
| ③ 连接层 | 一个连接一个活跃事务 | 多连接多事务并行 |

**② 在 MySQL 上不成立：**

| 事实 | 说明 |
| --- | --- |
| MySQL 协议是**请求-应答**式 | 同一连接必须等服务器回包才能发下一条 |
| **MySQL 不支持 pipeline** | 对比：PostgreSQL 14+ 支持 pipeline；MySQL 至今不支持 |
| Connector/J 无真正的 async execute | `executeAsync()` 是 JDBC 4.3 提案未实现；`useAsyncProtocol` 只是非阻塞 I/O 实现细节 |
| 同一连接不能并行事务 | 任一时刻只有一个活跃事务/结果集 |

➡️ **并行执行 SQL 只能靠「多连接 + 多线程」**，即「多行并行 = 多个并发事务各占一个连接」。

**但「把等待搬到别处」这半个直觉是对的（MQ 就在做这件事）：**

| 视角 | 效果 | 实测 |
| --- | --- | --- |
| **用户侧** | 不用等了 → 受理变快 | 2426ms → **674ms**（P90/P99 ↓6~9 倍）✅ |
| **DB 侧** | 一条都没少等（仍同一行串行） | 落库 **38 单/s 不变**（含队列开销反降 12%）❌ |
| 端到端 | 多了排队 + 轮询 | **反而慢 18%~30%** ❌ |

➡️ **等待没有消失，只是被「转移」与「并行化」了。**

**真正提速的两条路：**

| 路径 | 手段 | 本项目状态 |
| --- | --- | --- |
| ① **并行** | 多连接 + **多热点行**（多 SKU / 分桶） | ❌ 单行 → 并行度 **1** |
| ② **减少等待总量** | **批量提交**（一条 SQL 插 N 行，省 N-1 次往返与 fsync）、缩短事务、更快硬件 | ❌ 未做（P2-4） |

> 注意：「批量提交」是**减少等待**的正路；「不等结果连发」是**协议不支持**的路，两者别混。

**★ 有效并行度的三重上限（最容易被忽略）：**

```
有效并行度 = min( 消费者/线程数 , 连接池大小 , DB 可并行的热点行数 )
                     64          Hikari 50(dev)/100(prod)        ← 本项目 = 1 ❌
```

| 只加哪一项 | 结果 |
| --- | --- |
| 只加线程 / 消费者 | ❌ 无效（热点行仍是 1 行）—— **D1 的教训** |
| 只加连接池 | ❌ 无效（同上） |
| **加热点行数（多 SKU / 分桶）** | ✅ 才能真正提升（且需连接池与线程同步给够） |

**⚠️ 高频混淆：HikariCP 是「连接池」，不是「工作线程池」。**

| | HikariCP | 工作线程池 |
| --- | --- | --- |
| 全名 | **Hikari Connection Pool** | Tomcat / `seckillExecutor` / 消费者线程池 |
| 管什么 | **`Connection`（数据库连接）** | **`Thread`（执行任务的线程）** |
| 配置项 | `spring.datasource.hikari.maximum-pool-size` | `server.tomcat.threads.max` / `consumer-threads` |
| 本项目值 | dev **50** / prod **100** | Tomcat **120** / 舱壁 64 / 消费者 64 |

它内部仅有极少量**维护线程**（housekeeper、connection-adder 等），不执行 SQL，**不是工作线程**。

```
Tomcat 120 线程 ──┐
舱壁 64 线程    ──┼──→ 都要执行 SQL ──→ [ Hikari 池：50 条连接 ] ──→ MySQL(300)
消费者 64 线程  ──┘                          ↑ 闸门在这里
```

三个实践要点：

| # | 要点 |
| --- | --- |
| ① | **「等连接」与「等锁」是两回事**：等连接看 `hikaricp.connections.pending/active`；等行锁看 `SHOW ENGINE INNODB STATUS`。线程数 > 池大小时，多出来的线程是在**等连接**，不是在等锁 |
| ② | **连接池耗尽的典型症状：接口变慢/超时，但 DB 侧很「闲」** —— 请求根本没到 DB（卡在借连接），这是高频误判点 |
| ③ | **池不是越大越好**：`实例数 × 池大小 ≤ MySQL max_connections(300)`（项目已有启动期校验）；prod 池 100 → 最多 3 实例 |

**一次 SQL 的完整调用链（说明「借连接」而不是「借线程」）：**

```
线程 "seckill-consumer-7"（由线程池提供）
 ├─ 1. dataSource.getConnection()   ← 从 Hikari「借一条 Connection」（不是借线程！）
 ├─ 2. conn.prepareStatement(sql)   ← 在这条 TCP 连接上发 SQL
 ├─ 3. 等 MySQL 回包
 ├─ 4. 处理结果
 ├─ 5. conn.close()                 ← 还回池里（TCP 连接不关，复用）
 └─ 6. 线程继续处理下一条消息         ← 线程由线程池复用
```

| | **线程池** | **HikariCP（连接池）** |
| --- | --- | --- |
| 里面装的是 | `Thread` | **`Connection`（一条到 MySQL 的 TCP 连接）** |
| 借出的 API | `executor.execute(task)` / `submit()` | **`dataSource.getConnection()`** |
| 借不到会怎样 | 入队或拒绝（AbortPolicy） | 本项目配 **3s**（`connection-timeout: 3000`，Hikari 默认 30s）后抛异常 —— 刻意"快速失败，避免挂起 30s" |
| 数量上限 | 进程内资源，可开几千 | **受 MySQL `max_connections` 硬限制** |
| 复用的是 | 线程 | 连接 |

**HikariCP 的准确定位：它是「通用 JDBC 连接池」，不是「连 MySQL 的组件」。**

| 层 | 角色 | 本项目 |
| --- | --- | --- |
| **JDBC 驱动** | **实现 MySQL 协议**（打包 SQL、解析回包） | `com.mysql:mysql-connector-j`（`com.mysql.cj.jdbc.Driver`） |
| **HikariCP** | **连接复用与生命周期**（预建 / 借出 / 还回 / 健康检查 / 超时回收 / 泄漏检测） | `HikariDataSource`（`pool-name: GeekMallHikariCP`） |
| **Spring Boot** | 组装 + 配置 | `spring.datasource.*` |
| **MyBatis-Plus** | SQL 映射，调用 `getConnection()` | mapper / XML |

**连接池可替换的铁证（项目代码）：**

```java
/** 读取连接池上限；非 Hikari 实现返回 -1（跳过校验，不做无根据的推断）。 */
private int resolvePoolSize() {
    if (dataSource instanceof HikariDataSource hikari) {
        return hikari.getMaximumPoolSize();
    }
    return -1;   // ← 换成 Druid 也能跑，只是容量校验会跳过
}
```

**为什么要池化（量化）：**

| 动作 | 耗时量级 |
| --- | --- |
| 建立一条 MySQL 连接（TCP 握手 + 认证，可能 TLS） | **几 ms ~ 几十 ms** |
| 执行一条简单 SQL | **0.1 ~ 1 ms** |

→ 不池化则连接建立成本主导请求耗时；池化的价值是**用复用摊薄连接建立成本**。

**类比**：JDBC 驱动 = 会讲 MySQL 语言的翻译官；HikariCP = 电话总机（预接好 N 条线路，谁要就打、打完还回）；`Connection` = 一条已接通的线路；`DataSource.getConnection()` = 总机的服务窗口。

**顺带**：URL 中的 `rewriteBatchedStatements=true` 会让 JDBC 把多条 INSERT **合并成一条**发给 MySQL —— 正是 D.16「减少等待总量」那条正路（对应待办 P2-4 批量落库），**JDBC 层已具备条件**。

**常见误解：「HikariCP 保证我可以同时写 50 条 SQL」**

| 说法 | 更准确的说法 |
| --- | --- |
| 同时写 **50 个 SQL 语句** | 最多 **50 条连接**可同时被占用；**每条连接任一时刻只能跑 1 条 SQL**（请求-应答，不能连发） |
| **保证**能同时写 | Hikari 只提供 **50 个「坑位」（许可）**，不保证「发 50 条就能同时跑完」 |
| 可以**同时**写 | 实际并发 = `min(线程数, 连接数, 可并行的热点行数)` |

**谁保证什么（并发度全貌）：**

| 组件 | 保证什么 | 本项目值 |
| --- | --- | --- |
| **HikariCP** | 最多 N 条 SQL **同时持有连接** | **50**（dev） |
| Tomcat / 消费者线程池 | 最多 N 个任务**同时被线程处理** | 120 / 64 |
| **InnoDB 行锁** | 同一行最多 1 个事务**同时改** | **热点行 = 1** ❌ |
| MySQL `max_connections` | 实例最多 N 条连接 | **151**（项目声明 300，不一致） |

➡️ **实际能同时完成的 SQL 数 = 上表所有项的最小值。** 秒杀场景下：50 条连接开得出、64 线程够用，但**热点行只有 1 行** → 实际并发 = **1**。**Hikari 给足了许可，是被行锁卡住。**

**超过 50 会怎样（有界等待 + 明确失败）：**

| 情况 | 行为 |
| --- | --- |
| 第 51 个线程借连接 | **阻塞等待** `connection-timeout` = **3s** |
| 3s 内有人还回 | 拿到连接继续 |
| 3s 仍未等到 | ❌ 抛 `SQLTransientConnectionException`（Connection is not available） |

**「把 50 调大」有用吗？**

| 只调大连接池 | 结果 |
| --- | --- |
| 热点行仍 1 行 | ❌ **没用**：更多线程只是在同一行后面排队等锁（还可能加剧上下文切换与死锁） |
| 热点行变 N 行（多 SKU/分桶） | ✅ 有用，但**连接池要同步给够**（否则 N 行也会被 50 卡住） |

➡️ **连接池是「闸门」，不是能凭空造出并发度的东西 —— 治标调池、治本加热点行数。**

**实测证据（本机）：**

| 查询 | 结果 |
| --- | --- |
| `SHOW VARIABLES LIKE 'max_connections'` | **151**（MySQL 8.0 默认） |
| `performance_schema.threads` 中客户端连接对应的服务端线程名 | **`thread/sql/one_connection`** |

➡️ **一条连接 = 服务端一个线程** —— 所以连接是「两端都占资源」的稀缺物，才有硬上限；线程只是进程内资源。

**⚠️ 发现一个真实的配置不一致（建议修复）：**

| 位置 | 值 |
| --- | --- |
| 项目声明 `mall.cluster.mysql-max-connections` | **300** |
| MySQL 实际 `max_connections` | **151** |

`ClusterCapacityReporter` 用 **300** 校验（`实例数 × 池大小 ≤ 300`）：prod 若声明 3 实例 × 池 100 = 300 → 日志打印「连接池评估通过」，但实际 MySQL 只允许 151 → 第 152 条连接起被拒（`Too many connections`）。**这是「假通过」** —— 校验常量与真实上限不一致。修法：两者对齐（改配置，或调 MySQL `max_connections`）。

**一句话：MySQL 上「不等结果连发」不可行（协议不支持 pipeline）；MQ 异步只是把等待从请求线程搬到消费者线程 —— 用户侧变快、DB 侧不变。真正提速要么让「并行的对象」变多，要么减少等待总量，而有效并行度还受连接池限制。**

### D.17 澄清：MQ + 库存分桶下，「不等待」到底是谁不等待

| 角色 | 执行什么 | 是否等待 |
| --- | --- | --- |
| **请求线程**（Tomcat） | Redis Lua 挑桶预扣 → 写 QUEUED 结果 → `XADD` 入队 | **不发 SQL**，因此不等待 DB（只等 Redis 毫秒级回包） |
| **消费者线程**（`consumer-threads`=64） | `UPDATE 桶 → 建订单 → XACK` | ✅ **每个都必须等自己那条 SQL 的回包**（MySQL 请求-应答） |
| **DB** | N 行（多 SKU / 桶） | 不同行互不冲突 → 可并行 |

➡️ **「不等待」的效果确实存在，但机制不是「发完不等结果」（协议不支持），而是：队列把等待接过去、交给另一组线程** —— 请求线程立即返回，消费者线程各自等自己的 SQL。

**提速的真正来源是两件事的组合，缺一不可：**

| | MQ 提供 | 分桶 / 多 SKU 提供 |
| --- | --- | --- |
| 作用 | **并发的容器**：64 个消费者可同时干活；请求线程不被 DB 阻塞 | **可并发的资源**：N 行互不抢锁 |
| 缺失后果 | ❌ 无容器 → 请求线程自己等（用户侧慢） | ❌ 无资源 → **64 个消费者抢同一行，仍然串行** |

**实测已证明后半句**：单行 + MQ → 64 个消费者全在等同一行锁 → 落库 **37.7 单/s**（与同步 43 单/s 几乎相同）。

**四种组合的推算（有效并行度公式）：**

```
有效并行度 = min( 消费者/线程数 , 连接池大小 , DB 可并行的热点行数 )
```

| 组合 | 有效并行度 | 预期落库吞吐 |
| --- | --- | --- |
| 单行 + 同步 | 1 | **43 单/s**（实测） |
| **单行 + MQ** | min(64, 50, **1**) = **1** | **37.7 单/s**（实测） |
| **12 SKU + MQ** | min(64, 50, **12**) = **12** | **~456 单/s**（待验证） |
| 100 桶 + MQ | min(64, 50, 100) = **50**（连接池先到顶） | 受连接池与 fsync 约束 |

⚠️ 注意 min() 第二项：dev 环境 Hikari 池仅 **50** → 100 桶时并行度会被**连接池**卡在 50。
**桶数不是越多越好，必须与连接池、消费者数一起配。**

**完整公式（含上游约束与底座天花板）：**

```
并行度 = min( 消费者线程数 , Hikari 连接数 , 可并行的桶数/热点行数 )
         且须满足：实例数 × 池大小 ≤ MySQL max_connections

吞吐 = 并行度 ÷ 单事务耗时        ← 再被「底座」（redo/fsync/CPU）截断，表现为平台化
```

**套到本项目：**

| 因素 | 本项目值 | 现在是不是瓶颈 |
| --- | --- | --- |
| 消费者线程数 | **64** | ❌ 否 |
| Hikari 连接数 | **50**（dev） | ❌ 现在否，**但 100 桶时会成为瓶颈** |
| **可并行的桶数 / 热点行** | **1**（单 SKU） | ✅ **就是它** |
| MySQL `max_connections` | 151（单实例仅占 50，远没到；但项目声明 300 不一致） | ❌ 否 |

**配比规则：想让并行度达到 P，必须同时满足 ① 消费者线程 ≥ P　② 连接池 ≥ P　③ 桶数 ≥ P　④ 实例数 × 池 ≤ max_connections。**

| 目标吞吐（单事务 26ms） | 需要并行度 P | 桶数 | 消费者线程 | 连接池 |
| --- | --- | --- | --- | --- |
| 456 单/s | ≈ **12** | 12 ✅ | 64 ✅ | 50 ✅（现成够用） |
| 2000 单/s | ≈ **52** | ≥52 | 64 ✅ | **50 ❌ 要调大** |

**关键观察：三个因素里只有前两项能靠改配置解决，第三项（桶数/热点行）只能改数据模型或场景** —— 这就是「光调配置没用」的原因（64 / 50 早就够了，卡在桶数 = 1）。

**多 SKU 下取决于哪一项？→ 仍然取决于「热点行数」，只是它的值从 1 变成 SKU 数。**

```
单 SKU ： min(线程 64, 池 50, 热点行 1)   = 1
多 SKU ： min(线程 64, 池 50, 热点行 12)  = 12   ← 仍是第三项，值从 1 → 12
```

**★ 瓶颈转移阶梯（谁最小，瓶颈就是谁）：**

| 场景 | min(线程64, 池50, 行数) | 瓶颈归属 |
| --- | --- | --- |
| 单 SKU | min(64, 50, **1**) = 1 | **热点行数** ❌ |
| **12 SKU** | min(64, 50, **12**) = 12 | **仍是热点行数**（12 < 50） |
| 50 桶 | min(64, **50**, 50) = 50 | **连接池** ← 瓶颈转移 |
| 64 桶 + 池 128 | min(**64**, 128, 64) = 64 | **消费者线程** ← 再转移 |
| 200 桶 + 池 256 + 线程 256 | min(256, 256, 200) = 200 | 此时才可能撞**底座**（redo/fsync/CPU） |

➡️ **加资源只会把瓶颈「搬」到下一项，不会凭空提速。**

**⚠️ 重要前提：SKU 之间必须「均衡」，否则并行度远小于 SKU 数。**

> 真正起作用的是「**同时被打、且都有库存的 SKU 数**」（即热点行的实际分散程度）。

| 反例 | 实际并行度 |
| --- | --- |
| 12 个 SKU，但库存集中在 1 个（5000 件 : 其余各 10 件） | ≈ **1** |
| 12 个 SKU，但请求都打向最热门那个 | ≈ **1** |
| 12 个 SKU，库存各 200、VU 轮流打 | ≈ **12** ✅ |

→ 实验设计必须保证 **① 库存均分　② 请求轮流打**（`multi12` profile 每 SKU 各 200 + `ITEM_IDS=101..112` 让 VU 按序号轮流，正是为此）。

**该轮实验的可验证预测：**

| | 单 SKU | 多 SKU（12 个） |
| --- | --- | --- |
| 库存 | 200 件 | **2400 件**（12 × 200） |
| 并行度 | 1 | **12** |
| 落库吞吐 | 38 单/s | **~456 单/s** |
| **排空时长** | **5.2 s** | **≈ 5.2 s**（每 SKU 各 200 × 26ms） |
| 一次活动消化量 | 200 件 | **2400 件（12 倍）** |

👉 **最漂亮的验证点：同样 5.2 秒，单 SKU 只能卖 200 件，多 SKU 能卖 2400 件。**

**结论：MQ 提供「容器」、分桶提供「资源」，二者缺一不可 —— 光有 MQ 不会提升吞吐（已实测）。**

### D.18 多 SKU 还需要分桶吗？

**不一定 —— 判据是「单个 SKU 的库存是否超过单行的承载能力」。**

```
单个 SKU 排空时间 = 该 SKU 库存 ÷ 单行吞吐
单行吞吐 ≈ 1 ÷ 单事务耗时（本项目实测 38 单/s；生产 NVMe 约 500 单/s）
```

**判据：最大的那个 SKU 能在可接受时长内卖完 → 不需要分桶。**

| 场景 | 最大单 SKU 库存 | 单 SKU 排空（生产 ~500/s） | 需要分桶吗 |
| --- | --- | --- | --- |
| 12 个 SKU，各 200 件 | 200 | 0.4 s | ❌ **不需要** |
| 12 个 SKU，各 5000 件 | 5,000 | 10 s | ⚠️ 临界，看业务容忍度 |
| **1 个爆款 10 万台 + 11 个长尾各 100 件** | 100,000 | **200 s** | ✅ **必须给爆款分桶** |

⚠️ **环境差异极大**（本项目实测环境仅 38 单/s，单事务 26ms）：

| 单 SKU 库存 | 本项目环境排空 |
| --- | --- |
| 200 件 | 5.2 s ✅ |
| 1,000 件 | 26 s ⚠️ |
| 5,000 件 | **132 s ≈ 2.2 分钟** ❌ 必须分桶 |

➡️ 同一业务量在快环境不需分桶、在慢环境就必须分桶 —— 印证「绝对容量数字不能外推」。

**多 SKU 与分桶是「互补、可叠加」，不是二选一：**

| | 多 SKU | 分桶 |
| --- | --- | --- |
| 分散的是 | **不同商品**的库存行 | **同一商品内部**的库存 |
| 成本 | **0**（天然存在） | 路由 + 判重 + 回补 + 对账 |
| 何时必须 | 大促有多个爆款 | **单个 SKU 库存极大**，或**流量全打一个爆款** |

**正确顺序：先吃免费的多 SKU；对仍然超载的那几个 SKU 再单独分桶。**

**最佳 schema 形态：`(item_id, bucket_no)` 二维，每个 SKU 可配不同桶数**

```sql
CREATE TABLE mkt_seckill_bucket (
  item_id   BIGINT NOT NULL,   -- 哪个秒杀商品
  bucket_no INT    NOT NULL,   -- 第几个桶
  stock     INT    NOT NULL,
  PRIMARY KEY (item_id, bucket_no)
);
```

| SKU 类型 | 桶数 |
| --- | --- |
| 爆款（10 万台） | **100 桶** |
| 中等（5000 件） | 10 桶 |
| 长尾（200 件） | **1 桶**（= 不分桶） |

➡️ 这也统一了 D.6 的选桶：`WHERE item_id=? AND bucket_no=?`，桶数为 1 时即原写法。

**还有一个「多 SKU 帮不上忙」的场景**：流量全打一个 SKU（大促只有一个爆款）时，多 SKU 无从发挥，**分桶是唯一手段**。判断依据始终是「**同时被打、且有库存的热点行数**」—— 这个数是 1 时，有几个 SKU 都白搭。

### D.19 秒杀 = MQ + Redis + 分桶？—— 是「分层递进」，不是「三者相加」

**完整链路（这三者是中间三层，前后各还有一层）：**

```
① 前端/接入层     按钮置灰、答题、随机延迟提交、静态化 + CDN
        ↓
② 限流/防刷       全站限流、黑名单、防重放        ← @RateLimit（43 条规则）
        ↓
③ Redis 预扣      Lua 原子「判库存 + 一人一单 + 扣减」 ← GRAB_SCRIPT
        ↓
④ MQ 削峰         排队 + 异步落库                ← Redis Stream
        ↓
⑤ 库存分桶/多 SKU  让落库能并行                   ← multi12 / (item_id, bucket_no)
        ↓
⑥ DB 落库         CAS 扣减 + 建单 + 幂等          ← uk_user_request + 回退幂等表
        ↓
⑦ 对账/回补       预扣回补、按桶对账              ← releaseReservation + 对账
        ↓
⑧ 结果查询        轮询取终态                     ← /seckill/result/{requestId}
```

**哪些是必须的，哪些是按规模递进的：**

| 层 | 是否必须 | 理由 |
| --- | --- | --- |
| ② 限流/防刷 | ✅ 必须 | 成本最低、效果最好 |
| ③ **Redis 预扣** | ✅ **必须** | **把「抢不抢得到」从 DB 挪到内存 —— 收益最大的一层** |
| ⑥ **DB CAS + 幂等** | ✅ **必须** | 正确性底线（Redis 计数错了也不超卖） |
| ④ MQ 削峰 | ⚠️ 按需 | 改善**受理体验**、摊平脉冲；**不提吞吐**（已实测） |
| ⑤ 分桶/多 SKU | ⚠️ 按需 | 提升**落库并发度**；单 SKU 库存大时才必须 |

➡️ **准确表述：秒杀 = 「限流 → Redis 预扣 →（MQ）→（分桶）→ DB CAS 兜底 → 对账」，括号内是规模上来后才加。**

**每层的数量级收益（本项目真实数据）：**

| 层 | 拦下多少 |
| --- | --- |
| 限流 | 无效流量（防刷/重放） |
| **Redis 预扣** | **20,000 → 200（挡掉 99%）** ✅ |
| MQ 削峰 | 脉冲摊平，受理 P90/P99 ↓6~9 倍 |
| 分桶/多 SKU | 落库并发度 1 → N（12 SKU 预计 12 倍） |
| DB CAS | 保证不超卖 |

**收益最大的其实是第 ③ 层**：一个动作把 DB 压力降两个数量级；MQ 与分桶都在处理"剩下的 200 个"，收益量级小得多。

**按规模选组合：**

| 规模 | 需要的组合 |
| --- | --- |
| 库存几百、并发几千 | 限流 + **Redis 预扣 + DB CAS**（单行足够） |
| 库存几千、并发几万 | + **MQ**（受理体验）+ 可能多 SKU |
| 库存十万、并发百万 | + **分桶** + 多实例 + 独立集群隔离 |

## 附录 F：如何「实现多 SKU」（现状核实 → 前置条件 → 改造清单 → 验收）

### F.0 一句话

**「一场秒杀上架多个 SKU、各自独立抢购」本系统已经支持**，全链路都按 `itemId` 分区，无需改代码 —— D3 缺的是**实验**，不是功能。
**真正需要写代码的是另一种含义**：一次抢多个 SKU 合并成一张订单（购物车式）。

### F.1 先分清两种含义

| 含义 | 业务形态 | 本系统现状 |
| --- | --- | --- |
| **A. 并列多 SKU** | 一场里上 12 个商品，用户挑其中一个抢，每个 SKU 独立库存 / 独立限购 | ✅ **已天然支持**，只差造数据 |
| **B. 合并多 SKU** | 用户一次勾选 A、B、C，一次请求抢 3 件，合成**一张订单** | ❌ 未支持，需要改造（见 F.4） |

> 我们压测要验证的 D3 是 **A**；用户口语里的「多 SKU」多数是 **B**。别混淆。

### F.2 含义 A：全链路已是「按 itemId 分区」

| 环节 | 实现 | 多 SKU 性质 |
| --- | --- | --- |
| 表结构 | `mkt_seckill_item(PK id, session_id, product_id, stock, total, sold)` —— **一行一个 SKU** | ✅ 天然（`V1__init.sql:188`） |
| 商品列表 | `GET /seckill/items?sessionId=` → `selectList` + `selectBatchIds` 批取商品 | ✅ 返回列表（`SeckillController.java:72`） |

| Redis 库存 | `mall:seckill:stock:{itemId}` | ✅ 一 SKU 一键（`RedisKeys.java:29`） |
| 一人一单 | `mall:seckill:bought:{itemId}` 集合 | ✅ **每 SKU 各限 1 件**（`:32`、`SeckillServiceImpl.java:215`） |
| 启动预热 | `SeckillStockWarmUp` **遍历全部 item**，逐 key `setIfAbsent` | ✅（`SeckillStockWarmUp.java:48-58`） |

**所以含义 A 的"实现"= 造数据**（`prepare_seckill_scenario.py --profile multi12`，12 个 item 101→product 2… 一一对应），代码零改动。

### F.3 五个前置条件（缺一个就会「看着支持、实际没并行」）

| # | 条件 | 不满足的后果 | 验证方法 |
| --- | --- | --- | --- |
| 1 | **product_id 必须互不相同** | 若 12 个 item 都挂到同一个 product，`pms_product` 那一行仍串行 → 并行度白给 | `SELECT COUNT(DISTINCT product_id) FROM mkt_seckill_item WHERE id IN (101,...,112)` 应 = 12 |
| 2 | 场次 `state='running'` 且 `not_start=0` | `reserve()` 直接抛「本场秒杀尚未开始」 | `SELECT state FROM mkt_seckill_session WHERE id=3`；`SELECT id,not_start FROM mkt_seckill_item WHERE ...` |
| 3 | `pms_product.stock` 给足 | 商品库存 CAS 失败 → 落库失败 | 造数脚本第 2 步已 `stock=100000` |
| 4 | 每个 SKU 的 Redis 库存 key 都已预热 | 未预热则首个请求懒加载（能自愈，但会额外打 DB） | `SCAN mall:seckill:stock:*` 应命中 12 个 key |
| 5 | **想清楚「一人一单」的口径** | 现有语义是**每 SKU 各 1 件**（12 个 SKU 一个用户能买 12 件）；若业务要「整场限 1 件」，必须改成场次级计数，否则被薅 | 看 `bought` key 是否带 itemId |

### F.4 含义 B：合并下单（一次抢多个 SKU）的改造清单

按依赖顺序，共 8 处：

| # | 位置 | 改什么 | 难点 |
| --- | --- | --- | --- |
| 1 | `GrabSeckillDTO` / `SeckillController` | 路径单 `itemId` → 请求体 `items:[{itemId, qty}]`，新增 `POST /seckill/orders` | 保持旧接口兼容（前端未改时行为不变） |
| 2 | `GRAB_SCRIPT`（Lua） | 单 KEYS 两键 → 多 itemId 版：**先全判、再全扣** | 原子性：必须一次 Lua 完成，否则又回到"部分成功"；**KEYS 按 itemId 升序**（避免集群 slot 与死锁） |
| 3 | `reserve()` | 返回「已预扣清单」，失败时**逆序回补** | 回补的**幂等**：`releaseReservation` 用 `INCREMENT` 会重复加库存（队列重投会二次回补）→ 需比对 `bought` 集合后才加 |
| 4 | `SeckillOrderMessage` | `itemId` → `itemIds` 列表 | 消息体变大（Stream 无压力），但要兼容旧消息反序列化 |
| 5 | `grabInTx()` | 逐个 `deductStock` + 单事务内建单 | **统一加锁顺序**（按 itemId 升序），否则 A 抢 [1,2]、B 抢 [2,1] 会死锁 |
| 6 | `TradeService.createOrderWithFixedPrice` | 单商品 → 多明细（`oms_order_item` 多行、订单总额重算） | 金额校验、库存回滚 |
| 7 | 幂等粒度 | 仍是整单幂等（`uk_user_request(user_id, request_id)`），粒度正确 | 回补必须是**整单粒度**：任一 SKU 失败 → 整单回补，不留半单 |
| 8 | 前端 `SeckillView` | 从「立即抢购」→ 勾选 + 提交 | 轮询结果要能展示"哪个 SKU 失败" |

**两条设计红线**（面试常被追问）：

1. **部分成功不可接受**：要么全抢到要么全失败。所以 Lua 必须"先全判后全扣"，商品侧也要在同一事务里。
2. **回补必须幂等且整单粒度**：分布式下"回补执行两次"是常态（队列重投 + 用户重试），用 `INCREMENT` 无条件回补会凭空造库存。

### F.5 配套：多 SKU 想真换来吞吐，还要两件事

| 配套 | 现状 | 说明 |
| --- | --- | --- |
| **并行度对齐（D1）** | `CONSUMER_THREADS` 可配 | 上限 = `min(SKU 数, consumer-threads, DB 写总能力)`；12 SKU 下把消费者从 4 拉到 12+ 才有意义 |
| **队列按 SKU 分区** | ❌ 单 Stream + 单 group（`RedisStreamSeckillOrderQueue.java:46`） | **结论：不需要改**。DB 行锁已把同 SKU 的消息串行化了；按 itemId 分区反而带来负载不均（热门 SKU 积压、冷门 SKU 空闲）。只有「同一 SKU 要求严格顺序消费」才值得分区 |

预期：并行度 12 时理论上界 ≈ **12 × 38 ≈ 456 单/s**；但 A 机单事务均摊 26ms 偏高（Docker Desktop fsync 开销），**大概率提前平台化**，所以实验必须同时采 `innodb_flush_log_at_trx_commit` 与行锁等待。

### F.6 验收：怎么证明「多 SKU 真的生效了」

| # | 观测点 | 期望 |
| --- | --- | --- |
| 1 | `SCAN mall:seckill:stock:*` | **12 个** key（不是 1 个） |
| 2 | `SELECT id, product_id, stock, sold FROM mkt_seckill_item WHERE id IN (101..112)` | 每行 `stock=0`、`sold=total` |
| 3 | k6 `ITEM_IDS` 分布 | 各 SKU 收到 ≈ VUS/12 的请求（均匀，无某 SKU 独吞） |
| 4 | `SHOW ENGINE INNODB STATUS` → `TRANSACTIONS` | 等锁线程数接近 `consumer-threads`，**而不是 1 条长链** ← 这条是"并行度真的放开了"的硬证据 |

### F.7 面试口径（一段话）

> 多 SKU 我分两层看：**并列多 SKU**（一场多商品、各自抢）我们早就支持 —— 表是一行一个 SKU、Redis 是 `stock:{itemId}`、扣减是 `WHERE id=?`，所以并行度天然随 SKU 数上升，接入只是造数据。
> 真正要开发的是**合并下单**（一次抢多个合成一单），难点不在入口而在三处：Lua 要"先全判后全扣"保证原子、事务内多行扣减要**统一按 itemId 升序**避免死锁、回补必须**整单粒度且幂等**（否则重投会凭空造库存）。
> 但我也要提醒：多 SKU 提升的是**DB 并行度**，它对同步模式和削峰模式**同时有利**，所以它不是"让 MQ 变有效"的手段，而是"把行锁串行从 1 路放宽到 N 路"的手段 —— 并行度上限仍受消费线程数与 DB 写总能力约束。

### F.8 能不能「只做 A、不做 B」？

**结论：对压测与架构目标，可以；对业务完整性，也可以 —— 因为 B 的能力交易域已经具备。**

#### F.8.1 两个视角的判断

| 视角 | 只做 A 够吗 | 理由 |
| --- | --- | --- |
| **压测 / 架构验证（D3）** | ✅ 够 | B 完全不改变 DB 并行度（并行度只由"热点行个数"决定）；B 反而**扩大锁范围**（一个事务锁多行），让死锁风险上升，会污染性能结论 |
| **业务完整性** | ✅ 够 | 普通下单路径**本来就支持多商品合并下单**（见 F.8.2），"想一次买多件"走普通下单即可；秒杀的业务形态本就是**单品抢购** |

#### F.8.2 修正 F.4 第 6 项：B 是「复用已有能力」，不是「新建」

上一节把 `TradeService.createOrderWithFixedPrice` 列为「单商品 → 多明细」的改造点，**这个说法不准确**。核实后：

| 已有能力 | 位置 | 说明 |
| --- | --- | --- |
| 多商品合并下单入参 | `SubmitOrderDTO.cartItemIds: List<Long>`（为空=全部勾选项） | 交易域**已支持**一单多明细 |
| 多明细落库 | `TradeServiceImpl.doSubmit` → `drafts` 列表 → `persistOrder(..., drafts, ...)` | 订单主表 + 批量明细 + 状态日志 |
| 逐行扣减 + 整体回滚 | `for (draft : drafts) productMapper.deductStock(id, qty)`，受影响行数 0 即抛异常整体回滚 | 与秒杀的"先全判后全扣"是同一思路 |
| **回退幂等** | `restoreStock` 先写 `inventory_rollback_log`，**唯一索引保证每笔最多回退一次** | 这正是 F.4 强调的"回补必须幂等"的**现成范式** |

所以 B 的真实成本**比 F.4 描述的低**：不需要新建订单模型，而是"把秒杀预扣结果喂进已有的多明细下单逻辑"，核心工作量集中在 Lua 与回补链路上。

#### F.8.3 不做 B，会留下两个边界（都可接受）

| 边界 | 现象 | 是否可接受 |
| --- | --- | --- |
| 用户同时看中多个秒杀商品 | 需提交多次请求 → **多张订单**（一人一单是"每 SKU 各 1 件"） | ✅ 秒杀常态，用户预期本来如此 |
| 秒杀商品与普通商品**同车结算** | 做不到 —— 秒杀价只在秒杀接口产生，购物车按 `pms_product.price` 原价结算 | ✅ 秒杀一般要求"单独下单"，业务上通常**刻意隔离** |
| 合并支付（一次付多单） | 项目支付域本就排除在外 | ✅ 若将来要做，标准解法是**合并支付而非合并下单**（分别建单、一次付款），订单模型无需改动 |

#### F.8.4 但「不做 B」不等于「什么都不用做」：A 的 4 件收尾

| # | 事项 | 为什么必做 | 现状 |
| --- | --- | --- | --- |
| 1 | **确认「一人一单」口径** | 现在是"每 SKU 各 1 件"（12 SKU 一人可买 12 件）。若业务要"整场限 1 件"，必须改成场次级计数 —— 这是 **A 自身的语义问题**，与 B 无关 | `bought:{itemId}` 已带 itemId，改口径需动 key 设计 |
| 2 | **秒杀商品 `product_id` 必须互不相同** | 否则 `pms_product` 同一行仍串行，多 SKU 白做（F.3 条件 1） | 造数脚本已保证一一对应 |
| 3 | **`releaseReservation` 的幂等性** | 现在是无条件 `INCREMENT` 回补；队列重投 / 用户重试会让它执行两次 → **凭空造库存**。交易域已有 `inventory_rollback_log` 的幂等范式（F.8.2）可直接借鉴 | ⚠️ **未修，建议优先补**（与做不做 B 无关） |
| 4 | 场次级总库存 / 总单量限制（若业务需要） | 并列多 SKU 时，缺场次级额度约束，用户可在每个 SKU 各抢 1 件 | 视业务而定 |

#### F.8.5 什么条件下才「必须」做 B

| 条件 | 是否成立（本项目） |
| --- | --- |
| 业务明确要求"一次结算多个秒杀商品，只出一张订单" | ❌ 未提出，且与秒杀常规形态相悖 |
| 需要秒杀商品与普通商品混合结算（同车） | ❌ 秒杀场景一般刻意隔离 |
| 需要"整场限购 N 件"且要单张订单体现 | ⚠️ 可用 A + 场次级计数实现，**不必做 B** |

**三条全不成立 → 现阶段不做 B 是正确决策。**

#### F.8.6 一句话

> **A 是必需品，B 是可选品。** 只做 A 就能拿到"DB 并行度 1 → N"的全部收益，且不引入死锁与部分成功两个坑；B 的业务价值（一单多秒杀商品）在真实秒杀里极罕见，且其底层能力交易域已有，**真要做也应先确认业务需求，而不是为了"完整"去做**。
> 真正该做的是 F.8.4 的第 3 条 —— **回补幂等**，它是无论做不做 B 都存在的正确性隐患。
