# SKU 改造后的容量基线（2026-10-26）

> 背景：多规格 SKU（V17）于 2026-10-25 合入，商品详情新增规格/SKU 查询、下单新增 SKU 查询与
> 「桶 + SKU + 商品」三层扣减。此前所有容量数字（10-06 / 10-08 / 10-24）都早于这次改造，
> 不能直接引用。本报告补的就是这个缺口。
>
> 环境：Apple M2（8 核 / 16GB），单实例 8080（dev profile，Hikari 50 / Lettuce 16），
> MySQL 8 / Redis 7 / MinIO 容器。**压测前已停掉 3 个 app 容器实例**，避免 3 个 JVM 抢占压测机资源。
> 口径：限流关闭、MyBatis SQL 日志关闭、压测机与服务同机。

---

## 一、读链路（首页 + 详情，200VU × 100，3 轮）

| 轮次 | QPS | P50 | P90 | P99 | 失败 |

| 1 | 9,832 | 9.1 ms | 33.4 ms | 201.9 ms | 0 |
| 2 | 10,918 | 8.5 ms | 33.6 ms | 156.8 ms | 0 |
| 3 | 8,892 | 9.6 ms | 38.4 ms | 216.0 ms | 0 |
| **中位** | **9,832** | **9.1 ms** | **33.6 ms** | **201.9 ms** | **0** |
| 旧基线（10-06） | 9,091.7 | 18.7 ms | 34.8 ms | 73.8 ms | 0 |
| 变化 | **+8%** | −51% | −3% | **+174%** | — |

**判读**：吞吐没有退化，P50 反而更好；但 **P99 从 73.8ms 涨到 201.9ms**。
首轮（含冷启动 + 3 个容器实例仍在跑）曾读到 4,163 QPS / P99 404ms，不作为基线。
尾延迟退化的候选原因：详情缓存重建时的跨实例互斥锁等待（800ms 兜底）、
冷 key 回源时新增的 `specStructureOf`（维度 + SKU 两条查询）。建议下一轮用
`mall_cache_lock_wait_total` / `lock_timeout_total` 与详情回源耗时下钻确认。

它们依赖 `concurrency.js` 先造 `IDEM-*` / `CANCEL-PREP-*` 用例数据，本次未跑，不属于回归。

## 七、DISTRIBUTED 限流往返量化

| 测量 | 结果 |
| --- | --- |
| 串行 429 端到端 | 5.7 – 13.5 ms（中位约 9.3 ms，含 HTTP 连接） |
| 20 并发 429 P50 | 53.3 ms（同期 10 个 bcrypt 请求抢 CPU，非 Redis 问题） |
| 通过请求 P50 | 91.3 ms（其中 bcrypt 约 50ms） |

**结论**：7 条 DISTRIBUTED 限流的 Redis 往返是毫秒级，不是性能瓶颈；
真正成本是 bcrypt。把限流移出 Tomcat 线程的收益有限，建议维持现状。

## 八、结论与建议

1. **读链路**：吞吐持平、P99 退化 2.7 倍 —— 优先用缓存锁等待/回源指标下钻，而不是先调参。
2. **下单**：未退化，旧容量结论可以继续引用（但注明是 SKU 后复测）。
3. **秒杀落库**：批量占比已达 100%，落库 TPS 65.8；继续压提交开销的收益有限（见 10-24 报告）。
4. **长稳**：无泄漏，但有 2.7s P99 长尾，与第 1 项同源。
5. **商家端**：`overview` / `nav-badges` / `product-page` 三个接口是当前最严重的性能问题，
   应作为下一批首要修复项（加索引或改聚合 SQL）。
6. **prod / 限流**：prod 配置可用；分布式限流不是瓶颈，无需改造。
