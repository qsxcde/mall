# 秒杀库存分桶 × MQ 压测对比（本机 · 2026-10-08）

> 目的：回答「加入秒杀库存分桶后，QPS / P99 等指标怎么变」，并与「用 / 不用 MQ」交叉对比。
> 设计依据：`docs/benchmark/库存分桶实现分析.md`（分桶 = 把 1 行热点拆成 N 行热点；MQ 只搬排队位置）。
> 原始数据：`loadtest/results/final-*.json`（k6 summary-export）。

---

## 一、场景与方法

| 项 | 取值 |
| --- | --- |
| 拓扑 | 单机：后端 1 实例 + MySQL 8.0 容器 + Redis 7 容器（同一台机器） |
| SKU | **单热点**：`item1` → `product1`，活动库存 **200** |
| 负载 | k6 `seckill.js`，**200 VU × 100 轮**（每 VU 固定账号，每人最多成交 1 单 → 最多 200 单） |
| 开关 | `mall.seckill.async.enabled` = 同步 / 削峰；`mkt_seckill_item.bucket_count` = 1 / 10 |
| 对齐 | 限流关闭；削峰消费线程 **64**（对齐同步侧 `seckillExecutor` 有效并行度）；Hikari 池 50（dev 默认） |
| 采样 | 应用**只重启 1 次**、两组配置**交替重复 3 轮取中位数**（消除冷启动 + JIT 逐渐变热两种漂移） |

> ⚠️ 口径说明：`落库 TPS` 由应用日志「首笔成功 → 末笔成功」的墙钟跨度折算（200 单 / 跨度），
> 反映 DB 到底多快把这批单写完；`总 QPS` 含 19800 次「已抢光/重复」的快速拒绝，主要反映接入层吞吐。

## 三、结论

### 3.1 分桶的收益（本轮主结论）

| 指标 | 同步：1 桶 → 10 桶 | MQ：1 桶 → 10 桶 |
| --- | --- | --- |
| 落库 TPS | 117.9 → **204.7（+74%）** | 71.7 → **150.4（+110%）** |
| 端到端 P99 | 1654 → **958 ms（−42%）** | 2906 → **1596 ms（−45%）** |
| 总 QPS | 6753 → **8664（+28%）** | 6892 → **9146（+33%）** |

**两条路径上分桶都真实提升了落库吞吐、并显著压低端到端 P99** —— 与文档「**分桶才是把并行度 1→N、真正提吞吐的那一层**」一致。

### 3.2 MQ 的收益（复现文档结论）

- **受理侧大幅改善**：受理 P99 由同步的 958~1654 ms 降到异步的 53~100 ms（**↓10~17 倍**）—— 这是 MQ 的核心价值（把排队移出请求线程）。
- **落库吞吐不升反降**：同步 117.9 → 异步 71.7 单/s（多出 `XADD→XREADGROUP→XACK` 开销），与文档 §6.2「MQ 只改变排队位置、不提吞吐」一致。
- **端到端变差**：P99 1654 → 2906 ms（+76%），排队成为新的用户可见延迟。

### 3.3 收益远小于文档预测的 ~10×

文档按 `有效并行度 = min(线程64, 池50, 桶10) = 10` 预测理论上界 ≈ 10×，实测只有 **1.74× / 2.10×**。原因（按证据强度排序）：

1. **同事务还扣一行非分桶库存**：秒杀落库的**同一个 DB 事务**里，除了扣 `mkt_seckill_bucket`，还要扣 `pms_product.id=1`（`TradeServiceImpl.java:508` → `deductProductStock`）。该行**未分桶**，是全程唯一热点 → 事务尾部（商品行 UPDATE + commit/fsync）仍然串行，构成新瓶颈。
2. **全局资源截断**：redo 刷盘 / buffer pool latch / CPU，对应文档 §4.5「收益递减并平台化」。
3. **桶数扫描**（同机、同步路径，N=1/2/4/10/20/50）显示吞吐随桶数**持续上升但次线性**（N=1≈68 → N=20≈259 单/s），与「存在非桶维度瓶颈」一致；该扫描未做交叉重复，仅供参考。

> **要接近 10× 需要同时打破商品行**：让 `pms_product` 的热点行也并行化（多 SKU 天然多行，或让商品行扣减脱离同步事务）。
> 注意：现有 `inv_bucket`（商品库存分桶）的 `deduct` 仍会回写 `pms_product` 总库存行，**单靠它不能消除该热点**。

### 3.4 一个反直觉的取舍

MQ 模式下**受理 P99 反而从 53 ms 升到 100 ms**。原因是分桶 Lua 要在一次调用里探测 N 个桶 key（`EXISTS`×N + `GET`），Redis 侧工作变重；在同步模式下这点开销被 DB 排队淹没，在 MQ 的毫秒级受理里就被放大了。

## 四、复现方式

```bash
export MYSQL_PORT=3306        # 本机容器映射到 3306（dev 配置默认 3307）
# 首次需先起一次应用应用 Flyway V11/V12，再：
bash loadtest/scripts/run_bucket_compare.sh      # 2×2 单轮
# 交叉重复 3 轮的脚本见本文件 §一 的方法说明
```

> 注意：`data/users.js` 的 JWT 有效期仅 **120 分钟**，跨批次复用会 401（表现为全部拒绝、成交 0）；
> 需先 `python3 loadtest/scripts/prepare_data.py 1000 && python3 loadtest/scripts/gen_k6_users.py ...` 刷新。
> 重置 Redis 时**只能删** `mall:seckill:stock:*|bucket:*|bought:*|result:*`，**不能 flush 整片 `mall:seckill:*`**
> —— 会把队列流 `mall:seckill:order:stream` 及其消费组一起删掉，消费者 `XREADGROUP` 报 NOGROUP，消息永不投递。
