# 秒杀批量落库压测对比（本机 · 2026-10-24）

> 目的：回答两个问题 ——
> ① 消费端「批量落库 + 库存归并扣减」对落库吞吐的实际提升有多大？
> ② `pms_product` 总库存行是否仍是瓶颈，即 **Stage 2「总库存异步化」要不要做？**
>
> 口径与 `秒杀分桶×MQ对比-2026-10-08.md` 对齐，便于横向比较。
> 全部数字已汇总在下文表格中；原始 k6 summary-export 与行锁采样为可再生的中间产物，
> 按 §五 的配方重跑即可复现，不入库。

---

## 一、场景与方法

| 项 | 取值 |
| --- | --- |
| 拓扑 | 单机：后端 1 实例 + MySQL 8.0 容器 + Redis 7 容器 |
| SKU | **单热点**：`item1` → `product1`，活动库存 **200**，秒杀分桶 **10** |
| 负载 | k6 `seckill.js`，**200 VU × 100 轮**（每 VU 固定账号，每人最多成交 1 单 → 最多 200 单） |
| 对齐 | 限流关闭；削峰消费线程 **64**（对齐同步侧有效并行度）；`batch-size` 默认 **16** |
| 采样 | 主对比 **3 轮取中位数**；参数扫描 2 轮取均值 |
| 新增开关 | `mall.seckill.async.batch-enabled`（默认 false，关闭时行为与旧版完全一致） |

**落库 TPS 口径**：由应用日志「首笔成功 → 末笔成功」的墙钟跨度折算（200 单 / 跨度），
反映 DB 多快把这批单写完；与 k6 的总 QPS 不是一回事。

> ⚠️ **测量修正**：`drain_stats` 原先只匹配「落库成功：」逐条日志，
> 批量路径每批只打一行汇总，导致批量组被严重少计（首轮实测只统计到 95/200 笔）。
> 已改为同时匹配「批量落库完成：成功=N」并按行内计数折算，本次数据均为修正后口径。

## 二、主对比（线程 64 / batch-size 16，3 轮中位数）

| 指标 | 削峰·逐条 | 削峰·批量 | 变化 | 同步（参考上限） |
| --- | ---: | ---: | ---: | ---: |
| **落库 TPS** | 48.5 | **71.8** | **+48%** | 107.0 |
| **排空跨度** | 4126 ms | **2786 ms** | **−32%** | 1870 ms |
| UPDATE 语句数 | 400 | **211** | **−47%** | 400 |
| 行锁等待次数 | 259 | **125** | **−52%** | 362 |
| **行锁总时长** | 22327 ms | 21467 ms | **−4%** | 38434 ms |
| 成交 / 超卖 / 系统错误 | 200 / 0 / 0 | 200 / 0 / 0 | — | 200 / 0 / 0 |

DB 断言三组全过：订单数 == 发放库存、一人一单、`SUM(桶) == 初始量`、销量增量 == 200。

**批量参与度**（单跑留日志实测）：200 单中 145 单（**72.5%**）走批量、55 单走逐条；
14 批里 **6 批打满 `batch-size=16`**，平均批量 10.4。

## 三、参数扫描：批量的收益卡在「批量粒度」上

主对比里行锁总时长只降 4%，一度让人怀疑锁根本没省下来。但把批量真正做大之后，
结论完全反转：

| 配置 | 落库 TPS | 排空 | 批次数 | 平均批量 | 批量占比 | UPDATE | 行锁等待 | **行锁时长** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 逐条（基线） | 48.5 | 4126 ms | — | — | 0% | 400 | 259 | 22327 ms |
| 线程 64 / 批 16 | 71.8 | 2786 ms | 14 | 10.4 | 72.5% | 211 | 125 | 21467 ms |
| 线程 16 / 批 64 | 76.2 | 2627 ms | 6 | 29.1 | 87.3% | 100 | 34 | 3019 ms |
| **线程 8 / 批 128** | **96.0** | **2091 ms** | **2.5** | **79** | **96%** | **45** | **11** | **383 ms** |
| 同步（参考上限） | 107.0 | 1870 ms | — | — | — | 400 | 362 | 38434 ms |

（线程 16/批 64 与线程 8/批 128 为 2 轮均值；后两行的 UPDATE/行锁为对应轮次增量）

**从逐条到线程 8/批 128：**

| 指标 | 变化 |
| --- | --- |
| 落库 TPS | 48.5 → 96.0（**+98%**，已达同步上限的 90%） |
| UPDATE 语句 | 400 → 45（**−89%**） |
| 行锁等待 | 259 → 11（**−96%**） |
| **行锁总时长** | 22327 ms → **383 ms（−98%）** |

### 3.1 关键归因

主对比里「行锁时长只降 4%」不是锁没省下来，而是**批量根本没做大**：

- 64 个消费线程把 200 条消息摊开，多数 `XREADGROUP` 只取到 1~2 条，
  `deliveries.size() > 1` 的门槛让 **27.5% 的订单退回逐条路径**；
- 14 批里 6 批打满 `batch-size=16` —— 批量被**参数封顶**，不是被实现限制。

把消费线程降到 8、批量提到 128 后，200 单收敛到 **2~3 个事务**，
`pms_product` 行只被更新 **2~3 次**（而非逐条的 200 次），行锁时长随之塌掉 98%。

## 四、Stage 2 决策：**不建议做「总库存异步化」**

方案里的 Stage 2（`inv_stock_delta` 写后投影，把 `pms_product.stock` 改成读模型）
是为「同一事务里还有一行未分桶的 `pms_product` 在串行」这个瓶颈设计的。
本轮数据表明 **这个前提在批量归并之后已经不成立**：

1. **`pms_product` 已经不是热点行**。线程 8/批 128 下它每 200 单只更新 2~3 次，
   占该组总 UPDATE（45）的 5~7%。异步化能挪走的就是这 2~3 条 UPDATE。
2. **行锁时长已经塌到 383 ms**，占排空跨度（2091 ms）的 18%。锁不再是主要开销，
   剩下的时间在批量事务自身的写入与提交上 —— 异步化动不了这一块。
3. **为这点收益引入的代价不对等**：最终一致、聚合器、回滚对称、读模型滞后、
   「所有售卖路径必须走桶判断」的强约束，以及一套新的对账逻辑。

> 换句话说：**批量归并（Stage 1）已经解决了 Stage 2 想解决的问题，而且是强一致的。**
> 上一轮报告「要接近 10× 需要同时打破商品行」的结论，其修正方案应当是
> 「把批量做大」，而不是「把商品行改成异步」。

### 真正该做的三件事（按收益排序）

| 优先级 | 动作 | 预期 |
| --- | --- | --- |
| ① | **调优默认参数**：`mall.seckill.async.batch-size` 16 → 128，`consumer-threads` 64 → 8 | 落库 TPS +34%，行锁时长 −98% |
| ② | **消掉逐条回退**：当前 4~27.5% 的订单因「一次 poll 只取到 1 条」走逐条。可在消费端加短窗口攒批（如 5~10 ms），把批量占比推到 100% | 再拿 5~10% |
| ③ | **压测回归**：把 `mq-bucket-batch` 一组纳入 k6 回归，锁住「批量不得退化」 | 防回归 |

参数扫描未做交叉重复，① 的具体数值建议在改默认值前再跑一轮确认。

## 五、复现方式

```bash
# 1) 起中间件
docker compose -f infra/docker-compose.yml up -d

# 2) 打包后端（脚本会按组重启它）
cd backend && mvn -DskipTests package && cd ..

# 3) 主对比（3 组 × 3 轮）
for r in 1 2 3; do
  ARMS=mq-bucket,mq-bucket-batch,sync-bucket \
  USERS=250 VUS=200 ITER=100 ITEM=1 STOCK=200 \
    bash loadtest/scripts/run_bucket_compare.sh
done

# 4) 参数扫描（批量组）
ARMS=mq-bucket-batch CONSUMER_THREADS=8 BATCH_SIZE=128 \
  USERS=250 VUS=200 ITER=100 ITEM=1 STOCK=200 \
  bash loadtest/scripts/run_bucket_compare.sh
```

脚本新增能力（相对上一轮）：

- `SECKILL_BATCH_ENABLED` / `SECKILL_BATCH_SIZE`：批量落库开关与单批条数
- `arm_spec` 支持 `mq-bucket-batch` / `mq-nobucket-batch` 两个批量组
- 每组采集 MySQL `Innodb_row_lock_*` 到 `results/bench-rowlocks.tsv`
- `drain_stats` 同时识别逐条与批量日志，并输出批次数 / 平均批量 / 批量单数 / 逐条单数
- 阶段 0 前自动兜底拉起后端（原先冷启动时 `prepare_data.py` 会 Connection refused）

## 六、注意事项

- `data/users.js` 的 JWT 有效期仅 **120 分钟**，跨批复用会 401（表现为全部拒绝、成交 0）。
  `run_bucket_compare.sh` 每次开跑前会重新换取令牌。
- 重置 Redis 时**只能删** `mall:seckill:stock:*|bucket:*|bought:*|result:*`，
  **不能 flush 整片 `mall:seckill:*`** —— 会连消费组一起删掉，消费者 `XREADGROUP` 报 NOGROUP。
- `/actuator/prometheus` 现已收窄为需鉴权（见 `350df5e`），
  脚本里的批量指标采集会取不到值，本报告的批量参与度改由应用日志推算。
- `verify_results.py` 的 A（下单幂等）/ B（库存回退幂等）两项断言依赖 `run_tests.sh`
  预置的用例数据，单跑 `run_bucket_compare.sh` 时会失败，属预期；秒杀相关的 7 项断言全过。
