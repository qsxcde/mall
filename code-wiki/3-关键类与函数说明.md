## 3.1 限流：RateLimitPolicies + RateLimitInterceptor

### `RateLimitPolicies`（[源码](../backend/src/main/java/com/geekmall/common/ratelimit/RateLimitPolicies.java)）

全站限流规则的**唯一事实来源**，设计要点（类注释原文归纳）：

1. **集中**：所有规则都在 `RULES` 表中，一份文件即可完整审阅；
2. **顺序敏感**：自上而下首匹配生效，规则按"具体 → 笼统"排列（如 `/api/v1/merchant/auth/login` 必须排在 `/api/v1/merchant/**` 之前）；
3. **可证明无遗漏**：`DEFAULT` 兜底 + `RateLimitCoverageIntegrationTest` 遍历所有已注册端点，只落到兜底的端点视为"未分类"并使测试失败；
4. **可证明无重复**：类加载校验规则名唯一，测试校验"方法 + 路径模式"不重复。

辅助常量：`ANY` / `READ`（GET+HEAD，Spring 会把 HEAD 映射到 GET 处理器）/ `WRITE`（POST/PUT/DELETE/PATCH）。

### `RateLimitInterceptor`（[源码](../backend/src/main/java/com/geekmall/common/ratelimit/RateLimitInterceptor.java)）

```
preHandle(request, response, handler)
  解析策略与维度（IP / 用户 / 端点，未登录维度回退）
  → LOCAL  层 LocalRateLimiter   取配额（零网络往返，默认层）
  → DISTRIBUTED 层 DistributedRateLimiter 取配额（仅限流是唯一防线的接口）
  → 拒绝：写 Retry-After，抛 RateLimitException → 429
  → 通过：并发限制（acquire 槽位，afterCompletion 释放）
  → 响应头 X-RateLimit-*
```

边界处理：OPTIONS 豁免、异步二次分发不重复计数、并发槽位在异常路径也释放。

### `LocalRateLimiter` / `DistributedRateLimiter`

- 本地滑动窗口；`local-max-keys`（默认 20 万）防止伪造 IP 撑爆内存。
- 多实例下 LOCAL 层每实例额度 = `ceil(配置值 / instance-count)`（至少 1），保证全局总量不被放大（`common/cluster` 协同）。
- 降级：Redis 故障时按 `RateLimitFallback.FAIL_OPEN`（放行）或 `FAIL_CLOSED`（拒绝，防刷接口用）。

## 3.2 缓存三防：ResilientRedisCache 与配套

### `ResilientRedisCache`（[源码](../backend/src/main/java/com/geekmall/common/cache/ResilientRedisCache.java)）

| 问题 | 本类职责 | 配套 |
| --- | --- | --- |
| 穿透 | Redis 故障降级不阻断；空值由 `TtlFunction` 以短 TTL 承接（`null-ttl: 60s`） | `RedisBloomFilter` 挡"一定不存在"的 id |
| 击穿 | **跨实例互斥重建**：热点 key 失效时仅一个节点回源，其余等待复用（`lock.ttl: 3s`，`wait-timeout: 800ms`，超时放行保可用性） | — |
| 雪崩 | TTL 抖动（`jitter-ratio: 0.2`）打散失效时刻 | 本地 L1 白名单（`homeFloors`/`categoryTree`，3s）+ 熔断降级 |

配套：`JitterTtlFunctionFactory`（抖动 TTL 生成）、`CacheProperties`（TTL/L1 全部声明在 yml，改缓存行为不动代码）、`CacheGovernanceMetrics`（命中/回源/重建指标，供 Grafana 面板与"缓存回源激增"告警使用）。

> 多实例验证中发现并修复的两处缺陷与此相关：击穿互斥原本只覆盖 1/4 缓存、`homeFloors` 自调用绕过分类缓存（详见 `docs/benchmark/多实例部署验证-2026-10-08.md`）。

## 3.3 熔断降级：ResilienceGuard

`common/resilience/ResilienceGuard.java`（[源码](../backend/src/main/java/com/geekmall/common/resilience/ResilienceGuard.java)）——业务级熔断的**统一入口**：

```java
// 依赖调用、成功/失败记录、熔断判定、降级回退收敛到一处
<T> T execute(String resource, Action<T> action)                       // 无降级
<T> T execute(String resource, Action<T> action, Action<T> fallback)   // 熔断时走 fallback
CircuitBreaker breaker(String resource)                                // 取资源级熔断器
```

- 每个资源一个 `CircuitBreaker`（滑动窗口，样本不足 `minimum-calls: 10` 不判定，防低峰误熔断）；
- 并发 `Semaphore` 限流 + `finally` 释放许可；
- `CircuitOpenException` 触发降级路径，`ResilienceMetrics` 暴露状态；
- 覆盖资源：MinIO 上传、支付宝网关、秒杀队列等（`mall.resilience.*` 配置）。

注意分工：**缓存层熔断**（`ResilientRedisCache`）保护"Redis ↔ 数据库"；`ResilienceGuard` 保护"应用 ↔ 外部依赖"。

## 3.4 秒杀削峰：队列与消费

### `RedisStreamSeckillOrderQueue`（[源码](../backend/src/main/java/com/geekmall/modules/marketing/queue/RedisStreamSeckillOrderQueue.java)）

| `reclaimStale(...)` | 从 pending 取回超时未确认消息，记录投递次数；解析失败丢弃（防故障消息无限重投），死信计数 `mall_seckill_dead_letter_total` |
| `ensureGroup(...)` | `MKSTREAM` 创建消费组、处理 `BUSYGROUP`，消费组丢失后自愈 |

### `SeckillBucketManager`（[源码](../backend/src/main/java/com/geekmall/modules/marketing/bucket/SeckillBucketManager.java)）

秒杀库存分桶的"建桶 / 预热 / 汇总"：

- **为什么桶数显式配置**：抢购是超高 QPS 路径，Lua 的 `KEYS[1..N]` 必须在发指令前确定 N，故桶数存于 `mkt_seckill_item.bucket_count`（与商品元数据同一条 SQL、同一 3s 本地缓存）；
- **守恒边界**：只在完全没有桶行时按 `mkt_seckill_item.stock` 均分建桶；桶行一旦存在即以桶行为权威，绝不在运行时重拆（活动进行中 `item.stock` 是过期快照，重拆会凭空造库存）；
- 抢购判定不在此类，在 `SeckillServiceImpl` 的 `reserve(userId, itemId)` → `reserveFromBuckets(...)`（`GRAB_BUCKET_SCRIPT` Lua）内一次原子完成："挑余量 > 0 的桶 + DECR + 记一人一单"；未分桶商品走 `reserveFromSingleRow(...)`（`GRAB_SCRIPT`）。

### `OrderStateMachine`（[源码](../backend/src/main/java/com/geekmall/modules/trade/service/OrderStateMachine.java)）

订单状态变更的**唯一入口**：

```
transfer(order, target, operator, remark)   // 返回更新后的 Order
  → 校验当前状态合法（from）
  → 校验目标状态合法（to）
  → CAS 更新（WHERE 状态 = 期望值），并发下只有一方成功
  → 重复状态幂等返回，失败给出明确提示
  → 写状态日志（from/to/operator/remark + 时间戳）
  → 发布 OrderStatusChangedEvent（消息中心等异步副作用）
```

配套自动化断言：8 线程并发取消同一订单只产生 1 条状态日志（`OrderStateMachineConcurrencyIntegrationTest`）。

### 售后闭环：钱在什么时候出去

`modules/aftersale/service/impl/AfterSaleServiceImpl.java` 与
`modules/merchant/service/impl/MerchantAftersaleServiceImpl.java` 协作完成，关键约束：

| 环节 | 规则 | 为什么 |
| --- | --- | --- |
| 仅退款（refund） | 商家点「同意」时**立即**退款 | 买家没收到货/不要货，不存在寄回环节 |
| 退货退款（return） | 「同意」只改状态 → 买家登记寄回 → 商家「确认收货」才退款 | 先退钱等于白送一件商品 |
| 换货 / 维修 | 不产生任何资金流 | `amount` 落库为 0，退款入口直接跳过 |
| 买家撤销 | 处理中 / 待寄回可撤销；已寄回之后不可 | 商品还在买家手里时撤销对双方无损 |
| 商家拒绝 | `status` 保持 0 + `merchant_status=rejected` | 若写 2，买家会看到「你已取消」而非「商家拒绝」 |

两条决策点：

1. **退款必须在事务提交之后**（渠道调用是 HTTP，且要建立在状态已落库之上），
   因此 `resolve` 拆成 `doResolve`（事务内）+ 提交后逐单 `refundAfterSale`。
2. **幂等键是售后单维度**（`RFAS + 售后单号`）而不是支付单：
   同一笔支付可能先经历「订单取消退款」再进入售后退款，用订单号做键会互相顶掉，
   结果是「售后显示已退款，钱却没出去」。

买家侧状态统一由 `aftersale/enums/BuyerAfterSaleStatus` 解析，优先级为
**商家拒绝 > 买家撤销 > 商家侧未终结状态 > 数字状态**，与商家侧
`MerchantAftersaleStatus` 的口径逐字对齐。

## 3.8 安全：双端 JWT

```
请求 → JwtAuthenticationFilter（买家）/ MerchantJwtAuthenticationFilter（商家，仅 scope=merchant）
     → 解析 Authorization: Bearer <token>（JwtUtil）
     → LoginTokenLocalCache 本地缓存命中？（30s TTL）
     → 否则校验 Redis 会话（支持登出踢下线 / LoginSessionBroadcaster 广播失效）
     → 写入 SecurityContext（LoginUser / MerchantLoginUser）
```

多实例实测：重新登录后旧令牌在其它实例 86/93ms 内被拒（远小于 30s 本地缓存 TTL）。

## 3.9.1 搜索抽象：ProductSearchService 与三实现

`modules/product/search/`

| 类 | 职责 |
| --- | --- |
| `ProductSearchService`（接口） | 单一方法 `search(ProductQueryDTO)` + `engineName()`。**契约**：所有实现必须「同输入 → 同输出」，尤其 `total` 口径一致，否则前端分页错乱、A/B 对比失真 |
| `ProductQuerySupport` | 三实现共用的过滤条件构建 + 排序，避免任一处漏掉过滤导致语义漂移 |
| `LikeProductSearchService` | `LIKE '%kw%'`；默认实现，也是 ES 的降级兜底（`forFallback(mapper)` 让它不依赖 Spring 容器） |
| `FulltextProductSearchService` | `MATCH ... AGAINST('"kw"' IN BOOLEAN MODE)`。**必须短语模式**：ngram 把中文切成双字 token，普通模式是 OR，命中集比 LIKE 大 |
| `ElasticProductSearchService` | ES 召回 id → `ProductStockService.findOnShelfByIds` 回表。异常时 `degrade-to-mysql` 回落 LIKE |

**三个易错点（都已踩过并修复）**：

1. **排序语义**：有关键词时若把 `_score` 放排序首位，`sort=price_asc` 会退化成几乎无效的次级条件
   （实测返回 `7499 → 12999 → 1499`）。正确做法是**仅在用户未显式指定排序时**才用 `_score` 优先。
2. **超时必须显式设置**：官方 low-level 客户端默认 socket 超时 30s，与毫秒级目标严重不匹配 ——
   ES 变慢（而非拒绝）时会把 Tomcat 请求线程挂住几十秒。已配置 2s/5s，宁可失败降级。
3. **敏感字段不入索引**：`cost`（成本价）刻意不同步到 ES，避免买家侧搜索泄露商家端字段。

## 3.9.2 跨域耦合治理：场景化查询服务

治理前有 **24 处跨域 Mapper 直连**（merchant 直连 trade 的 `OrderMapper`/`OrderItemMapper` 各 4 处；
5 个域各自调用 `ProductMapper.deductStock`）。现由被依赖方提供场景化服务：

| 服务 | 所在域 | 解决的问题 |
| --- | --- | --- |
| `MerchantOrderQueryService` | trade | 所有方法强制附加 `shop_id = ?`，调用方无法漏写隔离条件 |
| `MerchantReviewQueryService` | review | 同上；只暴露商家可维护字段的更新 |
| `MerchantAfterSaleQueryService` | aftersale | 同上；`transferStatus` 是商家侧唯一写入口（CAS + 状态 SQL 口径） |
| `ProductStockService` | product | 把「影响行数为 0 即库存不足」收进商品域（返回 boolean），避免 5 个域各自理解 |

**收益**：跨域 Mapper 直连 24 → 0；顺带修复一处越权风险（商家售后按 `orderNo` 查订单时漏了 `shop_id`）。

**约束固化**：`architecture/LayeredArchitectureTest` 用编程式 API 判定「同域放行、跨域 mapper 禁止」，
并限制域间循环依赖数 ≤ 4。
